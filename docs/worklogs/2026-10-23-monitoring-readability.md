# 실행 모니터링 가독성 개선

## 요청과 범위

사용자는 실제 에이전트 모니터링이 텍스트 중심이라 읽기 어렵다고 보고했다. 기존 화면은 이름·상위 단계·상태·시간을 반복하고 모델 정보가 없는 에이전트 단계에도 미기록 항목이 나열됐다. [표시 설계](../superpowers/specs/2026-10-23-monitoring-readability-design.md)와 [수행 계획](../superpowers/plans/2026-10-23-monitoring-readability.md)에 따라 요약, 실제 관계와 선택 상세의 우선순위를 바꾼다.

프론트엔드 표시 변경이며 API·DB 스키마·권한·본문 보관 계약은 유지한다. 이전 실제 SDK 생성4/4회와 품질 결과는 보존하고 새 생성·임베딩·복구·승격을 실행하지 않는다. 모델·질문·업체 이름을 제품 코드에 고정하지 않는다. 기존 서비스 재기동·설치·staging·commit/push도 범위에서 제외한다.

## 역할과 보존

활성화 신호는 requirements-or-behavior, react-ui, feature-implementation이며 최소 역할은 요구 설계·프론트엔드·테스트 설계·독립 통합 검증이다. 메인은 요약/처리 시간·브라우저·통합, 프론트엔드 담당은 공유 위임 패널·합성 fixture, 독립 담당은 회귀/표시 계약 검토를 맡았다. 실제 API·DB·런타임을 바꾸지 않아 해당 구현 역할은 추가하지 않았다.

시작 시 기존 미커밋135파일의 SHA를 `.local-data/project-agent-work/agents-monitoring-readability-20261023/baseline-sha256.json`에 기록했다. 사용자 작업과 이전 SDK 변경은 보존 대상이다.

## 구현·검증 진행

실행 상세 상단의 실행·답변·품질·전체 시간을 별도 카드로 나눴다. 품질 실패와 실행 완료를 각각 표시하며 전체 시간은 기존 관측값을 사용한다. 처리 단계는 관측된 최장 단계와 비교하는 시간 막대를 사용한다. 합계나 진행률로 해석하지 않고 누락은0으로 바꾸지 않는다.

메인의 신규2개 검사는 수정 전 요약 영역/meter 부재로 실패했고, 변경 후 기존 실행·원문 조회 회귀를 포함한21개가 통과했다. 본래 로그인된 완료 실행에서도 네 요약 카드와 기존 처리 단계/시간을 읽기 전용으로 확인했다.

위임 패널은 종류별 단계 수, 아이콘·상태, 실제 `parent_id` 연결, 선택 상세로 구성했다. 위임 단계에서는 위임한 에이전트 → 위임받은 에이전트를 강조한다. 모델 단계에만 공급자 토큰과 모델 정보를 표시하고 ID·revision·정확한 시각은 접힌 기록 정보로 옮겼다. 비정렬 분기와 깊은 중첩을 지원하며 누락된 부모 연결을 추정하지 않는다. 깊이4부터는 실제 상위 이름을 표시하고 추가 들여쓰기를 제한한다.

## 근거와 문제 이력

사용자 가독성 보고는 관리자 DB **ISSUE-00035**(`02b75048-beee-4493-b227-2fd8f5a225e4`)로 등록하고 명시한 표시 범위를 검증 완료로 저장했다. 이전 상세404의 ISSUE-00034와 원인이 다르므로 분리한다. 요약 문서 `bb34f33a-3942-4256-a928-ee25448f0801`의 버전1을 연결하고 날짜별 진행 이력을 확인했다. 상태 수정 직후의 이력 폼은 이전 revision 충돌을 표시했으며, 정상적인 최신 내용 다시 열기로 갱신한 뒤 기록을 저장했다. 임의 DB 수정은 하지 않았다.

합성 캡처는 `.local-data/browser-verification/agents-readability-20261023/monitoring-readability-synthetic-1280.jpg`, 독립 검증은 `.local-data/project-agent-work/agents-monitoring-readability-20261023/review-ui-validation.json`에 보존한다. 캡처의 이름·시간·수치는 합성 UI 자료이며 실제 SDK 평가 결과로 사용하지 않는다.

시작 기준135파일 중126파일은 SHA가 같고, 변경9파일은 WORKBOARD와 이번에 배정한 UI8파일뿐이며 누락0이다. 이번에 새로 수정한 ExecutionStages/ExecutionMonitoring 테스트와 새 설계·계획·작업 기록은 별도 범위다. 관련 문서4개의 상대 파일 링크114개와 전체 `git diff --check`를 통과했다. 검증용 임시 Vite 서버만 종료했으며 본래 서비스와 관련 없는 변경을 보존했다. staging·commit·push는 하지 않았다.

## 후속 요청: 그림 중심 흐름과 에이전트 정보

사용자는 위임 흐름을 더 그림처럼 표현하고 호버 또는 클릭으로 어떤 에이전트인지 확인하기를 요청했으며, SDK가 `rag_manager`를 호출하는지도 질문했다. 기존 트리를 기본으로 둔 첫 개선에 이어 에이전트 중심 지도와 상호작용 정보를 보강한다. 새로운 보존 기준선은 `.local-data/project-agent-work/agents-flow-diagram-20261023/baseline-sha256.json`의140파일이다. 프론트엔드·독립 검증 역할을 분리하고 API/DB·실모델 실행 변경은 제외한다.

### SDK 호출에 대한 확인

현재 코드의 `search/pipeline.py`는 프로파일에 orchestration이 설정됐을 때 생성 요청을 `OpenAIAgentsOrchestrator.generate`로 전달한다. `orchestration/openai_agents.py`는 SDK `Agent`로 manager와 specialist를 만들고 `Runner.run(manager, ...)`로 시작한다. manager는 `tool_choice=required`와 `stop_on_first_tool`로 답변 도구에1회 위임하며, specialist의 `as_tool` 이름은 `write_grounded_answer`다. 실제 부모/자식 관측은 SDK hooks에서 기록한다. 검색·ACL·근거 선택·최종 인용 검증은 기존 애플리케이션이 수행한다.

본래 로그인된 기존 실행을 다시 확인한 결과, manager와 specialist의 모델 호출은 각각20.17초·107.63초이며 둘 다 **Gemma 4 E2B Ollama**로 표시됐다. 입력/출력은 manager217/39토큰, specialist4,632/171토큰이다. 이는 같은 저장 실행의 모델 관측값이며 새로운 호출이 아니다. 에이전트는 역할·도구·지침을 갖는 SDK 객체이고 Gemma는 그 역할이 사용하는 모델이다. manager가 여러 전문가 중 자유롭게 선택하는 구조로 확대 해석하지 않는다.

### 표시 범위

API에 역할 정의 본문은 별도로 없고 이전 실행의 지침은 수집하지 않았다. 따라서 이름별 설명을 UI에 하드코딩하지 않고 실제 부모/위임 관계와 가장 가까운 agent ID에 속한 호출로 역할·모델·대상을 설명한다. 이 설명은 관측 관계이며 당시 지침 전문으로 표시하지 않는다. 전체 단계·원문·입력·결과 상세와 기존 누락/실패/취소 계약은 보존한다.

### 그림과 상호작용 구현

`AgentFlowDiagram`은 에이전트를 큰 카드로 표시하고 실제 관계에 방향 화살표를 둔다. 작은 단일 흐름은 넓은 패널에서 가로로, 좁은 패널에서 세로로 배치한다. 복수 분기는 실제 부모 ID를 따라 나누며 일반 상하위 실행과 위임을 구분한다. 위임 버튼을 선택하면 기존 위임 상세를 연다. 전체 span 트리는 기본으로 접고 필요할 때 펼치며 선택은 그림·기록·상세가 공유한다.

이름을 해석하지 않고 `agent-flow.ts`가 부모 관계와 가장 가까운 agent ID를 이용해 역할·모델/도구 기록을 도출한다. 같은 이름의 에이전트도 실행 단계 번호로 구분하고 하위 에이전트 호출을 부모 수에 중복 포함하지 않는다. 호버/포커스는 짧은 정보를, 클릭/Enter/Space는 유지되는 선택 상세를 제공한다. 실패·취소·관측 누락은 전체 기록을 접어도 기본 영역에서 확인할 수 있다.

### 후속 브라우저 확인

- 실제 제품 CSS의 합성1280px 패널은 카드→화살표→카드,320/375px는 세로 흐름으로 표시됐다.320px 카드 폭은 약261.3px이며 패널 `clientWidth=scrollWidth=319`,375px는374로 가로 넘침이 없었다.
- 320px에서 Space로 에이전트를 선택하고 역할 팝업을 확인했다. 긴 모델명이 있는 팝업도 `clientWidth=scrollWidth=260`이며 Escape 이후 팝업만 닫히고 선택·키보드 포커스·2px 외곽선은 유지됐다.375px에서는 Enter로 위임선을 선택해 기존 방향과 as_tool 상세를 확인했다.
- 64단계 합성 중첩에서 에이전트64개·상하위 연결63개와 최소 카드 폭261.3px를 유지했으며320px 패널의 가로 넘침이 없었다. 하위 실행을 위임으로 바꾸지 않는다.
- 비정렬 합성9span의 에이전트3개·위임2개에서 manager→writer와 manager→reviewer를 서로 다른 분기로 표시하고 각 모델1개를 확인했다.320px 분기에서도 가로 넘침이 없고 handoff 버튼의 Enter 선택으로 제어권 인계 상세를 열었다.560px 컨테이너는 세로 카드384px·그림 `clientWidth=scrollWidth=525`였다.
- 본래5173의 로그인된 기존 완료 실행을 새로고침해 `rag_manager → answer_specialist`의 두 카드와 위임1개, 각 모델1단계·Gemma 표시를 확인했다. 클릭한 specialist에는 위임한 manager·관측 역할·모델·기존 상세가 표시됐다. 새 생성·임베딩은0회다.

마지막 상호작용 검사에서는 포인터가 이전 카드에 남아 있어도 Tab으로 새 카드에 포커스하면 새 에이전트 정보를 표시하도록 보강했다. 자동 회귀의 변경 전 실패와 실제 브라우저의 manager 클릭→Tab→위임선→Tab→writer 정보 전환을 확인했다. 전체 단계 기록을 펼쳐 모델을 선택하고 전달 입력을 열면 기존 이력의 **본문 미보관** 안내를 유지한다.

브라우저 도구는 네이티브 hover 이동 API를 제공하지 않아 포커스/선택/Escape를 실제 화면에서 검증하고 포인터 경계는 컴포넌트 테스트로 확인한다. 합성 패널 폭 검증과 전체 모바일 viewport 업무 검증은 구분한다.

설치된 user-event의 포인터 이동은 `relatedTarget`을 생략해 tooltip 자식으로 이동해도 영역 밖 이탈로 전달했다. 해당 전환만 실제 `relatedTarget`을 가진 native 이벤트로 보완해 정보 영역 안 이동·바깥 이탈·hover-only Escape를 검사했다. 제품 동작 기대를 완화하지 않았고 임시 디버그 코드는 제거했다.
