# Gemma 시간 초과 관측 보강 계획

**목표:** 완료 응답이 없는 경우에도 런타임 진행 카운터와 CPU·메모리 변화, 관측 실패 및 정리 결과를 남긴다. 사용자가 승인한 다음 관측 보강 작업이다.

**범위:** 새 `.local-data/project-agent-work/gemma-timeout-observation-20261029/`에서 기존 검증된 순수 입력·응답 검사와 후보 수명 관리 코드를 재사용한다. 과거 코드·승인·실패 ledger는 보존한다. 제품·프롬프트·근거·생성 설정·서비스/DB는 변경하지 않는다. 이전1/4 실측 범위는 종료됐으며 새 모델 적재·추론은 승인 전 실행하지 않는다.

## 설계

- 완료 응답만 기다리던 경로에 별도 관측 작업을 연결한다. 생성 전송은 한 번이며 기존360초 기한을 유지한다. 관측 장애가 재전송·모델 전환·응답 덮어쓰기나 기한 연장을 일으키지 않는다.
- 서명 후보의 인증된 loopback `/slots`와 `/props`만 읽는다. 공식 b11908 소스와 맞는 숫자·불리언·고정 상태만 추출한다. prompt·원문·token ID·전체 설정·오류 본문은 기록하지 않는다. GET은 제한 시간·크기·출처를 적용하며 proxy/redirect/retry를 사용하지 않는다.
- slot task ID와 이전 idle 표본을 대조한다. 처리 중이라는 사실만으로 prefill이라고 단정하지 않는다. 처리 토큰·출력 카운터의 관측/증가와 idle/unknown을 분리하며 미지원·누락·stale·reset은 명시한다. 카운터는 커널 완료 뒤 갱신될 수 있어 정지한 카운터를 계산 정지로 단정하지 않는다.
- OS 자원은 PID·실행 파일·생성 시각을 검증한 읽기 전용 Win32 표본으로 수집한다. CPU 누적값 차분/관측 간격, working set/private commit, 가용 물리 메모리, page-fault 차분, OS 스레드 수를 기록한다. page fault에는 soft fault가 포함된다. OS 스레드 수·CPU 사용 코어 상당값을 LLM의 설정 스레드 수로 부르지 않는다. 런타임 API가 설정 스레드를 제공하지 않으면 미확인으로 표시한다.
- 자원 질의는 별도 짧은 Python 프로세스에서 수행해 native 질의 지연이 생성 event loop를 막지 않게 한다. 5초 간격·단일 비중첩 표본·최대73표본, 자원 프로세스3초/HTTP1초 상한을 둔다. 측정 자체의 비용과 누락을 기록한다. 완료/timeout/cancel 뒤 관측을 종료하고 자신이 만든 자원 프로세스만 회수한다.
- 실제 연결은 후보1회 진단 실행기로 준비한다. 이전 서명 bundle/모델/현재 ACL/고정 입력·28근거/품질 검증을 재사용하며 새 승인 파일과 새 exclusive ledger 없이는 모델을 시작하지 않는다. 실패 결과와 최종 후보 정리를 별도 이벤트로 남긴다. 새 승인 전에는 offline·mock·현재 Python 자기 프로세스 읽기 검사만 수행한다.

## 수행 순서와 역할

1. AI 담당: 공식 source 계약 조사 → 순수 `progress_projection.py`와 합성 회귀. `/slots`의 이전 task·카운터 의미와 스레드 정보의 한계를 확인한다.
2. 인프라 담당: `windows_resources.py`의 stable-handle 자원 표본/차분/단일 표본 CLI와 fake Win32 테스트·자기 프로세스 읽기 검증.
3. root: `observation.py`와 후보1회 `run_observed.py` 연결. 입력 불변·단일 전송·기한·취소·관측 sink 실패·수명 정리·새 예산 게이트를 mock 검증한다.
4. 독립 코드/프라이버시 담당: 원문 유출·관측 실패와 생성 결과 분리·task/PID 재사용·기한/종료 경합을 독립 검증한다. 구현 책임과 분리한다.
5. root: 통합 pytest/Ruff/strict mypy, 본래 읽기 전용 준비/과거 산출물 보존, WORKBOARD/실제 한계 기록. 실측이 필요하면 검토 가능한 코드가 완성된 뒤 새 최대1회 범위를 확인한다.

## 검증 기준

- 원래 요청 bytes와 반환 bytes, 생성 호출 수·예외/취소 의미가 관측 on/off에서 같다.
- 모든 관측 실패는 안전한 상태로 남고 생성의 timeout·취소를 가리지 않는다. 불완전한 표본은 추정치로 채우지 않는다.
- HTTP·출력 파일·표본 수가 bounded이며 종료 후 관측 task/자체 child가 남지 않는다.
- 실제 민감 자료와 모델 호출 없이 성공·시간 초과·잘못된 JSON·미지원 endpoint·비정상 숫자·counter reset·PID reuse·느린 자원 질의를 검증한다.
- 코드 검증은 실제 모델 속도·품질·병목 원인 확인을 대신하지 않는다. UI·DB schema·검색/답변 정책 역할은 범위 밖이며 기존 문제 이력 화면의 실패도 별도 유지한다.

## 실제 실행 후 확인한 한계

구현·330개 검사·타입/린트·본래 준비 뒤 사용자가 새 최대1회 진단을 승인했다. 실제1/1회는 360.004초 timeout·응답0이며 64표본·입력3549/출력4·후보 회수와 환경 보존을 기록했다. HTTP1초/자원 자식3초 제한을 설정했지만 프로세스 시작·스케줄링을 포함한 표본 수집은 최대18.922초였고 자원21표본이 누락됐다. 따라서 명목 설정을 실제 벽시계 상한으로 보고하지 않는다. 오래된 표본 귀속은 차단됐고 생성 기한은 유지됐다. 다음은 관측 시작 비용 보완과 출력 계산/메모리 대기/형식 제약 비용을 분리하는 준비다.
