# Gemma 입력 처리 병목: 장치 조사와 실제 스레드 비교

상태: 승인4/4회 실측 종료(유효3개·첫1개 계측 불완전). 6스레드 첫 입력 처리가9.57% 느려 후보 미채택. 기존 기본값과 프로파일은 유지했다. 관련 ISSUE-00038·ISSUE-00035. 아래 준비 기록은 실측 전 시점이며 최종 수치·한계는 마지막 절을 따른다. 기존 실행의 시간 분해는 [10월27일 위임 검증](2026-10-27-delegation-rejection-verification.md), 배치 비교는 [10월26일 기록](2026-10-26-ollama-runtime-batch-threads.md), 설정 계약은 [ADR-0047](../decisions/0047-ollama-runtime-batch-threads.md)을 따른다.

## 확인한 사실과 한계

- 기존 첫 자율 실행341.617초 중 두 Gemma 호출의 입력 처리 합계는272.171초다. 현재 모델·런타임 조합의 prefill 병목은 확인됐으나 당시 CPU/GPU·메모리·실효 스레드의 동시 관측은 없다.
- 실제 호스트는 Windows11 ARM64, Snapdragon X2 Plus10코어/10논리 프로세서, 가용 물리 총량 약23.50GiB다. Windows CPU set은 빠른 등급6개·낮은 등급4개로 나뉜다. 이는 특정 스레드 수의 최적성이나 CPU affinity를 입증하지 않는다.
- 실제 실행 중인 Ollama0.40.3 serve와 설치된 runner·CPU 라이브러리는 PE ARM64다. 저장소의 AMD64 정책을 이 네이티브 실행 파일에 적용해 x64 에뮬레이션 원인으로 설명하면 안 된다. 아키텍처 전환은 수행하지 않았다.
- Adreno X2-45가 설치돼 있지만 조사한 Ollama 설치 트리에는 Vulkan DLL이 없다. 당시 GPU 사용 여부는 미확인이다. GPU 장치 존재, 서버 모델 GPU 할당량, PID별 GPU 엔진 사용률을 각각 구분한다.
- 모델이 내려간 현재 상태에서도 메모리 여유와 paging이 크게 변했다. 한 유휴 샘플은 available1,716,879,360bytes, committed47,587,020,800bytes, pages-input223/s다. 이는 현재 메모리 압박의 관측이며 과거341초의 원인 비중으로 귀속할 수 없다.
- 알려진 파일 로그 위치에 과거 해당 실행 로그가 없었다. 기존 콘솔의 읽기 접근도 Win32오류5로 실패해 중단했다. 현재 runner 없음·`/api/ps=[]` 상태에서 모델을 임의로 올리지 않았다.

설치 runner의 `--version` commit631109b34는 공식 b11351과 일치한다. [Ollama0.40.3 런처](https://github.com/ollama/ollama/blob/v0.40.3/llm/llama_server.go)는 명시한 num_thread만 `-t`로 넘기고 나머지는 runner 자동 선택에 맡긴다. [해당 runner 자동값 소스](https://github.com/ggml-org/llama.cpp/blob/631109b34/common/common.cpp)는 빌드 분기에 따라 이 호스트에서5 또는10을 예상하게 한다. 설치 라이브러리는 MinGW 분기를 뒷받침하나 컴파일 매크로와 당시 실효값을 직접 관측한 것은 아니다. `/props`도 스레드 수를 제공하지 않는다. **자동 실효 스레드는 미확인으로 유지**하며 OS ThreadCount25를 추론 스레드25로 해석하지 않는다.

## 준비한 개선·측정

기존 공개 합성 질문의 direct 실행에서 완전한 native 입력을 읽고 현재 제품의 계정·원문 접근 검사를 통과했다. 입력 SHA256은 과거 비교와 동일하고28개 근거 행이 공개 테스트 픽스처와 정확히 같다. 저장된 출력에 실제 제품의 응답 파서·근거 별칭 복원·CitationValidator를 다시 적용해 기존 답변·인용과 일치를 확인했다. 새 모델 호출은 없었다.

새 계측기는 정확한 serve/runner PID·생성 시각·모델 blob을 전후 확인한다. CPU 누적 시간, working/private memory, 호스트 메모리·paging, 해당 PID의 GPU 엔진 수치를 시간과 함께 수집한다. 누락값은 unknown으로 남긴다. 기존에 이미 읽는 전후 프로세스 수치로 짧은 반복 호출도 관측하며, 관측기 자체 CPU 시간도 구분한다. 이는 WMI provider까지 포함한 전체 계측 오버헤드는 아니다.

Windows PowerShell5.1 실제 유휴 관측에서 메모리/GPU 조회 시간 초과가 발생했다. 수치를0으로 채우지 않고 실패 증거를 보존했으며, 실제 유휴 수집에 성공한 기존 PS7 실행 파일을 측정기에 지정했다. 새 설치나 서비스 재시작은 없다.

실제 비교안은 동일 native 입력의 기존 설정2회와 명시6스레드 후보2회, 합계 최대4회·자동 재시도0이다. 빠른 코어군6개는 후보 선택의 근거일 뿐 최적값이 아니다. 모델·근거·배치·컨텍스트·출력 예산을 유지한다. 실행 중 batch/ubatch/context가 달라지면 조건 비교를 중단한다. 자동 실효값이 확인되지 않으면 “명시6 설정의 진단”으로 보고하고 정확한 스레드 수 간 인과 비교로 과장하지 않는다.

이 측정은 native LLM만 분리한다. 임베딩·검색 비용이나 이전 worker16MiB 누락을 이 실험의 변수로 포함하지 않는다. DB 평가 실행 신규 등록, 프로파일 변경, 기본 승격과 전체 RAG/UI 수용 검증은 수행하지 않는다. 원문 입출력·원시 명령·비밀값·비공개 내부 추론은 파일에 저장하지 않는다.

## 검증과 남은 일

- 샘플러 오프라인46항목을 PS7·PS5.1 각각 검증했다. 플랫폼 반복 실행을 합산하지 않는다.
- 호출 제한·입력 변경 차단7개, 독립 제품 파서·인용·출력 보존10항목을 검증했다.
- 준비 스크립트4개 Ruff,3개 범위 Mypy(`check-untyped-defs`, imported modules 제외) 통과. 제품 전체 타입 검사나 실제 모델 검증 통과를 뜻하지 않는다.
- 장시간 stdout 배출, 실패 시 정확한 관측 자식 종료, 마지막 실패의 종료 상태·호출 직전 재검증·샘플 사이 runner 교체·짧은 반복의 전후 CPU 수치 누락을 독립 모의10개로 검증했다. 최종 준비 코드의 독립 검토 차단 항목은 없다. 실행 직전 `review-final-prepared-wrapper.md`의 검토 SHA와 실제 파일이 일치해야 한다.
- 이전 모델 호출 승인 범위는 종료 상태다. 새 실행 범위를 확인한 뒤 실제 CPU/GPU·메모리와 입력 처리 시간을 기록하고, 출력·인용이 달라지면 추가 호출과 후보 채택을 중단한다. 기존 일반 지급 규칙 누락·정답0/2는 여전히 별도 미해결이다.
- 운영 정본 ISSUE DB 갱신은 미완료이며 이 문서만으로 등록 완료를 주장하지 않는다.

## 17:03~17:06 KST: 첫 실측과 계측 중단

사용자가 “남은 작업 진행해서 비교해”로 준비한 총4회·재시도0 비교를 승인했다. 위 준비 상태는 승인 전 기록이다. 검토한5개 파일 SHA를 확인하고 새 승인 파일과 단회 ledger를 생성했다.

첫 기존 설정 HTTP 요청은167.626초에 완료됐다. 그러나 초기 표본 이후 CIM 프로세스 조회가 시간 초과됐고, 이를 실제 신원 불일치와 동일하게 처리한 계측기가 다음 호출을 차단했다. 이 실행은 총4회 중1회를 소비했다. 당시 wrapper는 자원 검증을 응답 분석보다 먼저 수행했으므로 **첫 호출의 native load/prefill/decode·답변/인용 판정은 미확인으로 남는다**. 응답 본문을 보존하지 않았으므로 이후 호출로 이를 소급 복원했다고 주장하지 않는다.

유효한 초기3개 표본에서 runner175016, batch/ubatch1024/1024, context16384를 확인했다. 가용 물리 메모리 최저122,028,032bytes(116.38MiB), 호스트 pages-input137,544/s가 관측됐다. 디스크에서 읽은 페이지는 메모리 매핑 파일 읽기도 포함할 수 있으므로 전부 swap이라고 보지 않는다. 초기 CPU 구간은 요청 초반 약17초만 포괄하며 전체 요청이나 prefill 평균이 아니다. 서버 size_vram0과 PID GPU 엔진 미관측도 서로 구분한다. 첫 원시 계측 ledger는 변경하지 않는다.
