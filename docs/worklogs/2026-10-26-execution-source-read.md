# 실행 목록 원문 권한 조회·위치 추출 개선

2026-10-26, ISSUE-00042 후속. 사용자가 [검증 조회 일괄화 다음 단계](2026-10-26-execution-validation-batch.md)의 진행을 승인했다. 기존 권한·답변·인용·숫자 증명을 유지하면서 반복 읽기와 계산만 수정했다. [구현 계획](../superpowers/plans/2026-10-26-execution-source-read.md).

## 원인과 변경

`visible_run`은 snapshot의 원문 조합마다 SQL을 호출했다. 정확한 `(document_id, asset_version_id, projection_id)` 조합을 최대64개씩 조회하고 반환된 세 ID의 집합 전체를 비교하도록 바꿨다. 세 ID를 독립 IN으로 검사하지 않는다. 기존 owner·문서 active·버전/처리본 ready·현재 공간 권한 조건과 시작/종료 재검증을 유지한다. 현재 함수에 없던 index-build/active-version 조건은 추가하지 않았다.

`source_identities`는 scalar를 포함한 모든 자식을 재귀 호출하며 매번 빈 set을 만들고 합쳤다. 최초 CPU 진단에서574,157회·누적1.774초가 관측됐다. 호출당 지역 set 하나에 결과를 모으고 dict/list 자식만 재귀 방문하도록 바꿨다. 전체 깊이우선 순회·부모의 세 UUID 파싱 순서·부분키 자식 탐색·중복 제거·오류 전파·호출마다 새 결과를 보존한다. 입력을 수정하거나 요청 간 결과를 캐시하지 않는다.

제품은 `evaluation/generative_read.py`와 `conversations/access.py`의 위 두 함수만 바꿨다. 일반 대화의 SQL 권한 검사와 숫자 verifier, 모델·프롬프트·검색·생성·인용·백그라운드·UI 계약은 변경하지 않았다. 순수 위치 추출 함수는 일반 대화에도 공유되므로 그 회귀를 포함한다.

## 실측 방법과 결과

본래 DB의 접근 가능한508건(대화25/평가483)을 읽기 전용으로 조회했다. 이전5모듈 복사본을 측정 프로세스에만 로드했으며 제품 파일을 되돌리지 않았다. 모델 호출0회다.

초기 probe는 응답 동일성을 확인하려고 측정 구간에서 summary를 추가 생성했다. 이번에는 그 해시 계산을 timer와 profiler 종료 뒤로 분리했다. 독립 검토에서도 이를 확인했다. `timing-before-{1,2}.json`과 초기 CPU 진단은 원인 확인 자료이며 최종 시간 비교에는 쓰지 않는다. 아래는 보완된 동일 도구의 전후 교대2쌍이다.

전체 query의 documents 조회173→133회, 평가 총680→640회(5.9%) 감소를 확인했다. 원문 권한 SQL의 단위 검사에서는1/64/65/129개 source가1/1/2/3회, owner 불일치·빈 source는0회다. 위치 추출의 합성 scalar4096개에서는 같은 파일의 Python 호출 수(키 검사 generator 포함)가4100→5회, set 생성4098→1개로 줄었다.

네 실측에서 전체508건 summary와 첫25건 응답의 해시가 모두 동일했다. 첫 페이지 해시에는 정렬·cursor·전체 통계가 포함된다. 본문은 증거 파일로 저장하지 않았다.

## 검증·본래 반영

구현 담당을 두 함수별로 나누고 독립 QA를 별도로 배정했다. tuple 조회의 신규14개와 기존 실행 모니터링 회귀, 순회 의미·오류28개 및 비용2개를 검증했다. 두 비용 사례가 기존 코드에서 실패하는 것을 먼저 확인했다. 제품 범위 strict 타입 검사와 Ruff도 통과했다.

독립 pytest는 고유336개 통과·실패0, strict Mypy 제품2파일과 Ruff 제품/테스트5파일을 통과했다. 공개 합성 중첩 입력20개와 UUID 오류3개를 변경 전 함수에 대조하고, SQL AST의 정확한 tuple·전체 공간 권한 구조와 actor 결속을 별도로 검증했다. 독립 테스트의 SQLAlchemy 내부 alias 비교 오류는 정규화 AST 구조 비교로 바로잡고 재실행했으며 제품 결함은 아니었다.

업무 진행 중0·정확한 API/launcher 신원을 확인한 뒤 본래 Conda 실행기로 반영했다. health/ready200 및 대화202/동기응답·실행 조회 계약이 유지됐다. 기존25표2560행의 PK별 해시와 `.env`는 전후 동일했다. 본래 목록508건 표시 후 상세 이동에서 기존 관리자 세션이 만료되어 재로그인을 요청했다.

같은 날 사용자 재로그인 후 기존 평가 상세의 저장 답변·인용2개·근거28개·기존 품질실패 표시, 전체508건 목록과 실제대화 필터25건을 확인했다. ISSUE-00042의 원인·수정·검증·남은 작업과 날짜별 진행 이력을 저장하고 새로고침으로 재조회했다. 이전 이력을 유지하고 목록 지연이 남는 상태를 검증 완료로 바꾸지 않았다. 재로그인 후에는 제품 수정·서비스 재시작·모델 호출·성능 재측정을 하지 않았으며, 위336개 검증과 전후 실측은 앞선 구현 시점의 근거다.

근거는 `.local-data/project-agent-work/execution-source-read-20261026/`에 있다. 최종 시간은 `timing-{before,after}-actual-{1,2}.json`, 설계·구현 인계는 `source-access-design.md`, `source-batch-implementation.md`, `source-collector-implementation.md`, 독립 검사와 보존은 `qa-*`, `review-*`, `trace-runtime-*`를 사용한다.

## 남은 작업

현재 환경에서 목록은13~15초가 걸려 지연은 남는다. 숫자 증명의 각 근거/operand에 대한 현재 권한 조회와 결과·규칙 digest/판정 계산이 남은 비용이다. 다음 후보는 그 현재 검증을 보존하는 중복 조회·순수 계산의 축소이며 캐시로 검증을 생략하지 않는다.

이번에 새 모델 답변을 생성하지 않았다. 기존 정답0/2 한계를 품질 통과로 바꾸지 않는다. 신규 UI·모바일 검증으로 확대하지 않으며 기존 데이터/계정·환경과 다른 작업 변경을 보존했다. 설치·migration·커밋·push·캐시 삭제0.
