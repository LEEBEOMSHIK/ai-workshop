# Codex 문서 승인 이력·재승인 및 관리자 UI

- 상태: 사용자 방향 승인, 상세 계약 검토 요청
- 범위: 기존 Codex 문서 승인 흐름의 DB·실행 binding·관리자 UI
- 사용자 승인 방향: 취소 이력 보존, 같은 revision에 새 승인 생성, 이전 실행 승인 비부활,
  상태/설명/작업 구분 및 별도 취소 확인창.

## 1. 문제와 대안

현재 `rag_codex_evidence_approvals`는 revision을 PK로 사용한다. 취소된 행을 보존하므로
같은 revision의 새 승인을 INSERT할 수 없다. 프론트도 취소를 종단 상태로 고정한다.
실행 binding version 2는 revision과 SHA-256만 고정하므로 승인 상태만 복구하면 이전 요청이
다시 허용될 위험이 있다. 문서 재업로드나 hash 변경은 해결책으로 사용하지 않는다.

- 취소 행 복구: 이력과 이전 실행 무효화 요구를 충족하지 못하므로 제외.
- 현재 행 + 별도 감사 이력: 두 저장소의 상태를 함께 유지해야 하므로 이번 범위에서 제외.
- 채택 제안: 승인 세대별 행을 저장하고 실행에도 정확한 승인 ID를 고정한다.

## 2. 저장 계약

기존 테이블을 승인 이력 테이블로 확장한다. 승인마다 서버 생성 UUID `id`를 PK로 사용하고,
`revision_id`, `generation`, `content_sha256`, `classification`, `approved_by`,
`approved_at`, `revoked_at`을 보존한다. `(revision_id, generation)`은 unique이며
revision마다 `revoked_at IS NULL`인 행은 최대 1개인 partial unique index를 둔다.

승인 취소는 해당 행의 `revoked_at`을 최초 한 번 설정한다. 승인 본문과 기존 취소 시각은
수정하지 않는다. 재승인은 같은 revision에 다음 generation의 새 행을 INSERT한다.
처음 승인하는 문서는 generation 1이다. 취소된 마지막 행은 그대로 남는다.
분류는 public/synthetic만 허용하며 기존 owner·공간 권한·READY·정확 hash 검사를 유지한다.

조회는 revision당 최신 generation 하나만 반환하여 문서 목록이 중복되지 않도록 한다.
응답에 최신 `approval_id`, `approval_generation`, 취소 시각을 추가한다. 미승인은 null이다.
일반 화면은 UUID 대신 문서명·문서 버전·승인 상태·승인 회차/시각을 표시한다.
revision ID와 SHA-256은 기술 상세로 접는다. 전체 감사 이력 조회 화면은 이번 범위 밖이다.

## 3. 동시 요청과 API

기존 승인/취소 endpoint와 owner/Origin/요청 헤더 검사를 유지한다.
승인 POST에는 `expected_approval_id`를 필수 nullable 필드로 추가한다.
최초 승인은 null, 재승인은 사용자가 실제 본 마지막 취소 승인 ID를 전달한다.
최신 행과 불일치하면 409로 거절하고 새로고침 후 다시 확인하도록 안내한다.
필드 생략은 422로 거절하며 null 기본값으로 대체하지 않는다. 현재 활성 행이 있으면
새 승인을 만들지 않는다. DTO의 알 수 없는 필드는 거절한다.
취소 DELETE에는 필수 query `approval_id`를 전달해 보았던 정확한 승인만 취소한다.
과거 승인 ID에 대한 취소는 새 승인을 취소하지 않는다. 같은 취소의 재시도는 상태를 바꾸지 않는다.
성공 응답 유실 후 동일 POST를 재시도하면 409와 재조회 안내를 반환하고 세대를 늘리지 않는다.
취소 후 도착한 오래된 POST가 새 승인으로 해석되지 않도록 precondition을 먼저 확인한다.

승인·취소·실행 검증은 기존 외부 전송 정책 잠금과 호환되는 잠금 순서를 따른다.
동일 revision의 쓰기를 직렬화하고 DB 제약을 최종 방어선으로 둔다.
변경 경로는 정책 → owner/공간 → Asset Version → Document → 승인 행 순서를 유지한다.
Asset Version은 처음부터 FOR UPDATE로 잠그고 공유 잠금 후 승급하지 않는다.
잠금 순서를 뒤집거나 call과 evidence 간 교착을 유발하지 않도록 SQL 통합 테스트로 확인한다.

## 4. 이전 실행 비부활

실행 intent codec을 version 3으로 변경한다. 각 evidence binding에 문서 revision/hash와
정확한 `evidence_approval_id`를 포함한다. 발급, 영속 저장, 현재 상태 재구성, 실행 직전 검증에서
동일 ID·활성 상태·hash·분류를 확인한다. 승인 ID가 누락되거나 다르면 외부 실행 전에 거절한다.
문서 재승인으로 기존 call approval/consumption/request slot을 복구하거나 재발급하지 않는다.
문서 근거가 있는 후속 질문·평가도 같은 검증을 따른다.

기존 version 2 실행 binding을 새 승인 ID로 자동 업그레이드하지 않는다.
구형 실행 승인은 fail-closed로 거절하고 새 요청에서 다시 발급한다. 기존 기록은 보존한다.
이미 시작된 외부 전송은 소급 회수할 수 없다. 실행 예약과 취소가 경합할 때 기존 잠금 경계에
따라 선행한 실행이 종료될 수 있음을 UI에 알리고, 취소 완료 후 새 실행은 차단한다.

## 5. 관리자 UI

문서 카드 순서는 문서명/버전 → 상태 배지 → 현재 승인 정보/설명 → 작업 버튼이다.

- 미승인: 직접 자료 분류 선택 후 `자료 승인`. 자동 선택/승인 없음.
- 승인됨: 승인 분류·회차·시각과 `승인 취소…` 보조 위험 버튼.
- 취소됨: 취소 상태·시각과 이력 보존 안내, 분류를 다시 선택한 뒤 `새 승인 등록`.
- 재승인 성공: 새 승인 회차를 표시. 이전 실행은 재사용되지 않음을 안내.

기존 긴 체크박스를 카드에서 제거하고 `승인 취소…` 클릭 시 React 확인 대화상자를 연다.
문서명/버전, 외부 전송 사용 중단, 이력 보존, 새 승인 가능, 이미 전송된 내용 회수 불가를 설명한다.
`돌아가기`와 `승인 취소 확정` 버튼을 분리하고 초기 focus는 안전한 동작에 둔다.
Escape 닫기·focus trap·닫은 뒤 호출 버튼 focus 복귀를 지원한다.
확정 전 API 요청을 보내지 않고 처리 중 중복 제출을 막는다. 실패 시 성공 상태로 바꾸지 않는다.
지식 공간 변경/늦은 응답 격리는 유지한다. 취소를 체크박스 토글로 표현하지 않는다.

승인 카드 전용 CSS module과 기존 디자인 토큰을 사용한다. 긴 파일명·hash는 줄바꿈하고,
작은 폭에서는 버튼을 배치 가능한 방향으로 흐르게 한다. 공통 관리자 label/checkbox 스타일을
전체 변경하지 않아 상단 공급자 체크박스의 의미와 동작에 영향을 주지 않는다.

## 6. Migration·적용 경계

새 Alembic migration 후보는 `0030`이며 구현 전 실제 head를 재확인한다.
기존 각 승인 행에 고유 ID와 generation 1을 부여하되 분류·승인자·승인 시각·취소 상태는
그대로 유지한다. 기존 취소 이력은 삭제하거나 활성화하지 않는다. 불변/취소 trigger도 유지한다.
backfill은 migration 트랜잭션 안에서 evidence 테이블의 해당 trigger만 제거·복원하여 수행한다.
공유 trigger 함수와 call/consumption trigger는 변경하지 않는다. 새 확장 설치 없이 지원되는
서버 UUID 생성 방식으로 기존 행에 ID를 부여한다.
다중 이력이 생긴 뒤 단일행 구조로 되돌리는 downgrade는 데이터 손실 없이 불가능하므로
명시적으로 거절한다. 실제 DB 적용 전 격리 DB에서 upgrade와 기존 행 보존을 검증한다.
단일 세대라도 데이터가 있는 downgrade는 거절하고, 빈 테이블만 up/down/up을 검증한다.

실제 적용은 검토 후 private API의 승인 쓰기/실행을 중단한 상태에서 migration 후 재시작한다.
다른 API·Docker·모델 설정·공간 정책은 변경하지 않는다. 실제 문서 재승인은 사용자 직접 작업이다.
이 작업은 검색 평가·도메인 활성화 또는 실제 Codex 답변 검증 완료를 의미하지 않는다.

## 7. 성공 기준과 검증

1. 합성 revision을 승인→취소→재승인해 서로 다른 두 승인 ID와 보존된 취소 이력을 확인한다.
2. 기존 실제 미승인/활성/취소 행 migration 보존, 최신 조회 1행, active unique 제약을 검증한다.
3. 취소 전 발급한 intent는 동일 hash로 재승인한 뒤에도 모델 실행 0회로 거절된다.
4. 신규 승인에 기반한 새 intent만 정상 검증되며 old codec·누락 ID·틀린 ID는 거절된다.
5. stale POST/DELETE, 중복 요청, 동시 재승인, 권한 없음, hash 불일치, 비READY를 검증한다.
6. UI 미승인/승인/취소/재승인, 실패·busy·공간 전환, 대화상자 키보드 흐름을 테스트한다.
7. TypeScript/Python 타입·린트·관련 단위/API/격리 SQL 테스트와 독립 보안·코드 리뷰를 통과한다.
8. 실제 화면 스타일은 읽기 전용으로 확인한다. 자동화로 실제 보안 승인을 수행하지 않는다.

## 8. 역할과 범위

프론트 담당: 승인 카드·확인창·API 타입·접근성/상태 테스트.
독립 검토자: 보안·개인정보·코드 리뷰와 통합 검증 근거 확인(동일 변경 구현 금지).
