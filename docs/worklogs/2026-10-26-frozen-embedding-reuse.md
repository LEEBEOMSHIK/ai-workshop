# 고정 평가의 임베딩 반복 계산 제거

ISSUE-00038 후속, 2026-10-26. [설계 ADR-0045](../decisions/0045-frozen-evaluation-embedding-reuse.md), [구현 계획](../superpowers/plans/2026-10-26-frozen-embedding-reuse.md).

## 원인과 변경

직전 v6 반복 평가에서 임베딩 모델 준비11.637초·선택용 문서 계산15.069초가 관측됐다. 매 attempt의 새 CPU 임베딩 객체가 같은 입력의 토큰 수와 벡터를 다시 계산했다. 이 구조적 반복은 확인했지만 환경·메모리 차이의 기여도까지 확정하지 않았다. 두 시간은 포함 관계일 수 있어 합산하지 않는다.

하나의 평가 claim에 유한 계산 저장소를 두고, 현재 actor·candidate·case·전체 frozen component/execution snapshot·권한 시나리오가 같을 때만 완료값을 재사용한다. query/document 토큰 수와 query/vector batch의 네 연산은 분리한다. 문서 배치 전체 순서와 중복까지 정확히 같아야 hit이며 부분 재배치하지 않는다. 모델·tokenizer를 붙잡아 두지 않고 기존 생성 전 해제와 모든 현재 권한 검사·실제 검색·선택을 유지한다.

성공한 정수·정규화 벡터만 검증 후 atomic하게 보관하고 새 list로 반환한다. 실패·취소·불량 출력은 저장하지 않는다. 보관 상한을 넘으면 기존 계산 결과를 그대로 반환하고 저장만 생략한다. claim의 정상·예외·취소·종료 미확인 및 재claim 경계에서 참조를 제거한다. 기본 설정은0/off, 상한64MiB이며 명시한 worker 실험에서만 활성화한다. 일반 대화의 속도나 첫 실행 비용을 개선한 것으로 보고하지 않는다.

worker_runtime에 활성 여부·상한·claim 범위와 계약 버전을 저장한다. 실제 hit만 `embedding.result_reuse`로 횟수·항목 수를 기록하며 본문·벡터·키를 로그나 DB로 보내지 않는다. 같은 논리 모델 버전 실행 중 파일 변경은 지원 범위 밖이며 설치/건강 검증은 캐시0으로 수행한다.

## 검증과 반영

설정·관측 계약13개와 계산 저장소22개는 RED 확인 후 구현했다. 별도 담당의 독립12개에서 batch 민감 출력의 완전 동일성, 입력 변경 miss, 반환 변조 격리, 작은 상한, 모델/factory 참조 해제와 warm 상태 권한 철회를 확인했다.

관련 단위 범위는 평가·임베딩·검색·실행 기록·생성·오케스트레이션과 설정이다. 최초 broad의2,671개 통과·1개 실패·4개 skip 중 실패는 기존 취소 테스트 대역에 새 기본 설정이 빠진 것이었다. 대역에0을 명시해 해당1개가 통과했다. 제품 우회 처리는 추가하지 않았다. 연결 테스트39개로 확장한 최종 결과를 `(classname,name)` 기준으로 합쳐 **고유2,687개 통과·4개 skip·남은 실패0**을 확인했다. 전체 회귀를 불필요하게 반복 실행하지 않았다.

기존 DB rollback 검증1개에서 새 연산의 실제 저장→현재 소유자 상세 조회, 다른 actor 거절, terminal 기록 변경 차단과 기존5표 보존·합성3행 rollback을 확인했다. strict Mypy는 변경5파일과 타입 의존6파일의11개 범위에서 통과했다. 프로젝트 전체 타입 검사라는 뜻은 아니다. 변경 제품·테스트11파일 Ruff, OpenAPI 생성·일치 검사와 frontend TypeScript도 통과했다.

기존 API만 같은 Conda·설정으로 반영했다(새 API94624/launcher137740,18000). health/ready200, live OpenAPI의 새 연산·기존v6 변환표 스키마와 비활성 기본0을 확인했다. 재기동 준비의 생성 시각 비교가 PowerShell JSON 날짜 자동 변환으로 한 번 거절되어 중지 전에 종료됐고, 실제 동일 시각을 UTC ticks로 비교하도록 고쳐 신원 검사를 유지했다. 기존25표2,499행 SHA와 `.env`는 동일하다. 기존 작업242파일은235동일/허용7변경/누락0이며 기존 clean 상태였던 설정·취소 fixture 수정2개와 신규 구현/테스트/문서8개를 별도로 기록한다. 설치·캐시 삭제·새 환경/DB/계정·모델/프로파일 변경·commit/push는 없다.

재현 근거는 `.local-data/project-agent-work/frozen-embedding-reuse-20261026/`의 `final-unit-summary.json`, `independent-verification.md`, `wiring-final.xml`, `independent-existing-db.xml`, `mypy-final.txt`, `ruff-final.txt`, `trace-runtime-after-check.json`, `final-file-preservation.json`에 남겼다. 문제 이력 운영 정본 ISSUE-00038의 진행 이력·수정 내용·검증·남은 작업을 갱신하고 새로고침으로 저장을 확인했다. 구현됨 상태를 유지하며 실제 수용 미완료를 구분했다.

## 실제 수용과 다음 단계

구현 중 실제 생성/임베딩 호출은0회였다. 이후 사용자가 **새 최대4회·동일 질문2반복·자동 재시도0회** 품질/속도 비교를 승인했다. 직전 v6의 소진된4회와 별도이며 기존 비기본v6·worker 한정16MiB 조건으로 새 run만 실행한다. 실제 결과는 완료 후 아래에 기록한다.

v6 기준 run은 `16edd5ae-fb8e-4510-b6a0-c1fcab5d7d4a`이고 전체205.070/46.797초, 정답0/2였다. 새 run `cc82e756-b56b-44c1-951d-b7c4174e6178`을 본래 로그인 화면에서 등록하고 고정 snapshot 전체·digest·규칙·예산과 초기 대기2건을 독립 확인했다. 기존 v6 구성/프로파일을 그대로 사용했다. 실행 wrapper는 정확한 새 run에 한 번만 호출했고 exit0으로 종료했다. **모델4/최대4회·자동 재시도0회, 두 반복 모두 완료**했으며 이번 예산은 소진됐다.

반복 전체 응답은 **64.08% 감소**했다. DB의 연산 기록에서 검색2항목·선택88항목의 재사용과 반복 모델 load/tokenize 부재를 확인했다. 요청 내부 query/documents 계측은 각각0.113ms/2.940ms로 남으며 실제 모델 재계산 시간으로 해석하지 않는다. 첫 실행은 재사용0, 모델 준비23.317초였고 전체 응답은 개선되지 않았다. 첫 답변 담당 입력 처리도134.925초로 병목이 남는다. 포함 관계인 연산 시간을 합산하지 않고 전체는 observer의 시작/끝 시간을 사용했다. 단일 질문 두 표본의 결과를 일반 대화·첫 질문 또는 전체 지연 분포 개선으로 확대하지 않는다.

두 반복 모두 기존 v6와 **답변·인용·검색/선택 ID 순서·저장 근거 전체·28개 원문·출처 위치·참조표가 동일**했다. manager/specialist의 지침·agent 입력·실제 HTTP 입력/출력과 canonical 결과 SHA도 모두 같다. 이번 두 응답에서 추가 품질 퇴행은 관찰되지 않았다. 하지만 기존 일반 지급 규칙·예시 조건 누락과 **정답0/2**, 표본P95 약200.813초/기준120초 실패는 그대로다. 품질 통과나 일반 기본값 승격으로 보고하지 않는다.

DB `runtime_environment.embedding_result_reuse`에 version1/scope claim/enabled true/max_bytes16777216이 저장됐고 현재 소유자 조회·다른 actor 거절·연산 무결성을 확인했다. 실제 모델을 가진 임베딩의 생성 전 close1회와 이후 참조 없음이 관측됐다. 즉시 RSS 반환을 뜻하지는 않는다. 기존25표2,499행 수정/삭제0, 승인된 새 run1·attempt2·execution2·audit2·audit_workspace2의 **9행만 증가해2,508행**이며 `.env`와 기본0, 프로파일·구성·활성 연결은 유지됐다.

실제 근거: `review-reuse-comparison.json`, `quality-reuse-review.md`, `review-live-final-runtime.json`, `review-live-preservation.json`, `independent-live-preservation.md`, `approved-run.exit-code.txt`와 `embedding-close-cc82e756-b56b-44c1-951d-b7c4174e6178.jsonl`을 같은 task 디렉터리에 보존한다. 원문은 새 성능 로그에 덤프하지 않았다.

본래 화면에서 새 run 등록·대기2건·첫 실행 중까지 확인했다. 완료 결과 화면을 재확인하는 동안 브라우저 제어가 Windows의 현재 URL을 확실히 식별하지 못해 중단됐다. 따라서 **최종 완료 화면 및 ISSUE-00038의 이번 실제 결과 추가 갱신은 미완료**다. 구현 완료 이력은 앞서 UI에 저장·재조회했으며, 실제 결과는 실행 DB와 이 문서/WORKBOARD에 보존했다. UI 중단을 우회하지 않았고 추가 모델 호출은 없다.

다음은 첫 응답의 남은 입력 처리 비용을 품질 보존 조건에서 줄이는 별도 수정과 위 완료 화면/이슈 갱신이다. 이번 재사용은 고정 평가 반복에 한정되며 일반 요청 공유나 기본 활성화는 하지 않는다.
