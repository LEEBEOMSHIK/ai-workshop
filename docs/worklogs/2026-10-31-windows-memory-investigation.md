- 날짜: 2026-10-31 KST
- 상태: 진단·기록 완료, 메모리 개선은 미해결. 사용자가 ASA 유지·조사 결과만 기록하도록 지정했다. 메모리 회수 조치와 개선 후 비교는 미실행.
- 운영 기록: [ISSUE-00049](http://127.0.0.1:5173/admin/system/issues?offset=0&issue=24510c0a-a8b8-477b-91b6-8cb4cb38a6d0), 진행 중.
- 관련: [ISSUE48 백엔드 응답성 수정](2026-10-31-backend-response-improvements.md)
- 사용자 범위: 프로세스·드라이버 원인 확인, 영향이 확인된 개선, 같은 요청의 전후 비교. 기존 기능·설정·답변/인용 기준 보존.

## 지금 확인한 사실

Windows 11 Home ARM64, 26H1, build28000.3231, 물리 메모리 약23.5GiB다. 마지막 부팅은10월15일이다. 첫 호스트 표본에서 비페이지 풀은12,710,572,032bytes(약11.84GiB), 가용 메모리는1,569MiB였다. 프로세스의 private commit, working set, 시스템 pool은 서로 다른 지표이며 더해서 실제 RAM 사용량으로 해석하지 않는다.

읽기 전용 pool-tag 조회에서 다음 큰 할당을 확인했다. 구조64bit/stride40/offset8을 확인했고, 두 번째 표본의 반환150,008bytes는8+3,750×40과 일치한다. 내부 NT 정보 클래스는 공개 안정 계약이 아니므로 개별 표본의 구조 검산과 OS 카운터를 함께 남긴다. 태그별 합과 시스템 pool 카운터는 동일한 집계 범위라고 가정하지 않는다.

| 태그 | 첫 표본의 비페이지 할당 bytes | 해석 |
| --- | ---: | --- |
| `VadS` | 6,031,751,808 | VAD 계열 우선 조사 |
| `Vad ` | 4,000,840,000 | 끝 공백 보존 |
| `VadF` | 443,081,664 | VAD 계열 우선 조사 |
| `nsp7` | 662,372,352 | 별도 약632MiB, 소유 드라이버 미확정 |

VAD 이름의 세 태그 합은 약9.76GiB이며, 특정 장치 드라이버나 앱의 결함으로 확정한 것은 아니다. 첫 두 표본의211.49초 동안 세 태그 합은9.51MiB, 전체 태그 비페이지 합은2.60MiB 늘었다. 진단과 사용자 작업이 섞인 짧은 구간이므로 지속 누수율로 외삽하지 않는다. 태그는 대소문자를 구분한다.

현재 프로젝트의 API·프론트엔드4개 프로세스는 합계 약991MiB private commit이며, 종료할 수 있는 고아 테스트 프로세스는 발견되지 않았다. 다른 저장소의 pytest와 사용자 앱은 보존했다. Docker의 PostgreSQL/Redis/Elasticsearch는 정상이며 WSL 내부 가용량 약8.7GiB를 Windows에서 즉시 회수 가능한 물리 메모리로 해석하지 않는다.

일반 권한에서555개 프로세스를 시도해365개를 조회했고,190개는 접근 제한/종료 등으로 조회하지 못했다. 관리자 승인 뒤 추가 조사에서는564개 중538개를 전체 주소 범위까지 조회했고26개는 접근 제한/이미 종료 등으로 실패했다. 조회된 영역 합계653,661개, allocation-base run119,229개, 최대는WUDFCompanionHost의63,209개였다. 이 수는 VAD 노드 개수와 같지 않으며, 현재 자료만으로 세 태그의 약9,245만개 잔존 할당을 어느 프로세스에 귀속할 수 없다. WUDFCompanionHost가 목록 상위라는 이유만으로 원인으로 선정하지 않는다.

관리자 진단은 `PROCESS_QUERY_INFORMATION`과 `VirtualQueryEx`의 영역 통계만 읽었다. 프로세스 메모리 내용·주소·명령줄을 증거에 저장하지 않았고 debug privilege를 켜지 않았다. 두 스크립트는 문법·64bit 구조·자기 프로세스 조회와 독립 검토를 통과했으며 실행 전후 SHA-256이 동일하다. 관리자 권한으로도 보호된 프로세스는 남는다.

## 다음 원인 추적과 경계

큰 태그만으로 드라이버를 지정하거나 종료하지 않는다. Microsoft의 절차대로 태그와 실제 allocation stack을 대조했다. 필터된 Pool 추적의 원시 증거는 로컬 Git 제외 디렉터리에만 둔다. 드라이버 비활성화·보호 기능 해제·재부팅·캐시 삭제는 실행하지 않았다.

### 짧은 커널 할당 추적

Windows 기본 WPR의 별도 GUID 세션에서 네 태그와 `Loader+Pool`, `PoolAllocation/PoolFree` 스택만 수집했다. ProcessThread, .NET/JScript, 네트워크, 메모리 본문 dump provider는 사용하지 않았다. Loader에는 경로·주소 메타데이터가 포함되므로 원시 ETL은 외부로 전송하지 않았다.20MiB 버퍼, 파일 모드,25초 관측과128MiB/여유2GiB 감시를 사용했다. 이는 native 명령의 실행/종료까지 강제로 자르는 시간·크기 상한은 아니다.

실제 관측 대기25.449초, 전체 시작~종료37.842초, ETL99,614,720bytes였다. 시작/종료 코드0, own status `not_recording`, 기존 기본 세션 전후 모두 비실행, 종료 직전·분석 헤더의 손실0을 확인했다. 다른 세션 중단/취소는 없었다. 첫 실행 시도는 리뷰 중 보강된 파일의 해시 불일치로 추적 시작 전에 차단됐다. 보강본을 다시 검토·동결한 뒤1회만 수집했다.

이 OS의 `root/wmi` 이벤트 **클래스 정의만** 관리자 권한으로 읽어 필드 순서·포인터 크기·버전을 확인했다. Get-WinEvent는 접근 제한, TDH는 클래식 이벤트의 스키마를 찾지 못해 성공으로 간주하지 않았다. 로컬 정의와 공식 Microsoft Stack/Image 문서에 따라 native OpenTrace/ProcessTrace 분석기를 사용했다. 전체718,717개 이벤트를 읽었고, 지원하지 않는 Pool/Image/Stack 레코드0·주소 재사용 충돌0·스택 이벤트 연결 누락0이다. 별도 합성 계약13개로 다른 PID의 해제·주소 재사용·관측 전 할당의 해제·잘못된 버전/필드·원본 timestamp 결합·모듈의 load/unload 범위를 검증했다.

| 추적 항목 | 결과 |
| --- | ---: |
| Pool 할당 / 해제 | 63,543 / 50,025 |
| 관측 끝에 남은 새 할당 | 13,554개 |
| 관측 전에 생겼다가 해제된 할당 | 36개 |
| `VadS` 순증 | 1,137,216bytes |
| `VadF` 순증 | 160,512bytes |
| 두 태그 순증 합 | 1,297,728bytes(약1.24MiB) |
| 실제 Pool 이벤트 시간 범위 | 28.515초 |

작은 증가분의 실행 문맥은 여러 프로세스에 분산됐다. 가장 큰 단일 문맥의 잔존 새 할당107,136bytes는 Memory Compression PID였고 확인된 커널 모듈은 ntoskrnl.exe다. 이것은 그 프로세스나 특정 드라이버가 기존9.76GiB를 만들었다는 증거가 아니다. 다른 작업을 대신 수행하는 커널 문맥일 수 있고, 기존 누적분은 추적 시작 이전이어서 allocation stack이 없다. 스택 이벤트 연결100%와 개별 프레임의 모듈 해석100%는 구분한다. 일부 프레임은 해석되지 않았다.

할당 문맥473개 PID 중396개는 추적 전후 목록에 모두 없으며, 관측 종료 시 보유된 새 할당의81.27%(1,057,440bytes)를 차지한다. 짧은 프로세스 활동의 단서이지만 PID 재사용과 추적 종료 뒤 해제를 구분하지 못하므로 누수로 단정하지 않는다. 전체 할당 프레임의99.37%, 보유분 프레임의99.14%를 모듈에 대응시켰다. 함수 심볼과 일부 프레임은 미해석이며 상위100개 스택 목록은 전체5,979개 그룹의 일부다.

### ASA의 반복 DB 연결 경로와 사용자 결정

추가20.102초 관측에서 PostgreSQL 생성103건 중102건의 부모는 ASA의 PostgreSQL PID225656(127.0.0.1:55439)이었다. 다른1건은 다른 프로젝트 서버였다. 이 구간에는 git 생성이 없었으므로 앞선25초와 같은 발생량으로 가정하지 않는다. 현재 TCP 연결2개는 ASA의 대본 작업 프로세스 PID248108에 연결돼 있었다. 이는 순간 표본이며102건 전체를 해당 한 작업 프로세스에 귀속하지 않는다. 다른 프로젝트의 DB 내용은 조회하지 않았다.

ASA의 지침을 읽고 소스만 확인했다. `services/backend/src/asa/registry/repository.py:31`은 매번 `psycopg.connect`를 생성한다. 실행 중인 대본 작업 프로세스는 유휴 tick당3개 연결과1초 대기, 자동화 작업 프로세스는5개 연결과2초 대기 구조다. 연결/쿼리 시간을 제외한 약5.5개/초와 관측된 약5개/초는 부합하지만, 이것이 기존9.76GiB 전체를 만들었다는 인과는 확정하지 않았다.

검토한 수정 후보는 두 작업 프로세스의 일반 조회·저장 연결만 수명주기 풀로 재사용하고 잠금 전용 연결은 실제 세션 종료를 유지하는 방식이다. 세션 advisory lock은 rollback만으로 해제되지 않으므로 모든 연결을 단순히 풀로 바꾸지 않는다. 적용한다면 준비 후 유휴 신규 연결의 코드상 기대치는 약1.5개/초지만, 실제 개선 수치나 기존 누적 메모리 회수량이 아니다.

**사용자는 “ASA는 유지하고 조사 결과만 기록”을 선택했다.** ASA 파일·설정·DB·실행 프로세스를 변경하지 않았고 해당 수정 후보는 실행하지 않는다. AI Workshop 답변/인용 경로에도 변경이 없다. Windows의 기존 누적 점유에 대해 근거가 확인된 안전한 대상별 회수 조치는 아직 없다. 임의 재부팅도 하지 않았다. 따라서 원래 요청의 메모리 감소·개선 전후 비교는 미완료로 남는다.

추가 감시기의 첫 실행은 등록 반환 객체에 의존해 명시 구독 정리를 건너뛰었다. 증거의 `subscriptionStillPresent=true`를 그대로 보존했다. 해당 진단 PID267236이 종료됐음을 확인했고 임시 구독은 그 PowerShell 세션과 함께 끝났다. 이후 정확한 SourceIdentifier로 자신의 구독만 정리하도록 수집기를 수정하고 합성 타이머 두 개로 자기 구독 해제·다른 구독 보존을 검증했다. 실제 감시기를 반복 실행하지 않았다. 영구 WMI consumer는 만들지 않았다.

## 보존 확인과 후속 기준

진단 후 제품 소스1,013개와 `.env` 해시가 모두 동일했다. 원래 API PID246760과 프론트엔드 PID210204를 유지했고 health/ready 모두 HTTP200이었다. 마지막 확인의 nonpaged pool은12,809,625,600bytes(약11.93GiB), 가용 메모리는1,571,966,976bytes(약1.46GiB)로, 점유 감소를 관측하지 않았다. 일회성 health/ready 확인은 앞의100회 표본과 측정 방법이 달라 전후 성능 비교에 사용하지 않는다. 신규 모델 호출·추가 API 비용0이며 새 실제 답변 품질 실험을 수행했다는 뜻은 아니다.

기존 운영 문제 이력은 ISSUE49에 저장·재조회하고, 이전 애플리케이션 수정 ISSUE48의 검증 완료 상태는 유지한다. 제품 코드·드라이버·OS 설정 변경, 캐시 삭제, commit/push는 하지 않았다. 현재 증거/수집기는 로컬에 보존했다. 다음 회복 실험은 사용자 작업 종료 시점을 확인한 Windows 재시작 뒤 같은16개 구성·health·pool/가용 RAM을 측정하고 재발 추세를 보는 방식이지만, 이번에 실행하거나 승인된 것으로 취급하지 않는다.

재시작이 별도 승인되면 기존 Docker 컨테이너3개(PostgreSQL/Redis/Elasticsearch, 현재 restart policy `no`)와 원래 API/프론트엔드/Ollama의 복원이 필요하다. API는 정본 `scripts/run_backend_conda.ps1`, 프론트엔드는 `pnpm --dir frontend dev`, Ollama는 현재 `C:\\AI\\Ollama\\ollama.exe serve`를 사용 중임을 확인했다. 기존 설정·볼륨·계정·자료를 보존하고 새 환경을 만들지 않는다. 다른 사용자 앱과 프로젝트는 이번 작업에서 종료하지 않는다.

현재 빌드 이후의 공식 KB5127653(28000.3365) 설명에는 이번 VAD 점유에 대응하는 수정이 확인되지 않았다. 단순히 새 버전이라는 이유로 원인 해결로 취급하거나 설치하지 않았다.
