- 상태: 조사와 첫 범위 사용자 승인 완료. [상세 계약](../superpowers/specs/2026-09-14-rag-artifact-provenance-design.md) 작성·검토, 구현 전 문서 확인 대기.
- 상위 계약: [휴지통·영구 삭제](../superpowers/specs/2026-09-13-asset-trash-purge-design.md).
- 이전 완료: [SQL 출처·목록 연결](2026-09-14-rag-sql-provenance.md).
- 메인은 시스템/RAG 경계와 파일·색인 경로, 별도 DBA는 build·ingestion·일반 작업의 참조와 변경 경로를 조사한다.
- 실사용 저장소를 조사하거나 고아 파일이 실제 존재한다고 확인한 것은 아니다. 아래는 코드 순서에서 확인한 장애 가능성이다.

## 확인한 파일·색인 경계

| 대상 | 현재 코드 | 삭제 추적에 필요한 보완 |
|---|---|---|
| 파싱·청킹 JSON | `ingestion/service.py`의 workflow가 `_publish_artifact` 후 lifecycle 완료를 호출 | 파일 생성 성공·DB 기록 실패 구간도 추적 |
| 임베딩 JSON | `ingestion/stages.py`의 `_publish_embedding` 후 별도 트랜잭션에서 경로·해시 저장 | 쓰기 전 소유권 기록과 실패 후 대조 |
| 물리 검색 색인 | `IndexingService.prepare_projection`이 create/bulk/count 후 반환, stage가 그 뒤 build.index_name 저장 | 생성 전 정확한 build/물리 이름 연결, 부분 bulk 및 미활성 색인 확인 |
| 객체 저장 임시 파일 | `LocalObjectStore`가 임의 UUID `.tmp`를 만들고 finally에서 제거 | 강제 종료 시에도 문서/시도별 소유권을 추적할 수 있는 임시물 경계 |
| 파서·DOCX·PDF OCR 임시물 | `TemporaryDirectory`와 finally/context 종료 정리 | 정상 정리와 프로세스 강제 종료 후 잔존 확인을 구분 |

정상 예외의 finally 정리가 없다는 뜻이 아니다. 강제 종료로 finally 실행이 불가능한 경우를 DB 완료 목록만으로 증명할 수 없다는 뜻이다.
파일과 SQL, Elasticsearch는 하나의 DB rollback으로 함께 되돌릴 수 없다.
정해진 파일명 패턴이 있어도 해당 시점의 설정·source·실제 소유권 확인 없이 삭제 대상으로 추정하지 않는다.

## 다음 범위 후보

1. **권장: 파싱·청킹·임베딩 객체의 생성 전 등록과 확인부터 연결.** 실제 요구가 있는 세 종류에 한정해 작업/source/객체 식별자를 먼저 영속화하고, 저장 성공·실패·재시도를 대조한다. 임시 파일도 등록된 시도에 귀속시킨다. 기존 자료는 자동 완료 처리하지 않는다.
2. build SQL 목록부터 별도 연결. 이미 있는 관계를 다루기 쉬우나 DB 기록 전에 생성된 외부 파일·색인의 누락 위험은 계속 남는다.
3. 파일·색인·OCR·작업 기록을 한 번에 연결. 전체 경계를 함께 다루지만 변경·장애 검증 범위가 커져 단계별 확인이 어렵다.

권장안은 아직 구현 승인이 확정된 상세 계약이 아니다. 상태/불변성/revision·등록과 게시 순서·잠금·대조 실패 코드·기존 데이터 처리 계약을 상세 설계에서 확정한다.
공통 출처 목록에는 불투명 ID/revision만 전달하고 객체 경로·본문 해시는 소유 모듈 내부에 둔다.
원본은 Platform Assets, RAG 파생물은 RAG가 소유한다. Platform은 RAG를 import하지 않는다.
OCR·임베딩 모델 가중치와 공유 캐시는 문서 파생 파일이 아니므로 문서 영구 삭제 대상으로 삼지 않는다.

## DBA 확인과 설계 시 주의점

- `ingestion/stages.py:739`의 `_ensure_build`는 ES 호출 전에 build UUID를 저장한다. 물리 이름 저장이 나중이라는 사실을 build 식별자 자체가 없다는 뜻으로 해석하지 않는다.
- `ingestion/models.py:36`의 ingestion은 Job·projection·원본 버전에 CASCADE로 묶이고 파일 키를 보유한다. dispatch도 ingestion 삭제를 따라간다. handoff 기록은 원본 버전 삭제를 따라간다.
- `documents/models.py:135`의 build는 projection 삭제를 따라가며 ingestion의 build 포인터는 SET NULL이다. 원본/projection을 먼저 지우면 외부 자원 추적 정보가 유실될 수 있다.
- 따라서 작업 중단과 정리 목록 확정·외부 자원 검증이 참조 행 제거보다 먼저다. 작업 기록을 영구 보관하자는 의미가 아니며 마지막에는 본문 없는 최소 증명만 남긴다.
- DBA도 세 객체 종류의 사전 등록을 첫 단계로 권고했다. 공통 관계 재사용만으로 충분한지, 별도 소유권/작성 상태 행이 필요한지는 아직 확정하지 않았다.
- 고정 revision 1만으로 예약·실물 생성·무결성 확인 상태 변화를 모두 표현하면 오래된 목록의 유효성 문제가 생길 수 있다. 기존 SQL 묶음과 별개의 자원 revision/게시 계약을 상세 설계에서 검증해야 한다.

## 검증과 실행 경계

다음 구현의 검증 후보는 쓰기 전 등록 실패, 파일 생성 후 DB 실패, 재시작/중복 전달, 임시물 잔존, 다른 소유자와 경로 충돌, 루트 밖 경로·reparse 거부, 기존 미추적 자료 차단이다.
읽기 목록은 전체 영구 삭제 완료를 뜻하지 않는다. writer 차단·실제 삭제·잔존 검증·색인/작업/기타 모듈 연결은 별도 게이트다.
이번 조사에서는 제품 코드·DB·서버·파일 삭제·패키지·커밋/푸시를 변경하지 않았으며 애플리케이션 테스트를 실행하지 않았다.

## 상세 설계 작성 결과

사용자가 세 JSON 산출물의 생성 전 등록·실제 대조 범위를 승인했다. 상세안은 bundle/세 슬롯/시도별 정확한 임시 key를 별도 RAG 상태로 관리하고 공통 현재 relation을 재사용한다.
DBA 검토로 슬롯별 open 시도1개·I/O 밖 짧은 잠금·시간 초과 인계 금지·최종화의 lifecycle 트랜잭션 참여를 반영했다.
작성자가 종료됐다는 기존 증명이 없으므로 미확인 open 시도의 자동 복구/삭제는 이번에 구현하지 않는다. 기존 오류를 숨겨 완료 처리하는 기능이 아니다.
초기 상세안의 attempt store 필드 누락과 물리 저장소 변경 감지 근거 부족을 보완했다. 복합 FK·명명된 partial UNIQUE 및 사전 초기화된 저장소 binding 표식 검사를 명시했다.
이번 설계는 객체 게시용 임시 파일까지만 포함한다. 파서 원본 복사·OCR 이미지·뷰어 임시물은 별도 후속이며 완료로 계산하지 않는다.
DBA 보완 재검토에서 두 명세 누락 해결과 최종화 트랜잭션 경계를 확인했고 해당 검토 범위의 남은 차단 사항은 없다.
상세 문서 링크3개·중복 제목·미완성 표식·일본어 문자·공백 검사를 통과했다. 제품 코드를 변경하지 않아 애플리케이션 테스트는 실행하지 않았다.
