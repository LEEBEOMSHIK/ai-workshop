# 자산운용 문서 RAG AI 검색 설계

- 상태: 승인됨
- 기준일: 2026-08-30
- 상세 설계: [2026-08-30 AI 검색 상세 설계](designs/2026-08-30-ai-search-detailed-design.md)

## 1. 목적

첫 번째 RAG는 자산운용 전문 문서에서 관련 근거를 찾고, 사용자가 그 위치를 직접 확인할 수 있게 하는 AI 검색이다. 초기에는 자동 투자 판단, 투자 추천과 자동매매를 수행하지 않는다.

검색 품질과 근거 추적을 먼저 검증하고, LLM 답변과 에이전트 리서치는 후속 단계로 추가한다.

## 2. 검색 범위

```text
전사 지식 공간
├─ 규정·컴플라이언스
├─ 상품·펀드
├─ 운용 지침
└─ 리서치 자료

개인 지식 공간
├─ 개인 업로드
├─ 개인 폴더
└─ 실험용 문서

임시 작업 공간
└─ 현재 질의와 함께 첨부한 문서
```

사용자는 하나 이상의 허용된 공간과 폴더를 검색 범위로 선택한다. 개인 문서는 전사 검색에 자동으로 섞이지 않으며, 통합 검색은 사용자가 명시적으로 선택한 경우에만 실행한다.

결과에는 전사, 개인, 임시 첨부 배지와 폴더, 문서 버전, 원문 위치를 표시한다.

## 3. 문서 처리 파이프라인

Platform Asset 수명주기는 RAG projection 수명주기보다 먼저 완료된다.

```text
원본 파일 영속 저장(STORED, active pointer 없음)
  -> 저장 객체의 정확한 크기와 SHA-256 검증
  -> Asset Version READY와 버전 순서 기반 Document.active_version_id 갱신
```

Asset Version `READY`는 불변 원본 객체가 무결성 검증을 통과했다는 뜻이다. 같은 문서의
여러 과거 버전이 `READY`일 수 있으며, `Document.active_version_id`가 가리키는 가장 높은
검증 버전만 현재 Knowledge source다. 검증 실패는 Asset Version 상태와 active pointer를
바꾸지 않는다.

검증 Job 행은 업로드 commit 이후 worker 전달을 복구하는 영속 근거다. beat reconciler는
`QUEUED`, 오래 멈춘 `RUNNING`, 이전 릴리스의 `SUCCEEDED/stored + STORED` 조합을 다시
전달한다. 이전 조합도 객체 크기와 SHA-256을 다시 검증한 뒤에만 `READY`가 된다. 검증
worker는 late ack와 worker-loss redelivery를 사용하고, 객체·DB의 일시 오류만 제한적으로
재시도하며 checksum 불일치는 영구 오류로 기록한다.

검증된 현재 Knowledge source는 구독된 Indexing Profile별 RAG projection을 시작한다.
구독 조회, command 생성, outbox claim과 ingestion 각 단계는 모두 정확히 같은
`Document.active_version_id`의 `READY` 버전인지 다시 확인한다. 따라서 v2가 활성화된 뒤
늦게 도착한 v1 작업은 파싱이나 색인을 시작·계속하지 않는다.

`READY` commit과 구독별 command 생성 사이의 손실은 별도 중복 outbox가 아니라
`READY + active pointer + 현재 구독 + 기존 ingestion job` 상태를 읽는 주기적 handoff
reconciler가 복구한다. 누락된 `(Asset Version, Indexing Profile)`만 기존 멱등 command로
만들고, 그 뒤 broker 전달은 기존 RAG ingestion outbox가 담당한다. 일부 프로파일 생성만
실패해도 성공한 job은 유지되고 다음 주기에 누락 프로파일만 수렴한다.

```text
Asset Version READY
  -> 형식별 파싱 또는 OCR
  -> 공통 문서 모델 변환
  -> 구조 기반 청킹
  -> BM25 색인과 임베딩 생성
  -> 청크·벡터·provenance·alias 완성 검증
  -> RAG Projection READY와 색인 활성화
```

RAG Projection 상태는 다음 흐름을 사용한다.

```text
PENDING -> PARSING -> CHUNKING -> EMBEDDING -> INDEXING -> READY
```

처리할 수 없으면 `FAILED`, 일부 요소만 사용할 수 있으면 `PARTIAL_READY`로 기록한다. `READY`가 아닌 버전은 일반 검색에 포함하지 않는다. `PARTIAL_READY`는 사용자가 명시적으로 허용한 진단 또는 실험 검색에서만 사용할 수 있다.

RAG Projection `READY`는 Platform Asset `READY`와 별개다. 필요한 파싱과 색인이 모두
완성되고 개수, provenance와 alias를 검증한 뒤에만 검색 projection을 활성화한다. 이전
projection은 감사와 실험 재현을 위해 보존 정책에 따라 유지한다.

## 4. 공통 문서 모델

```text
Document
└─ DocumentVersion
   └─ StructuralElement
      ├─ Heading
      ├─ Paragraph
      ├─ List
      ├─ Table / Row / Cell
      ├─ Figure
      └─ TextSpan
```

각 요소는 다음 provenance를 가진다.

- 원본 파일과 문서 버전
- 페이지, 슬라이드 또는 시트
- 문단, 도형, 행·열·셀 식별자
- 문자 시작 및 종료 위치
- 사용할 수 있는 경우 원문 좌표
- 파서, OCR 엔진과 버전
- 파싱 또는 OCR 신뢰도

## 5. 문서 형식과 뷰어

- PDF와 스캔 PDF: 원본 페이지 위 좌표 기반 하이라이트
- DOCX, HTML, Markdown, HWPX: 통합 뷰어의 절·문단·표·문자 범위 하이라이트
- PPTX: 통합 뷰어의 슬라이드와 텍스트 도형 하이라이트
- XLSX: 통합 뷰어의 시트, 행과 셀 하이라이트
- 표: 관련 셀과 함께 필요한 행·열 머리글 표시

첫 수직 슬라이스는 Markdown, TXT와 텍스트가 포함된 PDF를 지원한다. 이후 DOCX, 스캔 PDF와 OCR 순서로 확장하고, PPTX, XLSX, HTML과 HWPX는 형식 확장 단계에서 추가한다.

원본 애플리케이션을 완전히 재현하지 않는다. 원본 위치의 정확한 확인과 일관된 검색 경험을 우선한다.

## 6. Hybrid retrieval

초기 기준 검색은 다음 구성이다.

```text
권한과 검색 범위 확정
  -> 질의 정규화
  -> BM25와 bi-encoder dense retrieval 병렬 실행
  -> RRF로 순위 결합
  -> 중복 청크 및 비활성 문서 버전 제거
  -> 의미상 관련된 문장 또는 표 셀 선택
  -> 원문 위치와 함께 결과 반환
```

BM25는 조항, 상품명, 종목명, 코드와 수치처럼 정확한 표현을 찾는다. Bi-encoder는 원문과 표현이 다른 의미 질의를 찾는다. 초기 검색 순위에는 LLM을 사용하지 않는다.

## 7. 의미 하이라이트

검색용 구조 청크 안에 문장, 목록 항목과 표 셀 같은 작은 의미 단위를 보존한다. 검색된 상위 청크에서 질의와 각 의미 단위의 bi-encoder 유사도를 계산해 관련 구간을 선택한다.

하이라이트 결과에는 다음을 포함한다.

- 강조할 원문 범위 또는 좌표
- 문서, 버전과 구조 요소 식별자
- 페이지, 슬라이드 또는 시트 위치
- keyword 또는 semantic 일치 유형
- 검색 프로파일과 관련도 정보
- 낮은 provenance 또는 파싱 신뢰도 경고

의미 하이라이트는 정확한 단어 일치가 아니라 관련성이 높은 구간이라는 점을 UI에서 구분한다.

## 8. 모델과 프로파일

개별 학습 모델은 Model Definition으로 등록한다. BM25와 RRF는 학습 모델이 아니라 검색 방식이므로 모델 목록에 포함하지 않는다.

### 색인 프로파일

- 파서 및 버전
- 청킹 방식 및 버전
- 임베딩 모델 및 정확한 버전
- 벡터 차원과 정규화
- 색인 알고리즘과 파라미터

임베딩 모델 또는 청킹 방식이 달라지면 별도 색인 버전을 만든다. 호환되지 않는 임베딩을 같은 벡터 필드에 혼합하지 않는다.

### 검색 프로파일

- BM25 분석기와 파라미터
- 사용할 dense 색인 프로파일
- 후보 수와 벡터 검색 파라미터
- 권한 및 메타데이터 필터
- RRF 설정
- 선택적 리랭커와 버전

예시는 다음과 같다.

```text
BM25 only
BM25 + Bi-encoder A + RRF
BM25 + Bi-encoder B + RRF
BM25 + Bi-encoder A + RRF + Reranker X
```

### 생성 프로파일

- LLM과 정확한 버전
- 실행 위치와 데이터 반출 정책
- 시스템 지침과 답변 템플릿 버전
- 컨텍스트 예산과 근거 정책

LLM 변경은 검색 색인을 다시 만들지 않는다. 검색 실험과 생성 실험을 별도로 기록한다.

### 저장된 RAG 구성

사용자 화면의 프로파일은 개별 모델이 아니라 Indexing, Retrieval, Generation 프로파일의 불변 버전을 조합한 저장된 RAG 구성을 뜻한다.

- 시스템이 미리 제공하는 저장 구성은 BM25 기준선 하나다.
- 나머지 조합은 사용자가 이름을 붙여 저장한 뒤 목록에 나타난다.
- 저장은 새 불변 버전을 만들며 운영 기본값을 자동으로 바꾸지 않는다.
- 저장된 구성만 비교 실험에 사용할 수 있다.
- 필수 평가를 통과한 구성만 승인 후 운영 기본값으로 승격한다.

## 9. 일반 검색과 실험 검색

일반 검색은 평가를 통과해 승인된 기본 RAG 구성을 사용한다. 실험 검색은 소유자가 저장한 RAG 구성을 선택해 동일한 질의와 문서 스냅샷에서 비교한다.

실험에는 다음을 기록한다.

- 목적과 가설
- 대상 문서 스냅샷
- 평가 질의와 정답 근거
- 사용한 모든 프로파일과 모델 버전
- 실행 환경
- Recall@K, MRR, nDCG와 P50/P95 응답 시간
- 근거 충분성 판정과 잘못된 근거 비율
- 하이라이트 위치 평가
- 접근권한 누출과 재현 가능성
- 실패 사례, 분석, 결론과 다음 실험

평가 실행을 만들 때 질의·문서·근거 원문, 권한 범위, 정확한 구성 버전, 물리 색인 이름과 빌드·프로젝션·모델 리비전을 하나의 정규화된 해시 스냅샷으로 고정한다. 작업자는 이후 현재 멤버십, 활성 문서·색인 별칭 또는 최신 구성 행을 다시 조회하지 않고 이 스냅샷과 정확한 물리 색인만 사용한다. 최초 작업자가 기록한 실행 리비전·장치·패키지·모델 환경 지문은 재개 시에도 바꾸지 않으며 다른 지문의 작업자가 부분 결과를 섞을 수 없다.

평가 작업자는 검색 순위, 답변 선택, 구조화된 하이라이트, 노출 표면, 지연 시간과 반복 서명으로 이루어진 원시 관측만 증명한다. PostgreSQL은 불변 정답 케이스와 원시 관측에서 케이스 지표와 후보 집계를 다시 검증한다. 완전한 정확 케이스 행과 정책 임계값을 만족한 실행만 승격 근거가 되며, 작업자가 제출한 스칼라 지표 자체는 신뢰 경계에 포함하지 않는다.

검증된 실험 프로파일만 별도의 승인 과정을 거쳐 일반 검색 기본값으로 승격한다.

## 10. RAG 에이전트 조직

```text
작업소 총괄 에이전트
└─ 자산운용 RAG 총괄 에이전트
   ├─ 문서 접수 담당
   ├─ 파싱·구조 분석 담당
   ├─ 색인 담당
   ├─ 질의 분석 담당
   ├─ 검색 담당
   ├─ 근거 검증 담당
   ├─ 답변 작성 담당
   └─ 품질 평가 담당
```

파싱과 색인은 결정적인 서비스 작업으로 구현한다. 질의 분해, 근거 충돌 판단과 답변 작성처럼 판단이 필요한 단계만 실제 LLM 에이전트 후보로 둔다.

- AI 검색 모드: hybrid retrieval과 의미 하이라이트만 사용
- 에이전트 리서치 모드: RAG 총괄이 검색, 근거 검증과 답변 도구를 조율

첫 구현은 AI 검색 모드를 대상으로 한다.

## 11. 오류와 복구

- 각 파이프라인 단계는 멱등성을 가져야 한다.
- 실패 단계와 문서 요소를 식별할 수 있어야 한다.
- 재시도는 같은 문서 및 프로파일에 중복 활성 버전을 만들지 않는다.
- 검증과 RAG handoff는 영속 Job, 현재 `READY` 버전과 구독 상태에서 주기적으로 복구한다.
- 이전 활성 버전의 지연된 dispatch 또는 worker 실행은 새 Knowledge source를 처리하지 않는다.
- 사용자 조치가 필요한 암호화 파일, 손상 파일과 미지원 형식을 구분한다.
- 파서 또는 모델의 자동 대체는 정책에 명시되고 실행 기록에 남아야 한다.
- 일부 문서만 색인된 상태에서 새 버전을 활성화하지 않는다.

## 12. 첫 AI 검색 완료 기준

- 모든 정상 검색 결과가 권한이 허용된 원문 위치로 이동한다.
- 전사, 개인, 임시 첨부의 검색 범위를 정확히 분리한다.
- 권한 밖 문서 노출 사례가 없다.
- BM25와 hybrid 결과를 동일 질의 세트에서 비교할 수 있다.
- 모델, 파서, 청커, 프로파일과 문서 버전으로 결과를 재현할 수 있다.
- 의미 하이라이트가 관련 문장 또는 표 셀을 식별한다.
- 실패와 부분 처리 문서를 정상 문서처럼 표시하지 않는다.
- 새 첨부 문서와 기존 문서를 함께 검색할 수 있다.
- 비공개 원문이 외부 모델 API로 전송되지 않는다.
- 첫 답변은 LLM 생성문이 아니라 원문 근거 발췌를 사용한다.
- 직접 답할 근거가 없으면 관련 문서가 있어도 INSUFFICIENT_EVIDENCE를 반환한다.
