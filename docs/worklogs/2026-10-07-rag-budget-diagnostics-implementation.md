# RAG 입력 예산 진단 구현과 본래 API 반영

- 기준일: 2026-10-07
- 관련 문제: ISSUE-00005, ISSUE-00029
- 승인 범위: [예산 진단 설계](../superpowers/specs/2026-10-06-rag-budget-diagnostics-design.md)
- 상태: 구현·독립 리뷰·본래 API 반영 완료. 실제 사용자 브라우저의 새 요청·모니터링 저장/복원 확인은 로그인 만료로 대기 중이다.

## 구현

적격 문맥 묶음의 실제 선택 검사 시점에 입력 단위·문자 수, 검사 직전 사용량, 해당 실행의 상한과 초과 종류를 기록한다. 문자 수는 원문 단위의 `len(text)` 합계이며 토큰·JSON 바이트가 아니다. 제외된 묶음은 사용량을 소비하지 않는다. 관련성 미달 후보는 예산 검사를 하지 않았으므로 기록을 붙이지 않는다. 충돌로 최종 선택이 취소되어도 앞선 검사 기록과 최종 차단 사유를 구분한다.

`BudgetTrace`는 본문 없는 정확한 9필드 객체다. 수치는 strict integer, 사용량은 0 이상, 한도는 양수, 초과 종류는 중복 없는 groups/units/characters 최대3개다. 추가 필드는 거절한다. Search diagnostics와 실행 selection candidate의 nullable additive 필드로 연결하고, None이면 이 필드만 생략한다. 그룹 행에만 기록하며 원문 단위 행에 복제하지 않는다. 진단 표시가 꺼져도 실행 관측을 저장하고 반환 top_k/200개 기록 상한은 유지한다.

대화의 검색 진단과 실행 모니터링의 기존 선택 사유 아래 실제 초과한 항목만 입력량·남은량·전체 한도로 표시한다. 옛 기록은 ‘세부 예산 미기록’, 관련성 미달은 ‘예산 검사 전 제외’로 구분한다. 새 메뉴·버튼·스크롤 영역은 추가하지 않는다.

선택 정책·정렬·전체 묶음 수용/제외·기존32단위 한도·프로파일·권한·모델·DB 구조는 유지했다. 실제33/36단위 묶음의 제외를 해소하거나 답변 품질을 높였다는 주장이 아니다. 문맥 재구성/후보 승격은 별도 평가·승인 계약이 필요한 후속 작업이다.

## 자동 검증과 독립 리뷰

- 첫 실제 선택 테스트: 새 기록 부재로7실패/1통과 → 구현 후 기존 회귀와 함께26통과.
- Search response 테스트: 기록 누락으로1실패/12통과 → 새 필드 연결 후 통과.
- 최종 집중 백엔드42통과: 개별·복합 초과, 정확한 경계, 누적 소비, 충돌, 진단 on/off와 임베딩 호출 수, JSON 저장/복원, legacy 생략, 입력 검증, top_k/200개 상한.
- 넓은 관련 백엔드 검사: 1,464통과/4skip/1실패. 실패는 저장소 루트 실행에서 기존 migration fixture의 상대 경로를 찾지 못한 것으로, backend 디렉터리에서 해당 파일4개를 재실행해 모두 통과했다. 전체를 단일 실행에서 통과했다고 기록하지 않는다.
- 독립 리뷰: 초기 type-only import의 annotation NameError를 발견해 수정한 뒤 별도42백엔드·16UI 테스트 통과, 남은 차단 의견0.
- 프론트 소비자 RED2실패/기존9통과 → 관련3파일16테스트 통과. TypeScript 전체 검사·변경6파일 ESLint·API 타입 생성 일치 검사 통과. 대화 폴더 전체 검사는 결과 없이 지속되어 해당 테스트 세션만 취소했고 전체 통과로 주장하지 않는다.
- 변경 백엔드7파일 Ruff와 신규/선택/테스트4파일 format check, 범위별 diff 공백 검사 통과.
- Python 타입 검사: 첫 실행은 Windows 애플리케이션 제어 DLL 로딩 차단으로 실행되지 않았다. 호스트에서 루트 기준 검사는 설정을 읽지 못해 결과 없이 지속되어 그 검사 세션만 취소했다. 본래 backend 디렉터리의 strict 설정으로 동일 설치본을 실행한 최종 검사는412개 소스 모두 통과했다. 보안 정책·설치·파일 변경은 없었다. 이후 실행 통과가 DLL 재발 방지나 영구 복구의 근거는 아니다.

## 본래 환경 반영과 확인 경계

구현 전 독립 READ ONLY 기준선으로55개 보호 테이블, 기존 선택 대화8턴/전체5세션, 동결 보고서6개 exact v1, 원래 환경·schema0063·활성v4·평가·frozen gate1/receipt0 보존을 확인했다. 재시작 직전 실행·대화·평가·시도 모두0이었다.

원래 API97488와 launcher96032의 정확한 실행 명령·경로·포트를 확인한 뒤 API만 종료하고 같은 저장소 루트/.env/공식 Python으로 숨김 실행했다. 새 API88028/launcher108200, 포트18000이다. 프론트7824/5173, Docker, worker/beat 기존 미실행 상태는 유지했다. 직접 health/readiness와 프론트/경유 health는 모두 HTTP200이다. 새로운 환경·DB·계정·worktree는 만들지 않았다.

재시작 후 독립 READ ONLY 점검에서55개 보호 테이블의 기존행 SHA·건수, 선택 대화의 기존8턴 SHA/수정번호17·전체5세션, 동결6보고서의 파일/DB exact v1 SHA, 원래 환경·gate OID·기존 평가와 복원 결과가 일치했다. 새 요청·세션0, 진행 실행·평가0이다. 새 API stdout/stderr에서 비밀값·SQL parameter·Traceback·본문 dump 신호는 모두0이었다. 이 시점은 새 보고서의 정상 등록 전 관찰이며 등록 후 보존 비교는 별도 인계 기록으로 남긴다.

기존 Chrome 대화 탭은 로그인 만료 화면이다. 사용자에게 같은 화면 재로그인을 요청했으며 새 질문은 아직 보내지 않았다. 따라서 실제 요청의 새 수치 표시, 실행 DB 저장과 새로고침 복원, 옛 결과의 화면 표시는 자동 테스트로만 확인된 상태다. health200을 답변·멀티턴 성공으로 대신하지 않는다. 로그인 후 기존 대화에서 승인된 합성 자료만 사용해 최대2개 새 요청을 검증한다.

ISSUE-00029의 DLL 재발 방지, 유효 답변/멀티턴·권한 철회·별칭 종료·Git 인계 등 기존 기능 마감 조건은 남아 있다. 이 작업만으로 품질 개선만 남았다고 보고하지 않는다. 비공개 본문·질문·답변·계정·비밀값·원시 로그는 이 문서에 포함하지 않는다.
