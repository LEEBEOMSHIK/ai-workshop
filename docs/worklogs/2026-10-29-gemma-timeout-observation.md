# Gemma 시간 초과 중 진행·자원 관측 보강

관련 문제는 ISSUE-00038이다. [이전 실제 비교](2026-10-28-gemma-signed-runtime-comparison.md)의 첫 후보 요청은 360초에 시간 초과됐으며 완료 응답이 없었다. 기존 도구는 완료 응답의 native timing에 의존해 입력 처리와 출력 생성 중 어디에서 지연됐는지 확인하지 못했다. 이번 작업은 그 관측 공백을 보강한다. 실제 속도 개선이나 후보 채택을 의미하지 않는다.

사용자의 다음 작업 지시에 따라 [수행 계획](../superpowers/plans/2026-10-29-gemma-timeout-observation.md)을 적용했다. AI 담당은 런타임 카운터와 단일 호출 실행기를, 인프라 담당은 Windows 자원 표본을, root는 비동기 관측 연결·통합을 맡았다. 독립 코드·프라이버시 검토는 구현 책임과 분리했다. UI·DB schema·검색·답변 정책은 변경 범위에서 제외했다.

## 변경 내용

새 진단 도구는 `.local-data/project-agent-work/gemma-timeout-observation-20261029/`에 둔다. 이전 비교 폴더의 승인·실패 ledger·종료 기록과 코드 25개 파일은 보존한다. 이전 수명 관리 모듈은 바이트 동일 복사본을 사용해 새 실행의 임시 인증 디렉터리만 새 폴더에 귀속시켰다.

- `progress_projection.py`: 인증된 후보 `/slots`·`/props` 응답에서 허용한 숫자·불리언·고정 상태만 추출한다. task가 바뀌거나 표본이 오래됐거나 카운터가 감소하면 현재 요청 진행으로 추정하지 않는다.
- `windows_resources.py`: PID·실행 파일·생성 시각을 대조하고 읽기 전용 handle로 CPU 누적값, working set/private commit, 가용 물리 메모리, page fault, OS 스레드 수를 읽는다. 연속 표본으로 CPU 차분과 코어 사용 상당값을 계산한다.
- `observation.py`: 생성 요청과 별도로 5초 간격·최대73개 표본을 수집한다. HTTP는 1초, 별도 자원 수집 프로세스는 3초 제한이며 중첩·몰아치기·재시도가 없다. 관측 종료 시간은 요청 시간과 분리한다.
- `run_observed.py`: 현재 권한·고정28근거·동일 입력·모델 해시와 새 승인/단일 호출 ledger를 결합한다. 기존360초 제한과 답변·인용 판정을 유지한다. timeout·취소 시 소유 후보를 먼저 종료하고 관측 작업을 회수하며 원래 실패를 보존한다.

질문·근거·프롬프트·생성 설정·제품 기본값·기존 서비스는 바꾸지 않는다. 본문·token ID·인증키·전체 설정·원시 오류는 관측 파일에 저장하지 않는다. 실제 호출은 최대1회·재시도0의 새 승인과 exclusive ledger 없이는 시작되지 않는다.

## 수치 해석

공식 llama.cpp b11908 소스에서 `/slots` 조회가 계산 중 queue yield에서 처리되는 것을 확인했지만, vendor 후보의 실제 응답 가용성은 아직 미검증이다. 카운터는 native 계산이 반환된 뒤 갱신될 수 있으므로 숫자가 그대로라는 사실만으로 CPU 계산 정지를 단정하지 않는다. `n_prompt_tokens`도 전체 입력 진행률의 분모가 아니다.

`is_processing`은 처리 중이라는 상태만 나타내며 현재 prefill/decode 단계를 직접 제공하지 않는다. 출력 카운터 관측·입력 처리 카운터 관측·미확인을 구분한다. `/props`에는 설정된 `n_threads`·`n_threads_batch`가 없어 이를 미확인으로 남긴다. OS 스레드 수와 CPU 코어 사용 상당값을 설정 스레드 수로 표현하지 않는다. page fault에는 soft fault가 포함돼 하드 페이징이나 메모리 병목의 인과 기여도를 직접 뜻하지 않는다.

고정 소스·필드 의미·Microsoft API 근거는 로컬 `progress-contract.md`와 `windows-resource-notes.md`, 독립 검토는 `review.md`에 기록한다. `/slots`가 잠든 모델을 깨울 수 있어 준비 단계에서는 호출하지 않는다. 새 승인을 받아 이미 시작한 소유 후보만 관측한다.

## 검증 중 수정한 결함

독립 검토에서 잘못된 수치·PID/생성 시각, raw JSON 오류의 본문 보존, 관측 종료 중 취소 누락, 요청 시간에 정리·검증 시간이 합산되는 결함을 재현하고 수정했다. 변경된 task ID가 과거 ID로 돌아와도 소유 요청으로 다시 귀속하지 않는다. 반복 취소 시 자원 수집 자식 프로세스 회수를 기다리고 원래 취소를 유지한다.

완료 응답과 별개로 관측 실패·sink 실패·후보 회수 실패를 기록하며, 정리 실패가 성공으로 바뀌지 않는다. 전송 예약 저장 중 오류도 사용1로 보수적으로 계산하고 동일 ledger의 재실행·자동 재전송을 차단한다.

최초 통합 검사에서는 Windows 공용 pytest 임시 디렉터리 접근 권한 때문에 setup9개가 실패했다. 기존 임시 디렉터리는 변경하지 않고 존재하지 않는 저장소 내 고유 경로를 확인해 최종 검사에 사용했다. 제한된 실행 환경의 Windows asyncio 초기화 지연은 실제 외부 호출을 mock한 검증만 호스트에서 실행해 구분한다.

승인된 Conda를 표준 활성화하고 `Resolve-ApprovedLocalPython`으로 확인한 뒤 root가 최종 전체 **330개를 3.16초에 통과**시켰다. 자체190개·독립140개이며 현재 Python의 Win32 읽기 smoke1개를 포함한다. 모델·DB·HTTP 전송은 mock이고 모델 적재·호출은0이다. 이전25개 파일의 정확한 파일 목록과 해시 보존 검사도 포함했다.

신규 폴더 전체의 기본 Ruff와 명시적 backend 설정 Ruff, 구현5파일 strict mypy가 통과했다. 최초 mypy는 저장소 소스 경로가 빠져 `import-untyped`1건이 발생했고 `MYPYPATH=backend/src`로 본래 소스를 명시한 최종 검사에서 통과했다. 코드 예외 처리나 타입 검사를 끄지 않았다. 독립 검토는 마지막 스타일·타입 변경까지 재확인했으며 `review.md` SHA256은 `aab505c5b06bf4b93c937e036da8479845fdb9d4c9391fe41cbe04aa49f071e5`다.

검증 명령의 핵심은 다음과 같다. 실제 호출이 없는 이 폴더의 테스트9개만 명시하며 공용 Temp 대신 신규 고유 `--basetemp`를 사용한다. 기본 수집은 `review_*.py`를 빠뜨리므로 독립 파일을 명시적으로 포함했다.

### CPU·메모리와 관측 한계

- 연속 유효 CPU 차분24구간·합계123.767초에서 가중평균5.986코어 상당값, 즉 논리10코어 기준59.860%였다. 구간별5.344~8.276코어이며 **전체360초 평균은 아니다**. 유효43표본의 PID219404와 생성 시각은 동일했다.
- 같은 PID/생성 시각의 첫·마지막 유효 자원 표본을 별도로 차분하면357.592초 동안 CPU 누적2,128.703초, 평균5.953코어 상당값(논리10코어 기준59.529%)이다. 이 값은 중간 표본 누락을 포함한 두 끝점 사이의 평균이며, 누락 구간의 순간 사용률이나 단계별 비중을 복원한 것은 아니다. root와 독립 담당이 각각 재계산했다.
