# 실제 Gemma 속도 재측정 — 2026-10-25

## 결과와 범위

실제 Gemma 생성은 승인한 최대4회 안에서4회 완료했다. 같은 공개 합성 질문의 최신2시도는
완료됐고 입력·출력·세부 연산의 저장과 현재 권한 상세 재조회를 확인했다. 그러나 **전체 응답
속도 개선은 확인되지 않았으며, 이번 환경에서는 이전보다 느렸다.** 정답0/2와 표본 P95
437.368초로 기존 품질·지연 기준도 통과하지 못했다. 품질 개선 보류와 후보 비승격을 유지한다.

관련 문제는 ISSUE-00038(근거 선택 비용·세부 시간 기록), 기존 품질 문제는 ISSUE-00005다.
앞선 [구현·합성 측정](2026-10-25-rag-selection-speed.md)과 이번 실제 측정을 구분한다.

사용자가 실제 재측정을 승인하고 본래 Chrome에서 로그인했다. 정상 평가가 요구하는 최소
2반복을 사용했으며, 별도 계정·DB·일반 큐 worker·외부 모델을 만들거나 실행하지 않았다.
새 제품 코드·프로파일·모델 설정·스키마·색인·설치·commit/push 변경은 없다.

## 측정 명령 중단과 정상 복구

첫 측정 명령은 Python 진단 출력을 `2>&1 | Tee-Object`로 받으면서 PowerShell
`ErrorActionPreference=Stop`을 사용했다. 일반 stderr도 `NativeCommandError`가 되어
wrapper와 실행 프로세스가 검색 준비 중 종료됐다. 이는 측정 명령 구성 오류다.
모델 없는 benign stderr 재현으로 확인했고, native 명령 구간만 Continue로 처리하되 실제
프로세스 exit code는 검사하도록 수정했다. 수정한 실행은 exit0으로 끝났다.

당시 trace/model span·generation audit0, 검색 단계 기록, 실행 프로세스 종료와 빈 Ollama 상태를
함께 확인했다. 이후 기존10분 lease 기준이 지나서 정상 `interrupt_stale`만 호출했다.
다른 실행0을 먼저 확인했고 일반 queue dispatch는 하지 않았다. 기존 DB trigger가 execution도
interrupted로 닫았다. 정상 로그인 UI의 실패 사례 재시도로 이전2attempt를 보존한 채
새 attempt_number2 두 건을 추가했다. DB 상태를 직접 고치거나 과거 결과를 덮어쓰지 않았다.

독립 최초24조건과 복구 후19조건, 과거 행 보존을 각각 확인하고 해당run만 실행했다.
최종 호출 수는 중단 이력까지 합쳐 저장된 모델4span이다. 공급자 요청 로그를 통한 별도
네트워크 전송 증명은 수행하지 않았다. 중단2건은 완료2건의 시간·품질 통계에 섞지 않는다.
