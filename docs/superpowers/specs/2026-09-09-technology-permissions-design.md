# 마스터·기술별 관리 권한

- 상태: 상세 설계·독립 보안 검토 후 사용자 구현 승인(2026-09-09).
- 목적: 마스터만 권한을 배정하고, 각 기술의 조회·설정·실행 권한을 독립적으로 관리한다.
- 로그아웃 UI는 기존 API를 사용하는 별도 소규모 구현이며 권한 관리 완료와 구별한다.

## 1. 호환성과 소유권

기존 저장 역할 `owner`는 마스터로 표시한다. 별도 `master` 저장값으로 일괄 치환하지 않는다.
`member`는 기본 기술 관리 권한이 없다. 기존 사용자를 이름/이메일로 찾아 자동 승격하지 않는다.
기술별 권한은 Platform Identity의 일반 권한 계약이 소유한다. Labs는 카탈로그와 검사 요구를
애플리케이션 조립 지점에 등록하며 Platform은 RAG 구현을 import하지 않는다.

## 2. 기술 권한과 데이터 권한

기술별 capability는 `view`, `configure`, `execute`다. `configure`와 `execute`는 각각
`view`를 전제로 하지만 서로를 포함하지 않는다. 화면에서 이를 명시하며 저장 시 서버가 검증한다.
기술별 접근 없음은 권한 행 부재/빈 집합으로 표현한다. 첫 실제 연결은 RAG이며 맵의 준비 공간은
아직 권한 부여 가능한 서비스로 노출하지 않는다. 새 Lab이 구현되면 같은 계약으로 추가한다.

마스터는 권한 배정/회수, 계정 활성 상태 및 마스터 역할 변경을 관리한다. 기술 담당자는 자신이나
타인의 권한을 바꿀 수 없다. 마스터라도 문서 열람·외부 전송·공개 승인 정책을 우회하지 않는다.
기술 권한과 Workspace membership, 문서 접근, 정확한 버전의 외부 전송 승인은 교집합으로 적용한다.

조회 응답은 표시용 모델명·버전·설정 요약과 권한 허용 실행 메타데이터로 제한한다.
비밀값·인증정보·실제 endpoint/reference·로컬 경로·타인의 문서/질문/응답은 조회권한만으로 노출하지 않는다.
전체 운영 로그·공개 승인·외부 전송 정책/승인·Codex 개인 계정 실행기 관리는 초기에는 마스터 전용이다.

## 3. 저장 및 경쟁 제어

- 사용자별 권한 revision과 `(user_id, technology_key)` 단위 grant를 관리한다.
  권한은 세 boolean과 view 전제 DB 제약을 갖는다. 마스터 승격 시 개별 grant는 감사 후 제거하며,
  이후 강등된 사용자는 권한 없음에서 다시 명시적으로 배정한다. 숨은 이전 권한이 부활하지 않는다.
- 활성 기술 카탈로그에 없는 key, 알 수 없는 capability와 잘못된 의존 관계는 거절한다.
- 변경은 대상 사용자의 expected revision을 요구한다. 충돌 시409와 다시 조회 안내를 반환한다.
- 행위자의 현재 활성 마스터 여부, 대상 상태, revision을 같은 변경 트랜잭션에서 재검사한다.
- 마스터 수에 영향을 주는 모든 변경/초기화는 동일한 DB 잠금 순서를 사용해 직렬화한다.
  설치 권한 상태 singleton 행을 먼저 FOR UPDATE로 잠그고 actor/target을 ID순으로 잠근다.
  권한 부여·회수도 같은 순서를 사용한다. 초기화 완료 여부를 보존해 마스터가 수동 손상으로
  사라져도 공개 setup이 다시 열리지 않게 한다. 기존 bootstrap도 이 계약으로 함께 이행한다.
  잠금 후 실제 활성 마스터 수를 다시 계산하며 마지막 활성 마스터의 강등·비활성화·삭제는 거절한다.
  migration은 기존 사용자 상태를 검사하며 불일치 상태를 자동 복구/활성화하지 않고 중단한다.
- 사용자 hard delete는 첫 범위에서 제공하지 않는다. 비활성화와 이력 보존을 사용한다.
- 권한 변경과 감사 행은 원자적으로 저장한다. 행위자/대상/기술/이전·이후 권한/revision/시간을
  기록하되 비밀값이나 문서 본문을 포함하지 않는다.
  감사 이력은 append-only이며 수정/삭제 API가 없다. 마스터만 페이지 단위로 조회한다.
  DB 관리자에 대한 위변조 방지를 보장한다는 의미는 아니다.

## 4. 권한 검사와 회수 의미

JWT의 사용자 식별자만 신뢰하고 매 요청 현재 활성 사용자와 서버 권한을 확인한다.
프론트 메뉴 숨김은 안내일 뿐 API 및 서비스 권한 검사를 대체하지 않는다.
조회/변경/실행 각각 다른 capability를 검사하며 기존 owner guard를 일괄 대체하지 않는다.
분류되지 않은 관리 경로는 기본 마스터 전용으로 남긴다.

회수 이후 시작된 요청은 최신 권한으로 거절한다. 변경 중 요청은 정의된 권한 잠금/검사 지점에서
순서를 정한다. 비동기 사용자 실행은 enqueue와 실제 실행 직전에 재검사하고, 회수 시 후속 실행을
차단한다. 이미 외부 서비스에 전송한 요청을 회수할 수 있다고 약속하지 않는다.
평가의 입력 재현 스냅샷과 실행 권한 gate는 분리한다. worker는 기존 계약대로 frozen membership·
문서·색인·구성 스냅샷을 재작성하지 않으며, 실행 허용 여부만 별도로 현재 활성 사용자와 기술
execute 권한으로 판단한다. 이 제어 gate 추가는 RAG 설계 §9의 worker 계약 변경이므로
해당 문서와 ADR을 구현 전에 함께 갱신하고, 기존 입력 재현성 회귀를 검증한다.
이 gate는 frozen 범위의 현재 Workspace 접근권한 상실도 중단 조건으로 검사한다.
현재 membership으로 입력을 다시 구성하거나 범위를 확대하지 않고, 고정된 필수 공간 중 하나라도
접근할 수 없으면 실행/재개를 거절한다. 이미 전송된 호출의 취소를 보장하지 않는 경계는 동일하다.
기존 ingestion 유지보수 등 시스템 작업은 사용자 수동 실행과 분리한다.
권한 회수와 외부 dispatch 사이의 판정은 짧은 인가 트랜잭션의 승인 시점을 기준으로 한다.
네트워크 중에는 DB 잠금을 유지하지 않으며 이미 승인되어 시작된 호출의 즉시 중단은 보장하지 않는다.
실행 중 작업/결과 조회도 행위자·공간 권한을 유지하며 execute를 잃어도 view가 남으면 허용된
메타데이터를 조회할 수 있다. 일반 RAG 검색 서비스 이용을 관리용 execute와 혼동하지 않는다.

## 5. 화면·API 방향

마스터 전용 `/admin/system/access`에서 기존 사용자 목록 → 사용자 상세 → 기술별 권한과
변경 이력을 보여준다. 수정 후 저장·취소를 제공하고 변경 전후와 영향 범위를 확인시킨다.
역할 변경/비활성화는 일반 기술 체크박스 저장과 분리된 명시적 확인을 요구한다.
마스터의 기술별 전체 관리 권한은 상속 표시로 보여주고 일반 grant로 편집하지 않는다.
마스터의 사용자 관리 조회는 비활성 사용자에게 저장된 권한도 표시한다. 계정 비활성으로
현재 사용할 수 없는 상태와 저장된 배정을 구분하며, 활성화 전에 잠재 권한을 확인할 수 있어야 한다.
자기 권한 조회는 활성 상태를 반영한 실제 권한만 반환한다. 감사는 실제 저장된 grant를 기록한다.

현재 사용자 응답에는 안전한 effective permissions를 제공한다. `/admin`의 고정 owner 판정을
기술별 페이지 guard와 마스터 전용 guard로 구분한다. 메뉴는 실제 허용된 경로만 노출하고,
관리자 기본 이동은 허용된 첫 기술 화면으로 계산해 RAG 모델 화면으로 무조건 보내지 않는다.
사용자 요청대로 위임 관리도 `/admin/rag/*`에 둔다. 부모 레이아웃의 owner 조건만 제거하지 않는다.
마스터 전용/기술별 route guard로 분리하고 모든 하위 페이지와 서버 fetch의 권한을 먼저 대조한다.
Publishing·시스템 런타임·권한 관리는 마스터 전용이다. 기술별 행위 scope는 첫 단계에서 RAG
전체가 아니라 기존 사용자가 소유하고 접근 가능한 구성/평가 자원이며 공유 전역 설정은 위임하지 않는다.
조회자는 입력 폼 대신 읽기 전용 상세를 보며, 설정 담당자의 실행 버튼은 execute가 없으면 제공하지 않는다.
기존 모델의 임의 config dictionary를 기술 조회 DTO로 그대로 재사용하지 않는다.
표시 허용 필드만 직렬화하는 DTO를 먼저 만들고 endpoint별 노출 검토를 통과한 뒤 개방한다.
권한 오류는401(미인증)/403(행위 거절) 및 기존 자원 존재 비노출404 계약을 구별한다.

사용자 가입/초대/메일 발송/비밀번호 재설정은 이 설계 첫 범위에 포함하지 않는다.
첫 UI는 기존 사용자만 관리하며 현재 한 명이면 마스터 본인과 보호 안내가 표시된다.
다중 사용자 provisioning은 별도 후속 승인 후 추가하며 테스트용 계정을 live DB에 만들지 않는다.

## 6. 단계와 수용 기준

초기 RAG 위임 행렬(관리용이며 일반 서비스 검색에는 추가 관리권한을 요구하지 않음):

| 영역 | 필요한 기술 권한 | 추가 제한 |
|---|---|---|
| 안전 모델명/버전·프로파일 요약 | view | 명시 DTO, 비밀/reference/임의 config 제외 |
| 본인 구성·평가 목록/상세 | view | 기존 자원 소유권·공간 접근 유지 |
| 본인 구성 생성·새 버전, 평가 품질 정책/통과 반영 | configure | 기존 exact 평가/소유권 유지, 공유 기본값 승격 제외 |
| 허용된 본인 평가 실행 | execute | frozen 입력과 별도 현재 권한 gate, 외부 승인 유지 |
| 모델 등록·배포·health·공유 기본값·전역 도메인 관리 | 마스터 | 초기 위임 제외, 안전한 세분화 후 확장 |
| 개인정보/외부 전송 정책·승인·개인 Codex | 마스터 | 기존 API 아래 계층의 owner 제한도 유지 |

구현 계획에는 실제 등록 route+method와 legacy alias를 전수 대응한다. 모델/profile 일반 GET의
기존 arbitrary config 노출도 같은 안전 DTO 정책으로 정리하되 기존 소비자의 필요 필드를 대조한다.
일반 대화/검색·RAG 원문 근거는 기존 로그인/문서/정책 권한을 유지하며 관리 execute/view와 별개다.

1. 권한 데이터/카탈로그/감사·revision·마스터 보호와 서버 검사. 기존 owner 호환 및 거절 테스트.
2. 마스터 사용자 권한 화면과 capability 기반 메뉴/페이지 guard. 기존 사용자만 관리.
3. RAG의 안전한 조회·설정·실행 경로를 명시 목록으로 연결. 비밀·자료·외부 승인 경로 분리.
4. 격리 DB에서 마스터 경쟁 강등, stale 저장, inactive 사용자, grant 회수, 교차 기술/공간 거절,
   직접 API 우회, 큐 실행 전 회수 및 감사 원자성 검증. 로그인/로그아웃 회귀·타입·린트·독립 검토.
   revision 누락 거절/충돌409, 잠금 후 fresh actor 조회, 회수 후 재개/다음 batch 차단,
   frozen 입력 hash 불변과 별도 membership 중단 gate도 검증한다.

실제 사용자 권한 부여/회수, 계정 변경, 운영 migration과 외부 모델 실행은 코드 검증과 구별하여
명시 승인 후 수행한다. ADR와 전체 시스템 설계의 기존 owner-only 설명은 구현 전에 함께 갱신한다.
