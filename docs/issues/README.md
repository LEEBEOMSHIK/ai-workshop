# 문제 이력

[관리자 문제·개선 이력](http://127.0.0.1:5173/admin/system/issues)의 **DB가 운영 정본**이다. [issues.json](issues.json)은 최초 이관한 8개 문제의 보존 자료이며 이후 변경을 자동 반영하지 않는다. WORKBOARD는 현재 작업과 순서를, worklogs는 상세 실행 근거를 기록한다. 문제 ID로 두 기록을 연결하며 최근 완료 목록에서 빠져도 이력을 삭제하지 않는다.

관리자 **문제·개선 이력**(`/admin/system/issues`)에서 검색, 상태·한글 카테고리 필터와 문제별 날짜순 이력을 조회한다. **이력 관리**에서 카테고리 추가·이름/정렬/사용 여부 수정, 문제 등록·편집, 진행 이력 추가, 문서 등록·새 버전·연결/해제를 수행한다. 검증 기록과 남은 작업을 분리해 유지한다.

카테고리는 **상위 기술·공통 영역 → 하위 세부 기능**의 2단계다. 현재 RAG 아래 6개, 공통 플랫폼 아래 3개 하위(요청 전송·로컬 환경·문제 이력)가 있다. 문제는 하위에 배정하며 상위만 검색하면 하위 전체를 조회한다. 상위를 바꾸면 하위 선택이 초기화된다. 3단계·순환·관계를 깨는 상하위 전환은 차단한다. 비활성 분류도 기존 문제에서는 보존한다.

문제 번호는 카테고리와 별개인 **`ISSUE-00001` 형식의 전역 자동 번호**다. 등록 시 서버가 발급하며 분류를 옮겨도 유지한다. 기존 `RAG-...` 번호는 이전 번호로 검색하거나 상세 링크를 열 수 있다. 내부 UUID와 문서·사건 연결은 바뀌지 않는다. 아래 최초 이관 목록과 과거 문서에 있는 번호는 당시 기록이다.

백엔드가 마스터 권한을 확인한 뒤 DB를 읽는다. 관련 문서는 정확한 문서 ID·버전으로 연결하며 새 버전을 등록해도 이전 연결의 본문은 바뀌지 않는다. 파일 경로는 출처 표시일 뿐 런타임 파일 조회에 사용하지 않는다. 공개 앱에는 API를 등록하지 않으며 내부 파일을 정적 공개 경로로 복사하지 않는다. 배포 시 저장소 Markdown 체크아웃 없이 조회할 수 있다.

기존 JSON/Markdown 이관은 최초에 명시적으로 실행했다. 같은 입력 재실행은 무변경, 변경된 입력 재수입은 충돌로 차단한다. 이후 변경은 인증된 관리 API 또는 화면을 사용한다. 접근할 수 없으면 DB 반영 미완료를 기록하고 JSON 편집만으로 반영됐다고 보고하지 않는다. 적용·실행 절차는 [로컬 개발 실행서](../runbooks/local-development.md#문제개선-이력-db-관리)를 따른다.

## 기록 규칙

- 같은 증상의 후속 작업은 기존 ID에 날짜별 진행 이력을 추가한다. 다른 원인이면 새 ID로 분리하고 관련 ID를 남긴다.
- 발견, 원인 확인, 수정, 검증, 재발 때 갱신한다. 원인을 확인하지 못했으면 추정 또는 미확인이라고 쓴다.
- 구현 완료와 본래 환경에서의 확인을 구분한다. 자동 테스트만으로 실제 업로드·화면·답변 품질을 확인했다고 쓰지 않는다.
- remaining에 남은 검증과 제한을 남긴다. 후속 수정으로 설명이 바뀌면 이전 history를 지우지 않는다.
- 관련 문서는 DB 문서 ID·버전으로 연결하고 출처 경로와 실제 커밋을 별도로 남긴다. 문서가 이동하거나 새 버전이 생겨도 과거 연결은 자동 교체하지 않는다.
- 비공개 원문, 사용자 질문 본문, 계정 식별자, 비밀값, 원시 로그는 저장하지 않는다. 상세 근거를 연결하되 이 데이터만으로 공개해도 된다고 간주하지 않는다.
- 이번 초기 목록은 2026-09-20~27 기록을 소급 정리한 것이다. 과거 모든 결함을 빠짐없이 수집했다는 뜻은 아니다.

## 상태와 최초 이관 데이터 필드

| 값 | 의미 |
| --- | --- |
| open | 미해결. 설계 또는 구현이 남음 |
| implemented | 수정은 구현했으나 명시한 실제 환경·화면·품질 검증이 남음 |
| verified | 해당 문제의 명시된 범위에서 수정과 검증 근거가 있음. 전체 제품 검증이나 영구 무결함을 뜻하지 않음 |

최상위 schema_version은 데이터 계약 버전, updated_at은 마지막 갱신일, visibility는 내부용 구분이다.
각 항목은 id, title, area, status, symptom, cause, resolution, verification, remaining, evidence, commits, history를 갖는다.
verification은 수행한 확인만, remaining은 미완료 사항을 담는다. history는 날짜와 사건을 오름차순으로 보존한다.
검증된 문제가 재발하면 status를 open으로 바꾸고 새 발견을 추가한다. 메뉴는 status만으로 남은 검증을 숨기지 않는다.

JSON 파싱, ID 유일성, 필수 필드, 상태 값, 참조 파일과 커밋 존재를 변경 때 확인한다.
