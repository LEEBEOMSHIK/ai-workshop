# RAG 질문별 실행 모니터링과 생성형 평가 경로 정렬

- 상태: 2026-09-27 사용자 승인. 구현 계획 작성 단계이며 제품 코드·DB 변경은 아직 적용하지 않음.
- 기준: 2026-09-27, 코드 `9e2f654`.
- 요청: 다음 생성형 RAG 개선을 진행하고, 질문에 대한 RAG 결과물을 모니터링할 메뉴를 제공한다.
- 선행 근거: [단계별 품질·지연 진단](../../worklogs/2026-09-27-rag-stage-quality-repair.md).

## 1. 사용자에게 제공할 결과

관리자 → RAG 관리 → **실행 모니터링**에서 질문 하나의 입력 범위, 검색 후보, 근거 선택·탈락 사유, 생성 답변·인용, 실패 단계, 소요 시간, 실행 구성을 확인한다. 실제 사용 결과와 평가 실행을 구분하고 서로 연결한다.

실행이 completed라고 정답으로 표시하지 않는다. 실행 상태, 답변 상태, 품질 검증 상태를 분리한다. 조회만으로 새 대화·실행·외부 모델 호출이 발생하지 않는다.

현재 사용자의 기존 계정·문서·대화를 보존한다. 별도 환경·DB·계정·관측 서버를 만들지 않는다. 우선 관리자 본인의 실행을 현재 문서 접근 권한 안에서 조회한다. 다른 사용자의 비공개 대화 열람 권한은 이번 메뉴 추가로 확대하지 않는다.

## 2. 현재 코드와 빈틈

- `conversations/models.py`: turn에 질문, request, response, error_code, 상태가 존재한다. 실패 시 response가 없으므로 응답 기반 진단만으로 실패 지점을 복원할 수 없다.
- `search/service.py`, `search/diagnostics.py`: 검색·선택·생성 시간이 있으나 일부는 정상 반환과 include_diagnostics에 의존한다. 인용 검증은 생성 처리에 포함돼 있다.
- `generation/audit_models.py`: 구성·모델·사용량·정책·correlation_id를 기록한다. turn과의 확정적인 실행 FK는 없다.
- `shared/request_context.py`: correlation ID는 외부 헤더에서 올 수 있다. 실행의 고유 식별자나 권한 조인 키로 사용할 수 없다.
- `conversations/access.py`, `service.py`: 저장된 결과의 현재 접근 권한과 이전 대화 의존성을 재검증한다. 기존 조회는 대화 소유자 전제이므로 관리자 전체 조회에 그대로 전용하지 않는다.
- `evaluation/tasks.py`: frozen 검색과 추출형 EvidenceSelector를 실행한다. 실제 대화의 문맥 예산·생성·인용 검증은 실행하지 않는다.
- 기존 [문맥 근거 설계](2026-09-21-contextual-rag-evidence-design.md)는 진단 상세의 별도 DB 자동 저장을 금지한다. 이번 제안은 본문 없는 제한된 실행 메타데이터를 영속화하는 계약 변경이다. 승인 전에는 기존 금지 규칙을 유지하며 구현 전에 정본과 ADR을 함께 갱신한다.

## 3. 대안과 선택

1. 기존 response JSON만 모아 조회: 빠르지만 실패 전 단계와 누락된 실행 정보를 제공할 수 없다. 과거 데이터의 호환 조회에만 사용한다.
2. **권장: 기존 대화 저장소 + RAG 전용 실행 기록 + 공통 처리 경로.** 본문을 중복 저장하지 않고 실행 메타데이터를 보강한다. 모니터링과 평가가 같은 단계 결과를 사용한다.
3. 외부 관측 제품·별도 저장소: 현재 요구에 비해 운영 환경과 데이터 사본이 늘어난다. 이번 범위에 포함하지 않는다.

## 4. 메뉴와 화면

경로는 `/admin/rag/executions`, 상세는 `/admin/rag/executions/[executionId]`로 둔다. 기존 공통 탐색과 RAG 관리 그룹에 하나의 메뉴를 추가한다.

새 실행 ID가 없는 과거 turn은 `/admin/rag/executions/legacy/[turnId]`에서 읽는다. 목록 DTO에 신규 실행/기존 turn 구분을 명시하고, 새 실행으로 연결된 turn은 중복 표시하지 않는다. 과거 turn을 위해 가짜 실행 행을 만들지 않는다.

### 목록

- 기본은 최신 질문순. 기간, 도메인, 실제 사용/평가, 실행 상태, 답변 상태, 실패 단계, 구성 버전으로 필터링한다.
- 질문 요약, 요청 시각, 상태, 문서 수, 전체 시간, 연결된 대화/평가를 표시한다. 본문 접근 불가 시 질문 요약·문서명도 노출하지 않는다.
- 질문 검색어를 URL·접근 로그에 남기지 않도록 검색 본문을 받는 조회 API를 사용한다.
- 집계는 동일한 권한·필터 범위의 실행 수, 오류·근거 부족 건수, 시간 중앙값/p95다. 시간 누락 건수와 집계 대상을 명시한다. 현재 페이지의 건수를 전체 통계로 표시하지 않는다.
- 정답률은 정답표 또는 검토 결과가 있는 실행에만 제공한다. 답변 생성률을 정답률로 표시하지 않는다.

### 질문 상세

상단에는 질문·답변·세 가지 상태와 가장 직접적인 실패 사유를 둔다. 아래는 단계 흐름과 다음 상세 탭으로 구성한다.

| 영역 | 내용 |
|---|---|
| 처리 단계 | 요청/권한 확인 → 이전 대화 준비 → 질문 문맥화 → 검색 → 근거 선택 → 생성 → 인용 검증 → 결과 저장 |
| 검색·근거 | 문서 버전·페이지, BM25/dense/RRF 순위·원점수, 문맥 cosine·키워드 충족률, 선택 여부·탈락 사유 |
| 입력 예산 | 적용한 그룹·단위·문자 제한, 실제 선택량, 초과로 제외된 문맥, 측정된 직렬화 크기 |
| 생성·인용 | 최종 답변, 사용 근거, 인용 검증 결과, 근거 부족의 발생 위치, 원문 열기 |
| 실행 구성 | 색인·검색·생성·정책의 정확한 버전, 요청/관측 모델 구분, 공급자가 보고한 사용량 |
| 평가 | 연결 평가 사례, 정답 근거 전달 여부, 검증 항목별 결과·미검증 이유 |

단계 상태는 대기/진행/완료/실패/생략/미기록을 구분한다. 누락 시간을 0초로 표시하지 않는다. 파싱·색인은 질문마다 실행되는 단계가 아니므로 문서의 ingestion 준비 이력으로 별도 연결한다.

`SearchDiagnostics`, `EvidencePanel`, 모델 식별 표시와 원문 뷰어를 재사용한다. 대화 답변에도 해당 실행 상세로 이동하는 링크를 제공하되 관리자 메뉴 권한이 있는 사용자에게만 노출한다.

공통 표시 부분만 추출하며 대화용 컴포넌트의 소유권·질문 입력·전송 동작을 관리자 화면으로 복제하지 않는다. 원문 대화상자는 포커스 이동·닫기·복귀를 지원한다. 평가 연결은 구성 화면의 비교 탭에 정확한 run/case를 여는 deep-link를 마련하고 해시로 유사 질문을 추정 연결하지 않는다. URL에는 민감한 질문 검색어를 넣지 않는다.

모바일에서는 필터를 접고 실행 목록을 카드로 표시한다. 단계는 세로 흐름, 상세는 한 영역씩 열도록 구성해 넓은 표의 가로 스크롤에 의존하지 않는다.

## 5. 실행 기록과 저장 경계

RAG 안에 실행 기록 서비스를 두고 Platform은 해당 구현에 의존하지 않는다. UI·handler는 상태 판정과 권한 규칙을 소유하지 않는다.

API는 관리자 실행 목록의 `POST /api/v1/admin/rag/executions/search`, 실행 상세의 `GET /api/v1/admin/rag/executions/{execution_id}`, 과거 turn 상세의 `GET /api/v1/admin/rag/executions/legacy/{turn_id}`로 나눈다. 목록은 안정적인 시각/ID 정렬과 cursor를 사용한다. 관리자/실제 소유자·원문 권한 조건은 서비스와 repository에서 공통 적용한다. 프론트에서 모든 대화를 순회하는 방식은 사용하지 않는다.

- 서버가 발급하는 execution_id를 사용한다. 실제 대화는 turn, 평가는 case attempt와 명시적으로 연결한다. 같은 요청 ID의 멱등 재전송은 기존 실행을 조회한다.
- 실행 종류, actor, 정확한 구성 버전, 시작/종료, 실행 상태, 답변 상태, 안전한 오류 코드, 관측 정보 완전성을 기록한다.
- 단계별 시작/종료/실측 시간, 상태, 안전한 사유 코드를 기록한다. 재시도는 새 attempt로 연결하며 이전 실패를 덮어쓰지 않는다.
- 검색 후보·선택 기록은 권한 내 반환된 후보에 한해 원문 ID·버전·위치 참조와 점수·사유를 기록한다. 본문, 프롬프트 전체, 공급자 원문 오류, 모델 내부 추론은 실행 메타데이터에 복사하지 않는다.
- 질문·답변은 기존 대화 저장소, 평가 입력·결과는 승인된 비공개 평가 스냅샷을 정본으로 참조한다.
- 공급자 감사 기록에 nullable 실행 참조를 추가해 신규 실행부터 정확히 연결한다. 과거 correlation ID나 발생 시각으로 연결 관계를 추측하지 않는다.
- 검색 진단 표시를 꺼도 단계·건수·선택 사유의 기본 기록은 남긴다. 진단을 위해 같은 원문을 추가 임베딩하지 않고 이미 계산된 점수를 사용한다.
- 후보 기록 크기는 검색 top_k와 명명된 정책 한도로 제한한다. 잘렸다면 전체 수·저장 수·truncated 상태를 표시하고 전부 기록된 것처럼 보이지 않는다.

단계 기록은 짧은 트랜잭션으로 저장하고 모델 호출 중 DB 잠금을 유지하지 않는다. 종료 시 turn/attempt 상태와 실행 종료 상태의 정합성을 보장한다. 취소·삭제 뒤 늦게 끝난 작업이 실행을 성공으로 바꾸거나 본문을 되살리지 못하도록 기존 종료 확인과 상태 조건을 재사용한다.

관측 저장 실패가 원래 처리 오류를 덮어쓰면 안 된다. 저장 가능한 응답에는 관측 누락 상태를 남기고, 안전한 운영 로그에는 서버 실행 ID·단계·오류 코드만 기록한다. DB 전체 장애 등 기록 자체가 불가능한 경우 상세 단계가 있다고 주장하지 않는다.

## 6. 권한·삭제·호환

- 목록, 상세, 검색, 집계 모두 서버에서 소유권과 현재 접근 권한을 먼저 적용한다. 페이징 후에만 권한 필터를 적용하지 않는다.
- 저장된 원문·이전 대화 의존성 접근을 재검증한다. 관리자 메뉴 권한만으로 개인 공간·다른 사용자의 대화 본문을 열 수 없다.
- 원문 열기는 현재 원문 API를 사용한다. 삭제·권한 회수된 자료의 저장된 excerpt를 우회 출력하지 않는다.
- 모니터링 전용 DTO를 사용하고 기존 response JSON을 그대로 반환하지 않는다. validation_token·인증 정보·프롬프트 원문은 제외하며 응답은 `Cache-Control: no-store`로 제공한다. 후보 제목·절 경로·식별자도 원문과 같은 권한 경계로 취급한다.
- 대화 삭제의 질문/request/response 비우기 계약을 유지한다. 기록에 별도 본문 사본이 없어야 하며 삭제된 대화 내용은 모니터링으로 복원할 수 없다.
- 감사 기록 보존과 대화 삭제는 기존 계약대로 분리한다. 이번 작업에서 자동 영구 삭제나 새 보존 기한을 임의 도입하지 않는다.
- 과거 대화는 기존 response에서 확인 가능한 결과만 제공한다. 새 실행 링크·실패 단계가 없으면 `이전 기록 · 상세 단계 미기록`으로 표시한다. 재실행·LLM 호출·가짜 backfill은 하지 않는다.
- DB migration은 가산 방식으로 시작한다. 구버전 행에 nullable 연결을 허용하고 기존 서비스·문서·평가 스냅샷을 재작성하지 않는다.

## 7. 생성형 평가와 실제 실행의 정렬

검색→문맥 선택→생성→인용 검증을 재사용 가능한 RAG 실행 경로로 추출한다. 실제 대화는 현재 권한·활성 구성을, 평가는 불변 문서·구성 스냅샷을 사용하되 핵심 알고리즘과 단계 관측 형식을 공유한다.

평가 스냅샷의 재현성과 외부 전송 권한은 별개다. 외부 생성 직전에는 승인된 분류·정확한 문서 revision·현재 전송 정책을 재검증한다. 승인이 철회되면 실행을 중단하며 frozen ACL을 외부 전송 허가로 사용하지 않는다. 기존 BM25/추출형 평가와 그 지표 버전은 유지한다.

생성형 평가에는 새 명시적 평가 종류와 지표 버전을 사용한다. 검색 도달, 필수 근거 전달, 생성 성공, 인용 무결성, 정답 판단, 음성 질문의 거절, 단계 시간과 실행 환경을 분리한다. 생성 성공·인용 ID 유효만으로 의미적 정답을 자동 판정하지 않는다. 정답 판단은 버전된 정답 규칙 또는 명시적인 검토 결과와 근거를 요구한다.

기존 PostgreSQL 검증 기반 승격 게이트와 정합성을 맞춰 원시 관측·정답 규칙·판정 출처를 검증한다. 기존 추출형 평가 통과를 생성형 평가 통과로 복사하지 않는다. 평가 실행 자체와 일반 기본값/도메인 승격을 분리한다.

외부 생성은 승인된 평가 실행에서만 발생하며, 모니터링 열기·새로고침·필터·원문 확인으로 발생하지 않는다. 평가 재시도도 기존 결과를 숨기거나 모델을 조용히 교체하지 않는다.

## 8. 구현 단위와 검증 기준

1. 실행 식별자·단계 관측·읽기 API·기존 대화 호환을 마련한다.
2. 관리자 목록/상세와 대화 링크를 연결해 정상·근거 부족·기술 실패·취소를 확인한다.
3. 평가가 공통 처리 경로와 같은 관측 형식을 사용하도록 연결하고 생성형 판정·승격 계약을 추가한다.
4. 기존 합성 PDF 3종·16문항과 별도 검증 질문으로 후보 구성을 평가하고, 검증된 버전만 정상 절차로 기존 도메인에 연결한다.

단계마다 독립 검토·관련 pytest/타입/린트·프론트 테스트를 수행한다. 구현과 독립 보안·통합 검증 책임은 분리한다.

- 검색 성공 뒤 threshold/budget 탈락과 생성 후 근거 부족을 다른 단계·사유로 표시한다.
- provider 실패·인용 오류·취소·중단은 마지막 확인 단계와 후속 미실행 단계를 구분한다.
- 재전송·동시 취소·삭제 경쟁에서 중복 모델 호출과 실행 상태 역전이 없어야 한다.
- 권한 회수·개인 공간·다른 사용자·이전 대화 의존성·삭제 후 조회에서 본문과 식별자가 누출되지 않아야 한다.
- 기존 기록은 읽을 수 있는 범위만 정확히 표시하고 missing 데이터를 추정하지 않는다.
- 관리자 진입·모바일 탐색·목록 필터·실행 상세·원문·새로고침 복원을 기존 환경에서 확인한다.
- 같은 문서/구성/질문에서 실제 대화와 생성형 평가의 근거 선택·인용 검증 경로가 일치해야 한다.
- 모니터링 전후 지연·DB 기록 크기를 측정하며 선택 결과가 표시 유무에 따라 바뀌지 않아야 한다.

## 9. 설계 검토와 다음 인계

사용자가 이 설계를 승인했다. 구현 계획에서 migration 제약·API DTO·단계 상태 전이·트랜잭션·테스트 명령을 구체화한다. 구현 전에 RAG 설계와 관련 ADR에 승인된 경계를 반영한다.

독립 보안 검토에서 확인한 관리자/소유자 권한 혼동, 삭제 본문 복구, 외부 correlation ID 오용 위험을 5·6절에 반영했다. 프론트 조사에서 확인한 목록 API 부재, 실패 turn 진단 부재, 탈락 근거 위치 부재, 평가 deep-link 부재를 4·5·7절에 반영했다. 이 검토는 설계 조사이며 제품 구현·브라우저 테스트 완료를 뜻하지 않는다.
