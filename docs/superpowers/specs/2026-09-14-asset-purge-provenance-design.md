# 휴지통 2C: 삭제 대상 추적과 최소 삭제 증명

- 상태: 상세안 제안, 사용자 확인 전. 구현·실사용 DB 조사·삭제는 하지 않았다.
- 검토: DBA 소스 조사와 독립 프라이버시 검토 완료. 공유 잔존·증명 결합·백업 복구 조건을 보완해 재검토 통과했다.
- 상위 승인안: [휴지통·복원·영구 삭제](2026-09-13-asset-trash-purge-design.md).
- 선행 완료: [2B 저장 기반](2026-09-14-asset-trash-persistence-design.md).
- 목적: 원본 행을 지운 뒤 복제본 위치를 잃거나, 일부 정리만으로 전체 삭제 완료를 표시하지 않게 한다.

## 1. 조사 결과와 선택

현재 `platform/assets/purge_contracts.py`의 `assess_purge`는 목록 완전성·작성자 중단·참조 해소·참여자별 잔존 검증을 요구한다.
2B job/outbox는 요청과 전달 상태를 저장하지만, 실제 대상 목록과 검증 결과를 특정 삭제 실행에 묶는 저장 계약은 아직 없다.
RAG 평가의 `fixture_bytes`·`document_snapshot_bytes`와 JSON, Learning revision의 `draft`, Publishing revision의 `snapshot`·command의 `export_payload`에는 FK로 모두 추적되지 않는 복제가 있을 수 있다.
DBA 소스 조사에서 생성 감사의 `evidence_ids` 배열과 별도 공개 SQLite payload도 확인했다. 현재 공통 출처 대장·영속 receipt·삭제 증명 저장소는 없다.

- FK만 따라 삭제: 단순하지만 JSON·바이트·공개 전송·임시 파일을 놓친다. 채택하지 않는다.
- 삭제 시 문자열/파일 전체 검색: 출처·소유권 증명이 안 되고 동명이인/동일 바이트의 독립 문서를 오인할 수 있다. 완료 근거로 채택하지 않는다.
- **구조화된 출처 관계 + 모듈별 목록 수집 + 독립 잔존 확인**을 채택하는 안이다. 과거 자료의 관계가 불명확하면 차단한다.

## 2. 모듈 경계

Platform Assets는 원본 식별자, 삭제 실행의 목록 버전과 최소 증명을 소유한다.
RAG·Learning·Publishing 등 소유 모듈은 자신이 만든 복제·파생 자원의 관계를 등록하고 자기 자원의 식별자를 해석한다.
조립 계층에서 참여자를 연결한다. Platform은 Labs 구현, 임의 SQL, ES 색인명 또는 물리 파일 경로를 업무 규칙에 고정하지 않는다.
정리 작업은 결정론적인 서비스 계약이며 LLM을 사용하지 않는다.
등록된 참여자 목록을 기준으로 검사한다. 응답한 참여자만 모아 필요한 참여자 목록으로 삼지 않는다.
미지원·누락·오류를 빈 목록 또는 성공으로 바꾸지 않는다.

## 3. 출처와 자원 식별

출처는 workspace/document/asset version의 정확한 조합으로 식별한다. 파일명이나 SHA-256만으로 소유권을 판정하지 않는다.
자원은 참여자 키, 자원 종류, 불투명 자원 ID 및 자원 revision으로 식별한다. 같은 자원에 여러 출처를 연결할 수 있다.
관계 유형은 원문 복제·파생 산출물·독립 작성물의 참조를 구분한다. 독립 연구 글은 링크 하나만으로 삭제 대상이 되지 않는다.
공유 여부는 단순 boolean이 아니라 현재 유효한 참조와 소유 모듈의 확인으로 판단한다.
대상 문서에서 파생된 복제본과, 동일 bytes를 독립적으로 소유하는 다른 문서를 구분한다. 다른 문서의 정당한 참조가 남은 공유 물리 객체는 상위 계약대로 보존한다.
본문이 섞인 공유 스냅샷은 일부 제거 가능성 및 별도 소유권을 확인한다. 분리가 불가능하면 영향 승인 전 차단한다.
새 복제본의 생성과 출처 등록은 같은 DB 트랜잭션에 둔다. 파일·외부 저장소는 쓰기 전 등록과 준비 상태 확인 계약이 필요하다.
출처 등록만으로 기존 worker의 재생성 차단을 달성했다고 보지 않는다. writer gate 연결은 후속 활성화 조건이다.
공통 추적 데이터에는 본문·질의·파일명·경로·원본 해시를 복제하지 않는다. 정확한 물리 locator는 소유 모듈이 제한된 실행 경계에서 해석한다.
locator 해석에 필요한 작업 메타데이터는 최종 잔존 확인 전 원본 CASCADE로 없어지지 않게 한다. 검증 뒤 상세 작업 정보와 함께 정리한다.

## 4. 삭제 목록과 완전성

삭제 실행마다 job ID와 연결된 목록 버전을 만든다. 목록에는 배치 대상 문서/폴더, 모든 버전 및 각 문서의 lifecycle generation을 고정한다.
목록 버전은 대상 집합·참여자 계약 버전·자원 revision이 달라지면 증가한다. 과거 목록의 검증 결과를 새 목록에 재사용하지 않는다.
배치 대상 집합은 2B batch ID만으로 추정하지 않는다. 후속 휴지통 명령이 확정한 구성과 현재 자료를 대조한다.
각 참여자의 전체 조회 완료 및 continuation 소진을 확인한다. 페이지 일부만 읽은 결과는 incomplete다.
기존 자료는 모듈별 결정론적 해석기로 출처를 확인한다. 불명확한 과거 JSON/바이트 참조를 없다고 간주하지 않는다.
dry-run 결과는 안전 코드·건수·불투명 ID만 반환한다. 실제 기존 DB dry-run과 backfill 적용은 별도 대상 확인 후 수행한다.
등록 누락, 지원하지 않는 자료 형식 또는 공유 소유권 미확정은 `inventory_incomplete` 또는 명명된 차단 이유로 남긴다.
이번 단계에서 기존 데이터 전체를 추적 완료로 일괄 표시하지 않는다.

## 5. 검증 결과의 결합

참여자 검증 결과는 job ID·목록 버전·참여자 키·실행 시도 및 검증 시각에 묶는다.
삭제 요청 성공과 실제 부재 확인은 다르다. 성공 응답만으로 `verified=true`를 만들지 않는다.
정확한 대상의 부재, 공유 자원 보존, 남은 대상 수를 검증한 결과만 기존 `CleanupReceipt`로 변환한다.
`retained_shared`는 대상 문서의 소유 복제 내용이 남았다는 사실을 우회하는 수단이 아니다. 대상 전용 복제·혼합 스냅샷의 대상 구간·참조·재생성 경로가 해소돼야 한다.
혼합 스냅샷의 대상 구간을 제거할 수 없으면 승인된 전체 정리 전 차단한다. 다른 문서의 독립 원본 또는 정당한 공유 참조 때문에 같은 bytes가 남는 경우와 구별하고 보존 결과를 명시한다.
다른 job·오래된 목록·다른 generation·중복 참여자의 결과는 거부한다. 누락된 참여자를 자동 성공 처리하지 않는다.
확정된 목록 밖의 자원이 발견되면 목록을 갱신하고 검증을 다시 수행한다.
작성자 중단과 참조 해소는 서버가 확인한 증거에 한정한다. UI나 일반 API가 보낸 boolean을 완료 근거로 신뢰하지 않는다.
`assess_purge`는 최종 순수 판정기로 유지하며, 영속 실행과의 결합 검증을 앞단 계약에서 수행한다.
2C 저장 기반만으로 실제 `purged` 전이를 개방하지 않는다. 삭제 실행기·현재 권한·writer gate·참조 해소가 연결된 후속 명령만 완료를 확정한다.

## 6. 최소 삭제 증명과 데이터 수명

진행 중에는 재시도에 필요한 정확한 대상 관계와 검증 결과를 제한된 작업 저장소에 보관한다. 일반 로그·공개 API에는 상세 목록을 내보내지 않는다.
원본·파생물·복제본 잔존 검증이 끝난 뒤, 후속 완료 트랜잭션은 최소 증명과 job 완료 시각을 저장하고 불필요한 상세 목록·locator·문서 해시를 정리한다.
증명은 불투명 원본/버전 ID, 작업·공간·행위자·정책 식별자, 완료 시각, 참여자별 처리 건수와 결과만 보유한다. 원본 행 CASCADE로 사라지지 않는다.
해당 삭제 generation·목록 버전·참여자 계약 버전도 보존하고, 불투명 대상 집합과 검증 결과를 정규화한 무결성 값으로 결합한다. 원본 내용의 해시는 포함하지 않는다.
원본 ID 목록은 과거 백업 복구 시 재노출을 막기 위한 용도로만 사용한다. 같은 bytes를 새 문서 ID로 업로드한 항목을 차단하지 않는다.
공유 자원이 남으면 대상 문서의 복제 내용과 참조가 해소됐는지 별도로 확인한다. 다른 문서의 유효 자원은 삭제하지 않는다.
최소 증명의 보관 종료도 명시 정책으로 관리하며 임의 일수를 코드에 넣지 않는다. 관련 백업의 복원 가능 기간과 재삭제 절차가 충족되기 전에는 자동 제거하지 않는다.
행위자 등 감사 식별자는 목적별 보존 기한을 따로 두고 불필요해지면 분리 정리한다. 재노출 방지에 필요한 최소 대상 식별 정보의 보관과 혼동하지 않는다.
백업 복구 시에는 복구 대상 DB의 rollback 경계 밖에서 보존된 권위 있는 삭제 원장을 공급받아야 한다. 원장의 무결성·발행 주체·연속성·최신성 확인이 안 되면 서비스 재공개를 차단한다.
복원된 원본의 generation이 삭제 증명보다 낮다는 이유로 증명을 무시하지 않는다. 같은 원본 ID의 과거 백업 자료에도 최신 권위 원장의 삭제 결정을 적용한다. 원장보다 오래되거나 결합이 맞지 않는 증명 사본은 신뢰하지 않는다.
외부 보존 원장과 복구 절차 구현은 후속 배포 게이트다. 2C의 단일 DB 증명 저장만으로 백업 복구 안전성이 완성됐다고 보고하지 않으며, 이번 설계가 새 인프라 생성 승인은 아니다.
앱 온라인 데이터 완료, 백업 보존 대기, 외부 사본 확인 필요를 별도로 기록한다. 외부 상태 미확인을 전체 사본 삭제 완료로 표시하지 않는다.
증명 테이블이 존재한다는 이유만으로 삭제가 검증됐다고 보지 않는다. 실제 완료 쓰기 경로는 후속 제한된 서비스 계약에 둔다.

## 7. 첫 구현 경계

첫 구현은 출처/자원 관계, 버전된 목록, 실행에 결합된 검증 결과, 본문 없는 증명의 공통 계약과 영속 기반이다.
모델과 repository는 `platform/assets` 아래 역할별 파일로 나누고 기존 job/outbox를 사용한다. 독립 범용 그래프 서비스나 새 인프라는 추가하지 않는다.
SQL FK·UNIQUE는 공간과 job/목록의 조합을 보장한다. 일반 문자열 resource ID의 의미·실제 소유권은 소유 모듈 검증을 거친다.
원본 삭제가 아직 필요한 목록을 CASCADE로 지우지 않게 한다. 상세 목록 정리는 최소 증명을 남기는 완료 명령과 결합한다.
정확한 필드·제약·migration 순서는 상세안 승인 후 구현 계획에서 고정하고 합성 PostgreSQL로 검증한다.
그다음 실제 모듈별 등록/목록 수집, 기존 자료 dry-run/backfill, 조회·검색·worker gate를 연결한다. 연결되지 않은 참여자가 있으면 삭제는 계속 차단된다.
이번에는 실제 삭제 실행기·불변 trigger 예외·정책 UI·전체 원본 정리·실사용 migration·서버 재시작을 포함하지 않는다.

## 8. 수용 기준

- 다른 공간/문서/버전 자원 등록, 다른 job 결과 소비, 오래된 목록 결과 및 중복 결과를 거부한다.
- 빈 목록, 미완성 페이지, 미지원 해석기, 과거 자료 출처 미확정은 완료 불가다.
- 모든 버전의 추적 및 여러 원본이 공유하는 자원의 보존을 합성 데이터로 검증한다.
- 원문 복제와 독립 작성물의 참조를 구별하고 혼합 스냅샷의 임의 삭제를 허용하지 않는다.
- 원본 행 삭제와 무관한 최소 증명 보존, 상세 목록의 불필요한 정보 제거 및 job 완료와의 원자성을 검증한다.
- 온라인 완료와 백업/외부 미확인을 구분하고 실제 writer/삭제 미연결 상태는 완료 판정을 만들지 않는다.
- migration의 기존 자료 보존·안전 downgrade, 타입·린트·권한 및 저장 계약 회귀를 검증한다.

## 9. 사용자 확인 사항

구조화된 출처 추적과 목록 버전에 묶인 검증을 채택하고, 출처를 완전하게 확인할 수 없는 기존 자료는 임의 정리하지 않는 방향을 제안한다.
상세 작업 정보는 정리 후 없애되, 백업 복원 시 삭제 자료의 재노출을 막는 본문 없는 최소 증명만 정책에 따라 유지한다.
