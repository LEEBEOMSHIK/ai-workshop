# Terra·Gemma 새 질문 비교 (2026-10-30)

사용자가 지정한 Terra(`gpt-6.1-terra`)와 기존 로컬 `gemma4:e2b-it-q4_K_M`를 새 공개 합성 질문으로 각각 두 번 실행했다. 기존 Luna 비교의 지급일 질문을 재사용하지 않았다. 자동 재시도는 0회이며 기존 모델·기본 구성·프롬프트·인용 검사·배포 설정을 유지했다. [계획](../superpowers/plans/2026-10-30-terra-gemma-new-question.md).

## 질문과 조건

> AM-SYN-101의 환매를 영업일 15:00까지 신청한 경우와 15:00이 지난 뒤 신청한 경우, 접수일과 적용 기준가격을 어떻게 정하나요? 정확한 날짜를 알려면 어떤 정보가 더 필요한가요?

- 기존 공개 합성 PDF의 같은 근거 28개와 순서, 시스템/사용자 메시지를 두 제공자에 동일하게 전달했다. 공개 fixture와 실제 SDK 입력을 대조하고 외부 전송 직전 현재 권한을 재검사했다.

- 실제 순서는 **Gemma 첫 → Gemma 반복 → Terra 첫 → Terra 반복**이다. 첫/반복은 실제 전송 순서다. DB의 사전 배정 repetition은 1→0 순서로 실행되어 화면의 회차 번호를 시간 순서로 사용하지 않았다.
- Gemma는 기존 비기본 직접 답변 후보의 실제 GenerativeWorkflow를 실행했다. 실행마다 answer_specialist 1개·LLM 호출 1개이며 위임은 0회다. Terra는 이 SDK 입력을 재사용하는 비교 전용 API 요청으로, 운영 기본값 승격이나 Terra SDK 전체 실행은 아니다.
- 첫 요청은 캐시와 장치를 강제로 초기화한 cold start가 아니다. 로컬의 다른 작업 부하는 완전히 통제하지 못했다. 새 질문으로 얻은 표본을 이전 질문과의 모델 단독 성능 비교로 해석하지 않는다.

## 답변·인용·최종 수용의 구분

| 검토 | Terra 첫/반복 | Gemma 첫/반복 |
| --- | --- | --- |
| JSON 형식 | 통과 / 통과 | 통과 / 통과 |
| 기존 자동 인용 검사 | 실패 / 실패 | 통과 / 통과 |
| 독립 원문 의미 검토 | 통과 / 통과 | 실패 / 실패 |
| 답변과 인용의 반복 일치 | 표현·인용 일부 다름, 의미 동일 | 완전히 동일 |
| 기존 제품 응답 수용 | 자동 검사 거절 / 거절 | 수용 / 수용 |
| 이번 비교의 종합 품질 판정 | 미통과 | 미통과 |

Terra는 마감 시각 포함, 당일/다음 영업일 접수, 두 조건 모두 접수일 T+2의 기준가격, 정확한 날짜 계산에 필요한 신청 날짜·시각과 영업일 달력을 설명했다. 원문 e5/e6의 T+N 정의, e9~e14의 표 관계, e25/e26의 달력·추정 금지 조건을 함께 적용했다. 신청 날짜가 필요하다는 것은 이 관계에 대한 논리적 해석이다.

다만 두 응답의 두 번째 주장에 있는 **“2영업일”**을 기존 인용 검사가 `exact_value_not_supported`로 거절했다. 검사기는 원문 `T+2`를 상대 오프셋으로 추출하고 “2영업일”을 별도의 기간 값으로 다룬다. `N영업일` 정의와 `T+2`의 결합을 검증하지 못한 것이며, 인용 개수 초과 문제가 아니다. 저장된 출력만 재생하여 이유를 확인했고 모델 재호출·답변 수정·검사 완화는 하지 않았다. 비교 화면의 Terra 답변은 **검사에서 거절된 실제 모델 출력**으로 읽어야 한다.

Gemma는 두 번 모두 다음과 같은 같은 오류를 냈다.

1. “접수일은 T”라고만 하고 마감 내 신청 영업일이 접수일이라는 설명이 불충분했다.
2. 원문 “마감 후 **신청일** 자체를 T로 세지 않는다”를 “**접수일** 자체를 T로 세지 않는다”로 바꿨다. T=접수일 정의와 모순이며 다음 영업일 접수 규칙도 누락했다.
3. 추가로 필요한 정보가 원문에 없다고 답했다. 인용한 e24는 제목일 뿐이며, e25/e26에 달력과 추가 정보 안내가 있다.

따라서 이번에도 속도와 의미 품질 차이는 관찰됐지만 **Terra가 현재 제품 검사까지 전부 통과했다**고 결론내릴 수 없다. Gemma의 자동 인용 통과도 의미 정확도를 보장하지 않는다. 두 모델의 결함을 하나의 점수로 감추지 않는다.

## 사용량과 비용

Terra 합계 입력 5,494 + 출력 429 = **5,923토큰**, 캐시 읽기·쓰기·추론 토큰은 모두 0이다. 2026-10-30 확인한 [공식 API 단가](https://developers.openai.com/api/docs/pricing) 입력 100만 토큰당 USD 1.00, 출력 USD 5.00으로 **예상 합계 USD 0.007639**다. 추론 토큰을 출력 비용에 이중 가산하지 않았다.

두 요청의 보수적 사전 예약 합계 USD 0.033006은 이번 USD 0.05 상한 이하였다. 원장에 예약→전송 식별→응답 usage→비용 확정→품질 판정 순서로 기록했다. 실제 호출 2회, 재시도 0회, 미확인 사용량 0회로 닫았다. 관리 비용 API 키가 없어 실제 청구·크레딧 차감액과 대조하지 못했다. 계정 잔액이나 Work/Codex 크레딧을 요청별 API 비용으로 취급하지 않는다.

Gemma 합계 입력 7,356·출력 312토큰이다. OpenAI API 요금은 해당 없으며 장치·전력 비용은 미측정이다. 서로 다른 토크나이저의 토큰 수 차이를 근거량 차이로 해석하지 않는다.

## 사이트 저장과 기록 수용

[새 비교 결과](http://127.0.0.1:5173/admin/rag/comparisons/1b71146c-8169-43b4-ade4-7634444095d5)를 본래 로그인 계정에서 가져왔다. 관리자 왼쪽 **RAG 관리 → 모델 비교 결과**에서 연다. API 예상 비용과 실제 청구 미확인, 모델별 실제 후보 답변·원문 인용·수동 의미 판정·자동 인용 실패를 모두 보존한다. 첫 요청·반복 전환도 실제 화면에서 확인했다.

기존 DB에서 정확한 source key의 보고서가 1행이며 4응답·28근거·전체 payload와 canonical SHA가 검토 파일과 같은 것을 READ ONLY로 확인했다. canonical SHA는 `faa82cdcc9d244c0eaa9304c5ed5753483c006019782fdffe3f30053b8bda44b`다. 저장 후 기존 행 변경 0, 기존 설정/게이트/이전 결과 보존, 새 보고서 1행 추가를 확인했다. 이후 이슈 이력 쓰기는 이 데이터 보존 검사와 별도로 수행했다.

독립 최종 출처 검사에서 Windows CRLF 저장과 LF 해시 계산의 차이를 발견했다. 원시 모델 응답·원장·DB 보고서는 바꾸지 않고 생성된 출처 manifest 두 파일의 CRLF 원본을 백업한 뒤 LF로 정규화했다. 실제 파일 해시가 이미 저장된 보고서의 해시와 정확히 일치함을 재검증했다. 재발 방지를 위해 가져오기 파일 생성기의 쓰기와 해시 계산이 같은 UTF-8 바이트 함수를 사용하도록 보강했다. 실패 검사 61통과/1실패와 복구 후 62통과 증거를 모두 남겼다.
