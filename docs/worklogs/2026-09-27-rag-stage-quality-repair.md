# PDF RAG 단계별 품질·지연 개선

- 상태: 단계 진단·중복 계산 수정·16문항 전후 측정 완료. 생성형 품질 개선 구성의 실제 답변 검증은 미완료.
- 기준 코드: `ffe2b7b`
- 환경: 기존 마스터·자산운용 도메인·기존 DB·E5 v2 색인. 별도 환경을 만들지 않는다.
- 연결 이력: ISSUE-00005

## 성공 기준과 작업 순서

1. 같은 합성 PDF 3종과 정답16문항으로 검색 도달률과 생성 전달 근거를 따로 측정한다.
2. PDF의 원문 ID·페이지·bbox 및 권한을 유지하고 문맥 전체 보존 계약을 지킨다.
3. 중복 임베딩은 요청 안에서만 재사용하며 점수·선택 결과가 변하지 않아야 한다.
4. 문맥 예산과 의미 기준 후보는 기존 색인에서 메모리 내 비교한다. 평가하지 않은 설정을 일반 기본값으로 승격하지 않는다.
5. 실제 설정 반영이 적합한 경우 새 불변 버전과 평가 기록을 남긴다. 기존 버전·문서·대화는 보존한다.
6. 단위·타입·린트·독립 검토 후 기존 API에 반영하고 실제 브라우저로 재확인한다.

## 설계 판단

기존 승인 설계는 하나의 문맥 묶음을 통째로 수용하거나 제외하며,8그룹·32단위·12000자는 초기 평가 후보였다.
따라서32 초과를 무시하거나 PDF 표에서 임의로 한 줄을 잘라내는 변경은 하지 않는다.
관찰된 실패는 현재 자료의 span 세분도와 배포된 예산의 불일치다. 더 큰 단위 예산 후보를 문자·공급자 입력 한도 안에서 평가한다.
의미 기준 역시 문장과 문맥에 동일한 성능을 가정하지 않고 양성·음성 질문으로 비교한다.
저장·로그·테스트에는 실제 민감 본문을 추가하지 않으며 합성 원문만 사용한다.

## 측정 해석과 범위

- 원문 추출 성공: 정답표의 인용문이 지정한 파일·페이지에서 추출되는지 확인한다.
- 검색 도달: 정답 파일·페이지·인용문이 상위 검색 후보에 있는지 확인한다.
- 근거 전달: 자격·예산 검사를 통과한 문맥에 필요한 인용문이 모두 남아 있는지 확인한다.
- 답변 성공: 실제 생성 결과의 사실·수치·예외 조건과 출처를 정답표에 대조한다. 검색 도달 또는 근거 전달만으로 답변 성공을 주장하지 않는다.
- 음성 질문: 관련 문서가 검색되는 것 자체는 실패가 아니다. 문서에 없는 미래 확정 수익률·실제 계좌번호를 답변으로 지어내는지가 핵심이다.
- 지연: 기존 대화의 저장 시각 차이, 서버 stage 시간, 생성 직전 중단한 평가 시간은 서로 다른 지표다. 외부 생성 시간을 포함하지 않은 평가를 사용자 응답 시간과 직접 비교하지 않는다.

이번 자료는 합성 PDF 3종·11청크이며 검색 top_k=10이다. 거의 전체 자료가 후보에 들어오는 작은 표본이므로 높은 검색 도달률이 대규모 문서 검색의 일반 품질을 입증하지 않는다. 질문은 16개이며 문서 외 정답표는 색인하지 않는다.

원문 문자 수와 입력 토큰 수는 다르다. 근거 직렬화에는 span마다 ID·페이지·출처 필드가 반복되므로 `max_characters=12000`만으로 전체 프롬프트 크기를 보장할 수 없다. 평가의 직렬화 바이트 수는 입력 크기를 비교하는 값이며 토큰 수로 표시하지 않는다.

## 구현 변경과 독립 검토

`RequestScopedEmbedding.encode_documents`가 같은 요청·같은 모델의 정확히 동일한 텍스트를 한 번만 계산한다. 입력 순서와 중복 항목을 복원하고, 내부 tuple과 반환 list 복사를 분리한다. 실패·개수 불일치 배치는 저장하지 않으며 질문 임베딩과 문서 임베딩의 캐시도 분리한다.

전역 캐시, 문서 간 권한 변경, 모델 대체, 표 행 임의 절단은 추가하지 않았다. 요청 안에서도 배치 크기가 달라지면 실제 모델의 부동소수점 결과에 미세한 차이가 생길 수 있어 비트 단위 동일성을 주장하지 않는다. 독립 검토에서 차단 결함은 발견되지 않았고 실제 선택 결과는 별도로 비교한다.

PDF 회귀 테스트는 33개 span·712문자 문맥의 예산32 제외/128 전체 수용, 원본 ID·page·bbox·표 좌표·예외 문장 보존, 진단 유무의 선택 불변성, 문자 제한, 누적 제한, 충돌 쌍, provenance 누락을 검증한다.

## 기존 평가 통과가 실제 대화를 보장하지 못한 이유

`backend/src/ai_workshop/labs/rag/evaluation/tasks.py`의 실행 경로는 `HybridRetrievalService`와 `EvidenceSelector`의 추출 결과를 `StableObservation`으로 기록한다. 실제 대화에서 사용하는 `select_context`의 문맥 예산, 외부 생성, 생성 답변의 인용 검증을 실행하지 않는다. 따라서 이 평가의 통과는 생성형 RAG 전체 품질 통과와 같은 뜻이 아니다.

또한 frozen 평가의 검색 순위는 청크에서 펼친 고유 evidence unit을 K개로 제한한다. 이번 진단의 청크 top_k=10 및 파일·페이지별 정답문구 도달률과 분모가 다르므로 수치를 같은 recall로 혼합하지 않는다.

도메인 연결 활성화에는 구성 평가 PASSED가 필요하다. 이번 메모리 내 후보 실험 결과만으로 DB 상태를 PASSED로 직접 바꾸거나 기존 평가를 새 구성에 복사하지 않는다. 일반 기본값 변경과 완전한 대화 품질 통과도 별개의 절차다.

## 전체 16문항의 수정 전 검색·근거 전달 결과

기존 환경의 실제 `DomainSearchExecutor`와 검색 서비스를 사용하되 생성 직전에서 반드시 중단했다. SQL 쓰기와 COMMIT을 차단하고 질문마다 롤백했다. 질문 이력은 비운 상태이며 정확히 승인된 합성 PDF 3개만 범위에 포함했다. 실행 중 설정·계정·DB·색인은 변경하지 않았다.

14개 양성 문항 모두 필요한 파일·페이지·인용문이 검색 후보에 도달했다. 그러나 기존 설정은 14개 모두 정답에 필요한 근거를 완전히 전달하지 못했다. 필요한 인용 23개 중 선택된 인용도 0개였다. 나머지 두 질문은 답변 거절을 확인해야 하는 음성 문항으로 별도 취급한다.

| 의미 기준 / 근거 단위 예산 | 양성 질문 전체 근거 전달 | 필수 인용 전달 | 미해결 질문 |
|---|---:|---:|---|
| 기존 0.90 / 32 | 0/14 | 0/23 | 양성 전체 |
| 후보 0.90 / 128 | 4/14 | 9/23 | Q01·04·05·06·08·10·11·12·13·14 |
| 후보 0.87 / 128 | 8/14 | 15/23 | Q05·10·11·12·13·14 |
| 후보 0.85 / 128 | 11/14 | 18/23 | Q05·10·13 |

위 세 후보의 단위 예산을 256으로 늘려도 전달률은 동일했다. 그룹 8개·원문 12,000자·키워드 기준 0.5는 유지했다. 이는 실험 후보의 비교이며 실제 활성 설정 변경이나 생성 답변 정확도 평가 결과가 아니다.

생성 직전까지 걸린 시간 중앙값은 38.39초, 범위는 36.25~58.80초였다. 기존 문서 임베딩 호출의 입력은 총 9,374회였고 이 중 4,606회는 앞 단계에서 이미 처리한 텍스트였다. 완전히 중복된 배치 14회의 계산 시간 합계가 138.48초였다. 이 수치는 제거할 수 있는 중복 작업의 측정치이지 최종 응답 단축 시간을 보장하는 수치는 아니다.

원시 자료: `.local-data/pdf-corpus-qa/retrieval-baseline-grid.json`, 요약: `retrieval-baseline-summary.md`. 수정 전 실제 생성·브라우저 5건은 `browser-test-results.json`에 별도로 기록돼 있다.

같은 “근거 부족” 문구라도 생성 전 필터 탈락, 부적절한 근거 전달, 문서에 원래 답이 없는 경우가 다르다. 사용자 화면의 메시지뿐 아니라 해당 요청의 선택 사유·실제 전달 문맥·생성 실행 여부를 함께 확인해야 한다.

## 후속 개선의 우선순위

1. 생성형 평가 실행 경로를 실제 대화와 맞춘다. 동일한 문맥 선택·예산·생성·인용 검증을 거치고, 검색 도달률·필수 근거 전달률·답변 정확도·잘못된 확신·지연을 별도 지표로 기록한다. 기존 추출형 BM25 비교 기준은 유지한다.
2. 질문별 문자열 예외 없이 모델·색인·문맥 단위에 맞는 근거 기준과 예산을 평가한다. 보수·예외·복수 문서·근거 없는 질문과 별도 검증 질문을 포함한다. 단순히 더 낮은 유사도 값이 더 좋다고 판단하지 않는다.
3. PDF의 스타일 span 수가 예산을 과도하게 소비하는 문제를 프로파일과 파싱 구조 양쪽에서 다룬다. 표 헤더·행·예외 관계를 보존하고, 원문 ID·페이지·좌표를 유지한다. 파싱·청킹 변경이 필요하면 새 처리/색인 버전으로 검증한다.
