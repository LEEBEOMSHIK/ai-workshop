# RAG 원문 문맥 보존과 입력 예산의 분리 검증

- 기준일: 2026-10-07
- 상태: 사용자가 작성된 설계를 승인함(2026-10-07). 구현 계획 작성·검토 단계이며 제품 구현·후보 생성·실모델 실행·활성 연결 변경 전이다.
- 관련 문제: ISSUE-00005. 예산 제외 원인의 개선 범위이며 RAG 전체 마감은 아니다.
- 선행 증거: [본래 요청·저장·화면 검증](../../worklogs/2026-10-07-rag-budget-diagnostics-browser.md), [예산 진단 계약](2026-10-06-rag-budget-diagnostics-design.md)

## 사용자 목표와 확인된 원인

모든 질문에서 관련 원문과 필요한 대상·조건·예외를 찾고, 실제 전달한 근거만 인용하는 것이 목표다. 지급일 문구나 특정 문서 ID에 대한 예외 분기를 만들지 않는다. 기존 대화·자료·계정과 본래 환경을 보존한다.

본래 요청에서는 관련성을 통과한 두 청크가 각각33단위/712자,36단위/683자다. 활성 구성의8그룹·32원문 단위·12000자 중 단위 상한만 초과해 모두 제외됐다. 두 청크를 모두 전달하면69원문 단위/1395자/2그룹이다. 이는 실제 저장 수치의 합이며 다음 요청의 검색 결과를 예측한 수치는 아니다.

현재 `parsing/pdf.py`는 PDF의 block→line→span을 순회하면서 span마다 `paragraph` 요소와 원문 ID를 만든다. `chunking/service.py`는 bbox가 있는 요소를 더 자르지 않는다. `highlighting/context.py`는 청크 전체를 수용하거나 제외한다. PDF의 글꼴 조각 수가 생성 입력 단위 수에 영향을 주는 구조다. PDF의 물리적 줄·bbox·ordinal은 의미상 표행·머리글·조건·예외 관계를 증명하지 않는다. 본래 PDF의 table row/column은 미기록이다.

현재 인용·수치 검증은 허용된 원문 ID와 값/계산 위치를 검사하지만, 서로 다른 상품·기간의 숫자를 의미상 올바르게 연결했다고 증명하지 않는다. 그러므로 일부 단위만 제거하거나 새 문자열/인용 ID로 합쳐 예산을 맞추는 수정은 채택하지 않는다.

## 대안과 권고

| 대안 | 기대 효과 | 현재 제약 | 판단 |
| --- | --- | --- | --- |
| 기존32단위 안에서 유사한 조각만 선택 | 입력량 감소 | 표·조건·예외의 의존 관계가 없고 먼 예외를 놓칠 수 있음 | 현재 PDF에는 적용하지 않음 |
| 새 PDF 구조 처리와 관계를 보존한 불변 projection/index | 원문 구조에 맞는 최소 완결 문맥 선택의 기반 | 새 파서/처리/색인 버전과 정확한 위치 검증 필요. 별칭 frozen gate를 해결해야 본래 색인 전환 가능 | 별도 구조 개선 단계로 분리 |
| 같은 원문 ID·전체 문맥을 유지하는 예산 한 변수 후보 | 기존 색인·표 위치를 바꾸지 않고 예산의 효과를 분리 | raw 단위 제한을 명시적으로 늘리는 실험이며 정답/속도 개선을 보장하지 않음 | 먼저 제한된 비교 검증을 권고 |

권고는 새 문맥 선택 알고리즘을 구현했다는 뜻이 아니다. 기존 전체 청크 선택을 그대로 사용하고 **별도 불변 후보에서만 raw 단위 상한32→128을 명시적으로 비교**한다. 활성32상한은 그대로 둔다. 128은 기존에 검토한 비교값이며 제품 코드의 새 기본값이 아니다. 글꼴 조각33개를1개로 세는 식으로 단위의 의미를 바꾸지 않는다.

독립 READ ONLY 확인(2026-10-07)에서 본래 활성 generation은v4/schema2/예산version1의8·32·12000이며, 같은 deployment의 기존pure-v4/128·v5/128·v6/128도 모두pending/defaultfalse다. pure-v4/128의 완료 평가에는 최신 수동5판정 중1실패가 있고, v5는재시도 포함68완료/14실패·수동68판정, v6 최신75회는64정상/11검증거절·수동63통과/1실패다. run의completed와 후보의passed를 혼동하지 않는다. 이 수치는 서로 다른 평가 세대·시도 집합이며 합산 비교하지 않는다.

기존128 후보의 이름이나 완료 상태만으로 동일 조건을 가정하지 않는다. 이전 실패·판정·pending/defaultfalse는 보존하며, 기존config를 수정·승격하거나 같은75회를 다시 돌려 예산 효과를 증명하지 않는다. 새 실험에 재사용 가능한 불변 profile은 실제 전체 업무 설정 비교로 결정한다. 원문 단위 상한을 제외한 모든 필드가 같으면 해당 profile을 읽기 참조로 재사용해 불필요한 중복 생성을 피하고, 차이가 있으면 새 불변 profile이 필요하다. 기존 평가는 새 비교 결과/승격 판정으로 복사하지 않는다.

본래 전체 설정 비교에서 기존pure-v4/128 generation profile은 활성v4와 `context_evidence.max_units`만 다르다. 처리/색인/검색 profile 및 binding/deployment도 같지만 기존128 **configuration의 `min_semantic_score`는 다르다**. 그러므로 해당 generation profile만 재사용하고, 현재 활성 answer policy를 고정한 새 pending configuration을 준비하는 것이 현재 관측에 맞는 최소 범위다. 기존128configuration을 그대로 실행하면 한 변수 비교가 아니다. 실제 준비 시에는 재확인하고 정확한 profile/configuration ID·버전은 비공개 실행 기록으로 결속한다.

## 1단계: 실제 입력의 한 변수 비교

구현 계획 작성 후 실행할 경계는 다음과 같다.

1. 본래 활성 연결에서 indexing/retrieval/generation/answer policy와 입력 예산의 exact 버전·설정을 읽어 기준선을 확보한다. 후보를 준비하는 순간 다시 확인하며 문서에 복사한 이름으로 선택하지 않는다.
2. 같은 generation profile의 설정을 기준으로 별도 불변 비교 구성안을 메모리에서 준비한다. 이름·버전·식별자와 원문 단위 상한만 다르고, 모델/deployment·prompt/schema·temperature·history·timeout·numeric policy·그룹/문자 상한·임계값은 같다. 위 조건을 실제 비교한 기존 불변 profile은 재사용하며 그렇지 않으면 새 profile이 필요하다고 기록한다. 기존profile/config는 수정하지 않는다. immutable 설정 비교에서 다른 업무 필드가 달라지면 실행을 중단한다. 필요 근거 포함이 확인되기 전 새 pending configuration을 등록하지 않아 불필요한 DB 산출물을 줄인다.
3. 같은 retrieval/index/원문 스냅샷과 질문을 사용한다. 첫 비교는 생성 호출 없이 검색→근거 선택까지이며, 동일한 실제 적격 그룹·점수를 메모리에서 두 예산에 적용한다. 현재 `select_context`는 호출마다 embedding/자격을 계산하므로 단순히 두 번 호출하고 같은 입력이라고 주장하지 않는다. 기존 `RequestScopedEmbedding`을 같은 요청에서 재사용하고, 두 번째 예산 검사에는 delegate 추가 호출0·exact source/질문/추출 결과/모델 버전 동일·자격/순서/점수 일치를 검증한다. cache miss나 차이가 있으면 비교를 중단한다. 검색을 두 번 실행한 결과 차이를 예산 차이로 오인하지 않는다. 임베딩 모델은 기존 로컬 모델만 사용한다. 이 반사실 입력 비교는 새 configuration의 정상 서비스 E2E 실행과 구별하며, 실제 후보 서비스 검증은2단계에 별도로 수행한다.
4. 선택 근거의 original ID/text/location/순서를 메모리에서 검증한다.33/36단위 두 그룹에 대해서32후보는0그룹,128후보는2그룹/69단위/1395자를 기대한다. 실제 입력이 달라지면 이 수치를 강제하지 않고 해당 실행 관측으로 기록한다. 미달 후보는128에서도 미달이어야 한다.
5. 추가 양성/음성은 기존 합성 정답표에서 표·대상 구분·조건·예외·다중 문서·유사 표현·속성 부재를 포함한 서로 다른 유형을 선택한다. 평가 정답은 검색·생성 입력에 넣지 않는다. 구현 계획에서 exact 사례 목록과 호출 상한을 고정한다. 전체25×3을 기본 반복 명령으로 삼지 않는다.

네트워크 없는 합성 회귀와 본래 로컬 모델 비교는 구별한다. 동일 원문을 전달할 수 있다는 사실은 생성 정확도 또는 사용자 대화 성공의 증거가 아니다. 비교 helper는 task-local에 두고, 제품 선택 경로에 숨은 monkeypatch나 프로파일 fallback을 넣지 않는다. 실제 자료/질문/벡터/원문 ID 목록은 보조 로그·Git fixture에 기록하지 않는다.

## 2단계: 제한된 생성과 의미 검증

1단계에서 필요한 근거가 실제 전달됨을 확인한 경우에만 정상 관리 API로 새 pending configuration을 등록한다. 외부 deployment의 configuration 생성 자체에 현재 owner의 `external_transfer_approval`가 필요하므로 정상 생성 승인과 이후 exact 후보의 실생성 연결 검사·매 질문 동의를 분리한다. 생성 승인 없이 먼저 레코드를 만들지 않는다. 기존 승인 레코드를 새 후보 ID에 복사하거나 승인 DB를 직접 수정하지 않는다. 후보 연결은 검증 대상으로만 선택하며 본래 도메인 기본 연결은 바꾸지 않는다. 정상 승인·연결 검사를 통과한 뒤 제한된 실모델 검증으로 넘어간다.

실제 답변은 원문 버전과 대조해 대상·조건·예외·숫자·단위·기간·인용 위치를 독립 검토한다. schema가 허용하지 않는 계산을 요구한 사례를 원문 직접값 질의의 통과 지표로 섞지 않는다. 계산 검증의 실패11건을 예산 변경으로 해결했다고 보고하지 않는다. 값이 허용되어도 다른 대상의 값을 차용하면 오답이다. 음성 질문의 답변 조작·모르는 인용·권한 누출은 허용하지 않는다.

모델 실패·timeout·인용 거절·근거 부족은 각각 보존한다. 재시도나 다른 모델 대체로 성공 수치를 만들지 않는다. 실패 초안·비공개 추론은 저장하지 않는다. requested 모델과 actual 관측 미기록을 구분한다.

이 단계가 통과해도 자동 승격하지 않는다. 후보의 정확한 전체 평가·불변 판정·엄격한 정상 수용 계약을 충족해야 하며, 승격과 본래 도메인 연결 변경은 구체적인 결과 검토 뒤 별도 단계다. 기존75회 판정을 새 후보의 평가로 복사하지 않는다. 본래 화면의 유효 답변·인용·새로고침·기존 세션 재개·성공한 멀티턴은 연결 적용 후 확인할 별도 완료 조건이다.

## 예산·진단·인용 불변식

- `max_units`는 실제 전달하는 원본 EvidenceUnit 수다. 새 논리 묶음 수로 재명명하지 않는다. max_groups/max_characters도 기존 정의를 유지한다.
- 전체 문맥의 원문 ID·text·element/page/bbox/offset·projection/asset version은 변하지 않는다. 가짜 합성 근거 ID나 문자열을 만들지 않으며 shared metadata 압축용 새 provider wire도 이번에는 만들지 않는다.
- 문자열 길이 합은 문자 상한이다. JSON 직렬화 byte/token 비용과 같다고 표시하지 않는다. 실행에서 기존 serialized_bytes와 실제 보고된 provider 사용량·단계 시간을 함께 비교한다.
- 동일 임베딩을 공유한 반사실 비교는 두 번째 검사가 캐시를 재사용하므로 그 시간 차이를 실제32/128 전체 요청 지연 개선으로 해석하지 않는다. 정상 서비스의 입력·동시 실행·캐시 조건과 반복 수를 별도로 명시한다.
- 진단 on/off는 선택 결과를 바꾸지 않는다. 원문 ID가 다르다고 동일 문자열을 자동 제거하지 않는다. 서로 다른 버전·문서를 합치지 않는다.
- 알려진 충돌 쌍의 한쪽만 전달할 수 없으면 전체 선택을 차단하는 기존 계약을 유지한다.128도 이 조건을 우회하지 않는다.
- 예산 기록은 각 실행에 적용된 실제32 또는128을 그대로 표시한다. 과거32결과에128을 소급 기입하지 않는다. 미기록·미계산·검사 전 제외를 유지한다.
- 현재 원문 권한·active READY exact 버전·전송 승인·사용자의 매 질문 동의를 실제 선택된 모든 근거와 navigation metadata에 적용한다. 범위·revision 변경 시 생성 전에 차단한다.

## 구조 선택의 후속 조건

앞으로 유사도를 이용해 작은 문맥을 선택하려면 원본 span refs를 유지한 별도 구조 관계가 필요하다. 관계에는 동일 exact projection의 대상/제목, 표행과 머리글, 조건·예외·주석의 필수 참조가 포함되어야 한다. 단순 bbox 인접성이나 제목 문자열 같음은 그 관계의 증거가 아니다. 신뢰할 수 없는 관계는 unresolved로 구분하고 현재 전체 묶음 보존으로 남긴다.

새 파서·청킹·원문 구조 계약은 새로운 처리/색인 버전과 불변 위치 매핑을 필요로 한다. 본래 이전 projection·unit·평가·인용은 보존한다. 해당 범위는 별도 설계/ADR·파서/DB/권한 전문 검토로 재분류하고 frozen alias 종료 증거 없이 새 색인 전환을 진행하지 않는다. 이번 비교 성공을 그 구조 선택의 구현으로 간주하지 않는다.

## 영향 범위와 검증 기준

기존 `models/context_evidence.py`와 `highlighting/context.py`는 이미128단위의 명시적 후보를 처리한다. 필요한 비교를 위해 선택 함수를 다시 작성하거나32 기본값을 바꾸지 않는다. 새 후보 준비·비교·관측은 [실제 대화와 평가의 공유 경로](../../decisions/0030-rag-generative-evaluation.md)와 기존 관리/검색/평가 서비스, task-local orchestration을 사용한다. 새 공개 계약이나 알고리즘 변경이 없어 이번 비교에 새 ADR은 필요하지 않다. UI·API 계약·DB migration·파서·provider·패키지·서버 재시작 변경이 필요해지면 이 설계를 확장하지 않고 범위를 재분류한다.

| 확인 | 성공 기준 |
| --- | --- |
| 합성 단위 회귀 |32/128·누적 예산·문자/그룹 상한·충돌·출처 무결성·진단 on/off 보존 |
| 실제 입력 비교 | 동일 적격 그룹·원문 identity, 필요한 근거 포함, 미달은 미달 유지 |
| 의미·음성 검토 | 다른 대상/조건 차용·지원되지 않은 답변·잘못된 인용0. 실패는 실패로 남음 |
| 권한·승인 | 생성 전 현재 권한·exact 버전·승인 재확인. 새 후보 승인 결속 정확 |
| 성능 | 검색/선택/생성·전체 시간과 입력 byte를 구분. 소수 측정으로 속도 보장하지 않음 |
| 보존 | 활성 연결·미승격 후보/판정·동결 보고서·원문·기존 세션·frozen gate 불변 |

제품 코드 변경이 없으면 존재하는 관련 회귀와 필요한 문서 검사를 실행한다. 새 비교 helper가 필요하면 실행 경계·동일 입력·비밀 미기록·한 변수 검증을 합성 fixture로 테스트한 뒤 본래 환경에 사용한다. 본래 서버 성공과 오프라인 fixture 성공을 분리한다.

## 책임과 다음 인계

메인이 요구/RAG/시스템 설계와 문서 통합을 맡는다. 독립 담당은 원문·인용·데이터 프라이버시 경계를 검토하며 같은 변경을 구현하지 않는다. 현재 설계는 정상 관리 흐름의 예산 한 변수 실험을 준비한 것이고 실행/정답/승격 완료가 아니다.

작성된 설계 승인 후 구현 계획에서 최소 비교 사례·실제 호출 상한·후보 승인·DB 보존 기준선·검증 담당을 고정한다. readiness용 합성 생성·승인 확인에 필요한 모델 호출도 별도 상한에 포함한다. 새 평가/판정은 exact 새 configuration/스냅샷에 결속하고 old75의 판정을 복사하지 않는다. SDK 도입·저장소 비교·학습은 기존 RAG 기능 마감 이후 순서를 유지한다. ISSUE-00005·별칭 종료·성공한 멀티턴 등 기존 미완료 조건은 열린 상태다.
