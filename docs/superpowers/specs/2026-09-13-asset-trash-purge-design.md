# 파일함 휴지통·복원·영구 삭제

- 상태: 상세 설계 승인(2026-09-13), 1단계 순수 계약 구현·검증 완료. DB/API/UI와 실제 삭제는 후속 단계이며 실사용 삭제 승인이 아니다.
- 기준일: 2026-09-13
- 정본 연결: [통합 파일함](2026-09-13-unified-cabinet-design.md), [이동 계약](2026-09-13-explorer-movement-design.md), [ADR-0023](../../decisions/0023-domain-cabinet-conversation.md).
- 목표: 사용자가 삭제한 파일·폴더를 일정 기간 복원할 수 있고, 영구 삭제 시 시스템이 관리하는 연관 원본·파생물·본문 복제·문서 전용 캐시까지 정리한다.

## 1. 범위와 선택

휴지통만 무기한 보관하는 안은 사용자가 거절했다. 즉시 물리 삭제는 실수 복구가 불가능하다.
따라서 휴지통 → 복원 또는 명시적/기간 만료 영구 삭제를 채택한다.
영구 삭제는 단일 DB cascade나 디렉터리 일괄 삭제가 아니라 영속 작업으로 수행한다.
기존 파일함·도메인 파일함·대화 내 선택기는 같은 Platform 계약을 사용한다.
Platform은 삭제 수명주기와 작업 목록을 소유하고 RAG·Learning·Publishing은 조립 계층에서 연결한 정리 참여자로 동작한다.
Platform에서 Labs 구현을 import하거나 문서 삭제에 LLM을 사용하지 않는다.

현재 코드에는 can_delete 저장값만 있고 휴지통 상태·삭제 API는 없다.
Assets의 ObjectStore.delete는 업로드 실패 정리용이며 전체 연관 데이터 삭제 기능이 아니다.
기존 파일·이동·원본 버전의 의미를 바꾸는 migration과 API 변경은 별도 구현·검증 후 적용한다.

## 2. 사용자 흐름과 권한

파일/폴더 행의 삭제 → 이름·현재 경로·하위 문서/폴더 수·복원 기한 확인 → 휴지통 이동.
파일함마다 휴지통 진입점을 두고 목록을 페이지네이션한다. 이름·종류·원래 위치·삭제일·자동 삭제 예정일·상태를 표시한다.
개인 파일함은 본인 생성 소유자와 기존 활성 접근 조건을 유지한다. 전역 마스터도 타인의 개인 공간을 우회하지 않는다.

| 회사 공간 행위 | 요구 capability |
|---|---|
| 휴지통 이동·휴지통 메타데이터 조회 | 현재 read + delete |
| 복원 | 현재 read + write + delete |
| 개별 영구 삭제 | 현재 read + delete, 별도 명시 확인 |
| 회사 공간 보관 정책 변경 | 해당 workspace OWNER |

개인 공간 정책은 해당 개인 소유자가 관리한다. 자동 정리는 만료 시점의 유효한 공간 정책으로 실행하는 시스템 작업이며 삭제한 사용자의 세션을 재사용하지 않는다.
회사 delete는 공간 전체 대상 권한이다. 현행 문서에는 업로더별 소유권이 없으므로 '내가 올린 문서만 삭제'라고 안내하지 않는다.
manage_members를 삭제 권한으로 재사용하지 않는다. 읽기 전용 사용자에게 휴지통 파일명·중복 상세를 노출하지 않는다.
휴지통 문서의 일반 원문·버전 열람·다운로드·새 버전·이동·승인·검색은 차단한다. 첫 버전의 휴지통 UI는 메타데이터와 복원/삭제만 제공한다.

영구 삭제 확인에는 모든 버전·연관 파생물이 포함되며 복원이 불가능하다는 설명, 영향 항목 수와 외부/백업 잔존 상태를 포함한다.
공유 평가·학습·공개 복제본에 대한 별도 소유권을 문서 delete 권한으로 넘지 않는다. 추가 승인 필요 의존성이 있으면 삭제를 차단하고 담당자의 조치를 안내한다.

## 3. 상태·계층·동시성

문서/폴더의 사용 상태는 원본 READY 및 RAG READY와 분리한다.

```text
active → trashed → active
             └→ purge_pending → purging → purged
                                  └→ retry_wait / blocked → purging
```

purge_pending 이후에는 일반 사용·복원을 허용하지 않는다. purged는 문서 본문 행을 남기는 상태가 아니라 최소 삭제 증명 기록의 결과다.
Document/Folder에는 lifecycle, metadata_revision, 삭제 배치 식별자·삭제 시각·예정 시각·정책 버전 등을 명시한다.
영구 삭제 작업은 별도 작업 ID, 시도 수, 안전 오류 코드, 단계별 완료 여부를 가진다. 원문·경로·전체 manifest를 일반 로그에 출력하지 않는다.

폴더 삭제는 현재 활성 하위 트리를 하나의 배치로 원자적으로 휴지통 처리한다. 이전에 따로 삭제된 항목은 새 배치에 합류하지 않는다.
복원은 선택한 배치의 항목만 복원한다. 원래 부모가 휴지통이거나 없으면 같은 공간의 활성 목적지를 명시 선택한다.
같은 이름 폴더가 있으면 덮어쓰기·자동 병합 없이 충돌로 안내한다. 하위 트리 깊이·순환도 기존 계약대로 검사한다.
휴지통 항목은 활성 폴더명 유일성에서 분리하고, 기존 nullable parent 제약을 포함해 활성 sibling 유일성을 보장하는 migration을 설계한다.

삭제 미리보기와 확정 사이에 하위 항목이 달라졌으면 재확인을 요구한다. 미리보기의 배치 구성 digest/계층 revision을 확정 시 검증한다.
새 버전·이동·삭제·복원·자동 만료 경합은 workspace → membership → 관련 원본/문서의 기존 잠금 순서와 일치시킨다.
RAG의 Asset Version → Document 순서를 역전시키지 않는다. 구현 전에 실제 모든 경로의 잠금 그래프를 대조하고 교착 회귀를 추가한다.
API는 expected_revision 및 요청 멱등 키를 검사한다. 동시 복원/만료는 잠금 아래 하나만 성공하고 충돌은409다.

## 4. 보관 기간과 자동 정리

보관 기간은 관리자 UI에 양의 일수로 명시 저장하는 버전된 정책이다. 코드에 보관 기간을 고정하지 않는다.
최초 숫자는 아직 사용자 지정 전이므로 자동 삭제를 몰래 활성화하지 않는다. 삭제 기능 활성화 전에 공간 소유자가 기간을 확인·저장해야 한다.
휴지통 이동 시 UTC 삭제 시각과 당시 정책으로 purge_after를 확정하고, UI는 사용자 시간대로 예정일과 남은 기간을 표시한다.
정책 변경은 새 휴지통 항목부터 적용한다. 기존 항목 기한 단축은 영향 수·새 예정일을 보여주는 별도 명시 적용을 요구한다.
Celery beat는 만료 항목을 정해진 상한으로 스캔해 같은 영구 삭제 명령을 발행한다. 중복 tick·재시작에도 같은 배치를 중복 실행하지 않는다.
만료됐으나 처리 중/실패한 항목을 사라진 것처럼 숨기지 않는다. 예정일은 처리 완료일 보장이 아니다.

## 5. 접근·검색·실행 차단

휴지통 commit 후 새 일반 목록/원문/버전/폴더 탐색은 현재 사용 상태를 권한과 함께 검사한다.
BM25·dense 모두 기존 정확한 Document/Asset/Projection/Build 선필터에서 비활성 문서를 제외한다.
원문 resolver, 승인 요청·승인 소비, 생성 직전의 근거 재검증에도 동일 상태를 적용한다.
선택 문서가 삭제됐으면 대화에 범위 변경을 안내하고 재선택을 요구한다. 파일을 빼고 전체 공간 검색으로 조용히 확대하지 않는다.
이미 사용자에게 전달된 화면·다운로드나 외부 모델에 전송된 입력은 소급 회수할 수 없다. 최종 응답 시에도 상태를 재검사해 폐기할 수 있지만 이미 전송된 사실은 지울 수 없다.

worker의 dispatch/claim, 원본 활성화, 파싱 산출물 게시, 색인·alias 활성화 전에 사용 상태와 lifecycle generation을 확인한다.
임시 산출물도 작성 전에 작업/문서 소유관계로 등록한다. 유효한 lease 없이 게시하지 않고 실패/취소 시 전용 임시물을 정리한다.
영구 삭제는 실행 중 작성자가 중단·반납됐음을 확인하기 전에는 완료하지 않는다. lease 만료만으로 살아 있는 프로세스의 파일 쓰기가 끝났다고 판단하지 않는다.
복원 시 기존 READY 파생물이 유효하면 재사용한다. 중단된 작업은 과거 terminal 기록을 되돌리지 않고 새 수명주기 실행으로 재개하며 준비 전 검색 가능으로 표시하지 않는다.

## 6. 정리 목록과 소유권

삭제 시작 전에 모든 버전 ID와 파생 관계를 확정하고, 참여자가 정확한 삭제 식별자·소유권·공유 참조·잔존 확인 방법을 반환한다.
FK만으로 찾을 수 없는 JSON·binary snapshot·배열 안의 참조도 구조화된 provenance 목록으로 추적한다.
기존 데이터의 연관 관계를 완전하게 증명할 수 없으면 inventory_incomplete로 차단한다. 추측한 문자열 검색이나 빈 목록을 정리 완료의 증거로 삼지 않는다.

| 영역 | 정리 대상·검증 |
|---|---|
| Assets | 원본 모든 버전, object key, 부분 업로드·임시물, 버전·폴더 관계, 목록 캐시 |
| 원문 뷰어/OCR | 페이지 렌더·미리보기·썸네일·DOCX 내장 이미지·OCR 입력/결과와 해당 작업 전용 임시 디렉터리 |
| RAG | 구조 요소·근거·청크·임베딩·모든 build/projection·과거 물리 색인의 해당 문서 레코드 |
| 작업·승인 | outbox/dispatch·진행 중 작업의 입력/결과·본문 승인 복제·캐시, FK 및 JSON 내 문서 참조 |
| 평가·학습 | 문서 snapshot·fixture_bytes·query/case/output 중 출처가 추적된 복제, 학습 데이터셋의 해당 항목 |
| 공개 복제 | 출처가 연결된 게시 revision·outbox payload·공개 projection·내보내기 패키지의 본문 복제 |
| 대화·클라이언트 | 서버에 실제 저장된 답변/근거 복제, query cache·Blob URL 등 앱이 관리하는 현재 세션 데이터 |

문서 전용 자산만 삭제한다. 다른 문서가 참조하는 모델 가중치·토크나이저·공유 객체·색인 전체를 삭제하지 않는다.
같은 bytes라도 독립적으로 소유한 다른 문서 원본은 대상 문서의 파생물이 아니다. 공유 저장 객체는 마지막 유효 참조가 없어질 때만 물리 삭제한다.
물리 색인이 문서 전용이라는 증명이 없으면 색인 전체 삭제 대신 정확한 불변 ID 조합으로 레코드를 삭제한다. wildcard/전역 flush/전역 Docker prune은 금지한다.
파일 key는 허용된 저장소 루트 안의 정규화된 경로와 소유권을 검증한다. reparse/junction 외부 경로와 임의 glob 재귀 삭제를 허용하지 않는다.
최종 manifest는 정리가 끝나면 경로·파일명·본문 hash 등 불필요한 값을 제거하고 건수·단계별 결과만 남긴다.

## 7. 불변 snapshot·공유 결과와의 충돌

현재 frozen 평가·Learning revision·Publishing revision은 불변 기록이다. 삭제를 이유로 몰래 본문만 고쳐 기존 digest/평가 성공을 유지하면 안 된다.
승인 이력과 생성 감사에도 DB 불변 trigger가 있다. 생성 감사의 evidence_ids 배열 등 FK 밖 참조까지 포함해
승인된 삭제 작업 ID·정확한 대상 집합에 한정된 프라이버시 삭제 예외를 migration/전용 명령으로 정의한다.
일반 API/worker는 이 예외를 사용할 수 없고 모델·프로파일·정책 등 무관한 불변 trigger를 전역 해제하지 않는다.
본문 없는 감사는 최소 증명으로 정리하되 불필요한 근거 ID 목록은 제거한다. RESTRICT FK 해소만으로 감사 정리가 끝났다고 판단하지 않는다.
영구 삭제 대상 복제본은 명시적인 철회/삭제 수명주기로 접근을 차단하고 payload를 제거한다. 영향 평가 결과는 재현 불가·사용 불가로 표시한다.
그 결과를 승격 근거로 사용하는 구성은 readiness를 재평가한다. 다른 모델로 자동 전환하지 않는다.
여러 문서가 섞인 snapshot은 해당 콘텐츠를 분리 제거할 수 있는 증명이 있어야 한다. 불가능하면 소유자에게 전체 snapshot 삭제 영향을 승인받고 그 전에는 blocked로 유지한다.
사람이 작성한 독립 연구 글 전체를 링크 하나만으로 삭제하지 않는다. 자동 인용/복제와 독립 작성 내용을 구분하고 관련 출처를 해소할 수 없으면 수동 검토가 필요하다.
공개 저장소는 직접 연결하지 않는다. 기존 승인된 전송 절차를 통한 철회/정리 확인을 받고, 원격 사본의 확인 전에는 전체 사본 삭제 완료로 표시하지 않는다.
아직 구현하지 않은 학습 실행/모델 가중치를 지웠다고 주장하지 않는다. 향후 파인튜닝 산출물의 문서 영향 제거는 별도 추적·재학습 계약이다.

## 8. 영구 삭제 작업 순서

1. 현재 권한·휴지통 상태·revision·정책/확인 토큰 검증 후 purge_pending과 outbox를 같은 트랜잭션으로 기록한다.
2. 새 작업 차단·활성 작업 정지와 소유 lease 해소, 의존 데이터 manifest를 확정한다.
3. 공유/외부 사본 영향 및 미확정 소유권을 사전 검사한다. 추가 승인 필요 대상은 파괴적 단계 전에 blocked로 알린다.
4. 모델 전송·검색·공개 소비를 차단하고 정리 참여자를 통해 본문 복제와 문서별 파생 자산을 정리한다.
5. ES refresh 후 모든 해당 레코드 부재, 객체/캐시 키 부재, DB 참조·본문 복제 부재, 재생성 작업 부재를 검증한다.
6. 승인·평가 등의 RESTRICT FK는 각 소유 모듈의 삭제 계약으로 먼저 해소한다. 문서·버전 행을 먼저 지워 정리 대상을 잃지 않는다.
7. 원본을 포함한 잔존 확인 뒤 본문 없는 삭제 증명만 남기고 purged로 마감한다.

단계는 멱등적이며 이미 없는 정확한 자원은 성공으로 처리한다. 다른 소유자의 자원이 같은 경로/ID로 발견되면 실패로 중단한다.
일시 실패는 제한된 backoff로 재시도하고 반복 실패/미지원 정리기는 blocked로 남긴다. 완료 이력을 조작하거나 원본을 휴지통으로 되돌리지 않는다.
manifest 밖 잔존물을 발견하면 소유권을 재확인해 목록에 추가하고 다시 검증한다. 목록에는 없다는 이유로 잔존물을 무시하지 않는다.

## 9. 백업·외부 보관과 완료 표시

앱이 소유한 온라인 데이터 정리와 백업/외부 보관을 별도 결과로 표시한다. '흔적이 전혀 없음'이나 물리적 secure erase를 보장하지 않는다.
DB WAL/MVCC, ES segment, Docker 가상 디스크는 논리 삭제와 즉시 물리 회수가 다르다. vacuum/압축을 문서마다 실행하지 않는다.
백업은 정확한 보존 정책·예상 만료일·마지막 정리 확인을 표시한다. 정책/목록을 확인할 수 없으면 '확인 필요'이지 '삭제 완료'가 아니다.
원본이 포함될 수 있는 복원 테스트 DB도 백업 사본 목록에 포함한다. 문서 worker가 임의로 DB/백업 전체를 삭제하지 않는다.
복구 시 서비스 공개 전에 삭제 증명 목록을 적용해 과거 백업으로부터 삭제 문서가 되살아나지 않도록 한다.
외부 provider·다운로드·수동 export 등 앱이 통제하지 못하는 사본은 회수 불가/별도 처리 범위로 안내한다.
UI는 '앱 데이터 삭제 완료 / 백업 보존 종료 대기 / 외부 사본 확인 필요'를 구분한다. 알려진 사본을 숨기지 않는다.
최소 감사에는 불투명 대상 ID·행위자·정책 버전·시각·처리 건수·안전 오류 코드만 남기고 파일명·경로·질의·본문은 보존하지 않는다.

## 10. API·UI 계약과 단계별 구현

기존 공간 아래 trash 목록, document/folder trash, batch restore, purge preview/confirm, 삭제 작업 상태, retention 정책 조회/저장을 추가한다.
서버 typed DTO에서 상태·정리 건수·차단 이유를 반환하고 UI에서 UUID를 사용자 설명 대신 노출하지 않는다.
영구 삭제 확정은 비동기202와 작업 ID를 반환한다. 목록에서 사라졌다는 사실만으로 완료를 판단하지 않는다.
휴지통 중 동일 SHA-256 재업로드는 휴지통 접근 가능 사용자에게 복원 안내, 접근 불가 사용자에게 상세 비노출 오류를 제공한다.
정리 중에는 중복 업로드를 보류하고 정리 완료 후 새 업로드는 새로운 문서 ID로 허용한다. 삭제 tombstone이 새 ID를 막아서는 안 된다.

구현 순서: 상태·권한·provenance/migration → 모든 읽기/검색/worker gate → 휴지통·복원 → 영구 삭제 참여자·검증 → 정책/자동 정리 → 공통 UI → 격리 E2E.
상태 필터와 삭제 재생성 방지 검증 전에 UI를 활성화하지 않는다. partial 구현을 완성된 영구 삭제 기능이라고 표시하지 않는다.
기존 데이터 backfill은 dry-run inventory를 먼저 검증한다. 실제 DB 적용·서버 재시작·실제 삭제는 별도 대상 확인 후 수행한다.

## 11. 수용 기준

- 개인/회사·OWNER/삭제/쓰기/읽기 권한의 정상·거부·철회 경합, 직접 API 우회 검사.
- PDF/텍스트/DOCX OCR 등 실제 지원 형식의 합성 원본과 모든 버전/파생물 정리.
- 폴더 하위 삭제·이전 독립 휴지통 보존·복원 충돌·상위 삭제·동일 revision 경쟁.
- BM25/dense의 새 검색 제외, 이미 선택된 문서 대화 차단, 승인·원문·작업 상태의 본문 비노출.
- 실행 중 업로드/OCR/색인과 삭제 경합, 오래된 worker 재전달, 프로세스 재시작 뒤 재생성 없음.
- object store/ES/DB/공개 정리 중 각각 실패·재시작·중복 호출 후 정확한 멱등 완료와 잔존 검증.
- 같은 bytes/공유 모델·색인에 있는 무관 문서 보존, source hash와 레코드 수로 확인.
- 불변 평가/학습/공개 payload·RESTRICT FK·JSON 참조의 삭제/철회 계약 검증, 미확정 inventory는 차단.
- 승인 이력/생성 감사의 제한된 삭제 예외와 대상 밖 UPDATE/DELETE 차단, 일반 실행 주체의 예외 사용 거부.
- 보관 정책 명시 저장·기존 만료일 유지·기한 단축 확인·만료와 복원 경합·자동 작업 중복 방지.
- 백업 복원 후 삭제 목록 재적용, 본문 없는 감사, 삭제 완료의 온라인/백업/외부 경계 표시.
- 사용한 합성 자산은 승인된 격리 범위에서 정리하고 테스트 원본 소스와 사용자 자료를 혼동하지 않는다.
