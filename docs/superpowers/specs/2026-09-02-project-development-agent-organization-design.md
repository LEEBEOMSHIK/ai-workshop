# 프로젝트 개발 에이전트 조직 설계

- 상태: 사용자 검토 대기
- 기준일: 2026-09-02
- 적용 범위: AI Workshop 저장소의 설계·구현·검증 작업

## 1. 목적

AI Workshop 개발을 메인 오케스트레이터와 온디맨드 전문 에이전트가 일관되게 수행하도록 도구 독립적인 역할 계약, 선택 규칙, 품질 게이트와 임시 기록 수명주기를 정의한다.

이 조직은 제품 안에서 실행되는 캐릭터·LLM 에이전트와 별개다.

- 프로젝트 개발 에이전트: 저장소의 설계, 구현, 검증과 기록을 담당한다.
- 제품 런타임 에이전트: 향후 사용자가 화면과 기능에서 만나는 RAG 총괄, 검색, 근거 검증과 안내 주체다.

## 2. 범위와 비범위

### 포함

- 도구 독립적인 역할 계약
- 메인 오케스트레이터와 계층형 역할 카탈로그
- 작업 영향도 기반 자동 역할 선택과 사용자 고지
- 공통 프로젝트 역할과 RAG 도메인 전문 역할
- 프로젝트 전체 하드코딩 방지 정책
- 역할 간 인계, 검증, 충돌과 실패 처리
- 임시 협업 기록의 생성·보존·자동 정리
- Codex를 현재 오케스트레이터로 연결하는 어댑터 경계

### 제외

- 제품 런타임 에이전트 구현
- 상시 실행되는 에이전트 서비스와 작업 큐
- 모든 작업에 모든 역할을 호출하는 고정 조직
- 에이전트 대화 전문 또는 비공개 내부 추론 보관
- 미래 Labs의 빈 소스 모듈이나 가짜 메뉴 생성

## 3. 핵심 결정

1. 역할 계약은 도구 독립적인 Markdown과 YAML frontmatter로 관리한다.
2. 현재 메인 Codex 세션이 프로젝트 오케스트레이터 역할을 수행한다.
3. 오케스트레이터만 실제 역할 호출과 최종 통합을 결정한다.
4. 역할은 작업별 온디맨드로 활성화하고 선택 이유와 제외 이유를 사용자에게 고지한다.
5. 구현자와 독립 검증자·리뷰어를 분리한다.
6. 작업 성공 뒤 임시 에이전트 기록은 자동 정리한다.
7. 저장소에는 최종 코드, 공식 설계, ADR, 실행 지침과 선별된 문제 기록만 남긴다.
8. 하드코딩 방지는 RAG가 아니라 모든 소스와 미래 AI 영역에 적용한다.

## 4. 조직 구조

```text
사용자(Project Owner)
└─ 프로젝트 오케스트레이터
   ├─ 공통 프로젝트 역할
   │  ├─ 설계
   │  ├─ 구현
   │  ├─ 운영
   │  ├─ 보호·품질
   │  └─ 기록
   └─ 기능별 조직
      └─ RAG 책임자
         └─ RAG 전문 역할
```

사용자는 제품 방향과 위험 작업의 최종 결정권자다. 오케스트레이터는 승인된 규칙에 따라 역할을 선택하지만 사용자 권한을 대신하지 않는다.

기능 책임자는 필요한 전문 역할을 오케스트레이터에게 요청할 수 있다. 직접 역할을 무제한 호출하거나 사용자 승인 없이 범위를 확장할 수 없다.

루트 `AGENTS.md`에는 오케스트레이터 의무와 정본 링크만 추가해 200줄 제한을 유지한다. 실제 기능을 시작하지 않은 미래 도메인 역할 폴더는 미리 생성하지 않는다.

## 6. 역할 계약 형식

각 역할 파일은 다음 frontmatter를 갖는다.

```yaml
---
role_id: python-backend-engineer
name: Python 백엔드 개발자
category: engineering
scope: project
activation: conditional
independent_from:
  - integration-verifier
  - independent-code-reviewer
---
```

각 역할 본문은 다음 항목을 포함한다.

1. 목적
2. 담당 범위와 소유 모듈
3. 호출해야 하는 조건
4. 호출하지 않아도 되는 조건
5. 작업 전에 읽을 문서
6. 필요한 입력
7. 수행 책임
8. 허용된 결정과 변경 권한
9. 금지 사항
10. 만들어야 하는 산출물
11. 다른 역할에 넘길 인계 항목
12. 설정·하드코딩 확인 항목
13. 필수 검증
14. 완료 조건
15. 중단·에스컬레이션 조건

역할 ID와 메타데이터는 각 역할 파일의 frontmatter가 정본이다. 별도 목록 파일에 같은 메타데이터를 중복하지 않는다.

## 8. 역할 선택 규칙

오케스트레이터는 요청마다 다음 특성을 분석한다.

- 읽기 전용인지 변경 작업인지
- 영향받는 소스와 모듈
- UI, API, worker, DB, AI, 인프라, 보안과 데이터 경계
- 공개 계약 또는 아키텍처 변경 여부
- 파괴적 작업, 외부 전송 또는 민감 데이터 위험
- 필요한 도메인 책임자와 전문 역할
- 병렬화 가능한 독립 범위

기본 활성화 규칙은 다음과 같다.

| 변경 영역 | 필수 역할 |
|---|---|
| 요구사항 또는 기능 동작 | 요구사항·구현 설계자 |
| 여러 모듈 또는 공개 계약 | 시스템 아키텍트 |
| React UI | 프론트엔드 개발자 |
| FastAPI, Python 또는 worker | Python 백엔드 개발자 |
| 모델, 임베딩, 리랭커 또는 LLM | AI 엔지니어 |
| DB 모델, query 또는 migration | DB 관리자 |
| Docker, Compose 또는 배포 | 인프라·Docker 엔지니어 |
| 인증, 권한 또는 문서 노출 | 보안·권한 검증자 |
| 개인정보 또는 외부 모델 전송 | 데이터·개인정보 검증자 |
| RAG 동작 | RAG 책임자와 관련 RAG 전문 역할 |
| 기능 구현 | 테스트 설계자와 통합 검증자 |
| 중요 기능 또는 병합 전 | 독립 코드 리뷰어 |
| 설계, ADR 또는 여러 공식 문서의 구조 변경 | 문서 관리자 |

읽기 전용 질문과 단순 상태 확인은 오케스트레이터 단독으로 처리할 수 있다. 작은 단일 영역 변경은 구현 역할 한 명과 독립 검증 역할 한 명을 기본으로 한다. 역할 수를 채우기 위한 호출은 금지한다.

작업 시작 전 사용자가 확인할 수 있도록 작업 분류, 위험도, 참여 역할과 역할별 이유, 제외 역할과 제외 이유를 고지한다. 사용자는 역할을 추가·제외하거나 작업을 중단할 수 있다.

## 9. 오케스트레이션 흐름

```text
요청 분석
  → 변경 영역·위험도 분류
  → 필수 역할 선택과 사용자 고지
  → 설계·검증 기준 확정
  → 역할별 비중복 범위 배정
  → 구현
  → 영역별 검증
  → 통합 검증
  → 독립 리뷰
  → 수정·재검증
  → 공식 문서와 WORKBOARD 갱신
  → 임시 기록 정리
  → 오케스트레이터의 커밋·푸시
```

동시에 작업하는 역할에는 같은 파일을 배정하지 않는다. 같은 계약이나 파일을 수정해야 하면 설계를 먼저 확정한 뒤 순차 인계한다. 실제 동시 실행 수는 도구의 현재 가용 용량에 맞추고 고정 숫자를 역할 계약에 넣지 않는다.

검증자와 리뷰어는 기본적으로 읽기 전용이다. 문제를 직접 조용히 수정하지 않고 근거와 재현 방법을 오케스트레이터에게 보고한다. 수정은 구현 역할에 재배정하고 같은 검증자가 결과를 다시 확인한다.

커밋, 푸시, 병합, 최종 문서 통합과 `WORKBOARD.md`의 일상적인 시작·종료 갱신은 오케스트레이터가 담당한다. 문서 관리자는 설계·ADR 또는 여러 공식 문서의 구조와 정본 관계가 바뀌는 작업에만 호출한다.

## 10. 역할 간 인계

모든 역할은 다음 형식으로 결과를 인계한다.

```text
작업 범위
변경한 파일
변경하지 않은 경계
설계·계약 준수 여부
설정·하드코딩 영향
실행한 검증과 실제 결과
발견한 위험과 미해결 사항
다음 역할이 확인할 내용
```

`문제없음` 같은 결론만으로는 완료 증거가 되지 않는다. 명령 결과, 파일 위치, 계약 또는 재현 가능한 관찰 근거를 포함해야 한다. 비공개 내부 추론은 기록하거나 인계하지 않는다.

## 11. 프로젝트 공통 하드코딩 정책

하드코딩 방지는 모든 프론트엔드, 백엔드, DB, 인프라, AI와 미래 Labs 소스에 적용한다.

### 직접 고정할 수 없는 값

- 비밀값과 실제 사용자 데이터
- 환경별 URL, 포트와 저장 경로
- 실제 사용자, workspace, role, 자산과 프로파일 ID
- 변경 가능한 업무 정책과 제한값
- 반복되는 magic string과 magic number
- 여러 위치에 중복된 권한 이름과 역할 판정
- 기능 활성화 여부와 환경별 capability
- 외부 provider와 제품별 식별값
- 메뉴, route, 권한과 기능 메타데이터의 분산 중복
- 오류 코드와 상태 문자열의 산발적 사용
- 재시도, timeout과 동시 실행 수 같은 운영 정책

### 값의 정본

| 영역 | 정본 |
|---|---|
| 프론트 메뉴·route·권한·기능 | 중앙 feature 또는 Lab registry |
| 반복 디자인 값 | design token |
| 백엔드 환경값 | 검증된 typed settings와 환경변수 |
| 업무 상태와 불변식 | enum, value object 또는 domain policy |
| API 오류와 상태 계약 | 모듈별 타입이 있는 정본 |
| DB identity | 명명된 identity와 repository 조회 |
| 인프라 주소·포트·제한 | 환경변수와 검증된 배포 설정 |
| AI 모델·provider·prompt·파라미터 | model registry와 versioned profile |
| 테스트 값 | 공개·합성 fixture와 factory |

프로토콜 표준, 변경되면 업무 의미가 달라지는 도메인 불변식, 명확한 enum, 테스트 전용 fixture와 단순 화면 문구는 코드에 둘 수 있다. 모든 리터럴을 설정화하지 않는다. 구현자는 기존 registry, profile, settings, enum을 먼저 재사용하고 실제 변경 가능성이 확인될 때만 새 설정 계약을 만든다.

모든 구현 역할은 인계에 새 변경 가능 값, 정본 위치, override 방법, 환경 차이, 코드에 남긴 불변식의 이유와 비밀·실제 데이터 포함 여부를 보고한다. 하드코딩 계약 위반은 검증 실패다.

## 12. 메뉴와 미래 AI 영역

메뉴와 기능 정보를 개별 컴포넌트에 반복해서 직접 추가하지 않는다. 실제 기능을 시작할 때 다음 의미를 갖는 Lab 등록 계약을 함께 추가한다.

```text
LabDefinition
├─ id
├─ 표시 이름과 설명
├─ route
├─ icon key
├─ 상태
├─ 필요한 권한
├─ 노출 조건
└─ capability
```

앱 셸, 메뉴, 권한 필터와 route 연결은 같은 등록 정보를 사용한다. 아직 구현하지 않은 Image, Voice, Vision 등 미래 영역의 빈 폴더와 가짜 등록은 만들지 않는다.

프로젝트 공통 하드코딩 정책 아래에 기술 영역별 정책과 기능별 확장 정책을 둘 수 있다. 하위 정책은 공통 정책을 완화하거나 같은 내용을 복제하지 않는다.

## 13. 임시 작업 기록 수명주기

다중 역할 작업의 임시 협업 정보는 Git에 포함하지 않는 다음 경로를 사용한다.

```text
.local-data/project-agent-work/<task-id>/
├─ task-brief.md
├─ assignments/
├─ handoffs/
├─ reviews/
└─ unresolved.md
```

상태 흐름은 다음과 같다.

```text
active
  → validating
     ├─ failed 또는 blocked → 해결에 필요한 최소 기록 유지
     └─ verified
          → 필요한 결정의 공식 문서 반영 확인
          → 임시 작업 디렉터리 자동 삭제
```

자동 삭제에는 요청 구현, 관련 검사, 통합 검증, 독립 리뷰, 보안·데이터·migration 확인과 공식 문서 반영이 모두 끝나야 한다. 성공한 작업의 에이전트 대화와 중간 인계는 프로젝트 자산으로 보존하지 않는다.

문제가 남으면 해결에 필요한 최소 기록만 유지한다. 문제가 해결되고 필요한 내용이 코드, 설계, ADR 또는 실행 지침에 반영되면 임시 기록을 삭제한다. 삭제된 Git 추적 파일도 이전 이력에 남으므로 비밀값과 민감 데이터는 처음부터 기록하지 않는다.

## 14. 오류, 충돌과 범위 확대

- 범위가 확대되면 작업을 중단하고 참여 역할과 위험도를 다시 계산해 고지한다.
- 역할 실패를 다른 역할의 성공으로 대신 보고하지 않는다.
- 승인된 설계, ADR, 실제 테스트 증거와 프로젝트 규칙 순으로 충돌을 판단한다.
- 제품 방향이나 사용자 선택이 필요한 충돌은 사용자가 결정한다.
- 권한, 데이터 또는 외부 전송 위험은 관련 검증자가 해제하기 전 커밋하지 않는다.
- 사용자 또는 다른 도구의 변경과 충돌하면 덮어쓰지 않고 범위를 확인한다.
- 검증 실패 시 임시 기록을 유지하고 완료·정리·푸시를 진행하지 않는다.

## 15. 품질 게이트

```text
요구사항
  → 설계·계약
  → 테스트 기준
  → 구현
  → 영역별 검증
  → 통합 검증
  → 독립 리뷰
  → 오케스트레이터 최종 검증
  → 커밋·푸시
```

다음 상태에서는 완료할 수 없다.

- 요구사항, 설계와 구현의 불일치
- activation rule상 필수 역할 누락
- 테스트, 타입 검사 또는 린트 실패
- 하드코딩 정책 위반
- 권한 밖 데이터 노출 가능성
- migration과 데이터 영향 불명확
- 구현자의 자기 최종 승인
- 문서와 코드의 충돌
- 미해결 리뷰 의견

## 16. 계약 검증

역할 계약은 자동 검증 가능한 형식을 유지한다.

- 모든 역할 파일의 필수 frontmatter와 본문 절 확인
- `role_id` 유일성 확인
- category, scope와 activation 값 검증
- 참조하는 역할 ID 존재 확인
- 구현 역할과 독립 검증 역할의 잘못된 결합 탐지
- activation rule의 존재하지 않는 역할 참조 탐지
- `TODO`, `TBD`와 빈 필수 절 탐지
- 루트 `AGENTS.md` 200줄 제한 확인
- `WORKBOARD.md` 최근 완료 5개 제한 확인
- 임시 작업 경로의 Git 비추적 확인

역할 선택 전체를 고정 알고리즘으로 대체하지 않는다. 작업 의미와 위험도는 오케스트레이터가 판단하고, 필수 역할 누락과 계약 구조는 검증 도구가 확인한다.

## 17. 완료 기준

- 도구 독립 역할 계약과 Codex 어댑터가 분리돼 있다.
- 공통 역할과 RAG 역할의 책임·권한·금지·인계·검증 기준이 명확하다.
- 작업 예시에서 activation rule에 맞는 필수 역할을 재현 가능하게 선택할 수 있다.
- 구현자와 독립 검증자가 분리된다.
- 공통 하드코딩 정책이 모든 소스와 미래 Labs에 적용된다.
- 메뉴와 Lab 등록 정보가 중앙 계약을 사용하도록 후속 구현 지침이 명확하다.
- 임시 작업 기록이 Git에서 제외되고 성공 시 자동 정리된다.
- 규칙 검증이 실패하면 오케스트레이터가 완료를 주장할 수 없다.
- `AGENTS.md`와 `WORKBOARD.md`의 기존 유지 제한을 지킨다.

## 18. 도입 순서

1. 도구 독립 governance 문서와 역할 계약 형식을 만든다.
2. 공통 역할 파일과 activation rule을 만든다.
3. RAG 책임자와 현재 필요한 RAG 전문 역할을 만든다.
4. Codex 오케스트레이션 어댑터와 루트 `AGENTS.md` 연결을 추가한다.
5. 임시 작업 경로의 Git 제외와 캐시 수명주기 정책을 연결한다.
6. 역할 계약 및 저장소 유지 규칙 검증 도구를 추가한다.
7. 대표 작업 시나리오로 역할 선택, 실패 유지와 성공 정리를 검증한다.

이 설계가 승인된 뒤에만 상세 구현 계획을 작성한다.
