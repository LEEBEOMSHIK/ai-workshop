# 2026-10-20 누적 변경 인계와 용량 정리

## 요청과 범위

사용자가 다음 RAG 품질 보강 전에 누적 변경·이력을 커밋하고 원격에 푸시하며 불필요한 파일을 정리하도록 요청했다. 작업 시작 시 main의 기준 커밋은 `db7417a88f0a8c4cfcd2101d3444129ccb4af3df`였고, 수정·미추적 파일은 239개였다. 누적 구현과 의존 테스트·설계·실행 이력을 함께 보존한다. 이전 기록에 따라 사용자 참고 이미지 `references/images/img.png`는 원본을 보존하고 커밋에서 제외한다.

누적 범위에는 Conda 실행 경계, HTTP/로컬 생성, 근거와 최종 입력 진단, 시작 전 평가 취소, 평가 준비 모드와 UI 기준, 범용 인용 값 검증과 A/D 비교 기록이 포함된다. 특정 업체의 답을 고정하지 않는다. 이번 인계에서는 새 모델 호출, 임베딩, 재색인, 설치, DB 수정, 도메인 승격을 수행하지 않았다.

## 이력 보존

- WORKBOARD의 오래된 진행 요약과 완료 목록을 [보존 문서](2026-10-20-workboard-history.md)로 옮겼다. 본문을 유지하고 이동에 필요한 상대 링크만 조정했다. 보드는 최근 완료 5개와 현재·다음 작업을 유지한다.
- 공개 합성 자료로 수행한 A/D의 실제 입력·출력 [HTML 보고서](assets/rag-ad-20261020/actual-comparison.html)와 [이미지](assets/rag-ad-20261020/actual-rag-flow.png)를 문서 자산으로 보존했다. 원래 로컬 결과와 SHA-256이 일치한다. 예시를 실제 결과로 바꾸지 않았다.
- 다른 원시 실행 증거와 요청 예산은 기존 경로에 보존했다. 관리자 문제 이력 DB는 이번 작업에서 갱신하지 않았으며, 이 문서만으로 운영 DB 반영을 주장하지 않는다.

## 인계 검증 중 수정한 문제

제품 동작이나 보안 검사를 완화하지 않고 검증 설정과 fixture를 수정했다.

1. backend 디렉터리에서 실행하는 pytest가 새 `scripts` 모듈 테스트를 수집하도록 `pythonpath`에 저장소 루트를 추가했다.
2. HTTP 엄격 실패 테스트의 응답 생성 인자가 잘못되어 TypeError를 실제 provider 실패로 오인하던 문제를 고쳤다. payload를 handler 밖에서 만들고 올바른 `choice_overrides`를 사용한다.
3. ingestion 테스트가 다른 모듈에서 가져온 helper의 autouse fixture까지 적용된다고 가정하던 문제를 고쳤다. 해당 테스트에 synthetic runtime 의존성을 명시한다.
4. 입력 진단 테스트의 호출 횟수 기반 visibility mock을 running/completed 상태 기반으로 바꿨다. route recorder 테스트는 환경변수를 비우는 fixture에 필요한 synthetic runtime을 제공한다. 실제 실행 경계는 유지한다.
5. Node 전용 `node:test` 두 파일을 Vitest가 수집하는 문제를 고쳤다. Vitest 기본 제외 목록을 유지하며 두 파일만 분리하고 `pnpm test:runtime`으로 실행한다.
6. 두 테스트 파일의 import 정렬을 고쳤다. 빌드가 잠시 바꾼 Next 타입 경로·tsconfig는 작업 시작 때 변경이 없었음을 확인한 뒤 원래 상태로 되돌렸다.

## 검증 결과와 제한

- backend 전체 단위 검사: **7,951 통과 / 19 제외 / 12 실패**. 이후 fixture 수정 대상 중 ingestion 및 관련 224개, 입력 진단·route 대상 37개와 관련 회귀 120개가 통과했다. 부분 재검증을 전체 통과로 합산하지 않는다.
- 남은 PDF preview 7개는 현재 Conda의 격리 실행 `python -I`에서 `ai_workshop` 패키지를 찾을 수 없는 환경 조건을 확인했다(`pymupdf`는 발견). 패키지를 설치하거나 격리 옵션을 없애지 않았다. PDF 작업자 검증은 미완료다.
- backend Mypy: **483개 소스 통과**. 최종 backend Ruff 통과.
- frontend 타입·린트, API 계약 검사와 production build 통과. 별도 서버·DB·계정을 만들지 않고 빌드 출력 위치만 작업 전용으로 지정했다.
- Node runtime 경계: **15개 통과**. 브라우저 로그인 업무 흐름의 실제 E2E 검증을 뜻하지 않는다.
- 수정한 러너 설정의 전체 Vitest: **152개 파일·1,077개 테스트 통과**, 종료 코드0, 934.01초. 일부 기존 React `act(...)` 경고는 남았다. 타입·린트도 최종 설정에서 다시 통과했다.
- 초기 두 실행은 출력 지연 조사 중 중단했고, 세 번째 실행은 Node 전용 테스트의 잘못된 수집을 확인한 뒤 중단했다. 이를 worker 고장으로 단정하지 않는다. 세 번째 실행에 표시된 CategoryPicker 실패는 별도6개 검사와 최종 전체 검사에서 통과했다. 최종 전체 실행을 기다리며 시작한 변경 테스트19파일의 중복 부분 실행은 전체 통과 확인 뒤 종료했으며, 별도 통과 수로 집계하지 않는다.

독립 검토는 backend/scripts 검토와 frontend/runtime 검토로 나누었다. 테스트 fixture 수정 담당과 최종 독립 리뷰 담당도 분리했다. 원시 로그·JUnit·리뷰·파일 해시는 로컬 `.local-data/project-agent-work/git-handoff-20261020/`에 남긴다. 검증 증거를 원격 저장소에 원시 로그째 올리지 않는다.

## 용량 정리

기존 원문을 삭제하는 대신, 사용 중이 아닌 로그·정적 검사 캐시에 가역적 NTFS 압축을 적용했다. 정확한 경로, reparse 부재, 프로세스 참조·열린 쓰기 핸들 부재를 확인하고 전후 SHA-256과 파일시스템 할당량을 대조했다. 아래 회수량은 파일시스템 보고 할당량의 차이이며, 다른 프로세스의 영향을 받는 호스트 전체 여유 공간 차이와 구분한다.

| 대상 | 결과 | 기존 점유 공간 감소 |
| --- | --- | ---: |
| 종료된 개발 로그 6개 | 원본 경로·바이트 보존, NTFS 압축 | 556,253,733 bytes |
| 루트·backend Mypy cache.db 2개 | 도구 캐시 바이트 보존, NTFS 압축 | 208,003,072 bytes |
| 합계 | 약 728.85 MiB | **764,256,805 bytes** |

종료 로그는 `original-rag-worker-alias-recovery-20261001-035450.err.log`, `worker-clean.err.log`, `alias-recovery-20260907-worker.err.log`, `original-rag-worker-20260930-012609.err.log`, `original-rag-generative-20260928-worker.err.log`, `original-rag-worker-sessions.err.log`로 한정했다. 압축 검토를 위해 이번 작업에서 만든 gzip 중복본 6개는 원문 SHA 일치를 다시 확인한 뒤 제거했다.

이번 production build가 만든 `frontend/.next/instances/handoff-20261020`의 646개 파일·106,043,987 bytes를 경계·미사용 상태 재검사 후 제거했다. 이는 이번 작업의 생성물을 없앤 것이므로 기존 공간 감소 합계에는 더하지 않는다. 실행 중 frontend의 다른 빌드, node_modules, 현재 Conda, 구 .venv, 모델, 업로드 원본, 검색 색인, Docker 데이터, .git과 미해결 작업 증거는 보존했다.

## 최종 인계

커밋 범위는 누적 변경·테스트·문서·선별 결과 자산 **246개 파일**이다. 상대 문서 링크, AGENTS 줄 제한, Git 공백 검사와 고위험 비밀값 패턴을 확인했다. PEM 파서의 문자열 표식1개는 실제 키가 아님을 수동 확인했다. 최종 독립 리뷰에서 추가 P1/P2 차단 사항은 발견되지 않았다. 발견했던 strict-response 테스트 결함은 수정 및 재검증으로 해소했다.

원격 대상은 기존 `origin/main`이다. 이 문서를 포함하는 체크포인트 커밋으로 인계하며, 커밋 ID는 Git 이력에서 확인한다. 푸시 뒤 로컬 HEAD와 원격 main의 일치를 확인하고 결과를 사용자에게 보고한다. 이 커밋은 위에 명시한 PDF 환경 검증과 RAG 품질 실패를 완료 처리하지 않는다.
