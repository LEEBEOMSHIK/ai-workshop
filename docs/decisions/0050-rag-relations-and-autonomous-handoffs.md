# ADR-0050: 관계를 보존하는 근거 선택과 RAG 자율 재위임

- 날짜: 2026-10-27
- 상태: 구현·독립 검증·본래 API 반영 완료. 실제 마감 후속의 정답/인용·저장 완료 확인. 자율 후보는 실제 실패 후 보강했으며 수정본의 실제 모델 수용·기존 연결 승격은 미완료다. [검증 기록](../worklogs/2026-10-27-rag-relations-handoffs.md).
- 근거: [실제 연속 질문 결과](../worklogs/2026-10-27-sdk-multiturn-live.md), ADR-0046·0049.

## 문제와 결정

1. 정답 표가 검색되어도 33개 단위가 32개 한도를 넘어 통째로 제외된다. 한도를 올리거나 문장을 임의 절단하지 않고, 규칙적인 단일 페이지 PDF 표에서 명시된 상품 열 하나를 투영한다. 표 머리의 대상 이름과 질문이 정확히 연결되고 전체 행 항목의 토큰이 순서대로 질문에 나타나는 경우 일반 항목 질의를 지원한다. 기존 지급일 동의어 경로는 보존한다. 대상 머리·모든 행 항목·대상 값·표 밖 조건/설명은 원래 ID/문자열/위치/순서 그대로 하나의 그룹으로 유지한다. 비교·부정·다중 대상·다른 셀 참조·잘못된 구조는 투영하지 않는다. 검색 순위/임베딩/인용 검증/한도는 변경하지 않는다.
2. 대화 턴 또는 생성형 평가 시도 저장 트리거가 실행을 먼저 종료해 뒤따르는 저장 단계 종료 관측이 거절된다. 종료 실행에는 같은 소유자·대화의 terminal 턴, 또는 같은 실행에 연결된 평가 시도와 그 실행 소유자를 검증한다. 일치하는 부모·실행 상태와 이미 시작된 persistence의 동일 시작 시각을 확인한 경우에만 저장 단계 종료 메타데이터를 허용한다. 부모에 추가 잠금을 잡지 않으며 부모 실행의 나중 claim 해제를 완료 관측 거절 사유로 삼지 않는다. 실행 결과/종료 시각/오류/본문은 변경하지 않으며 다른 늦은 관측은 계속 거부한다. 과거 실행 기록을 자동 재작성하지 않는다. 실패로 생략된 다른 단계를 완료로 꾸미거나 전체 관측 complete를 강제하지 않는다.
3. 기존 manager→answer 단일 as_tool과 direct_answer는 유지한다. 명시적인 orchestration version 2 / autonomous_handoffs에서 근거 담당·답변 담당·검토 담당이 서로 다음 담당을 선택하는 SDK handoff를 제공한다. 기존 version 1 계약은 그대로 검증한다. 새 경로는 첫 근거 검토에서 시작하며 최종 구조화 답변은 답변 담당만 반환한다. 근거 담당은 현재 권한으로 선별된 원문 묶음의 관계와 누락을 점검한다. 이번 버전은 추가 검색이나 지식 공간 확대를 제공하지 않는다.

## 재위임과 권한

- 등록된 세 역할끼리만 위임한다. 이전 역할로 돌아가는 것도 허용하되 자기 자신에게의 위임·동시 복수 위임·알 수 없는 도구는 거부한다.
- 매 이동마다 원래 질문/서버가 채택한 이력/선별 근거를 서버 소유의 동일 입력에서 재구성한다. 최신 위임 작업은 제한된 길이의 작업 데이터로만 추가한다. SDK의 누적 도구 이력이나 모델이 만든 내용으로 원문을 교체하지 않는다.
- 문맥화를 포함하는 모델 호출/출력 예약/시간 예산을 공유한다. v2는 모델 최대 8회, 위임 최대 7회의 등록 상한 안에서 프로파일별로 지정한다. 한도에 도달하면 명시 실패하며 재시도나 다른 모델 전환은 없다.
- 매 HTTP 호출 전 현재 권한/취소를 재검증한다. 최종 답변은 기존 현재 원문·claim·인용 검증을 반드시 거친다. 선택된 근거가 부족한 경우 기존 insufficient_evidence 계약을 유지한다.
- handoff마다 새 agent span을 만들고 from/to, parent, 입력/출력과 시간을 기존 비공개 관측에 기록한다. 동일 역할 재진입은 별도 실행 ID로 구분한다. 외부 SDK tracing과 비공개 추론 수집은 꺼 둔다.
- 독립적인 HTTP 응답에서 로컬 서버가 도구 호출 ID를 반복할 수 있으므로, 검증된 단일 handoff의 ID에 실행 내 호출 번호를 붙여 SDK에 전달한다. 같은 응답의 복수 호출은 먼저 거부하며 도구 이름·인자·원문은 바꾸지 않는다.
- 실제 검증에서 확인한 지침 충돌을 제거한다. 근거·검토 담당은 최종 답변 JSON 지침을 받지 않고 등록된 단일 handoff와 task 인자로만 넘긴다. 답변 담당의 기존 답변 지침·스키마는 최종 제출에 그대로 적용하고, 확인이 필요할 때는 handoff를 선택할 수 있음을 구분한다. 공통 원문 관계·비신뢰 입력·추론 미출력 경계는 모든 역할에서 유지한다. 이 충돌의 존재와 실제 실패 응답의 정확한 원인은 구분하며, 미보관된 응답 형식을 추정하지 않는다.

## 구현과 검증 순서

실제 재위임 수용에서 평가의 history 단계 누락을 추가 확인했다. 고정 평가에는 대화 저장소의 이력 선택 단계가 없으므로 기존 `history=skipped/not_executed` 계약을 평가가 아직 실행 중일 때 기록한다. 부모 시도 종료 후에 빠진 단계를 추가하는 방식이나 terminal repository 허용 범위 확대는 하지 않는다. 고정된 입력 이력·문맥화·답변·인용은 그대로 두며 과거 실행은 재작성하지 않는다.

2026-10-27 후속 관측 결정: 위임 거절의 최상위 `orchestration_invalid_delegation` 계약을 유지하면서 실패한 SDK/model span의 기존 `error_code`에 닫힌 세부 사유 코드를 저장한다. 필수 위임 누락, 복수 호출, 잘못된 호출 형식/ID, 허용되지 않은 대상, 종료 사유 불일치, 인자 JSON·task 스키마 위반, SDK 상태 전이 위반을 구분한다. 정상 HTTP 입력·답변 형식·기존 직접답변 경로는 바꾸지 않는다. 실패 원문·임의 도구 이름·인자 값·비공개 추론은 새 진단에 저장하지 않으며, 이미 제공된 토큰 수와 시간만 실패 모델 단계에 연결한다. 과거 기록의 세부 이유는 추정해 채우지 않는다. 이번 실제 검증 요청은 동일 공개 질문 2회, 기존 비기본 후보와 실행당 모델4회/합계6회·자동 재시도0으로 제안한다. 최초8회 계획은 자동 승인 검토에서 거절됐으며 낮춘6회 범위를 재확인한 뒤 실제 실행한다.

1. 기존 변경의 파일 해시를 보존하고 두 결함을 실패 회귀로 재현한다.
2. 관계 투영/terminal persistence를 독립 범위로 수정하고 원래 입력 및 상태 불변식을 검증한다.
3. v2 정책, SDK handoff, native Ollama 변환, 재진입 관측과 예산을 구현한다. 실제 SDK Runner와 합성 HTTP 응답으로 왕복 재위임·허용되지 않은 호출·한도·권한 철회·취소·본문 비공개를 확인한다.
4. 설정 화면에 새 선택과 명시 한도를 제공한다. 등록은 평가되지 않은 후보이며 활성 연결을 자동 변경하지 않는다.
5. 범위 테스트·타입·린트·기존 DB rollback 및 독립 검증 후 본래 서비스 반영을 확인한다. 실제 Gemma 비교는 별도 호출 범위를 확인하고 답변·인용·화면 복귀·저장 단계 종료를 함께 기록한다.

## 대안

근거 개수 상향은 다른 질문의 비용을 키우며 관계 선택 문제를 남긴다. 고정 관리자 체인을 늘리면 담당자가 재위임할 수 없다. 무제한 handoff는 실행 종료를 보장하지 못하므로 명시 예산 안에서만 자율적으로 경로를 고르도록 한다.
