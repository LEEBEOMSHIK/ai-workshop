# 문제 번호와 기술 분류 분리

## 문제와 승인 범위

공통 플랫폼으로 분류한 문제도 과거 `RAG-0007`·`RAG-0008` 표시 번호를 유지해 기술 분류로 오인할 수 있었다.
사용자는 문제 번호를 기술 분류와 분리하도록 승인했다. 전역 `ISSUE-00001` 자동 번호, 이전 번호 조회,
기존 UUID·문서 버전·사건 보존을 구현한다. 검색·모델·인증 정책 변경은 포함하지 않는다.

## 역할과 검증 기준

중간 위험의 기존 기능 변경이다. 메인 담당이 요구·계약·문서와 본래 환경 반영을 맡고,
백엔드/DB와 프론트엔드 구현을 분리했다. 독립 담당이 이관·동시성·구 링크·분류 변경 회귀를 검토한다.
성공 기준은 중립 번호 자동 발급, 멱등 재시도와 동시 생성의 유일성, 카테고리 이동 시 번호 유지,
이전 번호 검색/상세 진입, 기존 UUID·원문·사건·문서 연결의 보존이다.

## 본래 환경 보존

- 기존 체크아웃·DB·마스터 계정을 사용한다. 별도 환경·DB·계정은 생성하지 않는다.
- 0052 적용 상태에서 `.local-data/backups/20260927-issue-history-pre0053.dump` 백업(2,864,441 bytes)의 archive catalog를 확인했다.
- 기존 문제 8개, 사건 13개, 문서 6개와 버전·연결의 해시·식별자를 로컬 기준 자료로 기록했다.
- 사용자 1명·공간 3개·원본 문서 3개·자산 버전 3개·대화 1개를 보존 대상 수량으로 기록했다.
- 검증 쓰기는 본래 DB의 외부 트랜잭션으로 롤백한다. 백업 복원 실험을 위한 별도 DB는 만들지 않는다.

## 적용·검증 결과

- 본래 DB에 `0053_issue_numbers` 적용. 기존 8개는 `ISSUE-00001`~`ISSUE-00008`로 전환하고 이전 번호를 보존했다.
- 전환 전후 UUID·문제 내용·분류·문서 버전·연결과 과거 사건 13개의 해시가 일치한다. 번호 전환 사건 8개만 추가했다.
- 전역 할당 행과 현재/이전 번호 registry를 사용한다. 카테고리 이동은 번호를 바꾸지 않고 같은 요청 재시도도 새 번호를 만들지 않는다.
- 단위 26건, 본래 DB 롤백 통합 12건, 프론트·내비게이션 51건 통과. Python/TypeScript 타입·Ruff/ESLint·OpenAPI 생성 계약 검사 통과.
- 통합 테스트 최초 실행은 자동 승인 검토에서 롤백 보장 부족으로 거절됐다. 모든 테스트 연결에 외부 COMMIT 차단 가드를 추가하고 DB 없는 가드 검증 뒤 재검토가 승인됐다.
- 통합 테스트 후 사전 기준을 다시 대조해 시험 문제·분류·문서·명령 결과가 남지 않았고 기존 자료가 변하지 않았음을 확인했다.
- 기존 API18000을 본래 `.env`로 재시작했다. 프론트/백 health200, 익명 관리자 API401·no-store 확인.
- 브라우저는 로그인 화면으로 전환돼 실제 마스터 화면의 새 번호·이전 번호 조회는 재로그인 후 확인해야 한다. 자동 화면 테스트 통과를 실제 화면 확인으로 보고하지 않는다.
- 이번 실제 결함은 공통 플랫폼 > 문제·개선 이력에 `ISSUE-00009`로 기록하고 이 작업 문서의 DB 버전을 연결한다. 테스트용 더미 기록과 구분하며, 화면 확인은 남은 작업으로 유지한다.

## 복구·보존 제한

2026-09-27 후속 확인: 관리자 메뉴 개편 때 기존 마스터 브라우저가 로그인된 상태에서
새 번호와 이전 번호 표시를 확인했고, `?issue=RAG-0007`로 `ISSUE-00007`의 동일 문제를 여는 것까지 확인했다.
위 재로그인 대기 항목은 이 확인으로 해소됐다. 기존 문서 버전1은 당시 대기 상태를 유지하며 이 후속 내용은 새 버전으로 연결한다.

이전 번호 alias와 사건을 삭제하는 DB downgrade는 차단한다. 앱 롤백 시 가산 스키마·데이터를 보존하되
구버전의 수동 번호 생성은 새 DB 제약에 막힌다. 저장소의 최초 이관 JSON·과거 문서·사건 스냅샷·명령 응답은
당시 내용으로 유지한다. DB 문서는 등록 당시 버전이며 이후 Git 문서 편집이 자동 반영되지는 않는다.
