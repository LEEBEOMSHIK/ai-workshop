# 관리자 RAG 평가 작성과 기본값 독립 통과 반영

- 상태: 보완 방향·계속 진행 승인 / 독립 설계 검토 승인·단계별 구현 중
- 범위: 기존 RAG Evaluation·Configurations·관리자 비교 화면
- 관련 결정: [도메인 대화 경계](../../decisions/0015-domain-bound-rag-conversations.md)

## 1. 목적과 현재 문제

관리자가 처음 등록한 문서로 실제 평가 자료와 정책을 만들고, 통과한 정확한 RAG 구성 버전을
도메인에 연결할 수 있게 한다. 현재 비교 화면은 이미 만들어진 데이터셋·정책 UUID만 받는다.
서버에는 평가 실행·정책 등록 API가 있지만 실제 근거 전체를 안전하게 조회하는 작성 경로가 없다.
또 현재 평가 통과 상태 반영은 전체 기본값 승격에 묶여 있다.

이 보완은 평가 결과를 만들어내거나 품질 기준을 완화하지 않는다. 검색 평가 통과와 Codex 연결·
LLM 답변 품질 검증은 서로 다르며, 도메인 활성화에는 기존 생성 준비 조건도 계속 필요하다.

## 2. 선택한 방향과 대안

채택: 기존 비교 화면에 안내형 평가 작성 기능을 추가하고, 평가 통과 반영만 독립시킨다.
기존 평가 worker·불변 스냅샷·PromotionGate·도메인 활성화 검증을 재사용한다.

- JSON과 UUID만 직접 입력하는 안은 빠르지만 실제 근거 식별자와 전체 권한 범위를 사용자가
  정확히 작성하기 어렵다. 기존 고급 입력은 유지하되 첫 작성의 기본 경로로 쓰지 않는다.
- 평가를 생략하거나 합성 자료에 자동 PASS를 부여하는 안은 채택하지 않는다.
- 새 평가 플랫폼, 자동 정답 생성, 모델 학습 시스템은 만들지 않는다.

## 3. 사용자 흐름

기존 관리자 RAG 구성의 비교 영역에 `새 평가 만들기`를 제공한다.

1. 저장된 정확한 구성 버전과 평가할 지식 공간·문서를 선택한다.
2. `근거 불러오기`를 눌러 접근 가능한 활성 문서와 실제 READY 근거를 조회한다.
3. 질문을 직접 쓰고 기대 결과를 `근거 있음` 또는 `근거 부족`으로 정한다.
   근거 있음은 원문 근거와 기대 하이라이트를 직접 선택한다.
4. 평가 이름, K, 반복 횟수와 통과 기준을 작성하고 범위·보관 안내를 확인한다.
5. 명시적으로 최초 평가를 실행한다. 서버가 실제 자료 스냅샷을 만들고 BM25 기준선과 비교한다.
6. 반환된 데이터셋에 입력한 기준을 정책 버전으로 저장하고, 정책을 연결한 실제 평가를 실행한다.
   최초 실행은 자료 등록용이며 이것만으로 통과 반영할 수 없다고 표시한다.
7. 통과 결과에서 `이 버전의 평가 통과 반영`을 선택한다. 전체 기본값은 바뀌지 않는다.
8. 기존 도메인 관리에서 생성 준비까지 끝난 버전을 연결·활성화한다.

정책 저장이나 다음 실행은 자동으로 이어서 수행하지 않는다. 실패 시 성공한 앞 단계의 ID와
입력을 유지해 재시도하며 동일 자료를 중복 등록하지 않는다. 새 자료·범위 선택은 이전 근거 선택과
실행 연결을 무효화한다. 페이지 재진입 시 기존 실행 목록에서 이어갈 수 있게 안내한다.

## 4. 근거 작성 경계

새 owner 전용 작성 서비스는 현재 사용자의 구성 소유권, 공간 접근권한, 구성의 구독 범위,
활성 문서 버전, 파싱·색인 READY 상태를 본문 조회 **전에** 검증한다.
owner라는 이유만으로 다른 사용자의 비공개 공간을 열지 않는다.

첫 버전의 안내형 작성은 한 후보와 자동 BM25 기준선의 동일 문서 처리·색인 조합을 대상으로 한다.
서로 다른 프로젝션의 근거 ID를 합쳐 정답 집합으로 삼으면 기존 지표 v1의 Recall을 왜곡할 수
있으므로, 처리·색인 조합이 다르면 명시적으로 지원 범위를 안내한다. 기존 고급 비교 기능이나
모델 변경 기능을 없애지는 않는다. 서로 다른 색인의 의미상 근거 대응 평가는 별도 후속 범위다.

응답은 선택한 문서 버전·원본 해시·구성 버전·빌드 식별자·근거 ID와 원문·구조 위치를 가진
좁은 DTO다. 내부 실행 스냅샷을 그대로 반환하지 않는다. 물리 색인명, 호스트 경로, 모델 설정,
인증정보와 범위 밖 자료는 응답에 포함하지 않는다. 응답은 `Cache-Control: no-store`로 제공한다.

이 기능은 소형 평가 작성용이다. typed settings로 문서·근거 개수와 응답 크기를 제한하고,
제한을 넘으면 범위를 줄이라는 명시적 오류를 반환한다. 부분 결과를 완전한 범위로 취급하거나
조용히 자르지 않는다. 제한 내 전체 근거를 한 번에 받고 화면에서 페이지를 나눠 표시한다.

조회 응답에는 정규화한 범위·구성·문서·실제 빌드·근거 집합의 지문을 포함한다.
실행 요청 시 서버가 현재 권한과 같은 범위를 다시 검증하고 지문을 비교한다.
문서 새 버전, 색인 변경, 권한 회수, 불완전 조회는 저장·실행을 거절하고 재조회를 요구한다.

## 5. API와 서비스 책임

새 계약은 owner 인증 뒤 RAG 평가 서비스가 처리한다. 핸들러는 DTO 변환과 의존성 주입만 한다.

- 문서 목록: 정확한 후보 버전·공간에서 현재 접근 가능한 활성 문서 버전의 본문 없는 목록을
  페이지 단위로 제공한다. 제목·버전·준비 상태를 보고 선택하며 큰 문서나 미준비 문서가 있어도
  다른 작은 문서를 선택할 수 있다. 이 단계에서는 근거 본문이나 완료 지문을 발급하지 않는다.
- 작성 미리보기: 목록에서 명시적으로 선택한 정확한 문서 버전의 완전한 근거 DTO만 반환한다.
  문서 선택 생략은 허용하지 않는다. 클라이언트가 문서 번호에서 버전 UUID를 추측하지 않는다.
  목록과 미리보기 모두 DB 저장·평가·모델 호출은 없다.
- 작성 자료로 실행: 같은 선택 범위와 조회 지문, 평가 이름, 사람이 작성한 질문·기대 결과·근거
  선택·하이라이트, K·반복 횟수를 받는다. 서버가 ID·질의 해시·전체 근거 집합을 구성하고 기존
  데이터셋 검증 및 실제 실행 서비스를 호출한다. 클라이언트의 임의 `authorized_source_ids`나
  해시를 신뢰하지 않는다. 기존 실행 API의 자유 fixture 계약은 호환성을 유지한다.
- 정책 작성: 기존 `POST /api/v1/rag/evaluation-policies`와 기존 불변 정책 계약을 재사용한다.
- 통과 반영: 정확한 구성 버전과 명시적인 평가 실행 ID를 받는 새 owner 동작을 제공한다.
  구성의 최신 버전을 추측하거나 다른 버전의 성공 결과를 재사용하지 않는다.

근거 있음 케이스는 적어도 하나의 허용 근거와 유효한 위치를 요구한다. 근거 부족은 기대 근거를
비우고 기대 하이라이트를 허용하지 않는다. 문자열 하이라이트의 offset은 기존 서버 인덱스 규약을
따르며 한글·비 BMP 문자로 검증한다. 브라우저 UTF-16 위치를 서버 문자 위치로 가정하지 않는다.
그림 기반 좌표는 기존 원문 좌표계를 명시한다. 지원하지 않는 위치는 명시적으로 거절한다.

질문·정답을 검색 출력이나 LLM으로 자동 채우지 않는다. 저장 전에 불변 평가 스냅샷에
자료와 질문이 남는다는 안내를 제공한다. 공개 게시나 파인튜닝 데이터 등록은 하지 않는다.

## 6. 평가 통과와 기본값 분리

새 통과 반영 동작은 아래 조건을 전부 검증한 뒤 해당 버전의 `evaluation_state`만 PASSED로 한다.

- 요청자에게 속한 정확한 구성 버전·완료된 실행·평가 후보·불변 정책
- 정책과 실행의 데이터셋, 지표 버전, K 일치
- 기존 PromotionGate의 모든 성공·재현성·권한 누출·품질 조건
- 결과·정책의 ID 연결 및 완전한 서버 검증 지표

명시한 실패 실행을 무시하고 다른 성공 실행을 자동으로 찾지 않는다. 조건 불충족은 안전한
충돌 오류이며 상태 변경은 없다. 이미 반영된 동일 증거의 재요청은 멱등적으로 처리한다.
정확한 구성 버전 행을 잠그고 한 트랜잭션에서 처리하며, `is_default` 및 다른 구성 행은 변경하지 않는다.

`전체 기본값으로 지정`은 기존 별도 동작을 유지하고 같은 품질 게이트를 재사용한다.
새 버전은 항상 PENDING으로 시작한다. PASSED는 과거 검색 평가의 증거이며 현재 문서·생성 준비나
외부 전송 동의를 대신하지 않는다. 기본값이 아닌 PASSED도 기존 도메인 활성화 조건을 만족할 수 있다.
화면은 `검색 평가 통과`, `전체 기본값`, `서비스 사용 준비`를 서로 구분한다.

기존 DB 제약은 PASSED이며 기본값이 아닌 상태를 허용한다. 새 영속 테이블이나 migration은
추가하지 않는다. 기존 불변 실행·후보·정책을 정확한 구성 버전으로 조회해 검증하며 응답에는 이번
반영에 사용한 실행·정책 ID를 함께 반환한다. 별도의 영구 승인 행위를 저장하는 감사 시스템은
이번 범위에 포함하지 않으므로, 이후 조회 결과를 특정 승인 행위의 영구 감사 기록이라고 부르지 않는다.

## 7. 수용 테스트와 완료 기준

- owner/member/익명, 다른 공간·다른 구성, 범위 밖 근거, 불완전 색인·stale 지문·크기 초과 거절
- 실제 근거 전체와 기대 근거의 구분, 가짜 ID·위치·hash 거절, 한글·이모지 offset
- 자동 BM25 포함, 첫 자료 등록·정책 등록·정책 연결 반복 평가를 기존 worker로 실행
- 실패·무정책·다른 버전·다른 실행 결과로 PASS 반영 불가
- 정상 PASS 반영 후 기존 기본값 및 다른 모든 버전의 기본값 상태 불변
- 구버전 정확 지정과 새 버전 생성 동시성, 반복 요청, 도메인 기존 준비 조건 회귀
- 초기 화면·탭 전환으로 저장/실행 없음, 단계 실패 시 입력 보존, 버튼·레이블·키보드·좁은 화면
- 관련 단위·격리 DB 통합·API 타입·lint 및 구현과 분리된 리뷰

코드 검증 후에만 승인된 합성 문서로 실제 로컬 평가 및 도메인 연결을 수행한다.
최종 사용자 테스트 가능 판정은 실제 Codex 답변·정상 인용/하이라이트·후속 질문·근거 부족·취소를
확인한 뒤 내린다. 이 설계 또는 검색 평가 통과만으로 RAG 전체 완료를 알리지 않는다.

## 8. 제외 범위와 작업 방식

일반 사용자 권한 확장, 외부 반출 정책 변경, 자동 정답/정책 생성, 평가 지표 v2, 교차 색인 근거
정렬, 운영 기본값 자동 변경, 모델 학습·공개 게시, 인프라 교체는 제외한다.
기존 dirty main에서 관련 변경만 수행하고 작업트리·스테이징·커밋·push는 이번 단계에서 하지 않는다.
상세 계약 검토 후 실행 계획, TDD 구현, 독립 리뷰, 실제 연결 검증 순서로 진행한다.
