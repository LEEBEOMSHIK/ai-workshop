# OpenAI와 Gemma 동일 입력 비교·비용 관측

관련 성능 문제는 ISSUE-00038이다. 사용자가 OpenAI API를 연결해 기존 Gemma와 동일 질문·근거의 답변 품질과 속도를 비교하고 크레딧 사용량을 기록하도록 요청했다. [수행 계획](../superpowers/plans/2026-10-29-openai-gemma-comparison.md)에 따라 비교 전용 진단을 구현했다. 기존 제품의 기본 모델·프로파일·서비스·DB 정책은 유지한다.

## 준비 당시 결과

비교용 API 키로 `GET /v1/models/gpt-6-luna`가 HTTP200을 반환해 후보 접근을 확인했다. 생성 요청은 아직 **OpenAI0회·Gemma0회**이며 답변 품질·속도·실제 차감액의 비교 결과는 없다. 키는 Git 제외된 비교 전용 파일에서만 읽고 출력하거나 보고서에 보관하지 않는다.

인증된 Billing overview의 현재 `Personal` 조직에는 `Free trial`, 남은 크레딧 `$0.00`, ChatGPT Pro 혜택을 사용하려면 워크스페이스를 연결하라는 안내가 표시됐다. 이 조직과 API 키의 청구 조직이 같다는 사실은 아직 확인하지 않았다. 사용자에게 크레딧의 출처 또는 직접 연결 완료 여부를 확인 중이다. 결제·자동충전·계정 연결 설정은 변경하지 않았다.

Admin key와 project ID는 설정되지 않아 조직 Usage/Costs 자동 대조는 사용할 수 없다. 응답 토큰에 따른 예상 비용과 실제 청구·크레딧 잔액 차이를 구분하며, 계정 잔액 확인만으로 개별 호출의 청구액을 확정하지 않는다.

- 공개 합성 질문 한 건과 기존 고정 근거28개, 질문 이력·위임 요청·시스템 지침 문자열을 유지한다. 현재 사용자의 원문 권한을 매 요청 전에 읽기 확인한다.
- OpenAI `gpt-6-luna` 최대2회와 기존 Ollama Gemma 최대2회, 순차 실행·자동 재시도0이다. OpenAI 예상 총액 상한은 USD0.05이며 서비스 자체의 과금 차단 설정을 뜻하지 않는다.

- 완료 응답까지의 시간을 비교한다. 비스트리밍 비교이므로 첫 토큰 시간은 미측정이다. 2회 표본으로 일반적인 성능 우열이나 P95를 주장하지 않는다.
- 기존 답변과 완전 일치 여부, 인용 유효성, 일반 T+4 영업일 지급·마감 후 다음 영업일 접수 등 의미 품질을 구분한다. 기존 답변의 일반 지급 규칙 누락을 새 답변에 강제하지 않는다.

Billing은 구독 연결과USD46.00을 계속 표시했다. 이 표시만으로 실제 비용0 또는 크레딧 미차감을 확정하지 않는다. 집계 지연·표시 소수점 정밀도와 정확한 키의 조직 귀속 미확인 경계가 남으며, Admin key도 없어 **실제 청구액·크레딧 차감액은 미확인**이다. `billing-after-comparison.json`에 이를 예상 비용과 분리해 저장했다. 추가 유료 요청으로 대시보드 반영을 확인하지 않았다.

## 종료·보존과 확인 위치

독립 검토는4개 결과의 형식·인용과 의미 품질, 입력 해시, 정확한 O/G/O/G4회, usage/정산2회, Decimal 합계, `monitor.json=result.json`과 종료 상태를 확인했다. 원래 환경/백엔드/준비 코드 해시 보존을 재확인했고 제품 설정·기본 모델·프로파일·DB쓰기·서비스 재시작·후보 승격은0이다. 혜택 연결만 이번 사용자 요청에 따라 변경했다.

종료 후 보존 검사에서 시작 전용 ‘모델 미적재’ 조건을 잘못 재사용해 `existing_model_loaded`가 발생했다. 생성 완료 후 기존 keep_alive에 따라 모델이 남아 있는 정상 상태이므로 강제 해제하지 않았으며, 해당 조건을 종료 기준으로 사용하지 않았다. 원래 서비스 식별자·파일 보존·요청 완료는 별도로 검증한다. 이 검사 실패는 추가 추론이나4회 비교 결과 변경을 일으키지 않았다.

상세 자료는 동일 로컬 폴더의 `result.json`(네 답변·인용·usage·시간), `comparison.events.jsonl`(전송 예약부터 종료까지), `monitor.json`(최종 누적 비용), `actual-review.md`(독립 의미 검토), `final-verification.json`(보존/합계 검사)에 있다. **비교용 API 연결과 기록까지 완료했으며 일반 대화의 기본 모델은 변경하지 않았다.** 이번 한 질문의 결과를 근거로 기본 모델을 자동 승격하지 않는다. 실제 청구 대조와 ISSUE-00038 관리자 DB 이력 반영은 미완료다.

## 기존 Work·Codex 크레딧을 프로젝트에서 쓰는 방법 조사

사용자가 기존 Work·Codex 구매 크레딧을 AI Workshop에서도 사용할 수 있는지 확인하도록 요청했다. AI 엔지니어는 저장소 구현·과거 수용·현재 UI 차단을, 독립 보안·권한 담당은 공식 등록·동의·서비스 제공 범위를 조사했다. root는 공식 추론 계약과 실제 계정의 사용량 화면을 확인했다. 이 절은 읽기 조사 결과이며 제품 코드·계정 동의·설정 변경과 신규 모델 호출은0이다.

**공식 지원 경로가 있다.** [SIWC 구현 안내](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt)는 오픈소스, 개인용 로컬 프로젝트, 선정된 비공개 앱에 ChatGPT plan usage를 제공한다고 명시한다. [사용자 안내](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites)는 참여 앱의 요청이 Work·Codex 기본 사용량을 사용하고, 별도 허용 시 기본 한도 이후 가용 크레딧도 사용할 수 있다고 설명한다. API Platform 잔액으로 크레딧을 이전하거나 기존 API 키에 붙이는 방식과는 다르다.

공식 흐름은 **AI Workshop의 ChatGPT 로그인 → 사용자 계정/워크스페이스 선택 → 앱의 구독 사용에 별도 동의 → 허용된 계정 모델 조회 → OAuth로 Responses 호출 → 사용량 표시**다. 로그인 성공과 플랜 사용 동의를 구분하고 실제 부여된 권한을 검사해야 한다. 구독 공유는 ChatGPT의 기존 대화·메모리 읽기 권한을 주지 않는다. [등록·인증](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [모델·추론](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference).

### 크레딧 사용의 조건과 현재 계정 확인

- 기본 제공 사용량이 먼저 적용되고, 그 한도에 도달한 뒤 가용 크레딧을 사용할 수 있다. 크레딧이 있다는 사실만으로 앱에 사용 권한이 생기지 않는다.
- 다른 앱의 크레딧 사용 허용은 기본 off이며 별도 선택이 필요하다. 공식 안내상 해당 앱의 주간 한도가100%여야 크레딧 사용이 가능하고,100% 설정만으로 크레딧 사용 동의가 켜지지는 않는다. 계정 자격·전체 공유 한도도 적용된다. 자동충전 허용과도 별개의 설정이다.
- 실제 `https://chatgpt.com/settings/usage?tab=overview`를 읽기 확인했다. 구매 크레딧 잔액과 자동충전 off는 보였으나 **앱별 한도와 다른 앱의 크레딧 사용 허용 옵션은 현재 화면에 보이지 않았다.** 이것만으로 영구 미지원이나 등록 후 자동 활성화를 단정하지 않는다. 실제 SIWC 등록·동의 시 이 계정에서 제공되는 권한과 설정을 확인해야 한다.
- 현재 화면의 기본 사용량도 남아 있으므로, 향후 성공한 요청이 곧바로 구매 크레딧 차감을 입증하지는 않는다. 토큰 사용량·기본 한도 사용·구매 크레딧 차감을 별도 관측해야 한다.

위 조건의 정본은 [다른 앱의 사용 한도·크레딧 관리](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites)다. 이번 조사에서는 공유·한도·자동충전 설정을 켜지 않았다.

### 현재 프로젝트와의 차이

[ADR-0017](../decisions/0017-personal-codex-exec-provider.md)은 개인 owner·개발 환경·검토된 공개/합성 자료의 `development_codex_exec`를 승인한 과거 계약이다. 2026-10-08 정확한 구성의 합성 연결 검증 기록은 있지만, [실행 정본](../runbooks/local-development.md)의2026-10-14 결정에 따라 현재 신규 설정·자료 동의·연결 검사·질문 실행 UI는 종료돼 있다. 이는 OpenAI CLI 제품 전체의 지원 종료가 아니다. 현재 `ConversationPage.tsx`는 해당 provider일 때 질문 제출을 차단한다.

백엔드에 남아 있는 exec 계약은 특정 CLI 버전과 등록 증거를 확인하고, 개인용 동의·정책·프로세스·구조화 출력/인용을 검사한다. 등록 기본값은 비어 있으며 실제 활성 설정·CLI 로그인 상태는 이번 조사에서 읽지 않았다. 이 코드를 SIWC 구현 완료로 취급하지 않는다. 기존 관측은 토큰 수이고 Work·Codex 크레딧의 실제 차감 원장은 아니다.

현재 OpenAI 비교 실행기도 그대로 재사용할 수 없다. [SIWC 제한](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)에 따라 `store:false`·`stream:true`, instructions/developer 메시지, 요청별 명시 이력이 필요하다. `max_output_tokens`·temperature·top_p·truncation·background 등 기존 비교 파라미터 일부는 미지원이다. HTTP background 플래그 미지원과 우리 서버의 백그라운드 작업 지속은 별개다. 스트림 최종 완료/실패·사용량·인용 검증과 비용/중단 경계를 별도 검증해야 하므로 품질·속도가 기존 비교와 같다고 주장하지 않는다.

현재 개인 로컬 AI Workshop에는 **별도 SIWC 선택 연결을 검토할 근거가 충분하다.** 기존 Gemma·API 키 연결과 구분해 구현해야 하며 현재 활성화된 것은 아니다. 타인에게 제공하는 유료/원격 호스팅 서비스는 별도 접근 신청 대상이다. 개인 self-host 실행과 서비스 제공은 구분한다. 기존 App Server 인증의 로컬/OSS 허용을 상용·호스팅 서비스 허용으로 확대하지 않는다. [공식 제공 범위](https://developers.openai.com/siwc/request-client-id), [App Server 인증 경계](https://learn.chatgpt.com/docs/app-server#auth-endpoints).

이번 조사 결론은 ‘일반 API 키에서는 기존 Work·Codex 크레딧을 쓰지 않지만, 공식 ChatGPT 구독 공유로 개인 로컬 앱에서 사용할 경로가 있다’이다. 다음 구현을 진행할 경우 인증/사용 동의·계정별 사용량 구분·미지원 파라미터·답변/인용·화면 이동 후 작업 지속을 정식 설계 및 수용 범위로 잡아야 한다. 사용자 요청은 방법 확인이므로 새 등록·권한 부여·실측은 시작하지 않았다.

## 속도표의 상세 재분석: 처리 시간과 답변 품질을 분리

2026-10-29 사용자 요청으로 위 네 실행을 재분석했다. 작업은 기존 공개 증거 읽기·계산·문서 기록이며 운영 위험은 낮다. AI 담당은 비교 통제와 시간 분해를, 독립 검토 담당은 원문 대비 답변·인용을 검토하고 root가 통합했다. 제품·UI·DB·배포 변경이 없어 해당 구현 역할은 제외했다. **신규 모델 호출·외부 전송·계정/제품 설정 변경은0**이다. 준비 단계의151개 오프라인 검사는 실행기 구현 검증이며151개의 실제 질문을 평가했다는 뜻이 아니다.

결론은 두 비교 축으로 구분한다. **Gemma 첫→동일 입력 반복은 처리 시간만 줄고 기존 답변의 부족함은 그대로였다. OpenAI↔Gemma 비교에서는 OpenAI가 두 번 모두 빨랐고, 이 질문의 일반 규칙·조건 설명도 더 충실했다.** 이는 고유 질문1개를 모델별2회 반복한 결과다. 서로 다른 질문2개를 통과했거나 일반 정답률100%를 입증한 결과가 아니다.

### 답변 품질은 무엇이 달랐는가

질문은 신청 날짜를 지정하지 않은 **“AM-SYN-101을 현금화하면 돈은 며칠 뒤 받을 수 있어?”**다. 원문 정본은 [공개 합성 fixture](../../backend/tests/fixtures/rag/stored_payment_table.json)이며, 일반 지급은 접수일T+4영업일이고 T 다음 영업일부터 센다. 마감은 영업일15:00까지이며 마감을 넘긴 신청은 다음 영업일에 접수한다. 날짜 예시는 예시 기간에 휴일이 없다는 조건을 가진다.

| 날짜 예시의 휴일 없음 전제 | 날짜 예시를 사용하지 않아 해당 없음 | 날짜 예시를 사용하면서 전제 누락 |
| 다른 상품의 T+7·해외 시장 예외 혼입 | 관찰되지 않음 | 관찰되지 않음 |
| 답변 형식·기존 인용 검사 | 통과 | 통과 |
| 이 질문의 답변 완전성 | 기존에 빠진 일반 규칙·조건을 보완 | 기존 부족함 유지 |

실제 답변 전문은 위 ‘실제 답변과 인용 검토’에 보존했다. Gemma의09-14 날짜는 원문 예시에서 가져온 값이므로 무에서 만들어 낸 날짜라고 분류하지 않는다. 다만 사용자가 묻지 않은 특정 날짜의 조건부 예시만 제시하고 일반 지급 규칙을 답하지 않았으며, 예시 자체의 휴일 없음 조건도 빠졌다. OpenAI는 상대 영업일 규칙으로 답해 이 문제를 피했다. 두 OpenAI 응답은 문구·claim 구분이 다르지만 같은 핵심 규칙을 설명한다. 이 표는 기존 결과를 원문과 수동 대조한 항목별 검토이며 새 자동 평가 점수나 전체 모델 정확도가 아니다.

인용의 차이도 개수만으로 판단하지 않는다. OpenAI는 e5/e6의 계산 규칙, e9~e12의 마감·접수 규칙, e15/e16의 지급 규칙을 인용했다. Gemma의 e22/e23은 날짜 예시를 가리킨다. 두 모델 모두 존재하는 근거를 인용했지만 **근거가 유효하다는 사실만으로 질문에 필요한 답변이 완성되지는 않는다.** 기존 검사기는 허용 근거·출처·정확값 등을 검사하며 질문 충족과 모든 문장의 의미를 자동 판정하지 않는다.

`quality_preserved_for_exact_case`와 `answer_equal`은 과거 저장 답변·인용과의 일치 여부다. Gemma의true는 기존 부족함을 고쳤다는 뜻이 아니고, OpenAI의false는 답변 품질이 나빠졌다는 뜻이 아니다. 인용/형식 통과, 이전 결과와 동일, 이 질문의 의미 수용, 다양한 질문의 일반 품질 수용을 별도 상태로 읽어야 한다.

OpenAI에도 추가 검증할 경계가 남는다. 실제 문구는 ‘15:00 이후’여서 정확히15:00을 포함하는지 언어상 모호하다. 원문의 ‘15:00까지’를 보존하려면 ‘15:00을 넘긴 신청’처럼 쓰는 편이 명확하다. 이번 질문은 정각 경계를 묻지 않았으므로 일반 규칙 설명의 개선 결론은 유지하지만, 정각·공휴일·정확 날짜 계산까지 검증 완료했다고 표시하지 않는다.

### 앞선 개선 작업과 이어서 읽는 방법

앞선 [v6 입력 표현 축소](2026-10-26-rag-reference-packing.md)는 근거를 유지하며 입력4,691→3,549토큰, 첫 입력 처리181.092→135.293초를 관측했고 답변·인용은 같았다. 즉 처리 비용을 줄인 작업이며 기존 일반 지급 규칙 누락을 고친 작업은 아니었다. 이번 Gemma 첫 입력133.632초도 그 이후에 남은 약130초대 병목과 일치하는 수준이다. 서로 다른 날짜·상태의135.293→133.632초 차이를 새 개선 효과로 계산하지 않는다.

[배치256 비교](2026-10-26-ollama-runtime-batch-threads.md)는 첫 입력130.876→132.683초, [명시6스레드 비교](2026-10-28-gemma-runtime-prefill-diagnosis.md)는131.222→143.781초로 목표 개선을 확인하지 못해 채택하지 않았다. 별도 서명 ARM 후보의360초 시간 초과를 이번 원래 Ollama의159.72초 결과와 섞지 않는다. 이번 OpenAI 품질·속도 개선은 후보 비교 결과이며 기존 일반 대화의 기본 모델을 변경한 성과가 아니다.

다음 품질 비교가 필요하면 일반 규칙·마감 직전/정각/직후·휴일 포함 날짜·정보 부족·상품 구분·연속 질문을 서로 다른 문제로 나누고 원문 정답과 수용 기준을 먼저 고정해야 한다. 속도는 최초 요청·같은 입력 반복·새 질문/새 근거를 구분하고 TTFT와 완료 응답, 전체 RAG 시간을 각각 기록해야 한다. 이는 이번 결과의 미확인 범위를 설명한 것이며 새 모델 호출이나 기본값 승격을 시작한 것은 아니다.
