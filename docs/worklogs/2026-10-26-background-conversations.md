## 바뀐 동작

질문 POST에 `Prefer: respond-async`를 보내면 기존 원자적 접수 뒤 202와 대화 식별자를
반환한다. 기존 start/submit 실행 코어가 별도의 서버 소유 루프에서 계속 실행된다.
DB session·검색 클라이언트 등은 그 작업 안에서 생성하고 종료까지 유지한다. 동기
임베딩·근거 선택이 API 이벤트 루프를 직접 점유하지 않게 분리했으며 모델·입력·근거·
인용·검색 알고리즘은 변경하지 않았다. 기존 프로세스 단위 LocalModelHost 하나를 공유한다.

새 대화·다른 대화·도메인 이동·탭 종료는 질문 취소 의도가 아니다. 현재 화면의 조회만
분리하고, 명시 답변 취소·첨부 초안 취소·대화 삭제는 기존 취소 계약을 유지한다.
저장된 대화에 돌아오면 실행 중/종료 확인 중 상태를 2초 간격으로 조회한다.
다음 질문은 미리 입력할 수 있고 같은 대화의 전송만 이전 실행 종료까지 제한한다.
늦은 POST/조회가 다른 화면이나 더 최신 revision을 덮지 않으며, 현재 권한이 철회되면
제목 편집기·근거·응답을 정리하고 과거 요청의 화면 갱신 권한을 무효화한다.

헤더 없는 기존 API의 동기201/200, request ID/digest/revision 멱등성, 현재 권한,
인용 검증 및 종료 미확인 차단을 유지한다. 앱 정상 종료는 작업과 정리를 기다린 뒤
공유 모델 호스트를 닫는다. 강제 종료/서버 재시작 뒤 자동 추론 재시도는 추가하지 않았다.
요청 한정 생성 입력 진단을 새로 저장하지 않으며 기존 권한별 실행 상세를 사용한다.

  명시 취소·반복 종료 요청, 동일 합성 답변 및 완료 시 권한 철회를 검증했다.
- 프론트 관련 고유158개 범위: 최종 전체 실행157통과/1실패 뒤 기존 제목 편집 UX를

  서버의 가린 제목을 편집기에 유지하는 기존 기대의 차이였다. 신규8개에 화면 이탈,
  자동 조회/종료, draft 보존과 독립 경합4개를 포함한다.

  합성으로 주입했으므로 실제 활성 연결/모델 수용 검증은 아니다.
