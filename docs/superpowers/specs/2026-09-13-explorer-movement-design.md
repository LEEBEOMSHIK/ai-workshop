# 파일함 최상위 표현과 안전한 이동

- 상태: 사용자 상세 설계 승인(2026-09-13). 탐색기 표현·서버 이동·RAG 정합성·이동 UI 핵심 구현/검증 완료. 복구 중 뷰어 닫기 초점 Minor와 실사용0034 적용은 후속(작업 기록 참조).
- 정본 연결: [통합 파일함](2026-09-13-unified-cabinet-design.md), [ADR-0023](../../decisions/0023-domain-cabinet-conversation.md).
- 대상: Platform Assets, 공통 파일 탐색기, RAG 현재 위치 해석. 다른 공간 간 이동·삭제·소유권 이전은 제외한다.

## 1. 최상위 위치

`folder_id=null` 문서는 파일함 최상위에 저장된 문서다. 미분류 상태가 아니다.
`parent_id=null` 폴더는 최상위의 실제 자식 폴더이며 이름이 `root`라도 특별한 시스템 폴더로 취급하지 않는다.
화면은 null 위치를 **파일함 최상위**로 표시한다. 실제 root/test 등 폴더는 이름과 ID를 그대로 유지한다.
기존 최상위 문서의 자동 이동, root 폴더 자동 병합·생성·삭제는 하지 않는다.
현재 URI와 API null 의미는 유지하고 표시 문구만 교체한다.

폴더는 열림/닫힘 아이콘, 자식이 있는 경우 펼침 화살표, 일관된 계층 들여쓰기와 선택 행으로 표시한다.
자식이 없으면 장식용 화살표로 클릭을 유도하지 않는다. 키보드 버튼·포커스·aria-expanded/현재 위치 표시를 유지한다.
완전한 ARIA tree 키보드 계약을 구현하지 않은 상태에서 role=tree/treeitem만 추가하지 않는다.

## 2. 이동 UX

문서 행 또는 폴더 행의 **이동** 버튼에서 목적지 폴더 선택 창을 연다. 파일함 최상위도 목적지다.
동일 기능을 내부 드래그앤드롭으로 실행할 수 있다. 외부 OS 파일 드롭을 이동으로 해석하지 않는다.
1회에 문서 또는 폴더 하나만 이동한다. 다중 이동, 자동 폴더 병합, 공간 간 이동은 지원하지 않는다.
드래그 payload는 현재 화면이 발급한 객체 유형/ID/원래 위치/revision이며 브라우저 외부 텍스트를 명령으로 신뢰하지 않는다.
드롭 가능한 목적지는 강조하고 불가능한 목적지는 금지 상태를 표시한다.
드롭 시에도 출발 위치와 목적지를 보여주는 같은 이동 확인 창을 사용한다. 명시 확인 전에는 서버를 변경하지 않는다.
확인 중 중복 제출을 막고 Escape/취소는 미실행 명령만 취소한다. 이미 commit된 이동의 취소로 표현하지 않는다.

현재 위치에 놓으면 요청 없이 '이미 이 위치에 있습니다'를 안내한다. 서버도 같은 위치 요청은 성공 no-op으로 처리한다.
실패 시 원래 화면 항목을 유지한다. 성공 후 출발/목적지 트리·breadcrumb·목록을 서버에서 다시 조회한다.
서버 성공 후 조회 실패는 '이동 완료, 목록 새로고침 필요'로 구분하고 이동 POST를 재전송하지 않는다.
목록 갱신 전 성공 위치로 낙관적 확정하지 않는다. 실패 시 다른 위치로 자동 이동시키지 않는다.
새 위치가 대화의 고정 폴더 범위 밖이면 선택을 무효로 안내하고 명시 재선택을 요구한다. 검색 범위를 확대하지 않는다.
문서 ID 중심 선택은 유지하되 최신 위치/권한/활성 버전 검사 후에만 사용할 수 있다.

## 3. 서버 계약

이동은 Platform 서비스가 담당한다. API 핸들러는 검증된 입력을 서비스로 전달한다.
다음 계약의 서버 코드와 생성 타입은 구현·검증됐으며 실사용 DB 적용/서버 재시작은 별도 단계다.
UI는 실제 응답의 유효한 metadata_revision이 없으면 이동을 활성화하지 않고 임의 기본 revision을 만들지 않는다.

- `POST /api/v1/workspaces/{workspace_id}/documents/{document_id}/move`
- `POST /api/v1/workspaces/{workspace_id}/folders/{folder_id}/move`
- JSON: `destination_folder_id: UUID | null`(필수), `expected_revision: strict int >= 1`(필수). 알 수 없는 필드를 거부한다.
- 응답: 이동된 객체의 ID, workspace, 최신 위치, 표시 이름, `metadata_revision` 및 `changed`.
- 원본 문서/폴더 조회와 목록 DTO에도 metadata_revision을 반환해 UI가 임의 revision을 만들지 않게 한다.
- stale revision은409. 읽기 권한이 없는 객체/목적지는404로 비노출한다. 권한 확인보다 충돌 정보를 먼저 노출하지 않는다.
- 같은 위치 no-op도 현재 권한과 expected_revision을 검증한 뒤 revision을 증가시키지 않는다.
- 이름 충돌·순환·깊이 초과는 구분되는 안정 오류 코드와 한국어 안내에 연결한다. 자동 이름 변경하지 않는다.
- 서버409 이후 UI는 최신 메타데이터를 다시 읽고 사용자가 재확인해야 한다. 자동 덮어쓰기·자동 재시도는 없다.

회사 공간은 현재 read+write를 요구하고, 개인 공간은 기존 생성 소유자 경계를 유지한다.
같은 공간이므로 원본과 목적지의 유효 workspace 권한은 같지만 객체의 실제 소속은 각각 검사한다.
도메인 UI는 기존 domain preflight도 유지한다. 도메인 연결 검증과 Platform 저장은 원자적이지 않으며 외부 전송 승인으로 간주하지 않는다.

## 4. 영속성과 동시성

Folder/Document 각각에 `metadata_revision` non-null/default1/check>=1을 추가한다.
원본 내용 버전, membership permission_revision과 별도다. 이번 이동은 실제 위치가 바뀔 때만 metadata_revision을1 증가시킨다.
원본 bytes, object_key, SHA-256, 문서·버전·Asset·projection·build·chunk ID, 승인 이력은 바꾸지 않는다.

같은 workspace의 계층 변경은 기존 `require_workspace_write(lock=True)`가 획득하는 WorkspaceRecord 행 잠금으로 직렬화한다.
잠금 순서는 기존 workspace 행 → 정렬된 사용자 membership 행 → 수정 대상 행 순서로 유지한다. 중복 hierarchy advisory 잠금은 추가하지 않는다.
새 폴더 생성은 이미 같은 workspace 잠금에 참여한다. 기존 parent별 sibling 잠금은 이 잠금 이후에만 얻는다.
권한 변경 경로가 이미 사용하는 잠금 순서와 상충하지 않는지 격리 동시성 테스트로 검증한다.

계층 잠금 안에서 source revision, 같은 workspace인 목적지, 현재 부모 경로, 형제 이름을 재조회한다.
폴더는 자기 자신/자손으로 이동할 수 없다. 이동할 하위 트리의 높이까지 포함하여 기존 `library_max_depth` 한계를 검사한다.
새 폴더 생성에도 같은 깊이 검사를 적용하여 이동과 동시에 자식을 생성하는 경우에도 한계를 넘지 않게 한다.
깨진 기존 계층·순환이 발견되면 이동을 중단하고 복구 요청을 표시한다. 임의 트리 수리는 하지 않는다.
폴더 이름 중복은 기존 strip 후 비교 정책을 유지한다. null 최상위 형제도 동일하게 잠금과 조회로 검사한다.
문서 동명은 기존대로 허용하며 내용을 병합하지 않는다. 업로드 해시 중복 정책은 변경하지 않는다.
전체 이동은 단일 트랜잭션이다. 실패하면 위치와 revision 모두 롤백된다.
실제 UPDATE에도 `metadata_revision=expected_revision` 조건을 포함하고 영향 행1개를 확인한다.0개는 충돌로 처리한다.

## 5. 검색·인용 정합성

보완 전 DB scope resolver는 DocumentRecord.folder_id로 후보를 제한하지만 Elasticsearch build_scope_filter도 색인에 저장된 folder_id를 제한했다.
따라서 DB 위치만 바꾸면 새 폴더 검색에서 누락될 수 있었다. 현재는 아래 정확한 조합 선필터의 구현과 격리 검증을 완료했으며, 이동 UI를 연결하는 단계다.

채택 방향은 현재 권한·폴더를 DB에서 해석한 정확한 READY Asset/build allowlist를 양쪽 검색의 선필터로 사용하는 것이다.
현재 검색에서는 과거 색인의 folder_id를 추가 권한 조건으로 사용하지 않는다. allowlist가 없거나 비어 있으면 조회를 거부/빈 결과로 처리하며 넓은 검색으로 전환하지 않는다.
이 변경은 현재 검색과 frozen 평가를 구분해야 한다. frozen 평가는 기록된 snapshot/물리 색인 계약을 유지하고 현재 폴더 의미로 소급 변경하지 않는다.
검색 결과의 현재 위치는 권한 있는 DB 메타데이터에서 해석한다. 색인 시점 위치를 현재 위치로 표시하지 않는다.
DB scope를 검색 전 해석하고, 근거 사용·모델 전송 전에 현재 허용 `(document, asset, projection, build)` 조합과 준비된 근거의 정확한 조합을 비교한다.
개별 ID 집합의 임의 교차 조합을 허용된 근거로 인정하지 않는다.
보완 전 `revalidate_access`처럼 scope를 다시 읽은 결과를 버리지 않는다. 사용 예정 근거가 새 집합에서 빠지면 scope-changed로 중단한다.
제한 없는 명시 문서 선택은 같은 문서의 위치 변경만으로 무효화하지 않는다. 유지된 폴더 제한을 벗어나거나 권한/활성 원본이 바뀐 경우 재선택을 요구한다.
과거 답변은 기록으로 남되 인용 원문 접근은 현재 권한으로 검사한다. 안정 문서/버전 ID가 유지되어 폴더 이동만으로 인용이 끊기지 않아야 한다.
이동은 재파싱·재임베딩 사유가 아니다. worker가 저장한 오래된 문서 객체로 새 위치를 덮어쓰지 않는지 검증한다.

## 6. 검증과 적용

1. UI 선행: 최상위 null 선택, 실제 root 자식 보존, 아이콘/펼침/선택/중첩/좁은 폭 회귀. 실제 자료 변경 없음.
2. 서버: migration·서비스·repository·API 타입을 TDD로 구현. 기존 backend 환경과 격리 PostgreSQL에서만 테스트한다.
3. 동시성: A→B와 B→A 동시 이동, 같은 revision 두 요청, 생성과 이동의 동일 형제명 경쟁, 하위 트리 깊이 초과, 권한 철회 중 이동.
4. 보존: bytes/hash/ID/승인/버전 유지, 같은 위치 no-op, 루트 왕복, 타 공간·개인 타인 접근 거부.
5. 검색: 텍스트 색인 A폴더→B폴더 이동 뒤 BM25/dense 모두 A제외·B포함, 기존 인용 열람, frozen 평가 불변, 이동 중 대화 실패 안전성.
6. UI 연결: 서버 계약·검색 정합성 검증 완료 후에만 DnD/이동 메뉴를 노출한다. 취소·오류·409·외부 파일 drop 거부·중복 submit·focus 복귀를 검증한다.
7. 로컬 실사용 적용은 백업·복원 검증 및 API/worker 중지·재시작 범위를 별도로 확인한다. 자동 migration/실제 문서 이동은 하지 않는다.

표현 개선은 현재 기능으로 전달하고, 이동 상세 확인 후 실행 계획과 구현으로 진행한다.
