# RAG 생성 실행 경로와 기존 세션 후속 답변 검증

2026-10-07. ISSUE-00005의 제한 평가 실패 후속이며 기존 본래 환경에서 확인했다.

현재 활성 구성으로 기존 세션의 후속 질문을 정상 Chrome에서 한 번 전송해 **답변 생성,
인용 원문, 저장과 새로고침 복원**을 확인했다. 새 세션은 만들지 않았다. 이전의 실패한
12개 평가 시도는 보존했고 후보128을 승격하지 않았다. 이번 확인은 합성 Markdown 자료의
단일 후속 질문 범위이며 PDF 후보의 평가 통과나 전체 RAG 기능 완료를 의미하지 않는다.

## 실행 경로 대조

- 같은 원래 설정과 공식 Python을 사용한 모델 호출 없는 점검에서 공식 runner의 버전 확인은
  제한 실행과 일반 실행 모두 exit0, version 일치, cleanup true, 남은 자식0이었다.
- 두 실행의 runner configuration SHA는 동일했다. Python 부모 프로세스의 외부 TLS 연결은
  제한 실행에서 `PermissionError/errno13/winerror10013`, 일반 실행에서 성공했다.
- TLS 점검은 HTTP 요청·인증 정보 전송·모델 호출을 하지 않았다. 이 증거는 두 Python
  프로세스의 네트워크 권한 차이를 확인한다. 실제 Codex exec 자식의 정확한 provider HTTP
  통신이나 과거8건의 process failure를 직접 관측한 것은 아니다.
- 독립 읽기 전용 조회에서도 성공 연결2stage와 실패 생성8stage의 runner configuration SHA,
  실행 파일 SHA, runner reference와 CLI 버전이 같았다. 명시적 child environment는 부모의
  환경 변수를 자동 병합하지 않으므로 helper의 offline/PATH 설정을 그대로 원인으로 단정하지 않는다.
- 과거 감사는 `codex_stage_failed`와 `provider_request_failed`로 축약돼 정확한 process
  failure·exit·stderr를 복구할 수 없다. 네트워크 권한 차이는 확인됐지만 과거8건의 정확한
  실패 원인은 미확정이다. 로컬 이벤트 거부도 같은 provider 오류로 매핑될 수 있다.

[로컬 실행서](../runbooks/local-development.md)에 평가 실행 프로세스의 연결 권한을 사전에
확인하고 정상 서버 실행 경로와 웹 사용 검증을 구분하는 절차를 추가했다. 제품의 runner
보안 설정·전송 승인·모델·프롬프트·임계값·예산은 바꾸지 않았다.

## 본래 웹 확인

- 원래 관리자 계정·자료·활성32 구성을 사용했다. 기존 수동 제목의 세션을 다시 열고 합성
  자료 분류와 이번 질문의 전송 동의를 확인한 뒤 후속 질문1개를 전송했다.
- 상품 코드를 생략한 지시어 질문이 이전 대화의 상품에 연결됐다. 답변의 지급 시점과
  인용 근거 버튼2개가 표시됐고 두 번째 버튼에서 exactv1 원문·문맥 하이라이트가 답변과 일치했다.
  저장된 인용은 claim1개에 원문 근거 reference2개가 연결된 구조다. 버튼 수를 claim 수로 세지 않는다.
- 실행 `a02609d3-6dc4-4316-97df-26a2a829a969`는 completed/answered/error null이며
  새 turn의 execution terminated가 true였다. 기존 세션의4번째 turn으로 저장됐다.
- 독립 조회에서 이전3turn의 dependency 결속을 확인했다. 실제 전송된 이력 메시지 수는
  별도로 저장되지 않아 dependency3을 전송 메시지3으로 환산하지 않는다.
- 새로고침 후 같은 세션 URL에서 기존3turn과 새 답변·원문 근거 버튼2개를 복원했다.
- 실행 상세에서도 답변·원문 버튼과 아래8단계 완료를 확인했다. 실제 모델은 미확인으로,
  품질 평가는 미검증으로 표시됐다. 관측하지 않은 모델 식별을 요청 모델과 같다고 추정하지 않는다.

## 검증과 기록 경계

- 관련 기존 unit44개 통과: Codex stream, HTTP lifecycle, conversation service/access.
- 모델 호출 없는 점검 helper와 상태 조회 helper2개의 Ruff·mypy 통과.
- 본래 API·프론트 health200과 기존 프로세스의 생존을 확인했다. 서버·worker·beat·Docker
  재시작, migration, 새 계정·환경·문서 업로드, Git 변경은 수행하지 않았다.
- 새 질문 직전 독립 REPEATABLE READ READ ONLY 기준선으로 보호55테이블 원래행 해시,
  선택 세션 원래3turn과 다른4세션, 동결11보고서, 환경·별칭 gate·활성 구성을 확보했다.
  독립 후검증은 선택 세션 revision8→10·updated_at 변화와 새turn1개를 정확한 예외로
  구분해 기존행 해시 보존을 확인했다. 원래3turn·다른4세션·동결11보고서·기존 평가/판정·
  자료·프로파일·환경·활성32·frozen gate1/receipt0 보존, 새 세션0·진행0이다.
- 같은 generation audit의 correlation으로 결속된 실제 stage는 contextualize1+generate1이며
  둘 다 completed/error null/termination true/cleanup true였다. CLI가 보고한 사용량은
  문맥화 input8453/output90, 생성 input12405/output272로 합계 input20858/output362다.
  원시 이벤트·본문은 기록하지 않았고 미관측 실제 모델·과금액을 추정하지 않았다.
- 독립 보존/감사 검증은 통과했다. 독립 담당은 답변 문장의 의미 채점이나 PDF128 품질
  통과를 주장하지 않았으며 메인 Codex의 브라우저 원문 관찰과 별도로 구분한다.
- 문제 이력은 정상 관리자 API로 새 보고서 exactv1·진행 사건을 기존 ISSUE-00005에 추가한다.
  과거 문서·사건·판정·실패 평가를 수정하거나 성공으로 바꾸지 않는다.
