# 대화 원문 조회: 마지막 범위의 성능 검토

2026-10-26 · ISSUE-00042 · [계획](../superpowers/plans/2026-10-26-execution-conversation-read.md)

사용자가 다음 성능 작업까지 한 차례 진행하고, 개선이 안 되면 보류한 뒤 다음 프로젝트 작업을 확인하도록 요청했다. 이에 후보를 계속 확장하지 않고 내부 대화 원문 조회 한 가지에 한정한다. 모델 호출은0이다.

## 원인과 선택

기존 DB의 READ ONLY 진단에서 전체508건/대화25건, 대화SQL295회 중 문서93·공간31·대화62·audit36·profile36·profile bindings36을 확인했다. `_current_visible`의 의존 대화 최초/최종 조회는 소유권·연결·변경·숫자 근거를 재검증하므로 단순 중복으로 제거하지 않는다.

선택한 후보는 `conversations/access.py`의 내부 원문 조회만 최대64개 exact(document,version,projection) 단위로 묶는 것이다. 요청 공간·선택 문서, 전체 source 추출, 역사적 버전, active/ready/현재 workspace 권한을 유지한다. 외부 전송 승인 경로·의존 대화·숫자 검증·본문 복원과 생성/검색/인용/품질 기준은 그대로다. 요청 간 캐시나 추가 병렬 처리는 만들지 않는다.

source가 여러 개일 때 검사 시점이 한 statement로 합쳐지는 차이가 있다. source가 없더라도 기존 요청 공간 검사는 계속한다. 프로파일의 불필요 ORM 관계 조회는 별도 후보로 남기되 이번 범위에 섞지 않는다.

## 검증과 채택 판단

후보는 신규14개를 포함한 구현 회귀242개와 범위 Mypy/Ruff를 통과했다. 독립 검증은 고유52개 PASS이며 정확tuple·ACL·호출간철회·빈source/선택scope·오류/취소·session종료와 외부승인 루프가 시작 원본과 같음을 확인했다. 독립 시험의 초기4실패는 SQLAlchemy 내부 cache-key 비교 문제여서 전체 compiled predicate와tuple/actor/상태 값을 비교하도록 시험만 보정한 뒤 독립11개를 재실행했다. 제품 결함으로 판정하지 않았다.

실제508건의 READ ONLY 조회에서 수정 전 복사본과 후보를 profiler 없이 전후2쌍 교대로 측정했다. 해시 생성은 timer 밖이다. 아래 후보는 운영에 반영하지 않았다.

| 범위 | 변경 전1 / 2 | 후보1 / 2 |
| --- | --- | --- |
| 전체 서비스 | 7.211 / 7.479초 | 7.269 / 7.275초 |
| 대화 조회 | 1.967 / 2.015초 | 1.895 / 1.993초 |
| 평가 조회 | 5.172 / 5.387초 | 5.301 / 5.206초 |
| 대화 SQL | 295 / 295회 | 247 / 247회 |
| 평가 SQL | 470 / 470회 | 470 / 470회 |

대화 문서 SQL은93→45회로 줄었고 전체508건 summary·첫25건·대화25건의 해시는 네 번 모두 같았다. 전체평균7.345→7.272초(72.907ms/0.99%), 대화평균1.991→1.944초(2.40%)다. SQL 감소와 방향상 하한은 충족했지만 전체 첫쌍은58.218ms 느려졌고 둘째는204.033ms 빨라졌다. 기준선 두 표본의 차이267.671ms가 평균 개선보다 크고, 변경하지 않은 평가 시간도 평균25.483ms 변했다.

따라서 실질적인 전체 속도 개선을 입증했다고 보기 어려워 **미채택·보류**했다. 이는 기능 검증 실패나 통계적 회귀 확정이라는 뜻이 아니다. 독립 검토도 이 해석에 동의했다. 유리한 표본을 얻기 위한 추가 실측이나 두 번째 후보 구현은 하지 않았다. 이전 측정의7.6초와 직접 개선율을 계산하지 않는다.

후보 제품·신규 시험의 검증 시점 SHA를 확인해 증거 디렉터리의 `candidate-access.py`, `candidate-test_access_source_batch.py`로 보존하고 제품은 정확한 시작 복사본으로 되돌렸다. 새 시험은 일반 pytest 탐색 경로에서 제거해 미채택 후보를 요구하는 실패 시험을 남기지 않았다. 원복 후 기존 회귀27개가 통과했다. 시작2250파일 중2249개 동일·WORKBOARD만 변경·누락0이며 제품과 `.env`는 시작 SHA와 같다. 새 저장소 파일은 이 계획과 작업기록2개다.

기존25표2560행의 PK별 해시와 `.env`가 전후 동일하고 본래 API/launcher 프로세스 신원도 그대로다. health/ready200을 읽기 전용으로 확인했으며 API 재시작·신규 모델 호출0이다. ISSUE-00042에 후보 미채택·추가 성능 작업 보류와 다음 작업을 저장하고 진행 이력까지 새로고침으로 재조회했다. 상태 선택지에 보류가 없어 기존 `implemented` 상태를 유지하고 remaining과history에 보류 범위를 명시했다.

## 다음 프로젝트 작업

다음 등록 제품 작업은 **Agents SDK 모니터링의 대화 턴 연결과 실제 채택 문맥·문맥화 기록 보강**이다. 현재 코드와 최근 수용 기록을 별도 담당이 읽어 확인했다. 일반 연결4·백그라운드 실행·SDK 단일질문·Mermaid와 상세 모달은 이미 완료됐으므로 다시 착수하지 않는다.

1. 기존 대화 DTO의 sequence/segment/execution ID와 현재 권한 조회로 같은 대화의 턴별 실행 이동을 연결한다. 평가 반복을 대화 턴으로 표시하지 않는다.
2. 실제 모델 입력에 남은 이전 메시지·제외 이유·문맥 한도를 원래 턴 ID와 연결해 기록한다. 현재 dependencies는 프로파일의 최종 제한 전일 수 있으므로 전부 사용한 문맥으로 표시하지 않는다.
3. 문맥화 입력/응답과 `include_diagnostics=false`의 관측 경계를 오프라인 회귀로 확인한다. UI/default true인 일반 대화 정상 수집은 이미 실제 검증됐으며 전체 대화가 수집 실패라고 단정하지 않는다.

과거 manager 후보는 후속 질문에 문맥화+관리자+답변3회가 필요했다. 10/26 활성화된 direct 구성의 기존 기록과 현재 budget 코드는 문맥화1+답변1의2회 경로가 가능함을 보여준다. 이번에는 현재 DB 프로파일을 새로 읽지 않았으며 실제 멀티턴은 미검증이다. 새 대화 첫 질문+후속1개를 실제 비교하면 총 최대3회가 필요할 수 있다. 정확한 실행 계획과 새 호출 예산은 별도로 정하며, 소진된 승인을 재사용하지 않는다.

스레드만 바꾸는 첫 입력 속도 실험은 별도 후보로 남기고 이번 성능 한 차례 뒤 자동으로 연결하지 않는다. 후속 제품 순서는 SDK 모니터링 → 벡터 저장소 비교 → 로컬 LLM 파인튜닝 비교 → Kubernetes다. 이번에는 다음 작업의 확인만 수행했으며 구현·새 모델 호출·프로파일 변경은 하지 않았다. 상세 코드 근거는 작업 증거의 `next-work-audit.md`에 보존한다.

세부 근거는 `.local-data/project-agent-work/execution-conversation-read-20261026/`의 설계·독립검증·실측·원복·보존 기록이다. 앞선 채택 개선과 일반 연결·백그라운드 실행은 유지한다. 추가 목록 성능 최적화와 스레드 비교는 보류하며 재개를 자동 추정하지 않는다. 기존 정답0/2·첫 입력 지연은 남고 새 모델 품질 통과나 신규 UI/모바일 수용으로 확대하지 않는다.
