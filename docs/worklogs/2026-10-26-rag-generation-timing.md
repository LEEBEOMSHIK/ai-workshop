# 생성 단계 병목 확인과 모델 호출 계측

- 날짜: 2026-10-26
- 요청: 생성 단계가 무엇을 하는지 명확히 확인하고 성능 개선에 쓸 정보를 제품에 보관한다.
- 관련: ISSUE-00038, [계측 계약 ADR-0042](../decisions/0042-rag-model-call-timing.md), [이전 실측](2026-10-26-rag-embedding-lifetime.md)

## 확인한 사실

기존 실행 `6566ad3a-5066-479f-a12e-03e32143d552`의 저장 기록을 재확인했다. 생성 단계는 관리자가 답변 담당에게 위임할 작업을 생성하는 호출과, 답변 담당이 질문·선별 근거를 읽고 인용 포함 답변을 생성하는 호출을 포함한다. 관리자 최종 생성 호출이 한 번 더 있는 구조가 아니다.

| 같은 질문의 실행 순서 | 생성 단계 | 관리자 모델 span | 답변 담당 모델 span | 단계와 두 span의 차이 |
|---|---:|---:|---:|---:|
| 첫 실행 | 219.886초 | 25.146초 | 193.894초 | 0.846초 |
| 두 번째 | 20.793초 | 4.480초 | 15.874초 | 0.439초 |

차이는 순차적인 두 모델 span 밖의 애플리케이션 잔여 경과 시간이다. 네트워크·모델 적재·대기 시간으로 재분류할 근거가 없다. 부모 agent와 위임 span은 중첩되므로 합산하지 않는다. 첫 지연이 답변 담당 모델 호출에 집중된 것은 확인했지만, 해당 호출 내부의 적재·입력 처리·출력 생성 기여도는 미측정이다.

설치된 Ollama 0.40.3과 공식 해당 버전 소스를 대조했다. `/api/version` 읽기만 수행했으며 생성 호출은 하지 않았다. 바이너리 SHA256은 `539b92d2bfac33e553366e365110b7a9c69070ef5ec1703ea0e7789e2283d9d1`이다. 설치 SDK는 openai-agents 0.24.0, openai 3.37.0, httpx2 2.16.0이다.

- 현재 비스트리밍 `/v1/chat/completions`: `ToChatCompletion`이 timing을 응답에 넣지 않는다.
- 스트리밍+usage chunk: 입력/출력 시간 확장이 있지만 모델 적재·전체 서버 시간은 없다.
- native `/api/chat`: total_duration/load_duration/prompt_eval_duration/eval_duration을 제공한다.

이는 SDK가 이미 받은 값을 버린 문제가 아니라 현재 서버 응답 변환에서 빠지는 정보다. 기존 로그 후보에도 상관관계 있는 Ollama 로그를 확인하지 못했다. 로그 활성화나 프로토콜 전환은 하지 않았다. 공식 근거는 [native API](https://docs.ollama.com/api/chat), [0.40.3 비스트리밍 변환](https://github.com/ollama/ollama/blob/v0.40.3/openai/openai.go#L301-L329), [스트리밍 변환](https://github.com/ollama/ollama/blob/v0.40.3/middleware/openai.go#L126-L160)이다.

## 제품에 남기는 정보

관리자/답변 담당의 각 model span에 `model_timing`을 추가했다. 요청부터 헤더·전체 본문 iterator 완료까지의 누적 시간, 요청 종료 시간, 별도의 JSON/usage/출력 계약 검증 시간을 기록한다. 본문 iterator는 HTTPX 자동 close를 포함한다. 비스트리밍 헤더 도착을 첫 토큰 시간으로 부르지 않는다.

내부 시간의 미제공 사유 `not_exposed_by_non_streaming_api`를 명시하며 모르는 적재·입력·출력 시간을 0이나 추정값으로 저장하지 않는다. 과거 span의 model_timing은 None이다. 연결 실패에는 경과 시간만, 부분 수신에는 헤더까지, 전체 본문 뒤 검증 실패에는 검증 시간까지 남긴다. timeout과 사용자 취소의 기존 최종 상태를 보존한다.

기존 비공개 실행 DB JSON → 현재 권한 확인 → 상세 API로 이어진다. metadata-only 투영에도 본문 없는 timing은 유지된다. 새 테이블·migration·외부 전송·자격 증명·모델 추론 본문 기록은 추가하지 않았다. 요청/모델/프로파일/재시도/종료 확인 계약은 그대로다. 전용 UI와 직접 생성/문맥화 어댑터 계측은 이번 범위 밖이다.

## 검증과 본래 환경

- 구현 전 신규 테스트2개가 timing 부재로 실패하는 것을 확인하고 구현 후 통과했다.
- 최종 독립 orchestration+executions 단위 테스트 **282개 통과**. 성공·연결 실패·부분 수신·검증 실패·시간 초과·취소·숫자/순서 검증·과거 기록·개인정보 배제를 포함한다.
- 별도 결정론적 구간 및 계측 실패 테스트4개 통과(위282개와 중복). HTTPX가 EOF에서 자동 close한다는 설치 소스 확인 후 본문 시간 의미를 정정했다. NaN 계측은 관측 불완전으로 남고 답변은 바뀌지 않는다.
- 기존 DB rollback 통합 **1개 통과**: SDK mock2회 → 실제 recorder → 소유자 상세, 타 사용자 거부, terminal 변경 거절, 과거 JSON. COMMIT 거부·SAVEPOINT·외부 rollback 후 신규3행 없음과 기존5표 지문 동일을 확인했다.
- 변경 Python3파일 및 보조 generation/execution.py의 **strict Mypy4파일 통과**. 지정 파일 밖 프로젝트 import는 skip하고 Pydantic/HTTPX 등 외부 타입은 정상 추적했다. 전체 프로젝트 타입 통과를 의미하지 않는다. 전역 follow-imports=skip의 첫 검사는 외부 기반형도 Any가 되어 실패했으며 이 범위를 정정했다.
- 변경 Python/테스트 Ruff 통과. OpenAPI 재생성 및 frontend 전체 TypeScript 검사 통과.
- 본래 API의 실행 중 작업0건을 확인한 뒤 동일 Conda 실행기·포트·루프·루트 작업 폴더로 재시작했다. health/ready 정상과 실제 API의 model_timing 스키마·본문 경계 자동 close 설명까지 최종 반영한 것을 확인했다.
- 이전에 브라우저 문제로 남았던 완료 화면은 이번에 연결이 회복되어 결과 새로고침으로 2/2완료·정답0/2·첫 평가 내부253.6초를 확인했다. 이는 모니터링 전체254.080초와 기준이 다르다.

실제 모델 호출은 **0회**다. 기존 승인4회 예산은 이미 소진했으며 새 계측으로 실제 LLM을 다시 실행한 수용 검증은 아직 하지 않았다. 기존 품질 실패·후보 비승격을 유지한다. API 반영 자체를 지연 개선이나 모델 내부 병목 해결로 보고하지 않는다.

## 다음 성능 개선 판단

실제 내부 적재·입력·출력 시간을 얻으려면 native API 어댑터 또는 서버 측 상관관계 계측이 필요하다. 먼저 기존 도구 위임·출력 schema·reasoning·토큰 예산·취소/종료 의미의 동등성을 설계·검증해야 한다. 그 뒤 별도의 제한된 실제 호출 범위에서 같은 질문·근거·설정으로 수집한다. 현재 증거만으로 모델 적재나 입력 처리 중 하나를 확정 병목으로 선언하지 않는다.

중간 위험도의 관측 계약 변경으로 아키텍처·백엔드·AI·RAG·테스트/독립 검토·문서 역할을 적용하고 본래 반영 시 인프라 역할을 추가했다. UI·DB 구조·모델 선택은 변경하지 않았다. 기존 작업 변경과 실행 자료를 보존하며 commit/push는 수행하지 않았다.

## 최종 보존과 문제 이력

읽기 전용 트랜잭션의 전후 지문으로 기존 RAG 관련25표2,469행과 `.env` 동일을 확인했다. 작업 시작 시 기존 변경217파일 중212개 동일, 허용된5개 변경, 누락0이다. 변경된 기존 파일은 WORKBOARD, RAG 설계, agent_trace, model_transport, 생성 API 타입이다. 새 계약/테스트/ADR/본 기록은 별도로 추가했다.

본래 로그인 화면에서 [ISSUE-00038](http://127.0.0.1:5173/admin/system/issues?issue=5f3aab7a-d9a1-4704-a510-d892209bae3b)에 이번 결과와 직전 임베딩 실측의 누락 이력을 추가했다. 구현 내용과 남은 작업도 갱신하고 전체 새로고침 뒤 보존을 확인했다. 상태는 구현됨·검증 남음을 유지하며 기존 이력·문서 버전은 보존했다. 편집 중 revision 충돌은 정식 최신 내용 재열기 후 비교·저장으로 처리했다. 이 보고서 경로와 ADR 경로는 진행 이력에 기록했으며 별도 DB 문서 버전 등록은 하지 않았다.
