# 개발 및 운영 지침

- 상태: 승인됨
- 기준일: 2026-08-29

## 1. 변경 절차

1. 목적과 성공 기준을 먼저 정한다.
2. 모듈 경계나 공개 계약을 바꾸는 기능은 구현 전에 설계한다.
3. 중요한 기술 선택은 `docs/decisions`에 기록한다.
4. 구현과 테스트를 함께 변경한다.
5. 코드와 문서의 설명이 달라지면 같은 변경에서 갱신한다.
6. 검증 결과 없이 기능이 완료됐다고 판단하지 않는다.

## 2. 아키텍처

- `Platform`과 `Labs`의 책임을 섞지 않는다.
- API 핸들러와 UI 컴포넌트에 핵심 업무 규칙을 두지 않는다.
- 데이터베이스, 검색 엔진, 파서와 모델 런타임은 어댑터를 통해 호출한다.
- 특정 프레임워크의 객체를 도메인 경계 밖으로 전파하지 않는다.
- 한 파일이나 모듈이 여러 책임을 가지면 역할별로 분리한다.
- 실제 반복이 확인되기 전에는 공통 추상화를 만들지 않는다.

## 3. 문서와 검색 근거

- 운영 색인의 모든 청크는 원본 문서, 버전, 구조 요소와 위치로 추적할 수 있어야 한다.
- 페이지, 문단, 슬라이드, 시트 또는 셀 근거를 잃은 청크는 정상 색인으로 승격하지 않는다.
- 추출한 원문, 모델의 해석, LLM 생성 내용을 데이터와 화면에서 구분한다.
- 의미 하이라이트가 정확한 문자열 일치를 의미하는 것처럼 표현하지 않는다.
- 낮은 OCR 또는 파싱 신뢰도와 부분 실패를 사용자에게 표시한다.

## 4. 권한과 보안

- 모든 원본 문서와 학습 기록은 기본 비공개다.
- 권한 및 지식 공간 필터는 BM25와 벡터 검색 전에 적용한다.
- 검색 후 결과를 숨기는 방식으로 접근 제어를 구현하지 않는다.
- 에이전트는 호출 사용자의 권한보다 넓은 문서 범위를 사용할 수 없다.
- 로그, 오류 메시지, 검색 제안과 지표에 비공개 본문을 남기지 않는다.
- 외부 API에는 공개 또는 비식별로 승인된 데이터만 보낸다.
- 공개 환경은 비공개 저장소에 직접 연결하지 않는다.

## 5. 모델과 프로파일

- 모델명, 모델 버전과 중요 파라미터를 업무 코드에 직접 고정하지 않는다.
- 색인, 검색, 생성 프로파일을 분리한다.
- 임베딩 또는 청킹 방식이 바뀌면 호환되는 새 색인 버전을 만든다.
- LLM만 변경할 때는 기존 검색 색인을 재사용한다.
- 모든 실행은 사용한 프로파일과 모델의 정확한 버전을 기록한다.
- 평가되지 않은 프로파일은 일반 검색 기본값으로 승격하지 않는다.
- 실패한 실험도 원인 및 관찰 결과와 함께 보존한다.

## 6. 에이전트

- 정해진 알고리즘으로 해결 가능한 작업에는 LLM 에이전트를 사용하지 않는다.
- 에이전트 캐릭터, 서비스 작업자, LLM 실행 주체를 분리한다.
- 에이전트는 승인된 애플리케이션 도구만 호출한다.
- 도구의 입력 계약, 출력 계약, 제한 시간과 오류 유형을 명시한다.
- 도구 선택, 결과, 근거, 소요 시간과 오류를 감사 가능한 형태로 기록한다.
- 모델의 비공개 내부 추론을 저장하거나 사용자에게 실행 근거로 제시하지 않는다.

## 7. 비동기 작업과 오류

- 작업은 중복 요청이나 재시도에도 데이터가 손상되지 않도록 멱등성을 가진다.
- 문서 버전은 파싱과 필요한 색인이 완료된 뒤 원자적으로 활성화한다.
- 오류를 숨기고 다른 파서나 모델로 조용히 전환하지 않는다.
- 대체 처리와 재시도는 실행 기록과 사용자 상태에 표시한다.
- 전체 실패와 페이지 또는 요소 단위의 부분 실패를 구분한다.
- 재시도 가능한 오류와 사용자 조치가 필요한 오류를 구분한다.
- 실패한 작업은 원본과 진단 정보를 유지해 다시 실행할 수 있게 한다.

## 8. 코드와 테스트

- Python과 TypeScript에 정적 타입 검사를 적용한다.
- 단위 테스트는 외부 모델, 네트워크와 검색 엔진 없이 실행 가능해야 한다.
- PostgreSQL, Elasticsearch, 객체 저장소와 작업 큐는 통합 테스트에서 검증한다.
- 프론트엔드와 백엔드는 명시된 API 계약을 공유하고 프론트 타입을 생성한다.
- 문서 파서는 형식별 공개 또는 합성 고정 파일로 회귀 테스트한다.
- 권한 테스트에는 서로 다른 공간과 역할의 부정 사례를 포함한다.
- 검색 평가에는 BM25 기준선을 항상 포함한다.
- 실제 민감 문서를 테스트 데이터로 사용하지 않는다.

## 9. 관찰 가능성과 감사

요청, 비동기 작업, 모델 호출, 검색 실행과 에이전트 실행에 공통 상관관계 ID를 사용한다. 다음 항목을 구조화해 기록한다.

- 작업 상태와 단계별 소요 시간
- 파서, 모델 및 프로파일 버전
- 문서와 색인 버전 식별자
- 반환한 결과 수와 필터 범위
- 외부 API 사용 여부
- 재시도, 대체 처리와 오류 코드

민감한 본문과 비밀값은 관찰 데이터에서 제외한다.

## 10. 문서화와 공개

- 자유 메모와 공식 설계 문서를 구분한다.
- 실험 문서는 다른 사람이 같은 데이터 스냅샷과 프로파일로 재현할 수 있어야 한다.
- 공개 결과물은 내부 기록을 직접 복사하지 않고 승인된 인용과 설명으로 구성한다.
- 실패 사례를 공개할 때는 문제, 시도, 실패 원인, 변경과 배운 점을 함께 설명한다.
- 공개 전 원본 문서, 사용자 정보, 경로, 질의와 로그의 민감정보를 확인한다.
