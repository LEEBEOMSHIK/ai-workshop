# 첫 입력 처리의 배치·스레드 후속

2026-10-26, ISSUE-00038. 선택형 배치·스레드 설정 구현·검증·본래 API 반영과 사용자 승인4/4회·retry0 실측을 완료했다. **batch256은 첫 입력 처리 개선을 보여주지 못했다.** 새 기준130.876초→132.683초로1.807초(1.38%) 느렸다. 입력·두 답변·인용·28근거는 같고 추가 품질 퇴행은 관찰되지 않았지만 기존 정답0/2는 유지된다. 후보는 비기본·미승격이다. 실제 결과의 이슈 DB 갱신과 완료 화면 확인은 브라우저 도구 중단으로 남는다.

## 사전 조사와 판단

- 현재 Ollama0.40.3 serve는 실행 중이지만 적재 모델·runner는 없다. 저장 모델 parameters에는 배치·스레드 override가 없으며 직전 실행의 실효값은 미관측이다.
- API 기본 num_batch512와 scheduler의 자동 실행 배치는 다를 수 있다. 명시 num_batch는 논리 batch와 physical ubatch를 함께 변경한다. num_thread는 기본 실행 스레드 수이며 입력 전용 설정이 아니다.
- 첫 비교 후보는 num_batch256만 지정하고 스레드는 자동 선택을 유지한다. 작업 메모리·캐시 압박 완화 가능성을 검증하는 가설이며 더 빠르다는 증거는 없다.
- temperature0에서도 배치·병렬 연산에 따라 출력이 달라질 수 있다. 같은 모델·입력과 기존 품질 평가를 유지하고 실제 답변·인용을 비교하기 전에는 품질 보존을 확정하지 않는다.

[공식 옵션](https://github.com/ollama/ollama/blob/v0.40.3/api/types.go), [자동 배치](https://github.com/ollama/ollama/blob/v0.40.3/server/sched.go), [runner 인자](https://github.com/ollama/ollama/blob/v0.40.3/llm/llama_server.go), [수치 재현성](https://github.com/ggml-org/llama.cpp/blob/b11351/tools/server/README.md)을 확인했다. 현재 앱 AMD64 유지 정책을 실제 Ollama 바이너리의 아키텍처 확인으로 대신하지 않는다.

## 변경과 역할

[ADR-0047](../decisions/0047-ollama-runtime-batch-threads.md)의 strict/frozen `orchestration.ollama_runtime`을 policy→native codec→transport에 연결했다. 명시한 배치·스레드만 native options에 추가하고 잘못된 값·지원하지 않는 API는 전송 전에 거부한다. 생략/null인 기존 요청은 바이트 그대로 유지한다. 모델·검색·입력·근거·출력 예산·인용·권한·재시도 경계와 DB/UI 공용 계약은 유지했다.

프로파일과 고정 snapshot을 수정하지 않고 중첩 frozen mapping을 해석한다. 실제 native 요청에 보관한 값은 요청값이다. 해당 실행에서 관측한 runner 값과 구분하며 실효값을 추정해 채우지 않는다.

AI 런타임·생성 프로파일 변경으로 분류했다. 메인이 요구·경계·문서·통합을 담당하고 AI/백엔드 구현, 독립 테스트·DB 검증, 독립 코드/런타임 리뷰를 분리했다. UI·색인·권한·DB 구조 변경은 제외했다. 기존 미커밋 변경에 의존하므로 현재 checkout을 보존했다.

## 구현 검증과 본래 환경

- 관련 고유 회귀 **256개 통과**: 전체 orchestration 및 generation readiness/profile resolution. 신규 구현46개와 독립12개는 이 수에 포함하며 중복 합산하지 않는다.
- 기존 DB rollback 통합 **1개 통과**: 실제 SDK mock 요청값 저장→현재 owner 조회, 다른 actor 거부, 종료 후 변경 차단과 과거 기록 조회. 모델·실제 provider 호출0회.
- 범위 지정 strict Mypy6 source files, 제품3파일·신규 테스트 Ruff 통과. 전체 저장소 타입 검증으로 확대하지 않는다. 린트 서식 수정의 영향2사례 재검증 통과.
- 유휴 기존 API만 동일 launcher로 재기동했다. health/ready200과 기존 v6 상세 schema를 확인했다. 독립 재기동 전후 원본25표2,523행 전체 PK 해시와 `.env` 동일, 기본 cache0, pending/running run0이다.
- 설치·새 DB/계정·모델/전역 설정 변경·commit/push·캐시 삭제는 없다.
- 기존259파일 중253개 동일·허용한 제품3/WORKBOARD/RAG설계/runbook6개만 변경·누락0이다. 로컬 링크237개·최근 완료5개·지정 범위 `git diff --check`를 독립 확인했다.
- 실측 준비의 오프라인 검사34개와 모델 identity 순수 검증16개가 통과했다. 모델·네트워크·DB 호출 없이 상한/입력 변경/모델blob·PID·생성시각 불일치 거부를 확인한 결과이며 실제 측정 결과는 아니다.

명령, XML, source 조사, 독립 리뷰와 보존 결과는 `.local-data/project-agent-work/prefill-runtime-20261026/`에 보관했다. 실제 사용자 자료나 비밀값을 이 문서에 복사하지 않는다.

## 구현 후 준비한 실제 비교

직전 direct 후보의 고정 snapshot을 기준으로 runtime 옵션만 추가한 후보 JSON을 준비했다. 이 준비 단계에서는 프로파일·평가를 등록하지 않았다. 같은 공개 합성 질문·v6 입력·direct 답변·worker 재사용16MiB에서 기존 조건2회와 batch256 조건2회를 순차 비교하도록 했고, 이전 승인2/2 소진 뒤 새 승인을 받았다. 아래에 실제 실행 결과를 구분해 기록한다.

실행 도구는 승인 manifest, 전체4회/조건별2회 상한, 실패·불확실 전송도 소비로 계산, 고정 snapshot과 runtime 옵션 외 전체 요청 동일성 검사를 갖는다. 모델 alias의 예상 blob과 serve identity를 전송 전에 확인하고 요청 중 runner의 batch/ubatch/thread를 별도로 관측한다. blob 이름의 내용 주소를 대조하며 모델 파일 전체를 다시 해시한 검증으로 표현하지 않는다. 실행 원장은 독점 생성해 같은 승인 재실행을 막는다.

실행 시각순으로 첫/반복을 나누고 전체·load/prefill/decode·입력 토큰·답변·인용·28근거와 필수 조건을 비교한다. 기준 배치가 실제256이면 다른 설정의 효과로 해석하지 않는다. 임의 unload/warmup·추가 호출·자동 튜닝은 없다. 기존 정답0/2를 통과로 바꾸지 않으며 추가 퇴행 시 후보를 채택하지 않는다. 더 넓은 질문 품질과 일반 기본 승격은 별도 수용이 필요하다.

관리자 세션 만료 뒤 사용자가 본래 계정으로 다시 로그인했다. ISSUE-00038의 수정 내용·검증·남은 작업과 누적 진행 이력을 저장하고 전체 새로고침으로 재확인했다. 기존 품질 실패·비기본 상태와 과거 이력은 보존했다. 저장 화면은 로컬 산출물의 `issue38-runtime-saved.png`다.

## 추가 승인과 등록

사용자가 같은 날 **최대4회 품질·입력 처리 속도 비교 진행**을 승인했다. 위 준비 시점의 승인 대기 상태는 이 승인으로 해제됐다. 기존 조건2회와 batch256 조건2회·자동 재시도0회이며 다른 튜닝·기본 승격은 포함하지 않는다.

- 기준 run: `76b51592-89ef-480a-845a-5557f5bd2a46`, 기존 direct 구성·프로파일 재사용. 고정 snapshot SHA256은 과거 direct와 같다.
- batch256 run: `7c31b2fc-635a-4dba-9f51-30801b51780d`, 새 비기본 프로파일 `ea34f286-b05b-427d-b7e3-f2037b2738a6`·구성 버전 `58fc78cd-1cf0-430e-9608-6c10df7f3dfe`.
- 본래 관리자 화면으로 등록했고 독립 확인에서 기존2,523행 변경/삭제0, 허용 신규12행(후보6·run2·attempt4)만 추가됐다. 두 run은 각각 pending2·attempt1이고 execution/audit0, `.env`·기본cache0을 유지한다.
- 읽기 전용 사전검사가 전체 프로파일의 임베딩 연결을 생성 프로파일의 빈 모델 연결로 혼동해 차단했다. 실제 연결은 세 snapshot 모두 동일했다. 측정 helper의 비교를 기존 연결 전체 동일성 및 생성 연결 없음으로 바로잡으며 제품·고정 입력을 수정하지 않는다. 이 차단까지 실제 모델0회·실행 원장 미생성이다.

사전검사 도구의 가정을 바로잡은 뒤 전체 연결 동일성·baseline raw snapshot 동일성 검증6테스트/22하위사례를 통과했다. 모델 show 메타데이터의 FROM이2개임을 확인해 두 내용 주소를 순서대로 고정했고 identity 순수 검증30개를 통과했다. PowerShell JSON 변환이 생성 시각의 마지막0을 줄인 것은 원래7자리 문자열로 복원했다. 프로세스나 모델이 바뀐 것은 아니며 실제 파일 재해시·모델 호출·제품 수정은 없었다. 최종 원본 DB/두 snapshot/모델 출처/serve identity 읽기 전용 preflight 통과 후에만 실측을 시작했다.

## 실제 결과

최대4회 승인으로 기준2회→batch256 2회를 순차 실행했고 worker exit0, 실제 전송4와 DB 모델 span4가 일치했다. retry0·각 attempt_number1·두 run completed/claim 해제를 독립 확인했다. 실행 시각순으로 비교했으며 기준은 반복0→1, 후보는 반복1→0이었다.

|---|---:|---:|
| 전체 응답 | 195.312 / 18.391초 | 166.047 / 7.528초 |
| 답변 생성 단계 | 157.386 / 13.579초 | 151.983 / 6.785초 |
| 서버 준비·로드 | 15.414 / 0.395초 | 12.502 / 0.015초 |
| 서버 입력 처리 | 130.876 / 0.066초 | 132.683 / 0.158초 |
| 서버 출력 생성 | 9.076 / 11.932초 | 6.489 / 6.452초 |
| 각 입력 / 출력 토큰 | 3549 / 99 | 3549 / 99 |

첫 전체 응답은29.265초 줄었지만 검색27.791→7.129초·선택8.313→6.408초 차이가 크다. 배치 옵션이 직접 바꾸지 않는 비용이므로 전체 감소를 배치 효과로 귀속하지 않는다. 생성도 로드·출력이 감소했지만 목표인 입력 처리는1.38% 증가했다. 과거134.920초보다 작다는 사실만으로 개선이라고 하지 않고 같은 새 비교의130.876초를 기준으로 판정했다. OS 캐시·부하·실행 순서·열/스케줄링·관측 부하를 분리한 실험이 아니며 두 반복을 운영 P95로 일반화하지 않는다. 포함 관계의 시간을 합산하지 않는다.

기준 첫 요청에서 실제 runner batch/ubatch는1024/1024, 후보 첫/반복은256/256이었다. 예상 모델·serve identity와 활성 요청 구간을 대조했다. 기준 반복의 runner 관측은 TimeoutExpired로 실패했고 값은 미확인이다. 모든 관측에서 명시 스레드 인자는 없었으므로 자동 스레드 실효값도 미확인이다. API 기본512나 첫 관측값으로 누락값을 채우지 않았다.

runtime 옵션 외 실제 native 입력, 지침·agent 입력, 답변 JSON·최종 답변·인용·28개 근거의 원문/출처/위치/순서·eN변환표가 과거 direct 및 새 기준과 모두 같았다. 이번 공개 사례의 추가 퇴행은 관찰되지 않았다. 기존 일반 지급 규칙과 휴일 조건 누락·정답0/2는 그대로이며 전체 품질 통과가 아니다. 인용 유효·coverage1·권한 누출0을 확인했고 현재 owner 재조회 및 다른 actor 거부도 통과했다. 동일120초 정책의 두 표본 pipeline P95는 기준185.536초·후보157.976초로 둘 다 실패다.

원본25표2,523행 변경·누락0, 정확히 허용 신규24행(후보6·run2·attempt4·execution4·audit4·audit-workspace4)만 추가돼2,547행이다. `.env`·기본cache0 유지, worker만16MiB이며 worker 종료와 실행 시작 제품 소스62개 SHA 동일을 독립 확인했다. 기록은 `review-runtime-comparison.json`, `runtime-live-independent-review.md`, `review-live-final.json`, `review-live-preservation.json` 및 실제 전송 원장에 보관했다.

## 판정과 다음 작업

배치256을 첫 입력 처리 개선안으로 채택하지 않는다. 선택형 설정과 실제 요청값 보관 구현은 유지하고 후보는 draft/pending·비기본·미활성으로 남긴다. 기존 기본값·품질 기준·모델·검색은 변경하지 않았다. 새4/4 호출 예산은 소진됐으며 추가 호출은 하지 않았다.

다음 성능 수정은 batch256과 스레드를 한꺼번에 바꾸는 방식이 아니라, 기존 배치 조건을 유지하며 스레드 수만 명시하는 단일 조건 비교다. 자동 스레드 실효값과 장치 코어/런타임 선택 근거를 먼저 확인하고 수치를 정한다. 같은 입력·근거·답변/인용·필수조건을 비교하며 새 호출 범위 전에는 실제 실행하지 않는다.

구현 단계의 ISSUE-00038 갱신은 저장·새로고침으로 확인했다. 실측 완료 뒤 기존 탭이 복원된 새 ID로 바뀌었고 browser focus 연결이 실패했다. 이어 도구가 Windows의 현재 URL을 확정할 수 없어 Computer Use를 중단했으므로 우회하지 않았다. **실제 결과의 관리자 이슈 DB 갱신과 완료 화면 확인은 미완료**이며 로컬 비교 결과와 구분한다. 후속 전달할 실제 결과는 같은 산출물의 `issue38-live-update.json`에 준비한다.
