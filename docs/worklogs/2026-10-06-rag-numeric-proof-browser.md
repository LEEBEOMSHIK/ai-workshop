원문·실행 상세 링크 클릭 직후 현재 탭 상태는 변하지 않았다. 이미 표시된 정확한 href로 같은 탭을 이동하여 대상 화면을 확인했으므로 링크 클릭 전환까지 성공했다고 주장하지 않는다. 전체 사용자 탭 목록 조회는 개인 탭 메타데이터 노출 위험으로 자동 승인 검토가 거절하여 중단했다. 다른 탭을 조사하거나 보안 우회하지 않았다.

실제 화면 스크린샷은 도구 출력에서 관찰했다. 지속 저장 경로나 최종 이미지 링크를 제공받지 못하여 저장된 화면 증거 파일이 있다고 주장하지 않는다. 원문·답변 스냅샷을 보고서나 DB 문서 본문에 넣지 않는다.

## 본래 대화와 런타임

기존 합성 자료 대화 `e28d7d82-cf7b-41a9-a0c8-51a121fbd2d4`를 목록에서 열었다. 과거 실패·근거 부족·취소가 복원되고 기존 선택 PDF 범위를 유지했다. 새 질문 없이 메뉴 진입·복원만으로 새 세션이 생성됐다는 관측은 없다.

첫 추가 turn `86d94061-a4fd-46ea-b348-1c3529fc8976` / execution `2ceadaba-1c5b-4ddc-9372-e66f9603bdfe`는 `conversation_execution_failed`로 종료됐다. 실제 모니터링은 요청·권한 및 이전 대화 준비 완료, 검색26.5336초 실패, 근거 선택·생성·인용 생략, 저장 완료를 표시했다. 답변·audit·numeric receipt는0이다. root의 안전 로그는 `ImportError`, phase=execute, `__init__.py` line436만 기록한다.

같은 공식 Python3.13.15·기존 venv에서 모델 호출 없이 import-only 검사 첫 실행은 Torch 통과/Sentence Transformers의 SciPy 경유 DLL ImportError였다. 프로젝트 경로에 한정한 Windows CodeIntegrity 기록은21:37:49 및21:39:11 KST에 `_lsap.cp313-win_amd64.pyd`의3033/3077 차단을 확인했다. 이것은 검색 런타임 장애 근거이며 LLM 품질 문제와 구분한다. 이후 같은 환경의 두 번째 import-only 검사는 Torch2.13.0+cpu·Sentence Transformers6.0.0 모두 통과했다. 보안 설정·패키지·환경·서버를 변경하지 않았고 일시 통과를 영구 해결로 간주하지 않는다.

두 번째 추가 execution `dcdb7789-9d77-47fa-8a0b-9cffc7ccf810`은 검색13.33초·선택8.89초 완료 후 `InvalidRequestError`로 실패했다. 허용 audit1·선택 근거0·receipt0이며, audit commit 뒤 최종 원문 권한을 재조회할 때 HTTP 요청의 바깥 `session_factory.begin()`이 이미 닫혀 SQLAlchemy `_trans_ctx_check` line111에서 거절한 것이 원인이다. 평가 workflow는 바깥 begin 없는 세션을 사용하여 실제 HTTP와 실행 구성이 달랐다. 앞선 DLL 차단과 별개의 원인이다.

RAG 검색 전용 `get_search_session`을 추가하고 검색 서비스·구성 resolver 두 의존성이 같은 세션을 공유하도록 변경했다. 바깥 begin 없이 요청 성공 시 남은 작업을 commit하고 실패·취소 시 현재 미커밋 작업만 rollback한다. 이미 저장된 audit와 최종 원문 권한 재확인은 유지한다. 공통 Platform 세션·권한·프로파일·migration·모델·프론트 코드는 변경하지 않았다. [RAG 설계](../labs/rag/design.md)에 세션 경계를 반영했다.

실제 AsyncSession과 SQLite를 사용하는 외부 모델·네트워크 없는 회귀에서 변경 전3개가 같은 line111 오류로 실패하고 수정 후5개가 통과했다. 독립 리뷰는 관련21개 통과·차단 의견0을 확인했다. 루트 관련 전체 회귀는1335통과/4skip/기존 Starlette 경고1,96.93초·exit0이며 mypy411 source files와 변경 Python3파일 Ruff/format 검사도 통과했다. 첫 전체 실행은 backend 작업 디렉터리에서 필수 Settings.secret_key 미설정으로1325통과/10환경 검증 실패였다. 같은 명령을 공개 합성 secret을 해당 시험 자식 프로세스에만 지정하여 재실행했으며 본래 `.env`나 계정·DB를 바꾸지 않았다.

진행 실행·대화 turn·평가0과 기존 프로세스의 정확한 경로·명령을 확인한 뒤 본래 API만21:53:33 KST에 같은 저장소 루트·`.env`·공식 Python으로 재시작했다(API97488/venv launcher96032,18000). 프론트7824/5173·Docker·worker/beat 상태는 유지했고 직접 health/readiness·프론트 경유 health 모두200이었다. 이 재시작은 HTTP 세션 수정 반영이며 Windows 보안 정책 변경이나 DLL 차단의 영구 해결이 아니다.

같은 기존 대화·선택 PDF·같은 질문의 세 번째 execution `35a9ae93-614f-4cf4-82fa-27e0cfa98fc0`은 `conversation_execution_failed` 없이 **처리 완료·근거 부족**으로 정상 종료했다. 실제 실행 모니터링은 요청5.30초·검색25.68초·선택13.75초·저장0.09초·전체47.88초를 표시했다. 근거 선택0이므로 생성·인용은 생략됐다. 기존 대화를 새로고침하여 마지막 정상 결과와 앞선 두 실패 기록·선택 문서가 그대로 복원되는 것을 확인했고 임시 viewport는 원래 크기로 해제했다. 새 대화는 만들지 않았으며 추가 turn은3개다.

문맥 점수0.8730/0.8566/0.8534·키워드0.7143/0.7143/0.4286이 표시됐다. 앞의 두 후보는 자격 통과이나 입력 예산 초과로 전달 제외, 나머지는 임계값 미달이었다. 활성 v4 구성 `b7bec159-cc5f-45bb-af51-f29c588ce66b`의 실행 패널은 그룹8/근거 단위32/문자12000, 선택 단위0·근거 JSON2bytes를 표시했다. 유사도 부족만으로 원인을 설명하지 않으며 어느 개별 제한이 최종 초과됐는지와 범용적인 근거 단위 축소·선택 개선은 후속 조사 대상이다. 근거 부족은 정상 결과 저장 여부와 별개의 답변 품질 문제다.

독립 verifier의 읽기 전용 확인은 세 번째 실행 completed/insufficient_evidence·오류 없음·허용 audit1/근거0/토큰null/receipt0, 신규 turn3·신규 세션0·진행0이다. 저장 진단110개는 그룹3+단위107이며, 그룹 사유는 자격 통과 후 budget_exceeded2·below_threshold1, 단위107은 not_transmitted이다. 기존5turn과 먼저 추가된 두 실패의 turn/execution 전체 SHA가 보존됐다. 두 번째 실패는 response 미저장으로 상세 선택 분포를 독립 DB에서 복구할 수 없다.

독립 보존 검증의 최종 메타데이터와 이번 보고서의 정확한 DB 문서 ID·버전·SHA는 동결 본문을 다시 수정하지 않고 WORKBOARD와 작업 인계 기록에 남긴다. 과거 두 실패와 기존 결과를 지우거나 새 결과로 교체하지 않는다.

## 마감 경계

Task7 관리자 계산·진단 화면의 위 확인 범위와 실제 v6 대화 연결을 구분한다. v6 승격 조건이 미달이므로 연결을 변경하지 않았다. 실제 권한 철회·새 v6 대화·성공한 대화 문맥 유지·통화 환산 모델 결과·별칭 종료·Git 인계는 완료로 기록하지 않는다. 품질 개선만 남았다는 보고가 아니다.

이번 작업은 관리자 UI의 확인 범위와 HTTP 세션 오류의 구현·본래 재검증을 완료했다. 근본 DLL 차단 복구, 유효 답변·성공한 멀티턴 및 승인된 후보 연결 검증은 남는다. 실제 권한 철회·별칭 종료·Git 인계도 미완료이며, 전체 RAG 또는 품질 개선 외 작업 완료로 보고하지 않는다. 문제 이력에는 HTTP 세션 원인을 검증된 범위로, DLL 차단의 재발 방지는 open인 별개 원인으로 등록하고 관련5/26에는 후속 사건·정확한 보고서 버전을 추가 연결한다.
