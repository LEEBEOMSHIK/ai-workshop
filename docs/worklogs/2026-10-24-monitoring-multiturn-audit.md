# 실행 모니터링 가독성 재점검과 멀티턴 경계

날짜: 2026-10-24. 관련 문제: ISSUE-00035(재개), ISSUE-00036(이전 SDK 평가 본문 검증 범위).

## 요청과 작업 범위

사용자가 그림 보강 후에도 실행 모니터링을 읽기 어렵다고 재보고하고 멀티턴 고려 여부를 물었다. 본래 로그인 화면, 현재 소스, 저장된 SDK 후보 프로파일을 확인했다. 화면 담당과 AI·RAG 담당이 독립적으로 읽기 전용 조사했고 메인이 실제 화면·저장 설정과 대조했다. 제품·테스트 코드, 프로파일, 서비스는 변경하지 않았다. 실제 생성·임베딩 호출도 없다. 관리자 문제 이력과 이 문서·WORKBOARD만 갱신했다.

## 현재 화면에서 확인한 문제

- 본래 실행 상세의 1900×978 첫 화면은 실행 요약4개, 단계 종류 요약4개와 여러 안내 뒤 에이전트 그림의 시작만 보인다. 최종 답변은 에이전트 패널 아래에 있다.
- 질문·답변·검색 근거·LLM 전달 입력·처리 단계가 흩어져 있어 사용자가 서로 비교하며 읽어야 한다. 그림은 에이전트 호출 소속·부모 관계를 보여주지만 전체 RAG 처리 흐름은 별도 영역이다.
- 단계 선택 후 상세는 그림 아래에 나오므로 클릭 위치와 확인 위치가 멀다. 긴 지침·입력은 문자열 그대로 표시하여 JSON의 질문·이력·근거를 구분하기 어렵다.
- 실행 목록의 품질 표시는 `quality_status`와 무관하게 `품질 미검증`으로 고정돼 있다. API는 평가 품질 상태를 제공한다. 현재 코드에서 확인한 별도 표시 결함이며 이번에 수정하지 않았다.
- 이전 자동 검증은 가로 넘침, 키보드, 단계 선택과 실제 관계 표시를 확인한 것이다. 사용자가 전체 과정을 쉽게 이해한다는 수용 완료로 확대하지 않는다.

근거: `ExecutionDetailPage.tsx:66`, `AgentTracePanel.tsx:44,168,186`, `AgentFlowDiagram.tsx:132`, `AgentTracePanel.module.css:128`, `ExecutionListPage.tsx:70`, `evaluation/generative_monitoring.py:114`.

## 멀티턴의 구현과 한계

| 항목 | 확인 결과 |
|---|---|
| 과거 대화 사용 | 서버가 동일 대화 구간에서 현재 권한으로 볼 수 있는 완료·answered·서명된 Q/A를 골라 다음 요청에 전달한다. SDK 지속 세션 대신 매 요청에 이력을 재구성한다. |
| 이력 상한 | 서비스는 최대 최근20메시지를 준비하고 프로파일이 다시 제한한다. `max_history_turns`는 왕복 수가 아니라 메시지 수다. 질문/답변 쌍 보존을 보장하지 않으며 토큰 상한 때문에 이력이 비어질 수도 있다. |
| 검색 문맥화 | 유효 이력이 있으면 질문+이력으로 독립 검색 질의를 만든다. 원래 질문·재작성 질의·제한된 이력은 이후 SDK 입력에 전달된다. |
| 품질과 이력 | answered·서명 확인은 품질 평가 통과 조건이 아니다. 부정확한 이전 답변이 다음 이력에 들어갈 수 있다. 실패·취소·근거 부족 턴은 질문과 답변 모두 제외된다. |
| 대화 화면 연결 | 기존 턴 DTO에 sequence·segment·execution_id가 있고 턴별 실행 상세 링크가 있다. 한 대화의 턴 선택은 기존 API로 구성 가능하다. 실행 목록에는 대화별 묶음이 없다. |
| 실제 검증 | 기존 반복2회는 이력이 없는 질문을 독립 반복한 평가다. 실제 Gemma 연속 질문·후속 문맥 이해 품질을 검증한 것이 아니다. |

### 현재 SDK 후보 설정

본래 DB에서 읽기 전용 트랜잭션으로 프로파일 `114ab49b-99b2-4cbb-94ba-42e87cbd5239`를 조회했다. 이름은 `Gemma E2B SDK 위임 검증 2026-10-23`, 버전1, draft·is_default=false다. 일반 서비스의 기본 설정으로 해석하지 않는다.

| 설정 | 저장 값 |
|---|---:|
| 이력 메시지 수 | 4 (보통 Q/A 2쌍) |
| 이력 토큰 상한 | 1024 |
| 최대 모델 호출 | 2 |
| 호출별 출력 상한 | 512 |
| 전체 예약 출력 예산 | 1024 |
| timeout | 360초 |

이력이 없는 SDK 답변은 관리자1+답변 담당1의2회 경로다. 유효 이력이 있는 정상 후속 답변 경로는 문맥화1+관리자1+답변 담당1로3회가 필요하다. 현재 후보는 `orchestration_budget_exceeded`로 생성 전에 차단된다. 출력512 설정을 유지하면 예약 출력 예산도 최소1536이 필요하다. 이는 실제 사용 토큰1536을 뜻하지 않는다. 검색 근거가 없으면 이후 답변 생성은 생략될 수 있다. 임의로 제한을 올리거나 후보를 승격하지 않았다.

근거: `orchestration/budget.py:13`, `search/pipeline.py:417`. 기존 오프라인 테스트가2회 제한의 사전 거부와3회 예산의 문맥화+SDK 경로를 검증한다.

### 모니터링에 남은 관측 공백

- 채택·제외된 이전 턴과 제외 사유, 실제 적용된 문맥 예산이 명시적으로 조회되지 않는다. 단순히 대화에 있던 모든 턴을 LLM에 전달된 문맥으로 표시하면 안 된다. 내부 dependencies도 프로파일의 최종 제한 전 목록일 수 있다.
- 문맥화는 상태·시간만 기록하고 정확한 지침·HTTP 입력·원응답을 보관하지 않는다. SDK 입력의 history·resolved_query는 확인할 수 있지만 이것으로 앞선 문맥화 요청 전문을 복원할 수 없다. SDK 도식의 모델2단계가 전체 모델 호출 수와 같지 않을 수 있다.
- 일반 대화는 ContextVar로 observer를 전달하지만 pipeline의 본문 수집 조건은 명시 observer 인자 또는 include_diagnostics만 검사한다. 진단 옵션이 꺼진 일반 대화에서 본문 수집이 빠질 가능성이 소스상 보인다. **현재 실환경 재현 전 의심**이며 이전 평가 경로의 보관 검증 성공과 구분한다.

근거: `executions/domain.py:90`, `generation/openai_compatible.py:503,514`, `conversations/service.py:420`, `search/service.py:104`, `search/pipeline.py:266`.

## 개선 방향 비교와 권장안

| 선택지 | 실익 | 한계 |
|---|---|---|
| 현재 도식 압축 | 첫 화면 밀도를 작게 개선 | 정보 분산과 멀티턴 표시 문제는 남음 |
| 질문 중심 상세와 대화 턴 선택 | 질문·답변·품질을 먼저 이해하고 각 처리 단계의 근거·입력·결과를 가까이 비교 | 상세 배치와 본문 표시 재구성이 필요 |
| 대화 전체 중심 새 모니터링 | 턴 간 변화·통계·비교에 유리 | 대화별 조회·필터·문맥 의존 관계의 계약 확장이 필요 |

권장안은 두 번째다. 다음은 제안이며 구현 완료 또는 사용자 확정으로 기록하지 않는다.

1. 상단에 선택한 질문·답변·실행/품질 결과·핵심 실패 사유를 둔다. 대화 실행이면 턴 순서와 현재 턴을 함께 표시하고 평가 반복과 구분한다.
2. 이전 문맥 → 질의 문맥화 → 검색 → 근거 선택 → 에이전트 처리 → 인용 검증의 흐름을 보여준다. 실제 생략·실패·미기록 상태를 구분하고 저장된 관계가 없는 연결을 만들어내지 않는다.
3. 선택한 단계의 지침·입력·결과를 데스크톱에서는 흐름 옆에, 좁은 화면에서는 선택 위치 가까이에 배치한다. 에이전트 역할은 클릭 후에도 보인다.
4. 인식 가능한 저장 JSON은 질문·이전 메시지·근거·응답으로 구조화해 읽도록 하고 원문·해시·식별자는 별도 상세에서 유지한다. 모델의 숨은 추론이나 기록되지 않은 내용을 생성해 채우지 않는다.
5. 다음 구현에서 일반 대화의 수집 경로와 문맥화 기록을 먼저 회귀 검증한다. 실제 연속 질문을 실행하기 전에는 정확한 후보 설정·자료·이미 사용한 호출·새 실행 예산을 확인한다.

기존 데이터로 가능한 배치·턴 선택과 별도 계약이 필요한 실제 채택 문맥·대화별 검색을 구분한다. 이전5개 SDK 기록과 부모 관계, 원문 ACL, 본문 보관 상한은 유지해야 한다.

## 검증과 이력

- 기존 멀티턴·서명·권한·예산 테스트 **16 passed, 9.41초, exit0**. 외부 모델·DB 없이 합성/MockTransport 검증이다. 새 기능 테스트를 추가하거나 실제 연속 대화를 실행하지 않았다.
- 정본 Conda 실행 명령·출력은 `.local-data/project-agent-work/monitoring-multiturn-audit-20261024/runtime-test-result.txt`에 보존했다. 같은 디렉터리에 실행 전154파일 SHA, 저장 프로파일의 안전한 설정, 실제 화면과 상세 소스 감사를 보관했다.
- ISSUE-00035를 인증된 관리자 화면에서 open으로 되돌리고 사용자 재발·원인·검증 경계·남은 작업을 추가했다. 이전 검증과 관련 문서 버전1·2·3은 보존했다. ISSUE-00036의 실제 평가 본문 보관 성공은 취소하지 않았으며 일반 대화 전체 검증으로 확대하지 않는다.
- 제품 수정·프로파일 변경·실제 생성·임베딩·서비스 재시작·커밋·푸시는 없다. 이전 품질 실패와 운영 비승격 상태를 유지한다.
