# AI Workshop 프론트엔드 스타일 기준

- 기준일: 2026-10-30. 기존 다크·청록 정체성을 차분한 표면·명확한 정보 계층으로 유지한다.
- 적용: 작업소·관리·인증 화면과 공개 화면의 공통 조작부. 장면·문서 읽기 예외는 별도로 명시한다.
- 화면별 소스 적용과 실제 수용 범위는 [디자인 시스템 적용 현황](design-system-coverage.md)을 따른다. 소스 적용을 전체 화면의 브라우저 검증 완료로 해석하지 않는다.

## 코드 정본과 책임

- 값의 정본은 [tokens.css](../../frontend/src/shared/ui/tokens.css)이며 [앱 스타일](../../frontend/src/app/styles.css)에서 한 번 불러온다.
- 일반 링크의 기본 표현은 [links.css](../../frontend/src/shared/ui/links.css)에서 정하고 앱 스타일에서 불러온다. 기능별 카드·메뉴 링크는 해당 CSS가 표면과 배치를 소유하며 기본 인라인 장식을 중복 적용하지 않는다.
- 공통 조작은 [Button](../../frontend/src/shared/ui/Button.tsx)과 [ChoiceGroup](../../frontend/src/shared/ui/ChoiceGroup.tsx)을 사용한다. 기능 상태·권한·API 호출은 기능 코드에 둔다.
- 레이아웃은 기능 CSS Modules가 소유한다. 기존 `--file-*`, `--login-*`, `--access-*`, `--monitor-*`, `--study-*` 이름은 공통 의미 토큰을 참조하는 호환 계층으로 사용할 수 있다.
- 새 패키지·원격 폰트·장식 애니메이션을 추가하지 않고 기존 React/CSS 구조를 사용한다. 디자인 변경으로 검색·모델 입력·인용·대화 상태·권한·저장 동작을 바꾸지 않는다.

## 의미별 색상

색상 값은 CSS 정본에서 관리한다. 기능별로 같은 의미의 색을 다시 정의하거나 모든 상태를 강조색으로 통합하지 않는다.

| 역할 | 토큰 | 사용 기준 |
|---|---|---|
| 바탕·표면 | `--color-background`, `--color-surface`, `--color-surface-raised` | 페이지·카드·겹친 구역의 계층 |
| 조작 표면 | `--color-surface-input`, `--color-surface-hover`, `--color-surface-selected` | 입력·활성 hover·선택을 구분 |
| 글자 | `--color-text`, `--color-text-muted`, `--color-text-subtle` | 본문·설명·부가 정보; 필수 상태를 흐리게만 표시하지 않음 |
| 강조 | `--color-accent`, `--color-accent-strong`, `--color-on-accent` | 주요 동작·선택·링크와 강조 배경 위 글자 |
| 경계 | `--color-border`, `--color-border-control` | 구역 구분과 조작 가능한 입력 윤곽 |
| 성공 | `--color-success`, `--color-success-surface`, `--color-success-border` | 완료·통과·정상 상태 |
| 주의 | `--color-warning`, `--color-warning-surface`, `--color-warning-border` | 검토 필요·중단·취소 등 해당 기능의 주의 의미 |
| 오류 | `--color-danger`, `--color-danger-surface`, `--color-danger-border` | 실패·오류·위험 동작 |
| 정보 | `--color-info`, `--color-info-surface`, `--color-info-border` | 진행 중·설명·정보 상태 |
| 겹침·문서 | `--color-overlay`, `--color-paper`, `--color-link-visited` | 모달 뒤 배경·원문 종이·방문한 링크 |

상태 텍스트·아이콘·표면·경계를 함께 사용한다. 일반 UI의 선택 상태나 링크를 상시 밑줄로 장식하지 않으며, 선택·성공·실패를 색으로만 전달하지 않는다. 원문의 정확 일치·문맥·의미 하이라이트는 근거 종류를 구분하는 기능적 표시이므로 각각 `--color-highlight-keyword/context/semantic` 계열과 기존 실선·점선 패턴을 유지한다. 일반 텍스트 대비 4.5:1, 큰 텍스트·필수 컨트롤 상태 3:1은 실제 배경 조합으로 검증한다.

## 글자·간격·레이아웃

- `--font-family-ui`: Inter → Pretendard → Noto Sans KR → 시스템 산세리프. 원격 다운로드 없이 설치된 글꼴을 사용한다.
- 본문 `--font-size-ui`는 1rem, 컨트롤은 `.9375rem`, 설명·상태는 `--font-size-caption` `.8125rem`을 기준으로 한다. `.75rem`의 `--font-size-small`은 짧은 부가 표시에 한정한다.
- 업무 제목은 `--font-size-title`의 1.5–2.25rem, 줄높이 1.25와 산세리프를 사용한다. 구역 제목은 `--font-size-heading`의 1.125–1.375rem, 일반 제목 줄높이는 `--line-height-heading` 1.4다. 본문 줄높이는 `--line-height-ui` 1.65다.
- 전역 `h1`에 공개 hero의 Georgia·큰 크기를 적용하지 않는다. 공개 hero와 문서 읽기의 별도 타이포는 명시적으로 한정한다. 대화 헤더처럼 좁은 업무 구역은 더 작은 제목을 유지할 수 있다.
- 간격은 `--space-1/2/3/4/5/6/8/10/12`의 `.25/.5/.75/1/1.25/1.5/2/2.5/3rem`에서 고른다.
- 반경은 `--radius-small/control/panel/pill`의 `.375/.625/1rem/999px`, 그림자는 `--shadow-panel/overlay`를 사용한다.
- 기본 페이지 여백은 `--page-padding`, 업무 내용 폭은 `--content-max-width` 82rem을 따른다. 기존 읽기·다이어그램·상세 화면의 목적별 폭은 유지하며 새 컴포넌트가 상위 폭을 키우지 않는다.
- flex/grid 자식의 `min-width: 0`, 한글·긴 식별자 줄바꿈, 실제 사이드바를 제외한 컨테이너 폭을 고려한다. 일반 폼과 페이지 전체에 가로 스크롤을 만들지 않는다. 표·원문·다이어그램 내부 스크롤은 해당 내용 영역에 한정한다.
- 기존 `admin-content`, `workspace-content`, `public-content` 컨테이너 경계를 우선 사용한다. breakpoint를 추가할 때 이유를 남기며 기존 반응형 규칙의 최종 cascade까지 확인한다.

## 비교 결과의 정보 배치

같은 지표의 차이를 빠르게 읽는 비교 화면은 **대상 → 조건 → 지표** 순서로 구성한다. 모델처럼 서로 다른 비교 대상의 자료를 같은 구역에 섞지 않고 대상마다 독립된 구역을 둔다. 시간·사용량·비용·답변 등 모든 구역에서 대상의 위치와 순서를 일관되게 유지한다.

- 대상 이름·공급자는 구역 제목에 표시한다. API·로컬 비교는 실제 요청 순서와 관계없이 API를 왼쪽, 로컬을 오른쪽에 둔다. 공급자 표시명 `API`·`OpenAI`·`OpenAI API`와 `Local`·`로컬`·`Ollama`·`Ollama · 로컬`만 대소문자·연속 공백을 정규화해 분류하며 모델명으로 실행 위치를 추정하지 않는다. 같은 유형 안에서는 첫 등장 순서, 미분류 대상은 기존 자리와 순서를 유지한다. 시간·비용·답변 모두 같은 표시 순서를 사용하고 특정 모델 이름이나 후보 수를 고정하지 않는다.
- 각 대상 안에서 첫 요청·동일 입력 반복 등의 조건을 열, 같은 지표를 행으로 맞춘다. 조건과 요청 번호를 열 제목에 표시하고 두 대상의 조건 순서·지표 순서를 맞춘다. 조건 간 차이를 함께 읽을 수 있도록 한쪽 조건을 탭 뒤에 숨기지 않는다. 회차 선택은 긴 답변·인용처럼 한 번에 모두 표시하기 어려운 보조 상세에 사용할 수 있다.
- 완료 응답 등 핵심 지표는 표의 첫 행에서 글자 크기·굵기·강조 토큰으로 드러낸다. 동일 수치를 별도 요약 카드와 표에 반복 나열해 비교 대상을 다시 찾게 만들지 않는다. 보조 단계는 같은 행 정렬과 일정한 숫자 폭(`tabular-nums`)을 유지한다.
- 넓은 화면에서는 대상 구역을 나란히, 좁은 화면에서는 같은 대상 순서를 유지해 세로로 쌓는다. 구역 안의 조건별 열과 지표별 행 관계는 보존한다. 긴 이름은 줄바꿈하고, 관측 조건이 많아 읽기 폭을 확보해야 할 때만 표 내부 가로 스크롤·키보드 초점·이동 안내를 제공한다. 페이지 전체 가로 넘침이나 과도한 글자 축소로 해결하지 않는다.
- native `table`·`caption`·`th scope="col"/"row"`로 조건·대상·지표 관계를 전달한다. 구역 제목과 접근 가능한 이름을 일치시키고 단위는 값 또는 지표명에 명시한다. 선택·차이를 색만으로 구분하지 않는다.
- 미측정 시간, 미보고 사용량, 미확인 청구액과 실제 0을 구분한다. 예상 비용·실제 청구·청구 해당 없음도 별개로 표시하며, 작은 금액을 반올림해 0으로 만들지 않는다. 서로 다른 측정 경계를 한 합계나 우열 판정으로 합치지 않는다.
- 비교 배치 변경으로 원본 관측·답변·인용·품질 판정이나 원래 요청 순서의 기록(요청 번호)을 바꾸지 않는다. 관측되지 않은 대상·조건 조합은 값을 만들어 채우지 않는다. 데이터 보존 검사와 desktop·375px·320px의 실제 배치 검사를 분리해 기록한다.

저장된 모델 비교에 적용한 파일과 검증 범위는 [적용 현황](design-system-coverage.md#2026-10-29-비교-대상별-구역-정리)을 따른다. 색·간격·반경은 기존 의미 토큰을 사용하며 별도 비교 전용 팔레트를 만들지 않는다.

## 관리자 모델 연결과 RAG 설정

### 고급 관리의 작업 선택

고급 화면도 사용 목적을 먼저 선택하게 한다. 등록 현황 조회, 새 연결/정의 등록, 처리 설정 등록, 데이터 정책을 같은 긴 페이지에 모두 펼치지 않는다. RAG 구성에서는 저장 구성 확인과 새 구성 만들기를 분리한다. 같은 페이지의 작업·탭 이동 시 폼을 언마운트해 초안을 지우지 않는다. 페이지를 떠난 뒤까지 자동 저장된다고 표시하지 않는다.

현황의 첫 정보는 이름·버전·모델·준비 상태이며 전체 파이프라인, 불변 정의, 기술 식별자, JSON/YAML은 목적이 명확한 펼쳐 보기로 제공한다. ‘등록됨’과 ‘연결 준비’, ‘답변 평가 통과’, ‘실제 적용’은 구분한다. 단순 이동 링크만을 위한 빈 단계/탭을 만들지 않는다. 작업 선택에는 기존 ChoiceGroup/탭과 표면·경계 토큰을 재사용하고 탐색만으로 조회 이외의 동작을 실행하지 않는다.

Claude도 OpenAI와 같은 공개 카탈로그 선택 규칙을 따르되 수신자 Anthropic·native Messages 연결 방식·전용 답변 후보를 구분한다. 선택 모델의 별도 보관 조건은 해당 선택 아래 표시하고, 공개 목록·계정 접근·실제 품질 수용을 혼동하지 않는다. [ADR-0053](../decisions/0053-claude-and-admin-workflows.md).

일상 변경 메뉴 `모델 연결·RAG 설정`과 상세 관리 메뉴 `RAG 구성 · 고급`·`RAG 모델 · 고급`을 구분한다. 메뉴를 제거하거나 기존 URL을 바꾸지 않는다. OpenAI 모델 식별은 빈 선택을 가진 native select를 기본으로 하며 모델 이름·공개일을 표시하고 최신 공개일 순으로 정렬한다. 긴 ID와 공식 설명은 선택 아래에서 줄바꿈해 보여준다. 공개 카탈로그 확인일과 계정 권한 미확인을 구분하고, 목록 밖 ID 입력은 명시적인 고급 선택으로 제공한다. 선택만으로 등록·모델 호출·적용·지원 기능 확인을 수행하지 않는다. 공급자나 입력 방식이 바뀌면 이전 모델 ID와 기능 확인을 초기화한다.

`/admin/rag/setup`은 **모델 연결 → 기존 RAG 구성 복제 → 연결 상태·답변 평가 → 도메인에 적용** 순서로 배치한다. 단계 제목과 현재 선택을 유지해 저장한 모델·후보·적용 대상을 구분하며, 고급 모델·RAG 구성 화면 링크는 보조 탐색으로 제공한다. 상세 동작·평가 계약은 [승인 설계](../superpowers/specs/2026-10-30-model-setup-design.md)와 [ADR-0052](../decisions/0052-admin-model-setup.md)를 따른다.

- 기존 다크·청록 의미 토큰과 panel/input/selected 표면을 사용한다. 단계의 완료, 처리 중, 준비 필요, 평가 미수용, 실패를 텍스트와 상태 표현으로 구분하고 연결 성공을 답변 품질 통과처럼 표시하지 않는다.
- 기존 답변 설정 재사용과 공급자별 새 프리셋을 구분해 설명한다. 선택한 공급자에 호환되는 프리셋만 제공하고, 비호환 기존 설정은 이유를 알려 선택을 수정할 수 있게 한다. 기존 config의 자동 변환을 암시하지 않는다. 프리셋 선택에는 새 평가 후보라는 안내를 유지한다.
- 추출식 기반을 LLM 생성 답변으로 바꾸는 확인과 외부 전송 확인은 목적이 다른 별도 checkbox다. 각 label의 조작 영역을 44px 이상 확보하며 모델·기반·범위 변경 뒤 이전 확인이 남지 않도록 한다.
- 적용 구역은 정확한 후보의 답변 평가 통과 반영과 최신 준비 확인이 필요한 이유를 보여준다. 새로고침 뒤에는 기존 완료 평가에서 통과 반영을 다시 할 수 있고, 이 확인이 새 답변 생성을 시작하지 않음을 안내한다. 검색 평가의 통과 배지만으로 적용 가능 상태를 표현하지 않는다.
- 적용 전 도메인·모델·지식 공간과 기존 범위 유지·전역 기본값 미변경을 보여주고 명시적인 적용 확인을 둔다. 단계 이동·선택만으로 health/평가/활성화 동작을 자동 실행하지 않는다.
- 저장 중 이중 제출을 차단하되 입력은 보존한다. 부분 저장에는 저장된 대상과 다음에 재사용할 대상을 알려주고, 응답 유실 시 결과 확인이 필요함을 표시한다. 실패 상태를 단순 초기화하거나 완료로 표시하지 않는다. 완료/오류는 접근 가능한 상태·알림 영역으로 전달한다.
- 기본 버튼·select·입력·checkbox label과 독립 링크는 44px 조작 기준을 따른다. 320/375px에서는 단계·버튼·긴 모델명/식별자가 줄바꿈되며, 페이지 전체 가로 넘침을 만들지 않는다. 상태를 색으로만 전달하지 않고 키보드 순서·초점이 단계 흐름을 따른다.

이 절은 표현·검증 요구다. 실제 desktop·모바일·키보드 검증 여부와 본래 API/계정 확인은 작업 기록에서 별도로 보고한다. 합성 화면 검증을 실제 연결의 품질 평가나 운영 수용으로 해석하지 않는다.

## 버튼·네이티브 입력

공용 `Button`의 variant는 `primary`, `secondary`(기본), `quiet`, `danger`다. 중요한 실행은 명시적인 문구와 상태를 제공하고, 위험 동작은 danger 의미를 유지한다. 현재 로그인, 지식공간 생성, 문제 이력 관리의 **세 기능 파일**에서 사용한다. 모든 기존 버튼을 React 컴포넌트로 교체한 것은 아니며, 나머지 네이티브 버튼도 같은 토큰·조작 규격을 따른다.

- 기본 `type="button"`이며 폼 제출은 `type="submit"`을 명시한다. native props, `disabled`, `aria-*`, `ref`, 이벤트와 접근 가능한 이름을 보존한다.
- 버튼·텍스트 입력·select·직접 조작 summary는 `--control-min-height` 2.75rem(기본 44px) 이상으로 한다. 아이콘 단독 조작은 너비도 44px 이상 확보한다.
- radio/checkbox 기호는 `--control-choice-size` 1rem(기본 16px), 클릭 가능한 label은 44px 이상으로 분리한다. 텍스트 입력의 전체 너비·패딩·최소 높이를 두 기호에 적용하지 않는다.
- 입력 selector는 유형을 명시하거나 checkbox와 radio를 **모두** 제외한다. hidden/file/range도 별도 표현 목적을 고려한다. segmented의 시각적으로 숨긴 radio에 기능 CSS의 기호 크기를 덮어쓰지 않는다.
- 입력 label·설명·오류 연결을 유지한다. native `disabled`를 사용하며 비활성 hover를 막고, 비활성화 때문에 입력값을 삭제하지 않는다.
- 긴 버튼 문구는 줄바꿈한다. 원문 속 인라인 링크까지 큰 버튼으로 만들지 않으며, 독립 탐색 링크와 조작 링크는 충분한 클릭 영역을 확보한다.

## 화면 이동 링크

일반 UI 링크는 상시 밑줄 대신 옅은 표면·경계·hover·가시적인 포커스로 클릭 가능성을 드러낸다. 글자색만 바꾸고 식별 단서를 없애지 않는다. 기존 디자인 토큰을 사용하며 전역 기본값과 기능별 스타일이 충돌하지 않는지 확인한다.

독립 탐색·조작 링크는 둥근 경계·충분한 여백·최소 44px 높이를 확보한다. 본문 속 인라인 링크는 문장의 흐름과 줄바꿈을 유지하는 작은 표면·경계를 사용하며, 큰 버튼으로 만들지 않는다. 이미 카드·메뉴·목록 전체가 링크인 경우에는 기존 컨테이너의 모양과 선택 표시를 유지해 중복 장식을 피한다. 실제 동작은 native 링크와 기존 URL을 보존하며 `button` 역할로 바꾸지 않는다. 좁은 화면에서는 링크 문구를 줄바꿈한다.

인증 카드의 공개 화면 이동처럼 폼 밖에 놓인 보조 링크도 독립 탐색이다. DOM 위치에 따른 전역 추정에 맡기지 않고 기능 소유 class를 지정해 전체 폭·가운데 정렬·충분한 세로 여백을 제공한다. 주요 제출은 강조 배경, 보조 이동은 raised 표면·경계와 차분한 글자로 계층을 나누며 hover·키보드 focus·방문 후 상태에도 식별성을 유지한다.

이 기준은 상단 탐색뿐 아니라 본문·인용·상태 안내의 UI 링크에도 적용한다. 원문 자체의 강조·검색 하이라이트와 실선·점선은 링크 장식과 구분한다. 화면별 적용과 실제 검증 범위는 [전역 밑줄 스타일 정리](design-system-coverage.md#2026-10-29-전역-밑줄-스타일-정리)에 기록한다.

## ChoiceGroup·탭·포커스

단일 선택에는 `ChoiceGroup`을 우선 사용한다. `fieldset/legend`, native radio, 고유한 그룹 name, 설명 연결, label 전체 클릭, controlled value와 disabled를 제공한다. 기본 variant는 원형 radio이고 `variant="segmented"`는 평가 준비의 저장 자료 재사용/새 자료 작성처럼 같은 목적의 소수 모드를 선택할 때 사용한다.

segmented는 공통 외곽선·내부 구분선과 최소44px label을 사용한다. 선택은 채워진 배경·굵기·체크 또는 도형 표식과 native checked로 표현하며, 글자 밑줄이나 선택 항목의 아래쪽 선에 의존하지 않는다. 시각 표식은 접근 가능한 이름을 바꾸거나 선택 상태를 중복 낭독하게 만들지 않는다. 긴 문구는 각 세그먼트 안에서 줄바꿈하고 그룹 내부 폭24rem 이하에서는 세로로 쌓는다. 숨긴 native radio의 접근성 트리와 Tab·방향키·Space 조작을 보존하며 disabled 상태에서 선택이나 hover를 활성화하지 않는다.

실제 콘텐츠 탭도 둥근 표면·선택 경계·표식을 사용하고, 기존 `tablist/tab/tabpanel`, `aria-selected` 및 방향키·Home/End 패턴을 유지한다. 단일 선택을 on/off switch나 임의의 tab 역할로 바꾸지 않는다.

`:focus-visible`은 `--focus-width` 2px, `--focus-offset` 3px, `--focus-color`를 사용한다. outline을 제거하려면 부모 focus-within이나 SVG 선 등 동등한 가시적 표시가 있어야 하며 실제 키보드로 검증한다. 모달·스크롤 영역에서 포커스가 잘리지 않고 닫은 뒤 원래 조작으로 돌아오는지 확인한다. 애니메이션이 필요한 경우 reduced-motion을 지원한다.

## 적용 예외와 검증

게임 오피스와 공개 RAG 연구실의 픽셀 장면·캐릭터·캔버스 색은 기능 소유다. Publishing의 공개 문서 읽기는 50rem 폭, 1.0625rem 본문·1.85 행간 등 별도 타이포를 유지한다. 예외가 입력·메뉴·모달의 접근성 면제를 뜻하지는 않는다. 원문 위치·하이라이트·다이어그램 의미도 유지한다. 자세한 파일·route 경계는 [적용 현황](design-system-coverage.md)에 기록한다.

1. Vitest/Testing Library로 상태·콜백·폼 제출·disabled·접근 가능한 이름·키보드 동작을 확인한다. TypeScript와 변경 TS/TSX 린트를 실행한다. `frontend`의 `pnpm test:styles`로 토큰 대비를 별도 검사하며 실제 화면 검증을 대체하지 않는다.
2. 실제 CSS를 렌더링한 브라우저에서 desktop·375px·320px, 좁은 컨테이너, 긴 한글·식별자, focus·선택·disabled·오류·빈 상태를 확인한다. jsdom 통과는 레이아웃 수용이 아니다.
3. bounding box로 조작 영역, 페이지/내용 영역별 overflow, 실제 색 조합의 대비를 확인한다. 소스 토큰 참조만으로 합격을 선언하지 않는다.
4. 기존 설치 도구와 합성 자료를 사용하고 실제 API 제출·모델 호출·인증 우회를 하지 않는다. 인증된 본래 화면의 읽기 전용 확인과 합성 검증을 구분해 기록한다.
5. 실제 제공 파일이 변경 소스와 일치하는지 확인한다. 새 화면은 아래 체크리스트와 coverage의 route/CSS 목록을 함께 갱신한다.

기존 [평가 준비 브라우저 하네스](../../frontend/tests/ui-style/preparation-browser.mjs)는 `frontend`에서 `node tests/ui-style/preparation-browser.mjs`로 실행한다. 설치된 Edge와 임시 loopback 서버를 사용하며 종료 시 닫는다. 실제 컴포넌트·CSS를 사용하되 Next 링크 경계와 API를 합성 응답으로 대체하므로 실제 앱 로그인·라우팅·업무 E2E를 검증하지 않는다. 결과는 Git 제외된 `.local-data/browser-verification/preparation/` 또는 `UI_STYLE_OUTPUT_DIR`에 둔다. 도구가 없으면 임의로 설치하지 않는다.
