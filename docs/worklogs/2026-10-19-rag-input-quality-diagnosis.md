# RAG 입력 품질과 지연 원인 조사

- 날짜: 2026-10-19
- 사용자 요청: 앞선 실제 평가 실패 이후 품질 개선 진행.
- 현재 단계: 사용자가 “진행해봐”로 승인한 선택형 v5 입력 구성을 구현하고 오프라인 검증을 마쳤다. 실제 모델 답변·P95 개선과 운영 적용은 미검증이다.
- 범위: 일반 규칙·예시 조건 누락, 생성 입력 표현, 단계별 지연. 기존 평가 기준과 업체/질문 독립성을 유지한다.
- 제외: 추가 모델/임베딩 호출, 재평가, 설치·다운로드·재색인, DB/프로파일/활성 구성 변경, 도메인 활성화, commit/push.
- 등급/역할: 중간 위험. 메인 요구·RAG·AI·backend 분석/테스트 설계, 독립 검토 담당은 입력 표현 위험과 검증 근거를 읽기 전용 검토. UI·DB schema·배포 변경 역할은 범위 밖이다.
- 기존 실평가 정본: [4회 실행 결과](2026-10-19-rag-evaluation-execution.md). 성공 기준은 낮추지 않는다.

## 확인된 사실과 가설

1. v3/v4에는 이미 일반 규칙 우선, 예시 대체 금지와 조건 보존 지침이 있다. 지침을 반복 추가하는 것으로 해결됐다고 볼 수 없다.
2. 최근 정상 시도의 선택 원문28개와 기존 공개 합성 source-reading fixture의 ID·원문이 일치한다. 선택 원문은659자다.
3. 같은 근거와 질문을 **현재 코드로 재구성한** v4 user 입력은9,549자/UTF-8 10,356bytes다. evidence7,500자, source_reading1,205자이며 UUID가88회 등장한다. 기본 system prompt는1,262자다. 이 수치는 실제 토큰 수가 아니고, 재구성한 입력은 당시 전송 원문 증거가 아니다.
4. 근거28개 모두 bbox가 있고 table_cell은null이다. 표 관계 단서가 될 수 있는 공간정보를 일괄 삭제하면 안 된다. 파서상 연속 구간 길이는8/2/2/2/2/12다.
5. 일반 규칙은 짧은 표 조각이고 날짜 예시는 완성된 문장에 가깝다. 반복 식별자·메타데이터·별도 순서 목록을 연결해서 읽는 부담은 관측할 수 있다. 이것이 모델 실패의 직접 원인인지는 아직 입증되지 않았다.

## 제시한 제한된 설계

- 새 선택형 `rag-answer-v5` 경로에만 별도 순수 입력 packer를 적용한다. 공유 v1~v4 직렬화와 활성 프로파일은 보존한다.
- 비인용 식별자·중복 메타데이터를 줄이고 엄격한 출처·위치 연속 범위 안에서 원문 조각을 함께 배치한다. 원문·인용 UUID·순서·bbox·페이지/표/문서 경계를 유지한다.
- 인접성을 대상/규칙/조건의 의미 관계로 표시하지 않고, 답변 문장을 코드로 만들지 않는다. 예시 키워드·업체명·기간 값으로 분기하지 않는다.
- 다른 도메인·변경된 숫자·예시만 있는 자료·규칙 없는 자료, 중복/누락/역순과 출처 경계를 검사한다. 과거 오답은 계속 실패해야 한다.
- 바이트/문자 감소, 입력 계약 검증, 실제 모델 답변 품질/P95 개선을 별도로 보고한다. 실제 재평가는 새 승인 범위가 필요하다.
- 이 설계를 채팅에서 제시한 뒤 사용자가 “진행해봐”로 승인했다. 기존 미커밋 구현을 보존하며 현재 작업 경로에서 필요한 부분만 수정한다.

## 증거와 현재 한계

- `.local-data/project-agent-work/rag-quality-diagnosis-20261019/`에 작업 전 WORKBOARD/status·generation 소스 SHA, 오프라인 수치, 재구성 user payload를 보존했다.
- `analyze_saved.py`는 저장 파일과 현재 순수 직렬화만 사용했다. DB/HTTP/모델 호출은 없다.
- 기존 입력/인용/오프라인 오답 판정 회귀5파일은 **71 passed, 1 deselected in 1.24s**, exit0이다. 제외1개는 기존 비동기 HTTP mock이며 이번 동기 기준선에 포함하지 않았다. 검사 명령은 source_reading, source_reading_mock, http_evidence_groups, direct_answer_prompt, offline_rubric 테스트에 `-m 'not asyncio'`를 적용했다. 이 결과는 현재 계약의 기준선이며 v5 구현 또는 실제 품질 개선 증거가 아니다.
- `RequestScopedEmbedding`은 이미 요청 안에서 질문/본문 벡터를 재사용한다. 본문 단위 선택과 청크 문맥 선택은 서로 다른 텍스트를 소비하므로 호출 횟수만으로 중복 계산이라고 판정하지 않았다. 공유 캐시나 모델 수명 변경은 이번 제안에서 제외한다.
- 독립 검토자는 새 opt-in packing 방향을 수용 가능한 후보로 판단했고, 기존 v1~v4 보호·공간 단서 보존·인접성과 의미 구분·실모델 효과 미확정 조건을 확인했다.
- 조사 단계에서는 제품 코드 개선과 실제 답변 개선이 미완료였다. 아래 후속 구현과 구분한다. 인증된 관리자 문제 이력 DB 반영은 여전히 하지 않았다.
- 조사 마감 당시 generation 소스79파일 SHA와 기존 dirty 항목215개 보존, 문서 계약/링크/범위 내 diff 검사 통과를 확인했다. 당시 설계 승인 대기였으며 이후 승인된 구현 결과는 아래와 같다.

## 승인된 v5 구현 결과

- `generation/compact_evidence.py`에 순수 packer를 추가했다. HTTP v5만 `evidence_sources`·`evidence_blocks`를 사용하며 기존 v1~v4 입력 해시8개는 모두 같다.
- 파서상 연속된 원문만 블록으로 묶는다. A→B→A·역순·위치 누락/간격을 재정렬하지 않고, document/version/projection/chunk/page/kind/part/table/section 경계를 유지한다. 텍스트·인용 UUID·bbox·문자 범위·ordinal은 그대로다. 서버의 원본 `GroundingEvidence`도 변경하지 않는다.
- `answer-v5.txt`는 일반 규칙·적용 조건·예시 구분을 요구한다. 원문 조각의 인접성을 의미 관계로 확정하지 않으며 특정 업체·질문·숫자에 따른 분기와 답변 생성/수정 코드는 없다.
- 원문 속 지시문과 JSON 탈출 문자열도 user 데이터로 직렬화한다. 숫자 출처 참조·블록 번호는 인용으로 허용하지 않으며, UUID 형태의 가짜 인용은 기존 인용 검증기가 거부한다. 이 검사는 모델의 지시 거부 성능을 증명하지 않는다.
- 독립 검토에서 다른 provider가 v5 지시문과 기존 payload를 혼용할 수 있는 결함을 발견했다. `GenerationProfile`과 준비 상태 계산에서 v5는 명시된 `LOCAL_OPENAI_COMPATIBLE`·`LOCAL` deployment만 허용하도록 보완했다. 미지원 조합은 모델 호출과 health 조회 전에 거부한다. 기존 provider의 serializer와 v1~v4 조건은 보존한다.
- v5는 선택형으로 등록됐고 활성 DB·프로파일·구성·서버는 변경하지 않았다. 실제 모델/임베딩 호출, 재평가, 도메인 활성화, commit/push는 없다.

### 같은 원문으로 재구성한 입력 비교

| 항목 | v4 | v5 |
| --- | ---: | ---: |
| 선택 원문 조각 | 28 | 28 |
| user 메시지 문자 | 9,549 | 6,118 |
| user 메시지 UTF-8 bytes | 10,356 | 6,925 |
| 기본 system 지침 문자 | 1,262 | 1,001 |

user 메시지는 문자35.93%·UTF-8 bytes33.13% 감소했다. 실제 토큰 수·추론 지연 감소로 환산하지 않는다. 과거 실행에서 최종 system/user 원문을 수집하지 못했으므로 이 자료는 **현재 직렬화로 재구성한 입력**이며 당시 전송 증거가 아니다. mock에서는 현재 HTTP 경계에 전달되는 messages와 요청 내 캡처가 일치하고 요청 종료 후 폐기됨을 확인했다.

전체 backend 단위 검사는 처음 **7,628통과·19skip·116실패·66error**였다. 이 중 generation 모듈은1,489통과·4skip이었다. 전체 실행은 승인된 모델/DB 통합 실행이 아니라 단위 검사이며, 본래 환경 완료로 취급하지 않는다.

첫 실행의 루트 cwd·긴 임시 경로·제가 넣은 테스트용 `AI_WORKSHOP_SECRET_KEY` 때문에 결과가 왜곡됐다. 실패182개만 backend cwd와 짧은 임시 경로로 재실행하자37개가 통과했고, 제가 추가한 환경변수를 제거해 나머지145개만 재확인하자133개가 통과했다. `NativeSecuredReadAssembly`는 `AI_WORKSHOP_*` 환경변수 존재를 명시적으로 거부한다. 제품 보안 검사나 실제 환경 설정은 완화하지 않았다. 전체 suite를 다시 반복하지 않았으며 최초 결과와 부분 재확인 결과를 합쳐 한 번의 전체 통과로 보고하지 않는다.

최종 재확인에도 **12실패**가 남는다. PDF preview worker7개, ingestion credential launch1개, native route process3개, 대화 입력 확인의 권한 mock 소진(`StopAsyncIteration`)1개다. 이 실패는 v5 packer 실행과 다른 경계에서 발생했으며 이번 변경으로 해당 코드/테스트를 수정하지 않았다. 수정 전 전체 suite 기준선이 없으므로 모두 기존 결함이었다고 단정하지 않는다. 별도 원인 규명과 수정이 필요하며, 관리자 문제 이력 DB 등록도 미완료다.

증거는 `.local-data/project-agent-work/rag-quality-diagnosis-20261019/`의 `red.xml`, `mock-red.xml`, `provider-red.xml`, `final-targeted.xml`, `unit.xml`, `unit-recheck.xml`, `unit-clean-environment.xml`, `v5-input-comparison.json`에 있다. 단위 검사는 프로젝트 Conda에서 `python -X utf8 -B -m pytest`로 실행했다. 변경 제품 파일만 `mypy --config-file backend/pyproject.toml --follow-imports silent`와 Ruff로 확인했다.

최종 보존 검사에서 기존 dirty 상태 항목215개가 모두 남아 있고, 기존 generation79파일 중 의도한4파일 외75파일 SHA가 동일함을 확인했다. 문서3개의 로컬 링크138개, 최근 완료 목록 최대5개, 범위 내 diff 공백 검사도 통과했다. 수치와 남은 실패는 `final-verification.json`에 기록했다.

## 다음 단계

현재 완료 범위는 **범용 입력 구성의 구현과 오프라인 보존·경계 검사**다. 실제 품질 기준(correctness/context/refusal 각1, ACL0, P95≤120초)은 유지하며, v5의 실모델 정답·조건 보존·인용·지연은 아직 측정하지 않았다. 기존 4회 호출은 소진된 과거 평가이며 v5 재평가 승인으로 재사용하지 않는다. 추가 호출 범위와 별도 시험 구성을 정한 뒤 정상/근거 부족 평가를 실행해야 한다. 통과 전 도메인 READY나 연결을 활성화하지 않는다.
