## 질문 → 근거 → 전달 확인 범위 → 답변

- 정상 사례의 검색 근거 ID 299개 중 선택된 28개에는 합성 상품 설명서 2쪽의 일반 지급 규칙 **접수일 T+4 영업일**, 접수일 정의, 15:00 마감과 다음 영업일 접수 정보가 있다. 검색 K=10은 후보 청크 수로 근거 조각 수와 다르다.
- 두 정상 답변은 동일하며 특정 날짜 예시만 출력했다. 일반적인 지급일 질문에 필요한 상대 영업일 규칙이 빠졌고, 예시 원문의 휴일 없음 조건도 생략했다. 필요한 규칙의 검색·선택 누락은 아니다. 실제 답변과 인용 조각은 아래 로컬 원본과 그림에서 확인한다.
- 날짜 문자열과 인용 ID의 연결은 맞지만 이것만으로 조건을 보존한 의미상 정답이라고 판정할 수 없다. 저장된 `4`/`영업일` 검사는 부분 문자열 규칙이며 별도로 독립 의미 검토를 수행했다. 두 정상 답변 모두 실패다.
- 근거 부족 사례는 검색 근거 ID 300개 중 26개가 선택됐고, 합성 월간 운용보고서 3쪽에 다음 달 확정 수익률을 제공하지 않는다는 내용이 있다. 두 번 모두 `insufficient_evidence`와 `answer: null`이다. 실제 반환하지 않은 자연어 거절 문장을 만들어 인용하지 않는다.
- 감사에는 `rag-answer-v4`, 모델, 선택 근거 ID와 공급자 토큰 수가 있다. **최종 system/user 메시지 원문은 이번 평가 경로에서 수집하지 않았다.** 요청 내 진단의 기본값은 false이고 `PrivateGenerativeResult`에도 최종 입력 필드가 없다. 현재 코드로 재조립한 텍스트를 당시 전송 원문으로 표현하지 않는다.
- 따라서 일반 규칙이 선택된 사실과 생성 답변의 실패는 확인됐지만, 최종 직렬화 입력 문제인지 모델의 지침 준수 문제인지는 아직 분리 확정할 수 없다. 지연 초과도 별도 품질 실패다.

## 실행 범위와 보존 검증

- 정상 worker의 모델 등록과 본래 환경 admission을 먼저 적용했다. 실행 직전 ID·snapshot/rules digest·질문/규칙·후보 구성·프로파일·로컬 모델·K10·반복2·출력512·temperature0·timeout360·retry0·빈 이력·원래 네 시도·기존 감사0·중복 active 없음이 일치해야만 실행하도록 보호했다.
- 배타적 생성 영수증을 만든 뒤 지정 UUID만 기존 서비스 경로로 처리했다. 일반 큐를 열지 않았고 재시도·재등록·재실행은 하지 않았다.
- 생성 4회는 감사 건수만으로 판단하지 않았다. 서로 다른 실행4개의 generation 완료, 공급자 응답 토큰4건, 이력 없음으로 문맥화 생략4건, retry0 및 시도당 최대1 POST 코드 경계와 단일 호출 영수증을 함께 대조했다. 승인 최대4회를 모두 사용했다.
- 종료 후 읽기 전용 조회와 로컬 증거 검사18개 통과: 원래 실행10개/시도4개 유지, 다른 실행9개 동일, 이전 취소 실행 그대로, 데이터셋·규칙·정책·구성 보존, 네 결과 digest 일치, 허용/금지/동결 근거 ACL 검사, owner의 pending/running 없음.
- 독립 검토자가 별도로 네 결과 SHA-256, ACL 집합, required 근거, claim 순서·인용 합집합·답변 결합, 지표/P95와 생성 횟수 근거를 재계산해 일치를 확인했다.
- 최종 문서 계약 검사와 범위 내 `git diff --check`를 통과했고 로컬 Markdown 링크99개, 보조 Python 문법, 최근 완료 최대5개와 기존 dirty 항목214개 보존을 확인했다. Git의 기존 접근 제한 디렉터리/전역 ignore 경고는 남았으며 해당 경로는 건드리지 않았다. 제품 코드 변경이 없어 제품 회귀 테스트를 새로 실행한 것으로 보고하지 않는다.
- 이번 변경은 작업 기록과 로컬 실행/검증 도구·산출물이다. 제품 코드 변경·모델/의존성 다운로드·재색인·수동 DB 정정·commit/push는 없다. 기존 미커밋 변경은 보존했다.
