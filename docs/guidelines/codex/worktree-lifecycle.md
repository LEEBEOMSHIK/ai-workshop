# Codex worktree 수명주기

- 상태: 승인됨
- 기준일: 2026-09-01

## 목적

worktree를 작업 격리 수단으로만 사용하고, 완료된 구현과 검증 기록을 공식 저장소에 인계한 뒤 불필요한 복사본과 캐시를 남기지 않는다.

## 생성 시 기록

- worktree의 절대경로, 브랜치, 작업 목적과 제거 조건을 `WORKBOARD.md`에 기록한다.
- 작업 브랜치와 기준 브랜치의 관계를 확인한다.
- worktree 안에 영구 데이터나 다른 프로젝트 자산을 저장하지 않는다.

## 완료 판정

다음 조건을 모두 충족해야 정리 단계로 이동한다.

1. 관련 테스트와 정적 검사가 실제로 통과했다.
2. 기능 브랜치 커밋이 원격에 존재한다.
3. 구현이 `main`에 병합되고 원격 `main`에 반영됐다.
4. worktree의 추적 파일에 미커밋 변경이 없다.
5. worktree에만 존재하는 미추적·무시 파일을 조사했다.

## 제거 전 인계

- 최종 검증 보고서, 선별 실패 기록과 재사용할 목업만 공식 문서 또는 자산 영역으로 옮긴다.
- 중간 리뷰 diff, 테스트 캐시, 가상환경, 빌드 결과와 패키지 설치물은 영구 기록으로 취급하지 않는다.
- 컨테이너, 개발 서버와 도구 프로세스가 worktree 경로를 사용하는지 확인한다.
- Docker Compose 라벨이 worktree의 구성 파일이나 작업 디렉터리를 가리키면 `main`의 구성으로 관리 기준을 이전하고 서비스 상태를 재검증한다.
- junction과 reparse point가 있으면 실제 대상을 확인하고 승인 경계 밖 경로를 따라가지 않는다.

## 승인 보고

제거 전에 다음 내용을 사용자에게 제시한다.

- 정규화된 worktree 절대경로
- 브랜치와 `main`의 통합 증거
- 미추적·무시 파일의 보존 또는 제거 판단
- 예상 회수 용량
- 영향을 받는 실행 서비스와 인계 결과

이 보고에 대한 명시적 승인 없이 worktree를 제거하지 않는다.

## 제거와 검증

- 등록된 worktree는 `git worktree remove`로 제거한다.
- 일반 재귀 삭제나 강제 제거는 정상 제거가 불가능한 이유와 남은 파일을 다시 보고한 뒤에만 검토한다.
- 제거 후 `git worktree list --porcelain`로 등록이 사라졌는지 확인한다.
- worktree 메타데이터를 정리한 뒤 `main`의 Git 상태와 원격 반영 상태를 확인한다.
- 기능 브랜치 보존·삭제는 별도 결정으로 다룬다.
- `WORKBOARD.md`에서 완료 상태와 예외를 갱신한다.

## 예외

장기 비교 실험이나 병렬 유지가 실제로 필요하면 worktree를 남길 수 있다. 이때는 소유자, 보존 이유, 다음 검토 시점과 제거 조건을 `WORKBOARD.md`에 기록한다. 기록 없는 완료 worktree는 다음 캐시 점검의 우선 정리 대상이다.
