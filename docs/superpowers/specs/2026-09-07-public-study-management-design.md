# 개발·실험 기록 공개 관리

- 상태: 상세 설계 승인 / 기반 계약 검증 완료, 저장·API·UI 미구현
- 상위 정본: [학습·서비스 연결](2026-09-07-learning-service-link-design.md)
- 사용자 결정: 기존 RAG 개발·실험 기록은 공개 대상으로 준비하며 관리자 화면에서 언제든 공개·비공개를 전환한다.

## 범위와 승인 해석

현재 존재하는 RAG 개발·실험 기록을 목록화하고 공개용으로 편집한다. 한 사례만 임의로 선정하고
나머지를 누락하지 않는다. 각 후보에 공개 준비 완료 또는 보류 사유를 기록한다.
이 승인은 저장소 전체, 업로드 문서, 개인 메모, 원시 로그를 그대로 공개한다는 뜻이 아니다.
새 기록과 이후 수정본의 기본값은 비공개로 유지한다. 기존 후보의 공개 승인은 초기 검토한
정확한 편집본 목록과 해시에 기록하며, 검토 중 민감정보나 권리 불확실성이 발견되면 보류한다.

초기 inventory는 이 설계 작성 시점의 `docs/worklogs/` 중 RAG 기능을 다룬 완료·실패 기록과
owner가 소유한 Learning의 RAG 주제 기록이다. Learning 조회가 미활성 상태면 전체 준비 완료로
표시하지 않는다. 설계·ADR은 사례의 배경 근거로 연결하지만 실행된 실험으로 세지 않는다.
WORKBOARD는 후보 대조용이며 공개 본문 원천이 아니다. 임시 작업 패키지·캐시·업로드·원시 로그는
수집 대상에서 제외한다. 비공개 inventory에 출처와 revision/hash, 사례 계보, 처리 상태를 남기고
같은 사건의 파생 기록은 하나의 사례로 묶는다. 보관 기록도 포함해 검토하되 삭제 기록은 복구하지
않는다. 후보 총수와 공개 준비·보류·중복 연결 수의 합을 대조한다. 이후 생성 기록은 자동 포함하지 않는다.

## 선택한 구조

단순 React 정적 본문은 관리자 전환을 지속 저장할 수 없으므로 채택하지 않는다.
비공개 Learning 행에 public 플래그를 붙여 익명 조회하는 방식도 데이터 분리 원칙에 어긋난다.
Platform Publishing이 공개용 편집본과 승인 이력을 관리하고 별도 공개 저장소로 불변 snapshot을
전달하는 기존 설계를 적용한다. RAG는 기술 주제와 담당자 연결만 제공한다.

공개 조회 프로세스에는 비공개 DB 자격 증명과 파일 접근권한을 주지 않는다. 로컬도 별도
공개 저장 경계를 사용하고, 운영으로 넘어갈 때 공개·비공개 환경 간 런타임 네트워크 연결을
추가하지 않는다. 수동 패키지 전달과 적용 확인을 통해 운영 게시·철회를 처리한다.
구체적 저장 어댑터와 배포 적용 절차는 구현 계획에서 기존 실행 구조를 확인해 확정한다.

## 화면과 행동

- `/admin/publishing`: owner 전용 목록, 공개 상태 필터, 공개용 편집, 미리보기,
  `공개하기`와 `비공개로 전환`. 변경 중에는 중복 클릭을 막고 실패 시 실제 상태를 유지한다.
- `/labs/rag/studies`: 로그인 없이 보는 공개 개발·실험 기록 목록.
- `/studies/[publicSlug]`: 문제, 관찰 사실, 원인 가설, 확정 원인, 선택과 이유,
  변경 사항, 검증 결과, 남은 한계. 가설과 확정 원인, 과거 검증과 현재 운영 상태를 구별한다.
- `/labs/rag`: 총괄과 관련 담당자 대화에 기록 연결을 제공한다. 게시된 기록이 없으면
  존재하지 않는 상세 링크를 만들지 않는다. 검색 대화 화면에 기록 관리 UI를 섞지 않는다.

초기 UI는 공개/비공개로 이해하기 쉽게 표현하지만 내부 상태는
draft → approved → published → withdrawn을 보존한다.
`공개하기`는 미리 본 편집본 revision/hash를 명시적으로 승인하고 게시하는 동작이다.
게시본 수정은 새 초안이며 기존 공개본을 자동 교체하지 않는다. 새 편집본을 다시 승인해야 한다.
`비공개로 전환`은 공개본 철회이며 원본 학습 기록과 관리 이력은 삭제하지 않는다.
철회 후 재공개도 최신 편집본을 확인하는 명시적 동작이다.

## 데이터·실패 계약

공개 snapshot에는 공개 slug, 제목, 요약, 기술 주제, 담당자 공개 식별자, 안전한 본문,
검증 범위와 한계, 공개 revision만 허용한다. 모델명·버전은 검토한 설명에만 포함한다.
원본 ID·사용자 ID·호스트 경로·endpoint·인증 정보·개인정보·비공개 문서·raw log·
모델 내부 추론은 export에서 제외한다. 공개 본문에 원본 파일 링크를 넣지 않는다.
담당자 식별자는 수동 승인된 공개 persona registry의 slug/label만 사용하며 계정 ID·이메일·
계정 표시명에서 파생하지 않는다. 승인된 공개 persona가 없으면 해당 필드는 생략한다.
Markdown의 임의 HTML, 외부 이미지 자동 로딩, 위험 URL과 첨부는 지원하지 않는다.

승인 hash는 원본 Markdown이 아니라 스키마 버전·공개 slug·allowlist metadata·정제한 본문을
포함하는 canonical UTF-8 JSON export bytes의 SHA-256이다. 키 정렬·문자열·줄바꿈 직렬화를
명시된 export 버전으로 고정한다. 미리보기는 바로 이 package를 공개 렌더러로 보여준다.
저장소 적용과 조회에서 승인 digest를 검증하고 불일치는 공개하지 않는다. export/정제 규칙 변경은
새 package 승인 대상이며 UI 템플릿 변경으로 데이터 package를 조용히 바꾸지 않는다.

관리 API는 기존 owner 인증을 재사용하고 Publishing 변경 요청에 CSRF 검사를 보완한다.
현재 구현에 명시적인 CSRF 검사가 없어 허용 Origin·JSON·전용 요청 헤더를 확인한다.
일반 로그인 사용자와 익명은
관리 목록·미리보기·변경에 접근할 수 없다. 공개 API는 게시된 snapshot만 읽는다.
미게시·철회·없는 slug는 동일한 404이며 내부 제목이나 상태를 누출하지 않는다.
revision 충돌은 409로 반환하고 편집 중인 내용을 조용히 덮어쓰지 않는다.

게시·철회 명령에는 revision/hash와 멱등 식별자를 사용한다. 저장·배포 도중 실패하면
완료로 표시하지 않는다. 분리 배포에서는 요청 상태와 공개 저장소의 적용 확인 상태를
구별한다. 재시도와 오래된 게시 요청이 더 최신 철회를 되돌리지 못하도록 순서를 검증한다.
관리 응답은 최신 미적용 명령의 action·expected_revision·expected_digest·request_id를
owner 전용 `pending_command`로 제공한다. 현재 편집본으로 이 값을 추정하지 않으며,
새로고침·재선택 후에도 원래 요청을 재시도한다. 공개 응답에는 이 정보가 없다.

철회 완료는 공개 저장소 적용과 목록·상세·캐릭터 링크·캐시에서 제외된 것을 확인한 시점이다.
초기 공개 응답은 서버·CDN·브라우저 저장 캐시를 사용하지 않는 정책으로 구현한다.
이미 열린 화면과 방문자가 복사한 자료까지 소급 회수한다고 보장하지 않는다.
실시간 원격 배포가 없는 운영에서는 UI가 적용 대기를 표시하며 즉시 철회를 가장하지 않는다.

## 첫 작업 순서와 검증

1. 기존 RAG 기록 후보 목록과 공개용 편집본을 준비한다. 모든 후보의 처리 상태를 남긴다.
2. Publishing의 revision 승인·게시·철회·재시도 및 분리 저장 계약을 구현한다.
3. 관리자 목록·미리보기·상태 변경과 공개 목록·상세·NPC 연결을 구현한다.
4. 합성 기록으로 owner/일반 사용자/익명 권한, 409, 금지 필드 export, XSS,
   게시 실패·재시도·철회 후 직접 URL 및 재공개 순서를 검증한다.
5. 실제 로컬 관리자에서 공개 → 익명 열람 → 비공개 → 직접 URL 차단 → 재공개를 확인한다.
6. 초기 공개 후보 묶음의 검토가 끝난 뒤 사용자가 승인한 범위의 게시를 수행하고 결과를 보고한다.

Learning의 기존 migration 활성화는 코드 완료와 구별해 확인한다. 원본 연동이 필요하면
기존 DB 상태와 migration을 먼저 점검하며 현재 저장 기능이 작동한다고 가정하지 않는다.
이번 범위에는 외부 AI 호출·자동 학습·검색 모델 변경·Docker 정리·전체 관리자 재구성이 없다.
