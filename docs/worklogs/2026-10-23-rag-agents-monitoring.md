# OpenAI Agents SDK와 위임 모니터링

## 요청과 범위

사용자는 내부 에이전트 관리에 OpenAI Agents SDK를 사용하고, 어떤 에이전트에 무엇이 위임되는지 화면에서 확인하도록 요청했다. 기존 Gemma 첫 실제 RAG 연동 완료 기준을 유지한다. 이전 취소·색인·첨부 복구, 추가 품질 튜닝·외부 모델 비교는 재개하지 않았다. 설계는 [ADR-0039](../decisions/0039-rag-agents-sdk-monitoring.md), 수행 순서는 [구현 계획](../superpowers/plans/2026-10-23-rag-agents-monitoring.md)을 따른다.

## 구현

- 선택한 생성 프로파일에서 `rag_manager`가 `write_grounded_answer` 도구로 `answer_specialist`에 과제를 위임한다. 전문 역할은 서버가 보유한 원질문·허용된 이력·검색 근거를 받는다. 위임 과제가 원질문이나 근거를 대체하지 않는다.
- 기존 검색·ACL·인용 검증·대화/평가 저장은 유지한다. SDK는 공급자 종류가 아닌 생성 조정 계층이며 초기 지원은 local OpenAI-compatible + schema 2다.
- 프로파일 예산에는 필요한 문맥화 호출까지 포함한다. 첫 질문은 조정/답변 2회, 이력 문맥화가 필요한 후속 질문은 최대 3회다. 모델 호출·위임 횟수와 출력 예약량을 제한하고 재시도·외부 trace·조용한 fallback을 사용하지 않는다.
- 실행 상세의 위임 흐름과 현재 대화의 검색 진단에 공통 패널을 추가했다. 부모 관계·위임 대상/방식·실제 HTTP 입력·결과·시간·사용량을 구분한다. 호출 완료와 품질 통과, 취소와 실제 모델 종료를 혼동하지 않는다.
- 본문 이력 보관 질문에는 아직 답을 받지 않아 기존 요청 한정 정책을 유지한다. 실행/대화에는 본문을 제거한 메타데이터와 정확한 원문 manifest만 남긴다. 권한 철회 시 현재 응답과 이력 모두 재검사한다. 인용/답변 검증 실패 초안도 출력 진단으로 재노출하지 않는다.
- HTTP 생성 프로파일 폼에 SDK 방식과 예산을 추가했다. 직접 실행을 기본으로 유지하며 모드 변경 때 입력을 보존하고 선택한 방식만 제출한다. 미지원 배포는 SDK 제출을 차단한다. 등록은 draft이며 실제 실행이나 활성 연결 변경을 수행하지 않는다.

## 의존성과 기존 변경 보존

`openai-agents==0.24.0`, `openai==3.37.0`, `httpx2==2.16.0`을 포함하는 공식 wheel 19개만 기존 `backend/.conda`에 적용했다(신규 17개, PyJWT/urllib3 상향 2개). 공식 lock의 URL/SHA와 변경 목록을 확인한 뒤 기존 Conda 설치 도구로 dry run→설치→검사를 수행했다. Python/NumPy/SciPy/BLAS 보호 파일 6,121개 SHA가 동일하며 pip check는 통과했다. 별도 환경·모델 다운로드는 없다.

작업 전 기존 변경 78파일의 SHA를 `.local-data/project-agent-work/agents-monitoring-20261023/baseline-sha256.json`에 보존했다. 최종 검사에서 73파일은 바이트 동일하며, WORKBOARD·대화 service·RAG 설계·로컬 실행서·기존 SDK 계획 5파일만 이번 범위에 맞게 함께 갱신했다. 예상 밖 변경·누락은 없다. 의존성 delta와 설치 증거도 같은 로컬 작업 폴더에 보관한다. 본문·자격 증명은 문서/Git에 추가하지 않는다. commit/push는 수행하지 않았다.

## 검증 기록

제품 변경을 멈춘 뒤 영향 범위를 재검사했다. 실제 모델 호출은 0회다. 아래 검사들은 일부 범위가 겹치므로 합산해 고유 테스트 수로 보고하지 않는다.

- SDK 담당의 실제 SDK Runner·합성 HTTP, 기존 생성·입력 진단·프로파일·전체 검색 회귀 537개 통과. 실제 Gemma 응답을 사용한 검사는 아니다.
- 메인 최종 통합 검사 166개 통과: SDK·실행 관측·대화 trace projection·PyJWT 상향 영향의 identity 단위 검사를 함께 실행했다. 아래 독립 16개도 포함한다.
- 실 PostgreSQL 저장 통합 검사: 기존 계정/DB를 사용하는 transaction rollback 검사 1개 통과. 본문 비저장, revision 역전 차단, 취소된 실행의 늦은 trace 쓰기 거부를 확인했다. 검사 후 전체 rollback했다.
- 독립 계약/보안 검사 16개 통과: 본문 projection·manifest ACL·callback 순서·malformed 과거행 격리, strict role/dialect/JSON, library child 로그 비노출, 1MiB 수신 제한·응답 close·종료 미확인 의미를 포함한다.
- 메인 최종 화면 검사 7파일 92개 통과: 실행·진단 34개와 폼·관련 화면 58개다. 위임 패널 독립 검사 12개는 실행·진단 범위에 포함된다. 폼 독립 검토 뒤 안내 문구를 수정하고 폼 40개·ESLint를 다시 통과했다. 전체 프론트 검사는 구현과 동시에 실행되어 추가 전 소스를 읽은 2개 실패가 있었으며 전체 통과로 보고하지 않는다.
- 메인 영향 source 30개 Mypy, 영향 Python Ruff, TypeScript 전체 타입 검사, 변경 UI/fixture ESLint, OpenAPI 생성 일치 검사 통과.
- 변경 문서의 상대 링크 대상 64개와 `git diff --check`를 통과했다. WORKBOARD 최근 완료 항목은 5개로 유지하고 빠진 E 평가 요약의 상세가 원래 기록에 있음을 확인했다.

## 최초 브라우저 확인과 당시 남은 수용

기존 Chrome에서 본래 앱은 로그인 화면이었다. 로그인 요청을 보냈으나 본래 관리자 세션의 전체 흐름은 아직 검증하지 못했다. 합성 페이지에서는 실제 제품 컴포넌트/CSS를 사용해 펼치기→Enter로 위임 선택→전달 입력 열기까지 DOM을 확인했다. 이 자료는 실제 SDK/Gemma 실행 결과가 아니다.

설치 Edge의 빈 페이지 생성이 정지했고 Chrome headless는 GPU subprocess 종료 오류로 제품 페이지 이전에 실패했다. 기존 Chrome 연결에서는 viewport 1280 요청이 실제 innerWidth 1707로 관측됐고, 화면 캡처도 timeout/연결 단절로 끝났다. 따라서 **320/375/1280px 시각 검증과 스크린샷은 미완료**다. OS/브라우저 보호 설정을 변경하거나 사용자 브라우저를 강제 종료하지 않았다. 직접 시작한 합성 서버와 headless 테스트는 종료했다. 보고서는 `.local-data/browser-verification/agents-20261023/report.json`에 남긴다.

본래 서버는 이번 작업에서 재기동하지 않았다. 서버 반영 후 실제 Gemma의 SDK 도구 왕복, 로그인한 관리자 화면의 활성 경로, 새 프로파일의 평가/기본 승격은 이 오프라인 결과에 포함하지 않는다. 기존 프로파일·활성 연결·품질 기준은 그대로다.

## 발견 결함과 이력 반영

실행 ID가 바뀔 때 이전 실행의 질문·근거를 다음 조회가 끝날 때까지 표시하는 UI 결함을 테스트로 재현했다. 실행 identity에 묶어 컴포넌트를 초기화하고 갱신 중 상세/근거를 숨기도록 수정했다. SDK 구현 중 발견한 ACL·revision·응답/로그 경계도 같은 작업에서 수정·회귀 검사했다. 폼의 배포 재시도 검증 시점 안내는 실제 코드와 대조해 ‘등록 시’에서 ‘실행 준비 시’로 바로잡았으며 독립 검토자가 해소를 확인했다. 관리자 문제 이력 DB는 로그인 상태 때문에 반영하지 못했으며, 새 문제 번호를 임의로 발급하지 않는다. [문제 이력 규칙](../issues/README.md)에 따라 실제 등록 여부를 구분한다.

## 로그인 후 후속 검증 (2026-10-23)

사용자의 ‘다음 검증과 함께 모니터링 확인’과 ‘로그인했어’에 따라 기존 환경에서 계속했다. 메인이 브라우저·통합·기록을 맡고, SDK 담당은 평가 종료 경계, 독립 검토자는 수정 코드와 회귀를 담당했다. 이전 Gemma 첫 연동 완료 및 중단한 과거 복구 작업은 다시 열지 않았다.

### 본래 환경과 실제 호출

- frontend5173 응답200, API18000 health `ok`, Ollama11434 버전0.40.3을 읽기 전용으로 확인했다. 이 확인은 생성 성공 증거가 아니다.
- 기존 관리자 세션으로 모델 관리·실행 모니터링·문제 이력에 접근했다. 진행 중 실행 필터는0건이었다. 기존 공개 합성 실행 상세는 ‘에이전트 위임 기록이 없는 실행’으로 표시하고 과거 흐름을 추정하지 않았다.
- live OpenAPI에는 `AgentTrace`와 실행 상세의 `agent_trace` 계약이 없어, 디스크의 새 코드가 기존 API 프로세스에 반영되지 않았음을 확인했다. API PID101960의 Python 경로·명령·18000 listener를 정확히 확인했다.
- 같은 프로세스의 중지·재기동 요청은 자동 승인 검토가 ‘서비스 연결을 잠시 끊는 작업에 대한 명시 승인 없음’으로 거절했다. 다른 종료 방법으로 우회하지 않았고 사용자에게 구체적인 재기동 승인을 요청했다. 기존 API는 계속 실행 중이다.
- 이번 후속 검증의 실제 모델 호출0, 신규 SDK 프로파일·구성·평가 등록0, worker 기동0, 원본/색인/기본값 변경0이다. 기존 저장 평가의 호출 수를0이라고 판단한 기록은 아니다.

### 브라우저 모니터링

실제 제품 컴포넌트/CSS를 합성 자료 서버에서 확인했다. 기본 브라우저 캡처는 viewport override를 해제한 뒤 성공했다. viewport1280 요청에도 실제 innerWidth1707로 관측되고 캡처가 timeout되는 도구 한계가 있어 전체 화면의 정확한 모바일 viewport를 검증했다고 보고하지 않는다.

- test fixture에 모니터링 패널 폭 선택만 추가했다. 이력 패널320/375px에서 세로 배치·가로 넘침 없음·단계 선택 버튼44px 이상, 1280px에서 흐름/상세의 나란한 배치를 확인했다.
- 키보드 Enter로 위임 선택, 전달 대상·방식 표시, 현재 응답의 합성 입력 본문, 이력의 본문 미보관 안내를 확인했다. 320px 외부 컨테이너 안 현재 진단 패널은 내부 여백을 제외해 약294.67px였으며 긴 한글/무공백 입력도 가로 넘침 없이 표시됐다.
- 관측 누락·기록 한도·실패 코드·시간 미기록을 명시하고, 이전 실행은 빈 상태로 표시했다. 합성 데이터는 실제 Gemma 위임 결과가 아니다.
- fixture ESLint와 프론트 전체 TypeScript 검사를 다시 통과했다. 제품 UI의 기존92개 검증과 이번 브라우저 관측은 별개다.

### 실제 평가 전에 발견한 반복 호출 결함

정상 평가 경로는 최소2회 반복을 요구하며 DB0055의 제약도 같다. 최초의 질문1개·1회 반복/최대2생성 구상은 이 경로로 제출할 수 없어 폐기했다. 반복 기준이나 DB를 바꾸지 않고, 질문1개×2회에 각 조정/답변2회로 전체 최대4생성을 준비한다. 재시도0이며, 첫 시도의 로컬 HTTP 종료가 미확인이면 같은 run의 다음 시도를 시작하지 않아야 한다.

기존 workflow는 종료 추적 없이 실패만 저장하고 다음 반복으로 넘어갔다. 시간 초과, 선행 미완료 뒤 후속 응답 성공, pending HTTP 취소의3경로를 수정 전 테스트 실패로 재현했다. `GenerationTermination`을 시도별로 연결하고 기존 `complete_attempt` 부모 잠금 트랜잭션에서 현재 실패 저장·같은 run의 pending을 interrupted로 변경·부모 failed를 함께 처리한다. 동일 run의 수동 retry도 거부한다. 완료 결과·다른 run·claim token 검사를 유지하며, 호출 전 실패와 완전 수신 뒤 품질 실패의 기존 반복은 보존한다. 실제 모델 종료를 증명하거나 강제로 종료하는 기능은 아니다.
