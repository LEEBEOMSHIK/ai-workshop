# 생성형 평가의 임베딩 수명 수정 — 2026-10-26

## 요청과 성공 기준

사용자가 여전히 느린 RAG의 다음 속도 개선 작업을 요청했다. 직전 실제 측정은
[2026-10-25 결과](2026-10-25-rag-gemma-speed-verification.md)를 기준으로 삼는다.
전체 응답 시간 개선은 실제 전후 측정으로만 판정하며, 모델 참조 해제와 RSS 반환을 구분한다.

이번 수정의 수용 기준은 frozen 생성형 평가의 검색·근거 선택이 끝난 뒤 답변 생성 전에
해당 실행이 소유한 임베딩 모델 참조를 해제하고, 오류·취소에도 같은 정리 경로를 사용하는 것이다.
동일 준비 구성의 반복 실행은 새 런타임을 사용해야 하며 현재 검색 resolver의 모델을
frozen 모델 대신 사용하거나 외부에서 주입한 borrowed 런타임을 임의로 닫으면 안 된다.
근거·인용·현재 권한·불변 모델 및 프로파일·색인은 보존한다.

## 원인과 수정 범위

`FrozenGenerativeAdapter.prepare`는 frozen 모델로 치환하며 기존
`request_owned_embedding_factory`를 무조건 비웠다. 그 결과 `SearchService.execute`의
생성 전 해제와 `finally` 정리를 사용하지 못했다. `ProductionEvaluationSearch.close`는
Elasticsearch만 닫으며, 준비 입력과 결과가 모델 객체를 계속 참조할 수 있었다.
일반 검색에는 이미 실행별 독점 소유·생성 전 해제 경로가 있다.

기존 경로를 재사용하는 최소 수정을 선택했다. 기본 CPU frozen 설정에 정확한 검증 완료
`EmbeddingModelConfig`로 새 어댑터를 만드는 factory를 제공하고 생성형 adapter가 이를
전달한다. 현재 resolver factory는 사용하지 않는다. 기존 lazy placeholder는 로드하지
않으며 각 실행의 실제 모델은 pipeline이 소유·해제한다. 외부 주입 포트는 기존 borrowed
의미를 유지한다. CPU 외 장치도 기존 수명을 유지한다. factory는 불변 설정과 캐시 경로만
캡처하고 평가 소유자·Elasticsearch 클라이언트를 붙잡지 않는다.
공개 API·DB 스키마·검색 의미는 바꾸지 않는다.

상주 모델 풀은 메모리 압박을 키울 수 있고, 요청 간 벡터 캐시는 권한·버전·보존 정책의
별도 설계가 필요하므로 이번 수명 결함 수정에 섞지 않는다. 정상 요청의 기존 요청 내부
벡터 재사용은 이미 구현돼 있다.

## 역할과 검증 계획

중간 위험의 백엔드 성능 수정이다. 메인은 Python/RAG 경계와 통합·기록, AI/임베딩 담당은
수명 조사와 구현·회귀 테스트, 독립 리뷰어는 구현과 분리된 검증을 맡는다.
UI·DB 스키마·배포 변경 역할은 범위 밖이다. 기존 미커밋 변경 위에서 필요한 부분만 수정한다.

실패 회귀를 먼저 확인한 뒤 최소 수정과 관련 evaluation/search/embedding 테스트,
Mypy/Ruff, 독립 검토를 수행한다. 실제 모델·서비스 반영과 실제 전체 응답 시간 검증은
자동 테스트와 별도로 기록한다. 새 계정·DB·모델 설치나 품질 튜닝은 포함하지 않는다.

## 검증 상태

독립 evaluation/search/embeddings 단위 테스트 **531개 통과**(25.53초), 제품 2파일·테스트
3파일 Ruff와 변경 diff 검사를 통과했다. 구현자 315개와 앞선 독립 30개는 이 531개와
겹치므로 합산하지 않는다. 독립 검토의 차단 지적은 없다. strict Mypy는 변경 2파일과 기존
`service.py`, `metrics.py`를 포함한 4파일에서 `--follow-imports=skip`으로 통과했다.
전체 의존성 타입 검사는 Torch/Transformers 수천 모듈 탐색을 완료하지 못해 중단했다.
별도 `mypy.api` 진단의 DLL 정책 오류를 표준 검사 정체의 원인으로 단정하지 않는다.

독립 추가 4개는 실제 frozen adapter → frozen source resolver → 검색 pipeline을 연결해
생성 전 참조 해제, 반복 실행의 모델 분리와 결과·인용 일치, borrowed 보존, 현재 ACL
재검증, 원문 조회 실패·취소 정리를 확인한다. 기존 검색 테스트의 동시 실행·생성 실패·취소,
빈 검색·조기 거절 회귀도 포함했다. 합성 모델을 사용했으며 실제 메모리 반환량을 뜻하지 않는다.
최초 테스트는 Windows 샌드박스의 `socket.accept` → asyncio self-pipe 생성에서 멈췄다.
해당 시험 프로세스를 중단하고 자동 승인된 제한된 오프라인 시험을 같은 표준 이벤트 루프로
실행했다. 수정 전 실패 3개/통과 1개로 누락을 재현했으며 모델·DB·외부 네트워크는 쓰지 않았다.
실제 속도 개선 완료를 아직 주장하지 않는다.
관련 문제 ISSUE-00038 및 ISSUE-00005의 기존 이력을 보존한다. 관리자 DB 반영은 미실시다.

제품은 `evaluation/tasks.py`와 `evaluation/generative_adapter.py`만 수정했다. 일반 검색의
pipeline, 임베딩 알고리즘, 요청 내부 캐시와 검색 전용 평가 동작은 변경하지 않았다.
새 프로세스로 실행하는 다음 생성형 평가부터 소스를 사용하며 이미 떠 있는 worker의
모듈이 갱신됐다고 가정하지 않는다. 코드 검증 단계에서는 서비스 재시작·실제 생성·임베딩·
설치·DB 변경·commit/push를 수행하지 않았다.
