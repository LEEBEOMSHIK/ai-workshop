# RAG 벡터 저장소 비교·로컬 LLM 파인튜닝 후속 계획

> **For agentic workers:** 상세 구현 계획을 확정한 뒤 superpowers:executing-plans 또는 superpowers:subagent-driven-development로 작업별 실행·독립 검증을 수행한다.

**Goal:** Elasticsearch와 대안 벡터 저장소를 동일 조건에서 비교하고, 로컬 LLM의 학습 전후 RAG 답변을 비교하는 후속 작업을 준비한다.

**Architecture:** 저장·검색 실험과 생성 모델 학습 실험을 별도 작업으로 관리한다. 기존 권한 범위 검색·원문 추적·인용 검증·Model Registry·평가·Learning 기록을 재사용하고 측정 결과로 채택 여부를 판단한다.

**Tech Stack:** 기존 Elasticsearch, PostgreSQL/pgvector 후보, 전용 벡터 DB 후보, 로컬 LLM·학습 런타임 후보. 제품·모델·방법·버전은 착수 시 장치·라이선스·공식 지원 확인 후 결정한다.

**Spec:** [검색 기준선 ADR](../../decisions/0003-hybrid-retrieval-baseline.md), [RAG 설계](../../labs/rag/design.md), [학습·서비스 연결 설계](../specs/2026-09-07-learning-service-link-design.md).

- 등록일: 2026-10-04
- 상태: 사용자 요청으로 추가 후속 작업 등록. 설치·자료 이관·모델 다운로드·학습·평가 실행 미착수.
- 이 문서는 두 독립 작업의 범위·비교 조건·게이트를 정리한 인계 문서다. 실행 가능한 인터페이스·테스트·명령은 각 작업의 상세 설계·ADR·구현 계획에서 확정한다.

## 순서와 공통 경계

기본 착수 순서는 **Agents SDK 도입 → 벡터 저장소 비교 → 로컬 LLM 파인튜닝 비교**로 둔다. 사용자가 후속 우선순위를 제안하면 미착수 작업의 순서·의존성·상태를 WORKBOARD와 이 문서에서 함께 갱신한다. 프로젝트 진행 순서이며 저장소 비교나 파인튜닝이 SDK를 기술적 선행 조건으로 요구한다는 뜻은 아니다.

- [SDK 도입 계획](2026-10-04-rag-agents-sdk-adoption.md)을 현재 다음 작업으로 유지한다. ISSUE-00013의 종료 proof·receipt·frozen 쓰기 차단과 RAG 기능 마감 기준도 보존한다.
- 기존 계정·DB·문서·파일·활성 프로파일을 보존한다. 사용자 실행 검증용 별도 환경·DB·계정을 임의 생성하지 않는다.
- 비교에 필요한 후보 구성은 기존 개발 환경에서 준비한다. 추가 프로세스·컨테이너·볼륨·테이블·색인·학습 산출물은 생성 전에 소유자·정확한 위치·용도·보존/인계·정리 조건을 기록한다.
- 전용 벡터 DB도 배포 장치의 디스크를 사용한다. 무제한 용량을 기대하지 않고 실제 디스크·메모리·인덱스 용량을 측정한다.
- 승인된 공개·합성 또는 사용 권한이 확인된 자료만 사용한다. 민감 본문·비밀·가중치·생성 색인은 Git에 넣지 않는다.
- 실험 수행 완료·품질 개선·기본 구성 채택·운영 적용을 구분한다. 본래 환경 반영·검증 및 필요한 인계 전 후보 산출물을 삭제하지 않는다. 정리는 CACHE_POLICY의 정확 대상 확인·승인 절차를 따른다.

## 작업 A: 벡터 저장소·검색 비교

Elasticsearch도 벡터를 저장·검색하므로 비교 명칭은 **Elasticsearch 대 전용 벡터 DB 대 PostgreSQL/pgvector**로 사용한다. 로컬 JSON은 검색 엔진과 별도인 처리 산출물 보관 계층이다.

| 비교군 | 벡터 저장·검색 | 키워드 검색·결합 |
|---|---|---|
| A0 현재 기준선 | Elasticsearch dense vector | 기존 Elasticsearch BM25 + 동일 RRF |
| A1 전용 벡터 DB 후보 1개 | 공식 기능·로컬 지원 확인 후 제품 선정 | 같은 Elasticsearch BM25 결과 + 동일 RRF |
| A2 PostgreSQL/pgvector | 기존 PostgreSQL에 후보 청크·vector 컬럼·검색 인덱스 구성 | 같은 Elasticsearch BM25 결과 + 동일 RRF |

BM25 단독을 별도 기준선으로 유지한다. 먼저 벡터 경로만 바꿔 원인을 분리한다. 후보 엔진은 현재 권한·정확한 문서/버전/빌드 조건으로 제한된 범위에서 검색해야 하며, 검색 후 단순히 결과를 숨기는 방식은 허용하지 않는다.

**저장 정본과 전체 운영 구조는 별도 판정이다.** A2가 검색에 성공했다고 청크·벡터의 정본을 PostgreSQL로 이관하거나 ES를 제거하지 않는다. PostgreSQL 정본+ES 검색 또는 PostgreSQL 중심 검색 통합 여부는 수명주기·트랜잭션·키워드 품질·운영 비용을 포함한 후속 ADR에서 판단한다. 첫 A1/A2 실험에는 BM25용 ES가 남으므로 서비스 수 감소를 입증하지 않는다.

### 고정 조건·측정·진행

- 동일 문서 snapshot·청크 ID/본문·벡터 값·모델/차원/정규화·질문 벡터·권한·필터·top-k·정답 판단을 사용한다. 후보마다 재청킹하거나 임베딩 모델을 바꾸지 않는다.
- 거리/점수 변환을 명시한다. 엔진 원점수를 같은 척도로 가정하지 않고 ID·순위·Recall@K·MRR·nDCG를 비교한다. exact 검색 대비 근사 검색의 recall/지연과 인덱스 종류·파라미터·후보 수·캐시·동시성을 함께 기록한다.
- 검색 p50/p95, 색인/증분 갱신/삭제 시간, 디스크·메모리, 필터 누락·허용 결과 부족, 원문 추적·버전 정합성을 측정한다. 문서 수·청크 수·벡터 차원·실제 용량을 보고한다.
- 재시작 후 영속성·백업/복구·삭제·운영 복잡성은 비파괴 검증 계획으로 비교한다. 기존 서버를 임의 재시작하거나 실제 자료를 삭제하지 않는다.
- 검색만 비교하는 평가와 전체 RAG 평가를 구분한다. 전체 평가의 LLM·프롬프트·SDK/실행 구성을 고정해 답변·인용·실패·총 지연을 비교한다.
- [ ] 기존 청크/벡터·물리 색인·Profile snapshot·평가 범위를 확인한다. ISSUE-00013 때문에 새 ES 쓰기가 필요한 검증은 종료 게이트 충족까지 차단으로 남긴다.
- [ ] 후보 제품·pgvector 호환성·자원·필터 기능을 조사하고 상세 설계·ADR·비파괴 실행 계획을 작성한다.
- [ ] 기존 검색 포트를 구현하는 후보 어댑터와 권한·버전·오류·근사 검색 회귀 테스트를 준비한다. 운영 검색을 자동 전환하지 않는다.
- [ ] A0/A1/A2 및 BM25 단독 반복 평가의 원시 결과·실패·측정값·채택/보류 이유를 기존 평가·Learning에 연결한다.
- [ ] 본래 계정·자료의 검색·인용·모니터링을 확인한다. 정본 이관·기본 구성 변경은 결과와 회복 계획을 검토한 후 별도 단계로 진행한다.

## 작업 B: 로컬 LLM 파인튜닝·RAG 연결 비교

초기 대상은 **RAG 답변 생성용 로컬 LLM**이다. 근거 활용·인용 형식·질문 의도·근거 부족 처리 등 목표 행동을 정의한다. 파인튜닝을 검색 누락·문서 최신성 문제의 해결로 간주하지 않는다. 임베딩·리트리버·리랭커 학습은 별도 실험으로 남긴다.

| 비교군 | 생성 모델 | 비교 조건 |
|---|---|---|
| B0 현행 구성 | 현재 연결·승인된 모델 | 동일 평가 문서·질문·검색 근거·인용 검증 |
| B1 학습 전 | 선택한 기반 로컬 LLM | B2와 동일 기반 revision·추론 설정·프롬프트·근거 |
| B2 학습 후 | B1 기반 모델 + 학습 adapter 또는 새 가중치 버전 | 학습 외 변경을 고정하고 차이 기록 |

B0/B1은 모델·실행 경로 차이, B1/B2는 학습 효과를 판단한다. 프롬프트·양자화·검색 설정이 달라지면 별도 실험으로 분리한다. 평가 질문을 훈련에 넣어 성공률을 높이는 방식은 사용하지 않는다.

학습 효과 비교에서는 현재 권한이 허용한 이전 대화 이력과 검색 근거의 내용·순서도 고정한다. 모델 응답에 따라 후속 문맥화·검색 결과가 달라지는 전체 멀티턴 평가는 별도 실험으로 기록한다.

### 데이터·장치·산출물·진행

- 질문·현재 허용 근거·검토된 교정 답변·원문 인용·근거 부족 예제를 준비한다. 원시 대화나 좋아요/싫어요를 자동 학습에 가져오지 않는다.
- 기존 학습 정책의 동의·권한·비식별화·중복 제거·검토·버전 고정을 따른다. 문서/주제 그룹의 중복과 누출을 확인해 train/validation/test를 분리하고 최종 test를 학습·튜닝에 쓰지 않는다.
- 현재 PC의 GPU/VRAM·RAM·디스크·OS/아키텍처와 라이브러리 지원을 착수 시 확인한다. 학습 가능하다고 가정하거나 새 서버·클라우드 GPU를 임의 생성하지 않는다.
- 기반 모델은 한국어·도메인·구조 출력·문맥 길이·라이선스·장치 적합성으로 선정한다. LoRA/QLoRA는 자원 효율을 검토할 후보이며 현 PC의 동작을 확정한 것은 아니다.
- 기반 revision·tokenizer·데이터 hash·코드/라이브러리·seed·학습 파라미터·장치·시간·실패·checkpoint/adapter/최종 artifact 위치와 hash를 기록한다. 비공개 내부 추론은 기록하지 않는다.
- 새 모델 버전은 Model Registry에 등록하고 기존 Deployment/Profile·RAG 포트로 연결한다. 생성 LLM 변경만으로 문서 임베딩·검색 색인을 다시 만들지 않는다.
- 학습 구현은 별도 기술 Labs 경계를 사용하고 RAG가 직접 import하지 않는다. Platform 참조·애플리케이션 조립부로 연결하며 착수 전 빈 폴더·가짜 메뉴를 만들지 않는다.
- [ ] 목표 행동·장치·기반 모델·학습 방법·자료 사용 범위와 자원/산출물 예산을 조사해 상세 설계를 작성한다.
- [ ] 버전 있는 데이터셋·분리 평가 세트·B1 결과를 준비하고 검색 실패와 생성 실패를 분리해 기록한다.
- [ ] 실패/취소/재개·checkpoint 정합성·훈련 이력·모델 등록 테스트와 정확한 실행 명령을 계획에 포함한다. 구체적인 데이터셋·모델·장치·예상 자원을 확인한 수동 실행으로 시작한다.
- [ ] 학습 후 B0/B1/B2를 반복 평가한다. 정답·완전성·인용 지지·근거 부족 거절·환각·멀티턴·지연·토큰·메모리·학습 자원을 보고한다.
- [ ] 본래 환경의 후보 구성에서 대화·모니터링·기존 세션 이어가기를 검증한다. 학습 완료·평가 통과·RAG 연결·기본 승격·공개 릴리스는 각각 구분한다.

## 기록·검증·인계

기술 상위 분류와 하위 주제는 기존 체계를 따르고 RAG/벡터 저장소 비교, 파인튜닝/로컬 LLM 학습으로 구분한다. 화면에 표시할 기록은 기존 Learning/평가/모델·실행 참조에 연결한다. 이번 문서 등록은 DB 실험 레코드 생성이나 화면 구현 완료를 뜻하지 않는다.

이번 문서 검증은 상대 링크·정본 충돌·WORKBOARD 최근 완료 최대5개·공백 검사와 독립 문서 검토다. 구현 시 요구·아키텍처·RAG·AI/DB·권한·개인정보·테스트/독립 검증 역할을 실제 범위에 맞춰 다시 선택한다. 설치·학습·migration·비교를 실행하지 않은 이번 등록에서 구현 검증을 통과했다고 기록하지 않는다.

각 상세 계획은 실제 파일·인터페이스·단위/통합 명령·실행 대상·기록 위치를 준비 게이트에서 확정한다. 관찰을 재사용하면 시점·조건·미기록 항목을 명시하고 존재하지 않는 성공을 채우지 않는다.
