# 개발·실험 기록 공개 서비스

- 상태: 핵심 공개·관리 기능과 실제 15건 게시 확인 완료, 사용자 테스트 가능.
  당시 남았던 상단 공통 메뉴 대비는 [후속 가독성 개선](2026-09-08-publishing-readability.md)에서 해결했다.
- 정본: [공개 관리 설계](../superpowers/specs/2026-09-07-public-study-management-design.md),
  [구현 계획](../superpowers/plans/2026-09-08-publishing-service.md), [ADR 0019](../decisions/0019-public-study-snapshots.md).
- main의 기존 변경을 보존하며 커밋·push하지 않는다.

## 완료된 공개 저장 계층

기존 package/domain/projection 계약 위에 실제 SQLite 쓰기/읽기 어댑터를 추가했다.
게시·철회와 topic·멱등 fingerprint를 동일 트랜잭션으로 저장한다. 읽기는 mode=ro이며
canonical bytes와 digest를 재검사한다. 철회 후 과거 게시 요청이 재시도돼도 본문을 복원하지 않는다.

독립 리뷰에서 잘못된 Unicode 입력의 예외 노출과 수정 후의 저장소 장애 우선순위 문제를
발견했다. 각각 재현 테스트 후 보완했고 독립 재검토가 승인됐다.
메인 최종 집중 검증은 Publishing 102 passed(0.85초), 담당 Ruff/mypy 통과다.
이 수치는 API·PostgreSQL·브라우저 연결 검증을 포함하지 않는다.

## 공개 문구 준비

RAG 관련 worklog 후보 23개를 15개 사례로 연결했다. 같은 사건의 조사·수정·후속 검증은
하나의 계보로 묶었다. 편집본은 문제·원인·선택·개선·검증·한계를 설명하며 원시 작업 로그,
식별자·호스트 경로·계정 정보·비공개 원문을 복사하지 않는다. persona는 비워 두었다.

15개 편집본의 사실성·개인정보 검토를 구현과 별도로 수행했다. OCR 초안 상태, 클라이언트
응답 해석 문제, seed 복구 범위, 자원 검사 순서, 미실행 검증과 경로 개선의 표현을 교정한 뒤
재검토 승인을 받았다. StudyContent/StudySnapshot 검증과 slug 중복 검사도 통과했다.
정확한 출처·원본 해시·공개 revision/hash는 비공개 `.local-data/publishing-preparation/`에 있다.
최종 수정의 원자적 초기 게시 경로를 독립 검토한 뒤 15건 모두 revision 1로 실제 게시했다.

## 통합 중 확인한 복구 경계

화면 구현 중 대기 요청을 새로고침·재선택하면 원래 요청 ID 외의 승인 버전 정보가 없다는
점을 확인했다. 요청 후 새 편집본이 저장되면 현재 편집본의 revision/digest는 원래 명령과
다르므로 이를 사용한 재시도는 충돌한다. 비공개 outbox에는 원 정보가 이미 저장돼 있다.
owner 전용 응답에 최신 미적용 명령의 `pending_command`를 보완하고, 공개 API와 DB 스키마는
변경하지 않는 방식으로 수정했고 집중 38개 테스트·정적 검사와 독립 리뷰를 통과했다.
지연된 요청 응답도 호출 의도가 아닌 반환된 현재 적용 상태로 안내하도록 프론트 통합을 재개했다.
최신 호스트 API에서 대기 중인 공개 v1 이후 비공개 v2를 저장하고 다시 조회한 뒤 재시도해도
승인한 v1만 공개되고 v2는 비공개로 유지되는 것을 확인했다.

## 실행 경계와 남은 작업

관리자 `/admin/publishing`, 공개 `/labs/rag/studies`와 `/studies/[publicSlug]`, RAG 총괄·담당자의
관련 기록 링크를 구현했다. 미리보기와 공개 상세는 같은 일반 텍스트 렌더러를 사용한다.
관리자 변경에는 원본·비밀값·개인정보를 직접 검토해야 한다는 안내가 있으며 자동 비식별화는 아니다.
독립 리뷰에서 페이지 이동 시 미저장 편집 손실과 불확실한 요청의 재시도 정보 손실을 찾아
회귀 테스트로 수정했다. 원 요청이 해결되기 전에는 기록 교체·새 기록·페이지 이동을 제한한다.
338개 전체 프론트 테스트, 최종 변경 집중 33개, 타입·린트·API 타입 검사와 독립 재검토를 통과했다.
메인의 수정 후 빌드도 성공했다(컴파일 12.9초, 타입 28.1초, 정적 페이지 14개).

기존 5173 서버가 실행 중이어서 검증용 서버가 같은 빌드 잠금과 충돌했다. 기존 서버를 종료하지
않고 안전한 인스턴스 이름으로 `.next/instances/` 아래 빌드를 분리했다. 15173의 합성 계정용
통합 실행과 15174의 공개 전용 실행을 분리했다. 공개 전용에는 OS 필수 환경과 공개 설정만
전달했고 실제 HTTP에서 공개 조회 200, 관리자·작업소·로그인·비공개 API 404를 확인했다.
실제 Edge 2건에서 전체 편집본 비교·게시·철회·실제 잠금 장애·정확한 재시도·공개 전용 경계를
검증했고 독립 재검토가 승인됐다. 사용자용 API의 복구 계약 반영을 확인했고, 이후 최종
백엔드 수정까지 반영하기 위해 해당 API 프로세스만 갱신했다.
최종 리뷰의 초기 게시 경쟁 조건·미리보기 중 기록 전환을 한 번의 보완 작업으로 수정하고
독립 재검토를 받았다. 링크 대비는 기록·NPC·돌아가기에서 해결됐지만 상단 공통 메뉴는 남았다.

복구 계약 보완 후 메인의 전체 unit/contract 재실행은 1,030개 통과(44.62초, 종료 0)했다.
기존 Starlette/httpx 폐기 예정 경고 1개는 남아 있다. 독립 리뷰에서 예외 500의 no-store 누락과
DB 저장 가능 길이·NUL 경계가 발견됐다. RED 11개 실패 후 수정했고 집중 41개·Ruff/mypy 및
독립 재검토를 통과했다. 화면·실행 검증은 별도다.

- 백엔드 리뷰와 별도 PostgreSQL 검증 후 로컬 0023→0024→0025를 적용했다. 신규 대상 5개
  테이블 부재를 먼저 확인했고 기존 데이터를 변경하지 않았다. 적용 후 Learning 기록·공개 편집본·
  공개 명령은 모두 0개다. 따라서 초기 Learning 공개 후보는 없으며 worklog 15건만 준비됐다.
- 기존 웹 5173·비공개 API 18000을 보존했다. 공개 API 18001을 OS 환경 허용 목록과 정확한
  공개 DB 절대 경로만 전달해 실행했다. 게시 후 목록·상세는 200이며 15건을 반환한다.
- 비공개 PostgreSQL revision/outbox, owner API와 독립 공개 app은 구현·독립 검토를 마쳤다.
  관리자·공개 React 화면과 연구실 기록 링크도 연결·검증됐다.
- 관리자 변경 API는 기존 owner 인증에 명시적 CSRF 검사를 보완한다.
- 공개 저장소의 적용 확인 전에는 대기로 표시한다. 같은 Windows 계정의 프로세스 분리는
  OS 파일 접근 격리를 증명하지 않으며 운영 격리는 별도 검증한다.
- 실제 저장·공개·익명 조회·철회·재공개 흐름과 화면 동작을 검증한 뒤 사용자 테스트를 요청한다.
- 별도 합성 DB·계정과 호스트 API에서 실제 저장·게시·익명 조회·철회·재공개를 확인했다.
  철회 후 과거 게시 재시도는 404를 유지했다. 테스트 SQLite를 제한 시간 잠가 적용 실패를
  재현했고, 대기 상태·잠금 해제 후 같은 요청 재시도도 통과했다. 실제 사용자 데이터에
  테스트 기록을 넣지 않았다. Edge 검증에서 만든 합성 기록은 모두 철회·대기 없음·공개 404를
  확인한 뒤 해당 fixture DB teardown으로 회수했다.
- 외부 AI 호출·검색 모델 변경·Docker 정리는 이번 범위가 아니다. 공개 DB와 승인 자료는
  CACHE_POLICY에서 애플리케이션 데이터로 구분했으며 삭제하지 않았다.

## 최종 보완과 실제 확인

- 내부 `publish_initial`은 최초 편집본과 게시 명령을 같은 트랜잭션에서 만들거나 기존 행을
  잠근 뒤 최초 상태/정확한 원 요청만 허용한다. 철회 대기·다른 요청·후속 버전은 거절한다.
  단순 사전 조회의 경쟁 조건을 없앴으며 일반 관리자 HTTP 계약은 변경하지 않았다.
- 편집기의 busy 상태에 요청 소유권을 부여해 늦은 미리보기/재조회 응답이 다른 기록의
  편집을 잠그거나 새 요청의 대기를 풀지 못하게 했다. 최초 목록 오류도 선택 없이 표시한다.
- 담당 검증: Publishing 단위 133개, 격리 PostgreSQL 9개, HTTP 계약 13개, 관련 UI 47개,
  Ruff/mypy/TypeScript/ESLint 통과. 메인 최종 build와 실제 Edge 2건(27.9초)도 통과했다.
- 메인 전체 backend 재실행: 1,031 passed, 42.32초. 최초 backend 디렉터리 실행은 기존
  Learning 익명 테스트의 secret_key 설정 누락으로 1건 실패했다. 합성 secret과 접속 불가
  DB 주소를 프로세스에 명시한 재실행은 모두 통과했다. 실제 앱의 비밀값/DB에 의존하지 않았다.
- 실제 5173에서 익명 API 목록·15개 상세와 일치, 목록/상세 페이지, 총괄의 15개 링크를
  Tab으로 순회, 담당자 링크, 닫기/검색 액션, Escape 후 포커스 복귀를 1440/960에서 확인했다.
  페이지 실행 오류와 가로 넘침은 없었다. 관리자 경로의 익명 요청은 로그인으로 이동한다.
- 실제 owner 비밀번호/세션으로 브라우저를 조작하지 않았다. 관리자 전체 변경 흐름은 합성
  owner로 검증했고 실제 계정에서는 사용자가 최종 확인한다.
- 실제 API의 오래된 작업 프로세스만 정확히 확인해 갱신하고 기존 환경을 보존했다.
  현재 프론트 5173, private API 18000, public reader 18001을 유지한다.
- 테스트 포트 15173/15174/18100/18101을 종료하고 해당 fixture의 임의 이름 합성 DB만
  정상 teardown으로 회수했다. 실제 게시본 15건은 테스트가 아니므로 보존한다.
- 검증용 TS include/import 경로는 원래 설정으로 복구했다. 검증용 빌드 캐시 3개 폴더는
  정확 범위를 제시했으나 삭제 응답이 없어 보존했다. SQLite 증거와 승인 자료도 보존했다.

## 사용자 테스트 순서

1. `http://127.0.0.1:5173/labs/rag/studies`에서 기록 15건과 문제·개선·검증·남은 한계를 읽는다.
2. `/labs/rag`에서 RAG 총괄 또는 담당자 → 관련 공개 연구 → 상세 이동을 확인한다.
3. `/admin/publishing`에서 본인 관리자 계정으로 로그인하고 기록 선택·수정·저장·미리보기·
   공개/비공개 전환을 확인한다. 새 익명 탭/새로고침에서 공개 상태를 확인한다.

철회는 이후 조회를 막으며 이미 열린/복사된 내용을 회수하지 않는다. 이번 확인은 Publishing이며
실제 Codex LLM 답변·운영 OS 격리·파인튜닝 실행 완료가 아니다.

## 미완료·후속

아래 메뉴 대비 항목은 이 작업 종료 당시 기록이다. 이후 가독성 개선에서 메뉴 3개의
대비 4.5:1 이상을 실제 브라우저로 확인했다. 상세는 상단 후속 링크를 따른다.

- 공개 기록 화면의 상단 공통 메뉴 3개는 기본 파랑이며 배경 대비가 약 2.06:1이다.
  최종 재검토에서 부분 미해결로 남았고 실제 브라우저도 이 실패를 별도로 기록했다.
  `.shell` 범위의 기본/방문/포커스 색상 보완이 다음 작업이다. 기록/NPC 링크 검증과 구분한다.
- 운영 동시 접속 전 public SQLite 동기 읽기 offload, 새로운 명령 대기 중 과거 요청 재생
  추가 검증, E2E 잠금 자식 종료 보장/404 허용 범위/최종 상태 assertion 강화를 후속 처리한다.
- 공통 favicon 404와 Starlette/httpx 경고는 남아 있다. 운영 수동 전달 도구·OS 권한 격리는
  별도 배포 게이트다. 로컬 기능 확인을 운영 보안 증거로 사용하지 않는다.

## 작업 중 판단과 비용

1. 같은 계정 프로세스 검증은 기능 증거로만 분류했다. 잘못 분류하면 운영 격리를 과장한다.
2. 관리자 변경에 CSRF 검사를 보완했다. 잘못된 Origin 설정은 정상 관리자 요청을 거절할 수 있다.
3. 백엔드 검토 후 UI 완료 전에 추가형 0024/0025 migration을 적용했다. 새 스키마가 먼저
   생기는 비용이 있지만 원래 데이터는 변경하지 않았고 실제 공개는 후속 검증까지 보류했다.
4. owner 전용 pending_command를 추가했다. 비공개 DTO가 늘지만 공개 데이터/스키마는 늘리지 않았다.
5. 검증용 Next 인스턴스 빌드를 분리했다. 설정 하나와 재생성 가능한 빌드 산출물이 추가됐다.
6. 처음에는 최신 스키마의 실제 API를 보존했지만 후속 수정 전 프로세스임을 확인해 갱신했다.
   잘못된 판단의 비용은 오래된 코드 유지/불필요 재시작이므로 정확한 프로세스와 환경을 재확인했다.
7. 작은 로컬 범위에서 동시 조회/테스트 실패 경로 보완을 후속으로 두었다. 운영 처리량과
   실패 경로 검증의 한계가 남으며 배포 준비 완료로 주장하지 않는다.
