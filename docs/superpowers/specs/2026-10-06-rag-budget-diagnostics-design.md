# 입력 예산 초과 사유의 정확한 진단

- 상태: 사용자 승인 후 TDD 구현·독립 리뷰·본래 새 요청/저장/화면 복원 검증 완료(2026-10-07). 선택 변경이나 RAG 전체 마감은 이 진단 범위에 포함하지 않는다.
- 기준일: 2026-10-06
- 기존 계약: [문맥 근거 설계](2026-09-21-contextual-rag-evidence-design.md), [실행 모니터링](../../decisions/0029-rag-execution-monitoring.md)
- 목적: 관련성은 통과했지만 생성에 전달되지 않은 이유를 대화와 실행 모니터링에서 이해할 수 있게 한다.

## 확인한 경계

본래 활성 v4는 묶음8·원문 단위32·문자12000 상한을 적용한다. 실제 마지막 대화의 적격 두 청크는33단위/712문자와36단위/683문자다. 처음부터 각 묶음이 단위 상한을 넘으므로 선택0이며 문자·묶음 수가 초과 원인은 아니다. 세 번째38단위 청크는 관련성 임계값 미달로 선택 대상이 아니다.

현재 원문 위치는 PDF 페이지·bbox·문자 offset까지 검증되지만 표 셀 row/column 정보는 없다. 단위를 무작위로 빼거나 앞32개만 전달하면 헤더·다른 대상·조건·예외를 잃을 수 있다. 기존 계약의 전체 묶음 수용/제외는 유지한다. 문맥을 작은 구조 묶음으로 재구성하는 기능은 별도 버전 전략과 품질 평가가 필요한 후속 설계다.

## 제안하는 작은 변경

선택 알고리즘·한도·프로파일·권한·모델을 유지하고 현재 예산 판정을 수행하는 바로 그 지점의 수치만 추가로 전달한다. 실패나 옛 결과의 예산 수치를 현재 프로파일로 소급 추정하지 않는다.

- 후보별 선택 검사를 수행한 묶음의 원문 단위 수·문자 수를 기록한다.
- 검사 직전까지 선택된 묶음 수·원문 단위 수·문자 수를 기록한다.
- 그 실행에서 적용한 묶음·단위·문자 상한과 실제 초과한 종류를 기록한다. 초과 종류는 최대3개이며 동시에 여러 종류가 초과되면 모두 남긴다.
- 미달 후보는 예산 검사를 실행하지 않았으므로 진단을 붙이지 않는다. 충돌 때문에 최종 선택이 취소된 경우 예산 판정과 최종 충돌 차단 사유를 구분한다.
- `budget_trace`는 nullable additive 필드로 Search diagnostics와 실행 selection candidate에 전파한다. 원문·질문·답변·벡터를 포함하지 않는다. 새 API 타입을 생성하고 기존 JSON 저장 경로를 사용하며 DB migration은 없다.
- 수치는 strict nonnegative integer, 한도는 strict positive integer로 검증한다. typed 객체는 extra field를 거절하고 초과 종류 enum은 중복 없는 최대3개다. group 행에만 붙이고107개 문장 행에 같은 기록을 복제하지 않는다. 진단 표시가 꺼져도 기존 `context.observations`를 통해 실행 selection에 같은 실제 관측을 전파하며 후보200/top_k 상한을 유지한다.
- 옛 응답·실행의 필드 부재는 그대로 허용하고 필드 값이 None이면 직렬화에서 생략한다. 기존 결과·digest·원문 ID·인용·승인 결속은 변경하지 않는다.
- 대화·모니터링의 기존 ‘입력 예산 초과’ 사유 아래 `원문 단위 33개 / 남은 32개 (전체 한도32개)`처럼 해당 초과 수치만 짧게 표시한다. 별도 메뉴·버튼·큰 표·스크롤 영역을 추가하지 않는다.

## 구현 범위와 검증

서버 변경은 `highlighting/context.py`의 예산 관찰, `search/schemas.py`의 additive 응답, `executions/domain.py`와 `executions/selection.py`의 안전한 저장 메타데이터다. 표시 로직은 재사용하는 작은 컴포넌트 하나와 기존 `SearchDiagnostics`·`ExecutionDetailPage`에 한정한다. 기존 단위·통합 fixture에 합성 수치만 사용한다.

성공 기준은 다음과 같다.

1. 단위·문자·묶음 각각의 초과 및 복합 초과, 누적 소비 후 초과를 정확히 설명한다.
2. 진단 on/off의 선택 묶음·원문 단위가 동일하고 추가 임베딩 호출이 없다.
3. 충돌 쌍의 일부만 전달되지 않으며 예산 수치로 최종 충돌 차단을 덮지 않는다.
4. 선택 판정은 기존32/128 단위·전체 문맥 보존 회귀와 동일하다.
5. 옛 결과·새 필드 부재와 현재 권한 철회·후보 무결성 검증을 유지한다.
6. 실제 새 실행에서 수치가 저장·새로고침 복원되며 옛 실행은 ‘세부 예산 미기록’으로 표시한다. 자동 fixture 검증과 본래 화면 확인을 구분한다.

선택 결과가 달라지는 구현, 묵시적인 한도 증가, 후보 승격, 표 관계 복원이나 DLL 보안 정책 변경은 이 작은 변경에 포함하지 않는다.

## 사전 독립 검토

2026-10-06 구현 담당과 분리한 verifier가 기존 선택·응답·실행 저장·두 표시 컴포넌트를 읽고 설계 차단 의견0을 확인했다. `model_dump(mode="json")`의 기본 None 포함 때문에 새 필드만 명시적으로 생략해야 하며 광범위한 serializer 변경을 하지 않는다. 검토는 제품 구현·테스트·본래 화면 통과를 뜻하지 않는다. 범위 확인 뒤 위 성공 기준의 회귀를 RED부터 작성한다.
