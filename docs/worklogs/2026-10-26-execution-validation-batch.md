# 실행 목록 검증 조회 일괄화

2026-10-26, ISSUE-00042의 후속이다. 사용자가 다음 개선 방향으로 제안받은 반복 검증 조회 일괄화를 승인했다. 기존 체크아웃·DB·계정과 답변 품질을 보존하며 목록의 읽기 비용만 줄였다.

## 원인과 수정

숫자 검증 context에 필요한 것은 프로파일 설정인데 기존 ORM 조회가 연결 모델 목록까지 자동으로 읽었다. 새 기준선에서 Profile 조회445회에 model bindings 조회445회가 추가됐다. 완료된 평가 attempt마다 Audit/Profile을 반복 읽는 비용도 있었다.

목록의 `run_detail(list_only=True)`에만 최대64개 execution context를 묶어 읽는 `NumericValidationBatch`를 연결했다. 필요한 Audit 필드와 Profile 설정을 scalar projection으로 읽어 관계 자동 로딩을 피한다. schema3만 receipt 정보를 읽고 schema1/2는 숫자 테이블이 없는 과거 스키마와 호환된다.

기존 `verify_binding`과 `numeric_restore`는 수정하지 않았다. 숫자 payload digest·재구성, 새 receipt 조회, 감사기록, 현재 원문 권한과 operand의 정확한 위치 검사를 그대로 수행한다. batch 마지막에는 감사·프로파일·receipt를 새 SQL로 다시 읽어 변경을 거절한다. 중복 audit는 기존 단건 조회 의미를 보존하며 중복 전환도 감지한다. 결과 순서·한 번의 decode·품질 판정과 마지막 원문 권한 재확인을 유지한다.

요청 간 캐시·추가 worker·모델/프롬프트/검색/답변/인용 변경은 없다. 일반 대화와 상세 조회는 기존 경로를 사용한다. 승인 설계는 [계획](../superpowers/plans/2026-10-26-execution-validation-batch.md)에 있다.

## 기존 DB 읽기 전용 실측

기존 활성 소유자의 접근 가능한508건(대화25/평가483)을 읽었다. 변경 전 파일 복사본을 측정 프로세스 안에서만 로드하고 본래 제품 파일을 덮어쓰지 않았다. 전후 각각2회, profile 계측 없이 같은 방식으로 측정했다. DB 연결은 `default_transaction_read_only=on`이며 모델 호출0회다.

## 검증과 반영

구현 담당과 독립 보안/테스트 검토를 분리했다. 신규 batch·목록 연결·중복 profile 후검증의 실패를 먼저 확인하고 수정했다. 독립 pytest의 중복 제거 합집합284개가 통과했다. 혼합 schema, receipt11필드 변조, 유일↔중복 audit 전환, profile 객체 변경,64+1 chunk, 선행 pending, 순서·후검증, 기존 숫자 복원·권한·목록 회귀를 포함한다. 범위 strict Mypy3파일, Ruff4파일과 공백 검사를 통과했다. 전체 프로젝트 검사를 했다는 의미는 아니다.

기존 DB25표2560행·진행 중 작업0과 정확한 API/launcher 신원을 확인한 뒤 본래 Conda API를 같은 실행기로 재시작했다. health/ready200, 기존 대화202/동기응답과 실행 목록·상세 계약을 확인했다. 본래 로그인 브라우저에서 전체508건 목록, 저장 평가 상세의 답변·인용2개·근거28개와 기존 품질 실패 표시를 확인했다.

대화 필터25건을 확인하고 전후25표2560행의 PK별 해시와 `.env`가 모두 동일함을 확인했다. ISSUE-00042의 원인·수정·검증·남은 작업과 날짜별 진행 이력을 저장하고 새로고침 후 재조회했다. 기존 이력은 보존했다. 같은 화면에서 편집 직후 이력 추가는 버전 충돌로 거절되어 최신 상태를 새로 연 뒤 저장했다. 입력 손실·기존 기록 덮어쓰기는 없었고, 이 동작을 별도 결함으로 확정하지 않는다.

검증 근거는 `.local-data/project-agent-work/execution-validation-batch-20261026/`의 `timing-{before,after}-all{,-2}.json`, `qa-*.xml`, `qa-final-review.md`, `trace-runtime-*.json`, `review-*.json`이다. 본문·비밀번호·토큰은 기록하지 않았다.

## 남은 한계

목록 전체 조회는 여전히 약8.7초다. 이번 개선은 반복 context SQL에 한정되며 현재 원문 권한 조회·숫자 증명·품질 판정 비용은 남는다. 다음 개선 후보는 정확한 문서/버전/projection tuple을 유지하는 원문 권한 조회 일괄화와 목록에 필요한 계산 비용의 분리다. 현재 권한과 전후 재검증을 생략하는 캐시로 대체하지 않는다.

새 질문이나 모델 생성은 실행하지 않았다. 저장된 응답과 검증 결과를 보존한 것이며 기존 정답0/2 한계를 품질 통과로 바꾸지 않는다. 이번에는 프론트엔드 수정이 없어 이전320/375px 검증을 새 모바일 검증으로 다시 집계하지 않는다. 커밋·push·설치·데이터 migration은 수행하지 않았다.
