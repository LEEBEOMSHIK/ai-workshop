# Codex 전체 프로세스 OS 격리 대안

- 상태: 1차 호스트 변경 사용자 승인 / 실행기 소스 작성·컴파일 / 코드 실행 정책으로 실제 검증 차단
- 기준일: 2026-09-07
- 목적: Codex CLI를 로컬 개발용 RAG 생성 실행으로 연결하고 관리자 UI에서 관리한다.
- 기존 결정: [ADR-0011](../../decisions/0011-development-codex-app-server-provider.md)
- 기존 검사: [CLI 0.153.4 사전 계약 검증](../../worklogs/2026-09-07-codex-01534-isolation-preflight.md)
- 1차 구현 기록: [실행기와 Windows 정책 차단](../../worklogs/2026-09-07-codex-os-isolation-probe.md)

## 1. 변경할 기준과 유지할 기준

기존의 실행 전 built-in tool inventory 조회를 필수 증거로 삼는 방식 대신, Codex 본체와
자식 프로세스가 OS에서 실제로 행사할 수 있는 권한을 제한·검증하는 방식을 검토한다.
기존 조회 메서드를 반복 탐색하거나 실패 검사를 삭제해 통과시키는 방식이 아니다.

문서 권한, 승인된 데이터만 외부 전송, 근거 제한 생성, 인용 검증, 모델 실패 시 대체 금지는 유지한다.
Codex가 로컬 프로세스라는 이유로 추론을 로컬 처리라고 표시하지 않는다.

OS 격리 성공은 원격 web search 등 서버 측 도구 미사용 증명이 아니다. 호스트 보호와
추론 요청의 도구 통제를 별도로 검증하고, 둘 중 하나라도 실패하면 RAG 생성은 활성화하지 않는다.

## 2. 대안 비교와 선택

| 대안 | 판단 |
|---|---|
| Codex elevated command sandbox만 사용 | 명령 실행 경계와 Codex 본체 경계가 달라 전체 격리 대안으로 불충분 |
| 전용 WSL/VM 환경 | 검토 가능한 대안이나 새 환경 설치·용량·관리 비용이 추가됨. 이번 기본 경로로 선택하지 않음 |
| Windows AppContainer/LPAC 전체 프로세스 격리 | Windows 네이티브 1차 실험 후보. Docker 및 별도 Linux 서버 불필요. CLI 호환성은 미검증 |

현재 읽기 전용 점검에서는 Windows 11 Home ARM64와 WSL의 docker-desktop 배포판을 확인했다.
사용자 지침에 따라 기존 Docker 배포판을 수정하거나 RAG 실행용으로 재사용하지 않는다.

## 3. 1차 구현 경계: 네트워크·인증 없는 실행기 실험

첫 구현은 제품 Provider가 아니라 제한된 실행기와 합성 검증 프로그램이다.
다음 항목만 구현하며 실제 질문·문서·Codex 로그인은 사용하지 않는다.

1. 정확한 실행 파일·버전·hash를 설정에서 선택하고 대상 경로의 reparse 경계를 검증한다.
2. 전용 AppContainer 프로필을 생성하고 LPAC 적용을 확인한다. 보안 토큰을 확인할 수 없으면 실패한다.
3. 네트워크 capability는 부여하지 않는다. 전역 방화벽·인증서·기존 사용자 ACL을 바꾸지 않는다.
4. 실행 파일의 필요한 읽기·실행 권한과 전용 scratch의 쓰기 권한만 좁게 부여한다.
5. 허용 handle만 상속하고 자식 생성 제한을 적용한다. 프로세스를 정지 상태로 만들고 Job에
   편입한 뒤 제한을 확인해야 재개한다. Job breakaway는 금지하고 supervisor 종료 시 함께 종료한다.
6. 동일 프로필의 합성 검사 프로그램으로 파일·프로세스·네트워크 거부를 확인한다.
7. 검사가 통과한 경우에만 인증 없는 CLI 버전·초기화 호환성을 확인한다. CLI가 필요한 자식을
   실행하지 못해 실패하면 격리를 완화하지 않고 호환성 실패로 기록한다.

실행기는 입력으로 설정 참조·실행 ID·검사 종류를 받고, 결과로 단계별 성공 여부와 안전 오류 코드만
반환한다. 파일 본문, 계정, 인증값, 호스트 경로와 원시 stderr는 보고서에 포함하지 않는다.

### 1차 합성 검증

- 허용 scratch 읽기·쓰기 성공: 프로세스가 실행되지 않은 것을 거부 성공으로 오인하지 않는다.
- scratch 밖 별도 합성 보호 파일의 읽기·쓰기 거부. 사용자 실제 파일로 검사하지 않는다.
- shell·다른 실행 파일 생성, 권한 있는 외부 프로세스 handle 획득과 Job 이탈 거부.
- 통제된 수신기 대상 직접 연결, IPv4·IPv6·loopback 우회 거부. 단순 timeout만으로 성공 판정하지 않는다.
- 정책 설정 실패·토큰 불일치 시 실행 재개·본문 전송 0건.
- 취소·timeout·supervisor 종료 뒤 해당 작업의 프로세스·상속 handle 잔존 0건.

## 4. 필요한 호스트 변경 승인

1차 실험에도 저장소 밖 Windows AppContainer 프로필 등록과 전용 실행 파일·실험 디렉터리의
정확한 ACL 추가가 필요할 수 있다. 범위는 프로젝트가 이번 실험용으로 생성한 프로필과 디렉터리다.
개발자 홈, 기존 Codex 프로필, 프로젝트 소스 전체에 권한을 부여하지 않는다.

사용자의 일반적인 구현 승인과 OS 보안 설정의 상세 변경 승인을 구분한다. 실행 전에
프로필 식별자·절대경로·추가할 권한·예상 생성 크기·삭제 대상을 확정해 확인한다.
1차 범위에는 Windows 계정 생성, 상주 서비스 설치, 방화벽 변경, loopback 예외와 전역 CA 등록이 없다.
추가 권한이 필요해지면 멈추고 그 이유와 정확한 변경을 다시 보고한다.

복구 시 이번 실행이 새로 만든 프로필만 제거한다. ACL은 이번에 추가한 정확한 ACE만 제거하고
기존 ACL 전체를 덮어쓰지 않는다. 경로가 바뀌거나 다른 실행이 사용 중이면 정리를 중단한다.
캐시·산출물 삭제는 기존 CACHE_POLICY의 조사·승인·재검증을 따른다.

## 5. 2차 경계: 인증과 통제된 모델 통신

1차 성공 후 별도 설계·검증한다. 아직 승인된 통신 구현이 없다.

- RAG 실행 프로세스는 인터넷·LAN·다른 localhost 서비스로 직접 연결할 수 없어야 한다.
- 모델 통신은 요청을 검사하는 중계 계층만 사용한다. HTTPS CONNECT 터널과 proxy 환경변수만으로
  우회 방지 또는 원격 도구 금지를 주장하지 않는다.
- 허용 모델·요청 schema·도구 사용·출력 제한을 확인하고 모르는 필드나 경로는 거부한다.
- 지원되는 Codex 인증·전송 계약 안에서 구현 가능한지 먼저 확인한다. 개인 Codex 인증 파일을
  복사하거나 비공개 인증 endpoint를 임의 호출하는 방식은 사용하지 않는다.
- 프로젝트 전용 인증과 생성 요청의 권한을 분리한다. 인증정보가 격리 프로세스에 제공되는 경우
  그 노출 위험을 별도 검토하고 승인 없이 안전하다고 표시하지 않는다.
- broker 중단·설정 변조·직접 연결 시도에서 요청이 전송되지 않는지 실제 검사한다.

지원되는 통신·인증 경로로 이 조건을 달성하지 못하면 대체 설계를 다시 판단한다.
새 방화벽/WFP 설정·네트워크 예외·서비스 설치가 필요하면 정확 범위와 rollback을 별도로 승인받는다.

## 6. 3차 경계: RAG 및 관리자 UI

격리·통신 검증을 통과한 실행기만 기존 GenerationRuntime 어댑터로 연결한다.
문맥화와 답변은 서로 다른 임시 실행으로 처리하고, 서명된 대화 범위와 인용 hard gate를 유지한다.
다른 Provider·모델·추출 답변으로 조용히 전환하지 않는다.

관리자는 CLI 버전, 모델 선택, 프로젝트 인증 상태, 실제 추론 위치·외부 전송, 격리 검사 결과,
연결 상태와 안전 진단을 관리한다. OS 권한 변경은 웹 서버가 임의 수행하지 않는다.
미검증 상태를 준비 완료로 표시하지 않으며 일반 사용자에게 관리 기능을 노출하지 않는다.

생성 프로파일·자산운용용 Hybrid 구성·평가·도메인 연결은 그 이후다.
이번 문서 작성은 Codex Provider 또는 자산운용 대화 활성화 완료를 의미하지 않는다.

## 7. 독립 검토와 근거

주요 미확인 조건은 CLI 호환성과 우회 불가능한 egress·원격 도구 통제다. 실제 실행 검증은 아니다.
