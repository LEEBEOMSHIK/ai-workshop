# 질문 의미와 원문 문맥을 보존하는 RAG 근거 전달

- 상태: 사용자 목표 승인, 독립 설계 검토 통과, 구체 설계 사용자 검토 대기. 제품 구현·운영 반영 전.
- 기준: 2026-09-21, 기존 main의 RAG 흐름과 원래 개발 환경.
- 목표: 특정 상품·지급일 표현에 의존하지 않고 다양한 질문에서 관련 원문과 문맥을 찾아,
  답변의 각 인용을 실제 원문 위치까지 연결한다. 모든 질문에 답을 보장한다는 의미는 아니다.

## 1. 확인한 문제

`highlighting/service.py`는 문장별 keyword/semantic 판정 뒤 대표 근거와 문서 간 충돌만 반환한다.
`search/service.py::_generation_evidence`도 그 둘만 전달해 다른 관련 문장이 사라진다.
문장의 대상이 제목·앞 문장에 있고 답이 뒤 문장에 있으면 문장 단독 비교로 의미를 놓칠 수 있다.

세 생성 어댑터의 payload는 evidence ID와 text만 전달한다. 문서·버전·절·문단의 관계가 사라진다.
`ConversationAnswer.tsx`는 answer/conflicts만으로 인용을 찾으므로 추가 근거를 생성에만 보내면
그 인용은 화면에서 누락된다. `CitationValidator`의 ID·일부 수치 검사는 사실의 대상 관계를 증명하지 않는다.

## 2. 접근 선택

| 접근 | 판단 |
|---|---|
| 문장 유사도 임계값을 일괄 낮추기 | 무관한 근거와 잘못된 대상 연결 위험이 있어 채택하지 않는다. |
| 검색한 전체 문서/청크를 무조건 생성에 전달 | 전송량·지연·불필요한 근거가 늘어 채택하지 않는다. |
| 구조를 유지한 문맥 후보의 관련성을 평가하고 제한된 근거 묶음을 전달 | 채택. 기존 hybrid 검색·권한·원문 ID를 재사용한다. |

## 3. 검색과 문맥 후보

BM25 + dense + RRF 및 선택적 reranker 순서는 유지한다. 첫 검색 순위에는 LLM을 추가하지 않는다.
검색 범위와 현재 활성 문서·버전·projection·index build 확인을 통과한 source만 후보로 삼는다.
검색되지 않은 문서나 사용자가 선택하지 않은 공간을 이웃 문맥이라는 이유로 추가하지 않는다.

후보를 두 수준으로 만든다.

1. 문장: 기존 EvidenceUnit 원문과 정확한 위치.
2. 문맥: 하나의 검증된 RetrievedChunk에 있는 모든 유효 EvidenceUnit을 하나의 후보 묶음으로 만든다.
   묶음 안에서는 element_id별 경계를 유지하고 EvidenceUnit.ordinal 및 원문 offset 순서를 보존한다.
   서로 다른 element도 같은 chunk 안에서는 포함할 수 있으나 문장들을 하나의 가짜 인용으로 합치지 않는다.
   동일 element가 여러 chunk에 걸쳐 있어도 추가 fetch나 chunk 간 자동 병합은 하지 않는다.
   section_path는 묶음의 탐색 문맥이며 별도 EvidenceUnit으로 만들지 않는다.

문장 및 문맥의 의미 유사도를 비교한다. 한국어 조사·바꿔 말하기 때문에 정확 문자열이 달라도
문맥 의미 비교 경로를 사용할 수 있다. 키워드 하이라이트는 실제 일치 문자열만 표시한다.
키워드 점수와 cosine 점수를 단순 합산하거나 서로 같은 척도로 취급하지 않는다.
기존 keyword/semantic 정책으로 자격을 판정하고 동점에서는 검색 순위·원문 순서로 결정한다.
문맥 단위에서의 임계값 적정성은 별도 평가한다. 기존 문장 임계값의 성능이 그대로 유지된다고 가정하지 않는다.

선택된 묶음은 원문 EvidenceUnit 경계를 보존한다. 같은 묶음에 있다는 사실만으로 대상이 같다고
판정하지 않는다. 서로 다른 상품·사람·조건이 있는 원문은 각각의 문장을 그대로 보여 주고
모델이 질문 대상과 속성을 명확히 연결할 수 없으면 근거 부족으로 처리하도록 한다.

표는 기존 table/cell 위치 메타데이터가 확인되는 범위만 사용한다. 다른 행의 값을 연결하거나
누락된 머리글·병합 셀 관계를 추측하지 않는다. 파서/색인 구조에 없는 관계의 복원은 별도 작업이다.
이번 변경은 임베딩 모델·청킹 산출물·색인을 바꾸지 않는다.

## 4. 제한과 생성 입력 계약

생성용 근거 묶음은 추출형 대표 answer/conflicts와 별도 소유한다. 충돌을 일반 보조 근거로 위장하지 않는다.
생성 실행 여부는 생성용 근거의 자격으로 판단한다. 개별 문장의 추출형 selection.status가
insufficient_evidence여도 문맥 후보가 정책을 통과하면 원문 묶음으로 생성할 수 있다.
이때 추출형 status/answer를 supported로 위조하지 않으며 최종 생성 status는 별도로 반환한다.
문장과 문맥 후보가 모두 탈락하면 provider를 호출하지 않고 근거 부족을 반환한다.
제목만 있고 유효한 원문 EvidenceUnit이 없는 후보는 생성 자격을 얻지 못한다.
한 근거 ID에 서로 다른 원문/출처가 발견되면 정상 결과로 합치지 않는다.
기존 출처 경고가 있는 근거는 문맥 확장으로 우회하여 포함하지 않는다.

입력 예산은 검증되는 설정으로 둔다. 초기 평가 후보 상한은 8개 묶음·32개 EvidenceUnit·
원문 합계 12,000문자이며 provider의 실제 입력 제한도 적용한다. 이 숫자는 운영 기본값 승격 근거가 아니다.
하나의 문맥 묶음을 예산에 맞추려고 문장을 잘라 인용하지 않는다. 묶음 전체를 수용하거나 제외한다.
충돌 쌍 중 한쪽만 예산 때문에 사라지면 그 주장을 확정하지 않는다. 제외 수와 이유를 기록한다.
실제 token 제한을 초과하면 요청을 실패로 반환하며 조용히 잘라 보내지 않는다.

각 provider에 공통 직렬화를 사용한다.

- 묶음: 요청 내 ID, 문서·버전·projection·chunk ID, section_path와 원문 순서.
- 근거: 기존 evidence_id, 원문 text, element/page/char range 및 확인 가능한 표 위치.
- 제목/section_path는 탐색 문맥임을 명시한다. 그 자체를 인용 가능한 새 근거로 만들지 않는다.
- 원문의 명령형 내용은 지침이 아닌 비신뢰 데이터다.

새 버전 프롬프트는 각 주장의 대상·조건·예외가 인용 본문에 뒷받침되어야 하고 서로 다른 대상의
값을 합치면 안 된다고 명시한다. 기존 버전 파일을 덮어쓰지 않고 새 profile 후보로 검증한다.
Codex/OpenAI Responses/OpenAI-compatible에서 같은 의미 계약을 유지한다.
근거 부족과 모순을 그대로 허용하고 다른 모델로 조용히 전환하지 않는다.

## 5. API와 인용 화면

검색 응답에 additive `grounding_evidence` 목록을 추가한다. 항목은 기존 원문 source와 excerpt
계약을 재사용하되 문맥 포함 사실을 문장 의미 하이라이트 점수로 위장하지 않는다.
기존 answer/conflicts 의미와 추출형 검색 호환성을 유지한다. 목록은 provider에 실제 전달한 근거와 일치한다.

프론트는 이 목록과 기존 answer/conflicts로 인용을 해석한다. 생성된 모든 evidence_id가
허용된 목록에 있고 원문 뷰어로 열리는지 검사한다. 모르는 ID를 조용히 숨기지 않는다.
선택한 문서 버전과 인용 위치는 기존 source API를 통해 재검증한다.
대화 문서 선택 화면에는 관리 기능을 다시 추가하지 않는다.

## 6. 권한·외부 전송·성능

근거가 늘어나도 선필터, source resolver, 생성 전 현재 권한·버전 재확인, 외부 전송 승인을
모든 실제 전송 근거에 적용한다. 묶음에 포함됐다는 이유로 승인 범위를 넓히지 않는다.
외부로 보내는 section_path 등 추가 문맥도 같은 승인된 문서 버전의 데이터여야 한다.
본문·질문·사용자 식별자를 성능 로그에 저장하지 않는다.

질의 벡터는 같은 요청의 같은 모델 설정에서만 재사용하고 문맥 임베딩은 배치 처리한다.
다른 요청 사이에 비공개 질의/본문 벡터를 전역 캐시하지 않는다.
모델 장기 공유는 메모리 상한·동시 실행·실패 복구 검증이 필요한 후속 최적화로 분리한다.
이번에는 검색·근거 선택·질의 재작성·생성의 단계별 시간과 입력 크기를 측정한다.
정확도를 희생해 권한 확인이나 의미 비교를 생략하지 않는다.

## 7. 검증과 본래 환경 적용

단위 테스트는 네트워크·외부 모델 없는 합성 입력으로 작성한다. 실제 성능은 기존 로컬 임베딩과
이미 승인된 합성 참조 문서를 사용해 본래 환경에서 비교한다. 새 테스트 DB·계정·업로드 문서를 만들지 않는다.
실제 비공개 문서는 Git fixture에 복사하거나 외부 모델에 전송하지 않는다.

| 평가군 | 확인할 결과 |
|---|---|
| 이름·기간·금액·조건·절차·예외 | 표현이 달라도 관련 원문 근거가 생성 입력에 포함됨 |
| 한국어 조사·동의 표현·영어 paraphrase | 정확 일치와 의미 검색을 구분하면서 올바른 근거 발견 |
| 앞 문장의 대상 + 뒤 문장의 답 | 문맥이 보존되고 각각의 원문 ID로 인용 가능 |
| 같은 문서/문단의 두 대상·상반된 값 | 다른 대상의 값 차용 방지, 불명확하면 근거 부족 |
| 동일 제목의 다른 문서·버전 | 문자열 제목 때문에 출처가 합쳐지지 않음 |
| 표의 행/조건/머리글 부족 | 다른 행 연결과 임의 머리글 추측 방지 |
| 질문 대상만 있음·속성 없음·완전 무관 | 답변을 만들어 내지 않음 |
| 권한 철회·승인 철회·버전 변경 | 외부 생성 호출 전에 차단 |
| 예산 초과·중복·누락 provenance | 결정적 제외/실패, 잘린 가짜 원문 없음 |
| 실제 답변 인용 | 모든 인용을 해당 버전의 실제 위치로 열 수 있음 |

BM25 기준선과 기존 hybrid를 같은 질문 집합에서 비교한다. 검색 recall, 생성 입력의 필요한 근거
포함 여부, 인용/정답/근거 부족 정확도와 소요 시간을 각각 기록한다. 유사도 점수만으로 성공을 주장하지 않는다.
AM-LAB-840 질문은 여러 사례 중 하나이며 구현 분기나 모델 프롬프트의 특별 규칙으로 넣지 않는다.
기존 음성 회귀를 모두 유지하고, 새 평가군의 잘못된 대상 연결·권한 누출·끊긴 인용은 0건을 요구한다.
소규모 평가 통과를 모든 문서·질문에 대한 정확도 보장으로 표현하지 않는다.

후보 profile·프롬프트와 코드 revision으로 검증하고 통과 후 기존 관리 흐름으로 본래 도메인에 적용한다.
DB 평가 상태를 직접 성공으로 바꾸지 않는다. 서버 반영 후 같은 요청의 답변·인용·지연을 다시 확인한다.
실패하면 기존 평가된 구성으로 돌아갈 수 있도록 그 구성과 자료를 보존한다.

## 8. 책임과 승인 경계

메인: 요구/RAG·시스템 설계, 백엔드·프론트 구현, 테스트 설계, 문서와 통합.
독립 검토: 출처·전송·공개 응답 계약과 회귀 증거. 자신이 승인하는 제품 코드를 수정하지 않는다.
새 저장 정책·DB migration·파서 변경이 필요해지면 범위를 재분류한다.
현재는 설계 산출물만 변경한다. 설계 승인 후 구현 계획을 작성하고 구현·검증·본래 환경 적용을 진행한다.
