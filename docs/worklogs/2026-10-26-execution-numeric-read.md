# 실행 목록 숫자 근거 조회 비용 개선

2026-10-26 · ISSUE-00042 · [계획](../superpowers/plans/2026-10-26-execution-numeric-read.md)

## 원인과 변경

숫자 검증은 각 claim의 근거와 각 계산 operand마다 같은 현재 권한 JOIN을 반복했다. `generation/numeric_validation_repository.py` 한 제품 파일에서 claim별 근거와 proof별 위치를 최대64개씩 조회하도록 바꿨다. 조회한 ID 집합을 전체 대조하고 같은 evidence에 속한 여러 operand도 각각 문서·버전·projection·element·chunk·page·token/문자 범위가 일치해야 한다. 본문은 새로 조회하지 않는다.

receipt의 `populate_existing`, payload digest/재구성, audit actor·실행·구성·프로파일·허용근거·상태 검사는 그대로다. 원래 JOIN과 ready/active/current workspace 조건을 유지하고 index build의 새 active 조건은 추가하지 않았다. 중복 ready build는 존재성으로 처리한다. 각 claim/proof와 verify 호출은 새로 조회하며 evidence 단계의 허용 결과를 operand 단계에 재사용하지 않는다. 바깥 `NumericValidationBatch.revalidate`와 `visible_run` 후검증도 유지한다.

같은 batch 안에서 여러 원문의 권한 관측시점은 한 SQL로 묶인다. 내부의 뒤 operand membership 오류가 앞 SQL 오류보다 먼저 발견될 수 있으나 실패를 성공으로 바꾸지는 않는다. 호출 전체의 근거 union 또는 요청 간 권한 캐시는 도입하지 않았다. 생성·검색·프롬프트·인용·숫자 산술·품질 판정·UI·백그라운드 계약은 바꾸지 않았다.

## 채택하지 않은 계산 최적화

이번 CPU 진단에서 규칙 digest는960회65.014ms, 결과 digest는480회1729.075ms였다. 누적시간은 다른 함수 시간을 포함하므로 합산하지 않는다. 규칙 재사용은 기대 이득이 작아 제외했다.

전체 결과의 `model_dump_json → json.loads → canonical json.dumps` 직렬화 대안을 기존 방식과 공개 합성0/32/512/2048근거·7회 교대 sample로 비교했다. bytes는 같았지만 후보가1.30/1.37/1.51/1.41배 느려 기각했다. 저장 digest를 신뢰하거나 검증을 생략하는 방식으로 우회하지 않았다. CPU 제품 수정과 새 라이브러리 설치는 없다.

## 검증

구현자와 독립 검증자를 분리했다. 기존 코드에서64/65/129개 근거의 비용 회귀가 실패하는 것을 먼저 확인한 뒤 구현했다. 실제 합성 payload와 receipt를 만든 구현 회귀295개를 통과했다.

독립 회귀는 고유349개 PASS/실패0이며 strict Mypy 제품1파일과 Ruff 제품/테스트3파일을 통과했다. SQL의 현재권한·actor·ready 구조, NULL page, 같은 evidence의 두 operand 중 위치 변조, 중복 build, evidence→operand 사이 철회, 호출 사이 receipt 변조, SQL오류/취소 전파, 빈 claims와64/65/129개 query 경계·두 번째 chunk 실패 후 중단을 확인했다. 정상 proof의 arity는1/2이므로65 operands를 위해 검증을 우회하는 시험은 만들지 않았다.

시작2247파일/.env SHA와 수정 전 소스를 보존했다. 제한 실행에서 읽기 전용 probe2개가 응답하지 않아 정확한 자식 프로세스 신원을 확인해 종료하고 기존 환경 접근이 가능한 권한에서 재실행했다. 앱 서버·모델 프로세스를 이때 중지하지 않았으며 원시 본문·비밀값은 증거에 저장하지 않았다.

## 실측과 본래 환경 반영

기존 DB를 READ ONLY로 연결해 수정 전 복사본과 수정 후 코드를 같은 도구로 교대2쌍 비교했다. 제품 파일은 되돌리지 않고 측정 프로세스에서만 원본 모듈을 로드했다. 진단용 `profile-before.json`과 `timing-before-1.json`을 아래 최종 전후 평균에 합치지 않는다. 결과 동등성용 해시 계산은 timer 밖에 둔다.

환경 부하가 달라 수정 전 코드도 이전13~15초보다 빨랐다. 따라서 이전 작업 시간과 이번 시간을 직접 비교한 개선율로 해석하지 않는다. 전체 감소에는 대화 부하 변동도 포함되고 두 표본으로 P95·다중 사용자 성능을 보장하지 않는다.

실행 중 작업0·worker0과 정확 API/launcher 신원·`.env`/실행기 SHA를 재확인하고 본래 실행기로 API를 반영했다. health/ready200과 기존 대화202/201/200 및 실행 목록/상세 API 계약을 확인했다. 기존25표2560행의 PK별 해시와 `.env`가 변경 전·반영 직전·반영 후 동일했다.

본래 로그인 화면에서 전체508건, 실제대화 필터25건, 저장 평가 답변·인용2개·기록된 근거28개와 기존 품질실패 표시를 확인했다. ISSUE-00042의 원인·수정·검증·남은 작업과 날짜별 진행 이력을 저장하고 새로고침으로 재조회했다. 이전 이력을 보존하며 지연이 남는 상태를 완전해결로 변경하지 않았다.

기존2247파일 중2244개 동일, 허용3파일(제품1·기존 테스트1·WORKBOARD) 변경, 누락0을 확인했다. 새 파일은 테스트1·계획1·작업기록1뿐이다. 검증 시점 제품/테스트 SHA와 최종 파일이 같았고 관련 없는 미커밋 변경은 그대로 보존했다.

## 남은 작업과 범위

현재 측정에서도 전체조회7.5~7.7초가 남는다. 다음 후보는 대화 조회의 반복 현재권한 SQL295회와 전체 목록 복원 비용을 새로 분리 계측하고 결과 계약을 보존하는 축소안을 찾는 것이다. 검증 생략·저장 digest 신뢰·요청 간 권한 캐시는 사용하지 않는다.

새 모델 호출은0이며 기존 정답0/2 한계를 품질 통과로 변경하지 않는다. 이번 변경만으로 첫 질문의 모델 입력 처리 시간이 개선됐다고 주장하지 않는다. 설치·migration·commit/push·캐시 삭제0이며 새 UI/모바일 수용 범위도 추가하지 않았다.
