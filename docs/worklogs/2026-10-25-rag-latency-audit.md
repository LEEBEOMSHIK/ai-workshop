## 코드에서 확인한 개선 후보

### 1. 근거 선택에서 불필요한 원문 위치 계산 줄이기

`backend/src/ai_workshop/labs/rag/highlighting/service.py:58`의 `_normalize_with_original_offsets`는 글자마다 누적 문자열 전체를 NFKC·casefold하고 공통 접두어 비교와 위치 배열 복사를 반복한다. 길이에 대해 이차 시간 구조다. 실제 하이라이트에는 원문 위치가 필요하지만 `highlighting/context.py:92`의 문맥 관련성 계산은 긴 본문에 같은 함수를 호출한 뒤 coverage만 사용한다. 같은 질문의 정규화도 호출마다 반복된다.

기존 함수를 수정하지 않고 프로젝트 Conda Python으로 공개 합성 문자열을 길이별 3회 측정했다. 모델·임베딩·네트워크·DB 호출은 없었다.

| 합성 문자열 길이 | 함수 실행 중앙값 |
| --- | ---: |
| 500자 | 50.37ms |
| 1,000자 | 201.75ms |
| 2,000자 | 792.81ms |
| 4,000자 | 3,463.90ms |

이는 **함수만의 합성 측정**이며 실제 근거 선택 2.806초의 구성 비율이나 개선 후 응답 시간을 뜻하지 않는다. 긴 문자열에서 비용이 급증하는 현상은 확인했다. 첫 구현 후보는 coverage 전용 계산과 위치가 필요한 하이라이트를 분리하고 요청 안에서 질의어·동일 본문의 계산을 재사용하는 것이다. NFKC·결합 문자·casefold·공백 처리, 원문 위치와 최종 선택 결과의 동등성을 검증해야 한다.

### 2. 검색 시간을 모델 준비·DB·검색 서버로 나눠 측정하기

BM25/dense는 `retrieval/service.py:173`에서 이미 병렬 실행된다. `embeddings/request_cache.py`는 요청 안에서 질의와 동일 문서 텍스트의 벡터도 재사용한다. 따라서 병렬화 또는 요청 내부 벡터 캐시가 없다는 전제로 개선하지 않는다. 개별 근거와 문맥 그룹은 서로 다른 문자열이라 별도 계산이 남는다.

이번 평가의 frozen 검색은 물리 색인 하나·정상 성공 경로에서 각 분기가 `describe(HTTP 2회) → PIT 열기 → describe(2회) → 검색 → PIT 닫기`를 수행한다(`retrieval/elasticsearch.py:431`). BM25/dense 합계 14회 HTTP 경계이며 두 분기는 병렬이다. 일반 active alias 검색은 이 frozen 경로와 다르다. 평가의 4.097초를 일반 서비스 검색 지연으로 그대로 해석하지 않는다. frozen identity·현재 ACL·PIT 검사를 생략하는 최적화는 제안하지 않는다.

추가 계측은 토크나이저/모델 로드, 질의 encode, 개별 근거 encode, 문맥 encode, 정규화, 원문/ACL 조회, 검색 서버 describe/PIT/search/cleanup과 관측 저장으로 나눈다. 본문 대신 시간·개수·문자량·캐시 적중만 기록한다. 기존 단계 시간에는 순수 연산 외 관측 저장과 권한 재검사 경계도 포함된다.

### 3. 임베딩 수명과 LLM 초기 준비 비용 안정화

평가는 `evaluation/generative_workflow.py:149`에서 시도마다 `ProductionEvaluationSearch`를 만들고, `generative_adapter.py:61` → `tasks.py:544`의 기본 factory가 새 임베딩 어댑터를 만든다. pipeline은 이 어댑터를 시도 안에서 빌려 쓴다. 반복 간 같은 모델 객체를 재사용하는 구조는 아니다. 최초 토큰 계산이 `sentence_transformers.py:63`의 `_load()`를 호출한다. 실제 적재 시간이나 검색 27.077→4.097초 차이에 대한 기여는 기록되지 않았다.

일반 CPU 검색에서 생성 전에 요청 소유 임베딩을 해제하는 동작은 [기존 메모리 수명 결정](2026-10-11-rag-http-cancellation-regression.md)의 일부다. 무조건 상주시키는 방식은 이 결정을 되돌린다. 재사용을 도입한다면 정확한 모델 버전, 메모리 상한, 제한된 수명, 사용 중 close 방지, 요청별 본문 캐시 분리를 먼저 설계한다. 디스크 모델 캐시와 메모리의 모델 객체 재사용은 다르며 새 다운로드·재색인은 필요하다고 판단하지 않았다.

2026-10-25 01:40 KST 비추론 GET 조회에서 Ollama는 0.40.3이고 `/api/ps`의 적재 모델 목록은 비어 있었다. 이는 그 시점의 상태이며 10월 23일 첫 실행의 원인을 증명하지 않는다. 현재 Windows CIM CPU/GPU/RAM 조회는 접근 거부되어 미확인으로 기록했고 메모리 부족·GPU 미사용을 결론 내리지 않았다.

Ollama는 모델 사전 적재와 유지 시간을 지원한다. 사용 시간대만 준비 상태를 유지하는 정책은 초기 응답 안정화 후보이며 자원 점유와 함께 검증해야 한다. 현재 SDK의 OpenAI 호환 요청과 native API의 옵션을 혼동하지 않고 배포 설정/지원 범위를 확인한 뒤 적용한다. 이번에는 적재·설정·서비스 변경을 하지 않았다. [Ollama 공식 FAQ](https://docs.ollama.com/faq#how-do-i-keep-a-model-loaded-in-memory-or-make-it-unload-immediately)

현재 어댑터는 모델 HTTP 소요 시간과 입력/출력 토큰만 보관하며 모델 적재·입력 평가·출력 생성 시간을 분리하지 않는다. native API에는 해당 지표가 있지만 현재 OpenAI 호환 응답에서 그대로 제공된다고 가정할 수 없다. 런타임 계측 경로를 검증한 뒤 수집해야 한다. [Ollama chat 응답 계약](https://docs.ollama.com/api/chat), [호환 API 계약](https://docs.ollama.com/api/openai-compatibility)

### 4. 고정된 관리자 위임의 모델 호출 필요성 재검토

`orchestration/openai_agents.py`는 관리자에게 하나의 답변 도구를 지정하고 그 결과에서 종료한다. 답변 뒤 관리자 모델을 다시 호출하는 경로는 이미 없다. 관리자가 선택할 대상이 항상 하나인 흐름에서는 SDK 실행·단계 관측을 유지하면서 애플리케이션이 답변 담당을 직접 호출하는 선택 경로를 검토할 수 있다.

이 변경은 실제 LLM 위임을 결정적 배정으로 바꾸므로 별도 설계·동작 검증이 필요하다. 두 번째 실행에서 줄일 후보는 관리자 호출 약 1.404초이며 생성 전체 9.306초가 아니다. 관리자와 답변 담당은 의존 관계가 있어 단순 병렬화할 수 없다. 실제 여러 담당 중 판단이 필요한 흐름의 관리자 역할까지 제거하지 않는다.

출력 상한 512를 줄이는 것만으로 실제 39/171토큰의 생성 시간이 같은 비율로 줄지는 않는다. 근거 수·품질 기준을 낮추거나 타임아웃을 늘리는 방식도 속도 개선안으로 취급하지 않는다. 스트리밍은 첫 표시의 체감 개선이며 전체 연산 단축과 별개이고, 현재 구조화 답변·인용 검증 계약을 먼저 검토해야 한다.

## 권장 실행 순서와 검증 경계

1. 세부 시간 계측과 coverage 전용 정규화·요청 내부 계산 재사용을 구현한다. 합성 Unicode/원문 위치/선택 결과 동등성과 관련 단위 테스트로 먼저 검증한다.
2. 검색의 실제 병목에 따라 임베딩 수명·평가 검색 왕복을 최적화한다. 메모리 소유권·권한·동결 색인 검증을 유지한다. 변경되지 않은 문서 벡터의 요청 간 재사용은 정확한 문서·모델 버전과 현재 권한을 포함한 별도 설계 후 판단한다.
3. 로컬 LLM 적재·입력 평가·출력 생성 시간을 분리하고 사용 시간대의 준비 정책을 검증한다. 초기 실행, 같은 질문 반복, 다른 질문과 멀티턴을 구분해야 한다.
4. 이후에도 필요한 경우 고정 관리자 호출을 줄이는 SDK 경로를 별도 비교한다.

새 실제 검증은 사용자가 확정한 호출 범위에서 같은 질문·근거·프로파일의 전후 비교로 수행한다. 평균뿐 아니라 초기 지연·메모리·출력/근거 동등성을 확인하며 작은 표본으로 운영 P95나 특정 목표 초 달성을 주장하지 않는다. 이번 합성 함수 결과를 실제 RAG 개선 효과로 보고하지 않는다.
