# 문제 이력

[issues.json](issues.json)은 사용자 보고와 발견된 결함의 누적 이력이다. WORKBOARD는 현재 작업과 순서를, worklogs는 상세 실행 근거를 기록한다. 이 목록은 두 기록을 안정적인 문제 ID로 연결하며 최근 완료 목록에서 빠져도 삭제하지 않는다.

현재는 저장소 내부 데이터이며 메뉴·조회 API는 아직 구현하지 않았다. 추후 관리자 메뉴에서 영역, 상태, 날짜로 조회할 수 있도록 구조화했다. 파일을 정적 공개 경로로 복사하지 않는다. 메뉴를 구현할 때 접근 권한과 노출 필드를 별도로 검토한다.

## 기록 규칙

- 같은 증상의 후속 작업은 기존 ID에 날짜별 history를 추가한다. 다른 원인이면 새 ID로 분리하고 관련 ID를 남긴다.
- 발견, 원인 확인, 수정, 검증, 재발 때 갱신한다. 원인을 확인하지 못했으면 추정 또는 미확인이라고 쓴다.
- 구현 완료와 본래 환경에서의 확인을 구분한다. 자동 테스트만으로 실제 업로드·화면·답변 품질을 확인했다고 쓰지 않는다.
- remaining에 남은 검증과 제한을 남긴다. 후속 수정으로 설명이 바뀌면 이전 history를 지우지 않는다.
- evidence는 저장소 루트 기준 파일 경로, commits는 실제 존재하는 커밋이다. 문서가 이동하면 참조도 갱신한다.
- 비공개 원문, 사용자 질문 본문, 계정 식별자, 비밀값, 원시 로그는 저장하지 않는다. 상세 근거를 연결하되 이 데이터만으로 공개해도 된다고 간주하지 않는다.
- 이번 초기 목록은 2026-09-20~27 기록을 소급 정리한 것이다. 과거 모든 결함을 빠짐없이 수집했다는 뜻은 아니다.

## 상태와 필드

| 값 | 의미 |
| --- | --- |
| open | 미해결. 설계 또는 구현이 남음 |
| implemented | 수정은 구현했으나 명시한 실제 환경·화면·품질 검증이 남음 |
| verified | 해당 문제의 명시된 범위에서 수정과 검증 근거가 있음. 전체 제품 검증이나 영구 무결함을 뜻하지 않음 |

최상위 schema_version은 데이터 계약 버전, updated_at은 마지막 갱신일, visibility는 내부용 구분이다.
각 항목은 id, title, area, status, symptom, cause, resolution, verification, remaining, evidence, commits, history를 갖는다.
verification은 수행한 확인만, remaining은 미완료 사항을 담는다. history는 날짜와 사건을 오름차순으로 보존한다.
검증된 문제가 재발하면 status를 open으로 바꾸고 새 발견을 추가한다. 미래 메뉴는 status만으로 남은 검증을 숨기지 않는다.

JSON 파싱, ID 유일성, 필수 필드, 상태 값, 참조 파일과 커밋 존재를 변경 때 확인한다.
