# 첫 질문 기준 대화 생성과 첨부 초안

- 상태: 사용자 동작 방향 승인, 구현 계약 검토 대기
- 기준일: 2026-09-27
- 문제 이력: `docs/issues/issues.json`의 대화 선행 생성 항목
- 범위: 기존 RAG conversations·Asset upload·현재 프론트. 기존 DB/계정/공간 사용.

## 문제와 성공 기준

현재 화면 진입과 새 대화 버튼 자체는 서버 세션을 만들지 않는다. 그러나 첨부 컴포넌트가
`ensureSession()`을 호출하고 생성 결과가 즉시 목록·URL에 반영된다. 첨부 실패/취소 후에도
질문 없는 세션이 남는다. 첫 질문도 create와 submit이 별도 요청이라 중간 실패 시 빈 세션이 남을 수 있다.

사용자에게 보이는 세션뿐 아니라 신규 `rag_conversations` 행도 첫 질문을 서버가 유효하게 접수할 때만 만든다.
질문 전 첨부에는 별도의 사용자 소유 초안 식별자를 사용한다. 기존 세션을 숨기는 것만으로 해결하지 않는다.
첫 질문과 첨부 연결은 하나의 트랜잭션이며 재시도·동시 전송에도 대화 한 개와 첫 turn 한 개만 생긴다.
기존 질문이 있는 대화, 원본·권한·저장/생성 범위 분리 및 기존 마스터 환경은 유지한다.

## 선택한 방식

서버 첨부 초안을 도입한다. 화면 진입·새 대화·기존 문서 선택은 클라이언트 상태만 변경한다.
실제 PC 파일 선택/드롭 시에만 초안을 만들고 기존 Asset 저장·검증 파이프라인으로 첨부한다.
브라우저 메모리에만 파일을 보관하면 새로고침 시 파일이 사라지고 질문 전 업로드 상태 확인도 불가능하므로 채택하지 않는다.
서버 세션을 먼저 만들고 목록에서만 숨기는 방식도 신규 빈 세션을 없애지 못하므로 채택하지 않는다.

## 데이터 및 권한

- 신규 `rag_attachment_drafts`: id, owner_id, domain_id, state(open/bound/abandoned/expired),
  revision, created_at, updated_at, expires_at, bound_conversation_id 및 최초 전송의 멱등성 정보.
- 기존 첨부의 conversation_id를 nullable로 변경하고 draft_id를 추가한다.
  첨부는 정확히 하나의 conversation/draft에 속하도록 DB 제약을 둔다. 원본·intake 식별자는 바꾸지 않는다.
- draft 접근은 현재 도메인 접근 + 현재 활성 사용자 + 본인 소유를 모두 검사한다.
  저장 위치는 기존 본인 개인/유효 임시 공간의 현재 쓰기 권한으로 검사한다.
- 초안 생성/예약/최종 업로드 연결/첫 질문 결합에서 상태·revision·권한을 다시 검사한다.
  도메인 접근 철회·초안 포기 후 늦게 끝난 업로드는 정상 연결할 수 없다.
- 초안이나 첨부가 존재한다고 검색·외부 전송 권한이 생기지 않는다. stored 파일은 기존 정책대로 자동 선택하지 않는다.

## API와 첫 질문 접수

기존 세션의 후속 turn API는 유지한다. 신규 시작은 다음 계약으로 바꾼다.

- `POST /rag/domains/{slug}/attachment-drafts`: 요청 식별자로 멱등 생성. 파일 선택 시에만 호출.
- 초안별 옵션·첨부 upload/list API: 기존 세션 첨부 계약을 재사용하되 대상 소유자를 draft로 구분한다.
- 초안 조회/포기 API: owner 전용, 포기는 revision을 확인하고 중복 요청은 같은 결과를 반환한다.
- `POST /rag/domains/{slug}/conversations/start`: 첫 질문의 기존 요청 필드와 선택적 draft_id/draft_revision을 받는다.
  request_id는 최초 제출부터 재시도까지 유지한다. 클라이언트가 생성한 세션 ID를 신뢰하지 않는다.
- 기존 무질문 `POST /conversations` 생성 경로는 제거하고 410과 신규 start 사용 안내를 반환한다.
  구버전 클라이언트의 호출도 빈 세션을 만들 수 없어야 한다. 서버·프론트·API 타입을 함께 배포한다.

start는 도메인·검색 범위·선택 문서·자료 분류와 외부 처리 동의 등 검증을 수행한 뒤,
트랜잭션 안에서 초안을 잠그고 만료/소유/revision/활성 업로드 여부를 재확인한다.
대화 생성, 첫 turn 예약, 첨부 소유 관계 이전, draft bound 전환을 원자적으로 처리한다.
첫 질문 접수 키 `(owner_id, domain_id, request_id)`와 요청 해시로 중복/충돌을 DB에서도 차단한다.
같은 키·같은 내용은 기존 결과를 반환하고, 다른 내용은 409다. 초안 없는 첫 질문에도 같은 보장을 적용한다.
현재 사용자·도메인 접근 확인 후 기존 접수 키를 먼저 조회한다. 성공한 요청의 replay는 이미 bound된 초안이나
접수 과정에서 바뀐 revision 때문에 실패하면 안 된다. replay 응답에는 기존 대화의 현재 읽기/가림 처리를 적용한다.
같은 초안을 다른 request_id로 다시 제출하면 409 `draft_already_bound`와 본인에게만 기존 대화 식별자를 반환한다.
동시 요청은 unique 제약 충돌 후 기존 키/초안 결합 결과를 재조회하여 같은 규칙으로 처리한다.
요청 해시는 최초 질문 payload와 draft_id/draft_revision을 포함한다. 클라이언트는 응답 유실 재시도 때
동일한 원본 payload를 유지한다. 이미 접수된 대화가 삭제되었으면 같은 키는 410으로 종료하며 새 대화를 만들지 않는다.
draft revision은 파일 추가/제외 등 사용자 manifest 변경을 나타낸다. 업로드 완료·poll 상태 갱신만으로
revision을 증가시키지 않는다. 업로드 최종 연결은 예약 토큰과 현재 소유/상태/쓰기 권한으로 검증하여
다른 파일의 추가나 완료가 정상 업로드를 stale 처리하지 않게 한다.

생성 호출은 commit 후 실행한다. 검증 실패·트랜잭션 실패는 새 세션을 남기지 않는다.
접수 후 생성 실패/취소는 사용자가 실제 제출한 질문과 오류 상태를 가진 세션으로 보존한다.
응답 유실 후 같은 키로 조회/재시도하면 새 세션·중복 생성 호출이 발생하지 않아야 한다.
commit과 생성 실행 사이에 프로세스가 중단되거나 실행 결과가 불명확하면 기존 recovery 규칙으로 첫 turn을
interrupted로 보존한다. 같은 request_id replay가 외부 생성을 다시 호출하지 않는다. 복구 UI는 중단 이유와
새 질문으로 재요청하는 행동을 제공하며, 멈춘 running 상태를 영구히 유지하지 않는다.
start 중 업로드/검증이 진행 중이면 409와 대기 상태를 반환하고 세션을 만들지 않는다.
stored 첨부는 저장 이력으로 연결할 수 있지만 질문의 검색 대상으로 암묵적으로 포함하지 않는다.

## 프론트와 이탈

sessionId와 draftId를 별도 상태로 관리한다. draftId는 owner 전용 복원용 URL 상태로 보존할 수 있지만
대화 목록에는 나타나지 않는다. 첫 질문 접수가 확인된 시점에만 대화 목록·conversation URL을 갱신한다.
질문 입력, Enter/버튼 전송, 파일 업로드 대기, 중복 클릭을 같은 상태 전이로 관리한다.
start 응답이 늦게 도착해도 이미 새 초안/다른 대화로 이동했다면 현재 화면을 덮어쓰지 않는다.
이전 start의 성공은 서버에 보존하고 목록 재조회로 확인할 수 있다.

명시적 새 대화/초안 취소는 포기를 요청한다. 창 닫기 이벤트 전달만으로 정리를 보장하지 않는다.
새로고침은 유효한 초안을 복원한다. 만료된 초안은 복원 불가 이유와 첨부 보존/정리 상태를 표시한다.
업로드가 없는 단순 화면 방문은 서버 초안도 만들지 않는다.

## 만료와 원본 정리

미전송 초안의 보존 기간은 설정으로 관리하며 초기 제안은 마지막 사용자 변경부터 24시간이다.
조회/poll만으로 만료를 무기한 연장하지 않는다. 서버 worker가 만료를 판정하며 실행 간격도 설정값이다.
bound 전환과 만료는 동일 draft 잠금으로 직렬화한다. 업로드 종료가 미확인이면 만료 상태로 신규 쓰기를 막고
기존 intake·writer 종료 확인이 끝날 때까지 원본을 보존한다.

취소·만료는 원본 영구 삭제를 뜻하지 않는다. 기존 provenance/참조/실행 종료 인벤토리에 따라
cleanup_waiting 또는 cleanup_candidate로 전환하고 이유·시각을 기록한다.
파일함에서 이미 재사용하거나 다른 대화가 참조하는 원본은 제거하지 않는다.
현재 코드의 정리 후보 판정과 실제 삭제가 분리되어 있으므로, 만료를 물리 삭제 완료로 표시하지 않는다.
후속 관리 메뉴에서도 보존 사유를 읽을 수 있도록 owner 전용 초안 정리 inventory를 제공한다.

## 기존 빈 세션과 마이그레이션

질문이 있는 기존 세션은 그대로 유지한다. 기존 질문 없는 세션은 전체 삭제하지 않는다.
마이그레이션 전 질문 수·첨부·intake·원본 참조를 읽기 전용으로 조사한다.
목록은 실제 turn이 있는 대화만 반환하도록 변경하며 기존 빈 세션의 원본/감사 ID는 보존한다.
기존 빈 세션 URL은 owner 확인 후 '이전 미전송 초안' 상태로 복원한다. 새 초안에 legacy_conversation_id를 기록해
첨부 소유 관계를 트랜잭션으로 이전하고, 기존 행은 legacy 기록으로 남긴다. 첫 질문 접수 전 목록에 노출하지 않는다.
진행 중 intake/writer가 있으면 이전을 보류하고 쓰기 종료 확인 후 재시도한다. 임의 원본 삭제는 하지 않는다.
기존 링크 접근과 정리 인벤토리는 legacy 매핑을 따라가며, 같은 초안에 중복 이전되지 않도록 unique 제약을 둔다.
기존 빈 세션에는 명시적 legacy 전환 상태를 두고, 기존 turns/upload/rename 경로로 신규 변경을 받을 수 없게 한다.
구 경로는 owner 확인 후 초안 전환 필요 응답을 반환한다. 읽기/정리 경로는 유지한다.
이관은 기존 conversation→attachments 잠금 순서로 전환 차단 상태를 확정하고, 별도 초안 결합 작업이 해당
legacy 행을 역순으로 잠그지 않도록 한다. 활성 writer가 존재할 때 첨부 FK만 먼저 옮기는 것은 금지한다.
백업·migration 검증 후 본래 DB에 반영하며 별도 사용자 실행 환경·계정은 만들지 않는다.

## 문제 이력

`docs/issues/issues.json`을 문제별 상태 정본으로 두고 README에서 사람이 읽는 목록을 연결한다.
id/area/status/symptom/cause/resolution/verification/remaining/evidence/history를 기록한다.
작업 문서·ADR·커밋은 근거로 연결한다. 본래 환경 미검증을 해결 완료로 표기하지 않는다.
메뉴 구현 시 이 데이터를 읽는 어댑터와 관리자 접근 경계를 추가한다. 지금 공개 페이지나 빈 메뉴는 만들지 않는다.
실제 질문 본문·문서 내용·계정 비밀·원시 로그는 이력에 복사하지 않는다.

## 검증 및 완료 기준

1. 화면 진입·새 대화 반복·기존 문서 선택 시 conversation/draft 생성 요청 0회.
2. 질문 전 실제 첨부는 draft와 첨부만 생성하고 대화 목록은 증가하지 않음.
3. 첫 질문은 대화/첫 turn/첨부 결합을 한 번만 수행. 검증 거부·트랜잭션 실패 시 빈 세션 없음.
4. 이중 클릭·두 탭·응답 유실 재시도·새 화면으로 이동한 뒤 늦은 응답 검증.
   commit 직후/외부 호출 직후 프로세스 중단, 삭제된 대화의 같은 키 replay, 구 무질문 생성 API 차단도 포함한다.
5. 저장 권한 철회·도메인 접근 철회·만료/결합 경합·최종 업로드 경합은 안전하게 차단.
6. 생성 실패도 실제 질문 이력은 보존하고, stored 문서는 외부 전송/검색으로 자동 승격되지 않음.
7. 초안 취소/만료는 새로 만든 첨부만 정리 대상으로 판단하며 기존 문서·공유 참조·실행 중 원본 보존.
8. 기존 질문이 있는 세션은 계속 복원 가능. 기존 빈 세션은 이관 결과·보류 이유와 함께 보존.
9. 백엔드 단위·DB 통합·API와 프론트 상태 전이 검증, 타입/린트, 독립 권한 리뷰.
10. 본래 환경에서 메뉴 반복·첨부 초안·첫 질문·목록 복원 검증 후 이력 상태를 갱신.

구현 파일 경계: conversations 모델/repository/service/API/lifecycle, migration, ConversationPage/Attachments와
sessions-api, API 타입 생성물 및 관련 테스트. 새 메뉴·새 모델 런타임·외부 전송 정책 변경은 포함하지 않는다.
