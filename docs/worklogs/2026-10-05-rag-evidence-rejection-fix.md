# PDF 근거 제외와 프론트 검증 실패 원인 수정 — 2026-10-05

## 범위와 성공 기준

사용자가 원인을 찾아 수정하도록 요청했다. 기존 환경·계정·문서·모델·권한·별칭 동결 조건을 보존한다. 특정 질문에만 적용하는 예외나 평가 기준 완화 없이, 정상 권한의 PDF 검색에서 질문에 필요한 원문이 답변·인용까지 전달되는지 확인한다. 메인은 RAG 조사와 통합을, 프론트 담당은 테스트·검토 표시 수정을, 별도 담당은 DB 조회와 독립 검증을 맡았다. 주장 기록의 선택적 API 필드를 추가했으며 DB migration·권한·모델 신뢰 경계는 변경하지 않았다.

이 기록은 [이전 브라우저 마감 보고서](2026-10-05-rag-browser-closure.md)의 후속이다. 이전 DB 문서 `2d709e90-3b42-488e-8757-a9d8592773a6` v1과 원문 SHA `BA47BE87BB37D247E8422DD966ED1320CA74E6E76ACC2C70729EABA586E433AC`는 수정하지 않는다.

## 직접 원인

활성 RAG-TEST v4의 생성 프로파일 v2는 원문 묶음 8개·원문 단위 32개·문자 12,000자를 허용한다. 실제 합성 PDF의 검색 청크에는 33·36·38개의 유효 원문 단위가 있고, 본문 길이는 598~712자였다. 문자 제한에 여유가 있어도 원문 단위 상한을 넘으면 승인된 전체 청크 선택 규칙에 따라 묶음이 제외된다.

이전 실제 대화의 세 검색 결과는 서로 구분한다. 첫 결과는 문맥 유사도·키워드 기준 미달, 두 번째는 기준을 충족한 33단위 청크의 예산 초과, 세 번째는 세 청크 모두의 단위 예산 초과였다. dense 검색 점수와 묶음 문맥 유사도는 다른 측정값이다. `serialized_bytes=2`는 빈 배열 `[]`의 실제 직렬화 길이이며 2바이트 제한이 아니다.

기존 0.80/128 후보 v1은 단위 예산 문제를 해결하지만 활성화할 수 있는 완성된 결과는 아니었다. 독립 검토의 최신 75개 결과는 정확한 기존 ID·digest·본문·원문·고정 규칙과 일치했다. 엄격한 정직한 판정은 73통과·2실패다. 한 양성 답변은 필수 주의 상태가 누락됐고, 한 음성 답변은 안전하게 거절했어도 `answered` 상태 계약이 틀렸다. 원문 coverage 1.0과 P95 86,964.18ms는 충족하지만 정확도 73/75와 기권율 11/12는 저장된 각각 1.0 기준을 충족하지 못한다. 상세 검토의 DB 미등록을 해소해도 이 실험을 통과시킬 수 없다.

## 반영

- 생성 프로파일 `개인 Codex 근거 기반 대화` v4 (`211e16dd-5272-4aee-b27f-435ad09914fe`)를 정상 관리자 화면에서 새 불변 버전으로 등록했다. 기존 8/128/12000 예산·배포·대화 이력·시간 제한·출력 설정을 유지하고, 이미 구현된 선택형 거절 지침 `rag-codex-answer-v5`를 선택했다.
- `RAG-PDF 평가 후보 0.80-128` v2 (`c85cf0fd-7090-44de-93c8-a0b794fc3bc3`)를 같은 처리·색인·검색 프로파일과 같은 지식 공간에 저장했다. 답변 정책 내용은 0.80/0.50·완전한 원문 추적·출처 분리 그대로다. 현재 평가 대기이며 활성 대화 연결을 바꿨다고 주장하지 않는다.
- 정확한 새 구성의 합성 연결 검사 `cf9f2e3b-2673-4a72-a740-262b918775c4`는 성공했다. CLI0.160.0·등록 해시·v5 지침·새 구성/프로파일/배포가 일치하고 사용량 기록이 있다. 실제 모델 식별은 미확인을 유지하며, 연결 검사를 답변 품질 통과로 해석하지 않는다.
- 공개 진입 테스트는 기존 승인된 `비공개 작업소 입장`과 보호된 작업소 목적지를 검사하도록 낡은 기대값을 갱신했다. 검색 대화의 늦은 응답 회귀는 실제 클릭·붙여넣기로 입력해 문자별 입력 비용을 줄였다. 취소 신호·새 이력·새 동의·늦은 성공/실패 억제 검사는 유지했다.
- 첫 질문 상태 새로고침 테스트의 실제 2.1초 `act` 정리 대기를 가상 polling 시계로 교체했다. 테스트 시간 초과 뒤 남은 비동기 `act`가 다음 F6 테스트를 오염시키는 경고 연쇄를 통제된 진단에서 재현했다. 제품 코드나 전역 테스트 경고 설정을 바꾸지 않았다.

## 검증과 남은 확인

프론트 관련 두 파일 24개, 첫 질문 파일 38개, 최종 세 파일을 포함한 TypeScript와 ESLint가 통과했다. 원문 선택·요청 캐시의 기존 오프라인 백엔드 69개도 통과했다. 최종 전체 프론트 `vitest run --pool=threads --maxWorkers=1 --reporter=verbose`는 **140파일·938테스트 통과**, exit 0, 1,138.07초다. 초기 전체 실행은 중단(exit 1)했으며 최종 실행과 구분한다.

새 실제 평가 `b5cd916f-01fa-43c1-8cd2-37a5655c2394`를 기존 25문항·3회·동일 스냅샷·고정 정책·멀티턴 문맥으로 접수했다. 현재 worker/beat 프로세스가 없어 대기했다. 최초 단독 실행은 제한된 작업 터미널에서 생산 workflow를 호출했으나 실제 생성 5건이 `provider_request_failed`로 실패했다. 공급자 단계는 약 11초였고 60초 timeout의 증거는 아니다. 같은 구성의 정상 API 합성 연결 검사는 통과했다. 터미널 실행 제한의 영향을 정상 호스트 실행과 대조해야 하며, 이 단계에서는 네트워크 제한을 확정 원인으로 단정하지 않는다.

이 단독 workflow는 중단했다. 정상 10분 stale 복구가 과거 5실패·70중단을 남겼고, UI 명시 재시도로 새75시도가 접수됐다. 표준 DB trigger는 마지막 미완료 실행 `3418809d-c8d4-4f1b-a03f-2ed3d23180c1`의 상태를 interrupted와 중단 시각으로 동기화했다. 기존 부분 단계는 동일하고 `complete=false`를 유지했다. 이를 실제 하위 프로세스 종료 증빙이나 완료 단계 보충으로 해석하지 않는다. 더 오래된 `146c3bc3-5567-4316-ad70-85b089667430` 실행의 cancelled/complete=false/terminated=false와 기존 시각은 독립 조회에서 불변이다. 별칭 동결 조건도 유지했다.

정상 호스트 권한에서 같은 공개 `execute_run` workflow를 실행한 첫 새 답변 `a6302869-2316-4b41-80eb-afcb10f4e1c8`은 answered/인용 유효/관측 완료로 저장됐다. 공급자 실행·이벤트 실패 코드는 없고 cleanup=true·잔여 프로세스0이다. 총 관측96.375초(request2.823·retrieval21.320·selection38.385·generation32.796·citation0.014·persistence0.135), 선택115단위/상한128이었다. 선택 단계 전체38.385초를 임베딩 단독 시간으로 오해하지 않는다. 제한된 터미널과 다른 실제 생성 결과를 확인했지만 전체75개의 정답·기권·멀티턴·지연과 본래 대화 검증은 아직 진행 중이다. 연결 검사나 첫 성공만으로 후보를 승격하지 않는다.

최초 완료6건은 새 실제 답변·인용 원문·고정 rubric·상태 계약을 독립적으로 읽고 passed로 판정했다(Q08·Q10·Q16·H05·Q02·Q05). 이전 판정을 복사하지 않았다. 정상 마스터 로그인과 관리 API로 정확한 attempt2·구성·result/rule digest를 대조해6개 판정을 등록하고 저장 응답까지 확인했다. 전체75통과나 후보 승인 주장은 아니다. 등록 보조 도구는 계정 이메일을 읽기 전용으로 조회하고 정상 인증·평가 API를 사용했으며 비밀번호·쿠키·본문을 파일에 저장하지 않았다.

ISSUE-00005에 확인한 원인·후보·정상 재시도·첫 호스트 응답을, ISSUE-00017에 프론트 비동기 정리 회귀와 전체 검사를 정상 관리 화면으로 기록했다. 독립 DB 조회가 각 진행 사건과 기존 상태 유지를 확인했다. 실제 평가 중 직접 health/readiness·프론트 경유 health도200이었다. 이 문서의 정확한 DB 버전 연결과 본래 대화 검증은 진행 중이다. 이 작업으로 RAG 전체나 남은 기능이 완료됐다고 주장하지 않는다. Agents SDK·벡터 저장소 비교·로컬 LLM 학습은 기존 후속 순서에 남아 있다.

## 후속 원인 — 주장 경계를 잃는 평가 기록

실제 답변은 여러 문장을 하나의 주장으로 묶거나 한 문장 중간에서 주장을 나눌 수 있다. 기존 결과는 합쳐진 답변과 `claim_index/evidence_ids`만 남겼다. 문장 분할로 원래 주장 경계를 복원할 수 없어 주장별 인용의 의미를 확정할 수 없는 결함을 확인했다.

Q14 반복1의 잠정 인용 실패 의견은 실제 경계를 복원할 수 없음을 확인한 뒤 철회했다. 잘못된 failed 판정을 DB에 등록하거나 모델 지침을 v6으로 바꾸지 않았다. 같은 결과의 전체 답변은 인용 원문 전체와 고정 primary 기준에 맞으므로 답변 정답성은 통과로 검토하되, 원래 주장 경계가 없어 주장별 의미 인용은 미증명이라는 한계를 함께 기록한다. 철회·정정 이력과 이전 결과 본문/digest는 보존한다.

[ADR-0034](../decisions/0034-rag-claim-citation-trace.md)와 [구현 계획](../superpowers/plans/2026-10-05-rag-claim-citation-trace.md)에 따라 검증된 `GeneratedClaim.text`를 `claim_text`로 전달·저장하고 기존 평가 조회에서 제공한다. 새로운 주장 텍스트는 결과 digest에 결속한다. 과거 JSON에는 없는 키를 보충하지 않으며 API 검색 응답도 미기록 값은 생략한다. 거절·검증 실패는 답변과 주장을 꾸며 넣지 않는다.

검토 탭의 기본 접힌 **주장별 인용 근거**에서 정확한 주장·개행과 해당 주장에 연결된 기존 원문 링크를 표시한다. 미기록 경계·전체 또는 일부 원문 조회 불가를 구분한다. 추가 원문/모델 호출·내부 스크롤·새 탐색 영역은 없다. 본래 Chrome에서 이전 결과의 기본 접힘과 경계 미기록 설명을 직접 확인했다.

백엔드 회귀 RED5/1통과 후 수정, 평가 전체 관련128통과·추가 호환/성공 workflow 관련22통과·7파일 Mypy·관련 Ruff 통과. 독립 담당의 최종45테스트와 코드 리뷰에서 차단 결함0이며, 본래 DB 과거215개 결과의 dict/canonical bytes/저장 SHA/재로딩 digest와 기존11판정의 binding이 모두 동일했다. 프론트 신규 RED5를 거쳐 관련35통과·후속 부분 원문 미조회 RED1→관련7통과·전체 TypeScript·관련 ESLint가 통과했다. 앞선 전체938 검사는 신규 주장 UI 추가 전이며 두 검사 범위를 구분한다.

본래 DB 통합 `test_original_claim_citation_trace.py` 1건도 통과했다. 기존 승인된 공개 합성 스냅샷과 정책을 재사용하고, outer transaction/savepoint에서 새 주장 경계의 실제 저장 JSON/bytes/digest와 같은 소유자의 권한 조회를 확인했다. 종료 시 시험 run/attempt가 모두0건이며 실제 모델 호출·새 환경·DB·계정·영속 더미 자료는 만들지 않았다. 최초 읽기 함수는 실제 JSONB 형식에 맞게 정정한 후 통과했고, import 순서의 pytest anyio rewrite warning1건은 남았다. 진행 중 평가를 중단시킬 수 있는 기존 global stale 테스트는 실행하지 않았다.

확정된 기록 원인은 기존 **RAG → 검색·근거** 분류의 `ISSUE-00021`(`eddaa5dc-c373-4699-8ba5-a9d72439f0f3`, implemented)로 정상 인증 관리자 API에 등록했다. 기존 ISSUE-00005의 근거 예산 원인과 분리하며 새 모델 결과 검증·과거 경계 미기록·Q12 실패의 원래 값 미확인을 remaining에 남겼다. 이 문서는 진행 검증의 정확한 스냅샷을 DB 버전으로 연결하고 이후 진행은 새 버전으로 남긴다.

본래 API의 진행 중 대화/질문0과 exact 프로세스 소유권을 독립 확인한 뒤 기존 API만 같은 실행서·`.env`·루트 작업 디렉터리로 재시작했다(숨김 launcher54760). 별도 호스트 평가 프로세스5076과 기존 프론트5173·DB·계정·자료·별칭 open/frozen1·receipt0을 보존했다. 수정 후 직접 health/readiness·프론트 경유 health200이다. 실행 중 v5 workflow는 시작 때의 코드를 유지하므로 이 평가 결과에 새 경계가 기록됐다고 주장하지 않는다. 새 런타임의 실제 주장 저장·UI와 최종 후보 승인·본래 대화 생성/멀티턴 확인은 남아 있다.

20:33UTC 독립 읽기에서 새75시도 중36완료·1실패·1진행·37대기였다. 실패1건(Q12 반복2)은 generation 완료 뒤 인용 검증 `exact_value_not_supported`, 총80.170초·complete=true·8단계 종료였다. 원래 생성 문장이 남아 있지 않아 형식만 다른 값인지 실제 잘못된 값인지 확정할 수 없다. 이 실패를 시간 초과나 특정 지침 오류로 단정하지 않고, 전체 품질 통과·후보 승격도 하지 않는다. 확정된 새 결과26개는 정상 API 등록 후 정확한 result/rule/reason/owner 독립 대조에서 모두 일치했다.
