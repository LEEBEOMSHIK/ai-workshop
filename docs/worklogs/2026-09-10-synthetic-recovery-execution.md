# 합성 테스트 데이터 정리 실행

- 상태: 승인된 DB·파일·ES 후보 정리와 보존 검사, 로컬 API 재시작 및 접속 확인 완료.
- 승인 범위: [읽기 전용 명세](2026-09-10-synthetic-recovery-dryrun.md)의 DB 126행·파일 24개·물리 색인 4개.
- 역할: DB 담당은 정확한 PK 삭제 도구, 메인은 백업·서비스 조정·파일/ES 처리,
  독립 보안/리뷰 담당은 실행 게이트와 보존 검증을 맡는다. UI·모델·권한 정책은 변경하지 않는다.
- 대상: 기존 loopback15432 `ai_workshop_local_clean`, ES loopback9200, `.local-data/objects`의 정확한 후보 파일.
- 제외: DB 자체·DB 파일·Docker 볼륨·공통 alias·비후보 색인 2개·실사용자·공통 프로파일/모델·감사 기록.

## 백업 및 실행 순서

1. 해당 API 프로세스의 실행 경로를 재확인한 뒤 중단하고 대상 DB의 남은 연결 0을 확인한다.
   프론트는 유지한다. Redis/worker는 중지 상태이며 별도로 시작하지 않는다.
2. 새 PostgreSQL custom archive를 만들고 목록 검사와 컨테이너/호스트 SHA-256을 비교한다.
3. 파일 24개는 정확한 경로별 복사 후 원본/복사본 해시를 비교한다. 파일 내용은 출력하지 않는다.
4. ES 후보 4개와 보존 2개의 mapping/settings/aliases 및 ID별 source를 로컬 백업한다.
   `_source.exclude_vectors=false`로 벡터를 포함하고 mapping 차원과 모든 embedding 길이를 비교한다.
   전체 레코드 수와 직렬화 round-trip 지문을 검사한다. 백업 내용을 테스트 픽스처나 Git에 넣지 않는다.
5. 파일 존재·해시·ES 소유 범위와 alias 연결이 기존 명세 및 백업과 같아야 한다.
6. DB 단일 트랜잭션에서 모든 public 테이블의 writer lock을 잡고 명세를 재검증한다.
   실제 FK의 자식 우선 순서로 정확한 PK만 제거하며 테이블별 건수와 합계 126을 확인한다.
   모든 비대상 행의 전후 SHA-256·건수, 대상 잔존 0, 활성 마스터 1을 확인한 뒤 commit한다.
   제약·트리거·감사를 끄거나 권한 변경으로 우회하지 않는다.
7. 이번 manifest/DB 백업 해시와 연결된 DB 완료 결과를 확인한 뒤 ES 후보 4개만 삭제한다.
   각각 404를 확인하고 파일 24개를 비재귀·리터럴 경로로 제거한다. 공통 alias 전체를 삭제하지 않는다.
8. 비후보 색인 2개의 전체 지문·공통 alias 연결 및 파일 부재를 확인한다. API를 같은 로컬 방식으로 재시작한다.

실행 단계 중 하나라도 실패하면 후속 삭제를 중단한다. 이미 성공한 단계와 미수행 단계를 구분하며,
commit 연결 오류는 성공/rollback으로 추정하지 않고 DB를 읽기 전용으로 확인한다.

## 백업 위치와 복원 경계

Git 제외 `.local-data/backups/synthetic-recovery-20260910/`:

- `database.dump`: 419,598 bytes, SHA-256 `7ec39bac9dc13034c5833ceb794d87ff16183352b95ee7b888e2c446e4126b5c`.
  아카이브 목록 522줄 및 컨테이너 복사본 일치 확인. 실제 별도 DB 복원 시험은 미수행이다.
- `files/`: 원본 객체 키 상대 경로를 유지하는 후보 파일 백업.
- `es-backup.json`: 후보/보존 색인의 원본 메타데이터·벡터 포함 레코드와 복원용 payload.
- `assets-ready.json`: 파일 수·크기 및 ES 백업 해시.

복원은 실패 범위와 이후 사용자 변경을 검토한 별도 승인 작업이다. 자동 전체 복원은 하지 않는다.

- **DB:** writer를 중단한 상태에서 이 custom archive의 대상 DB를 확인한다. 전체 복원은 이후 변경을
  덮을 수 있으므로 정확한 복원 대상/충돌을 먼저 검토한다. 원본 DB drop·볼륨 삭제·migration downgrade는 사용하지 않는다.
- **파일:** `files/` 상대 경로를 원래 `.local-data/objects/` 아래로만 복사한다. 상위 reparse point를
  재검증하고 이미 존재하는 파일은 해시가 다르면 덮어쓰지 않는다. 복사 후 명세 SHA-256을 비교한다.
- **ES:** 백업에서 승인된 후보의 정확한 이름 한 개를 선택한다. 그 이름이 실제 부재인지 먼저 확인한다.
  `PUT /<exact-index>`에 해당 항목의 `restore` payload(settings/mappings/aliases)를 사용한다.
  `settings`는 shard/replica 및 명시된 변경 가능 분석 설정만 담으며 uuid/creation_date/version 등
  생성 금지 메타데이터는 사용하지 않는다. `records`의 각 `id`를 URL 인코딩해
  `PUT /<exact-index>/_doc/<id>`에 `source`를 넣고 `POST /<exact-index>/_refresh` 후
  전체 건수·ID/source·벡터 차원과 alias 연결을 검증한다. 기존 이름이 있으면 자동 덮어쓰기하지 않는다.
  공통 alias 전체 치환, 비후보 2개 색인 변경, prefix/wildcard 삭제는 하지 않는다.

백업은 복구 자료로 보존하며, 지금 정리할 임시 캐시로 취급하지 않는다.

## 실제 실행 결과

- API launcher4712/child33820의 정확한 실행 경로를 대조해 중단했다. 대상 DB의 다른 연결은 0이었다.
- DB 재검증 명세는 승인 스냅샷과 모든 섹션이 동일했다. 실제 FK 순환은 없었다.
- DB 안전 단위 검사 7개(메인 0.84초, 독립 0.83초), Ruff, PowerShell 구문 검사 통과.
- 자산 Backup 및 별도 Verify 실행 성공. 벡터 포함·차원·JSON round-trip·파일 해시 일치 확인.
- 독립 보안/리뷰의 최종 실행 게이트를 통과한 뒤에만 정리를 실행했다.
- DB 16테이블 126행 삭제 commit 성공. 비대상 65테이블 232행의 전후 SHA-256·건수 동일,
  모든 후보 PK 잔존 0 및 남은 활성 마스터 1 확인. 권한/감사/모델 테이블의 비대상 행은 변경하지 않았다.
- 물리 색인 4개 각각 삭제 승인 응답과 404 확인. 정확한 파일 24개 제거 후 32개 기록 경로 모두 부재 확인.
- 공통201 active alias는 비후보 색인 2개만 가리킨다. 두 색인의 메타데이터·벡터 포함 검색 레코드 8개의 지문 동일.
- 제거한 파일의 논리적 합계는 94,286 bytes다. 백업을 보존하므로 이 수치를 호스트 여유 공간 증가로 보고하지 않는다.

  최초 후보 명세의 `deletion_authorized:false`는 당시 스냅샷이다. 이후 사용자 승인과 실제 실행은 본 문서로 구분한다.
